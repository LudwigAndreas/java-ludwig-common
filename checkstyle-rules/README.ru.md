# checkstyle-rules

*[English](README.md) · **Русский***

> Общая конфигурация Checkstyle: форматирование, повторяющее умолчания IntelliJ IDEA, плюс
> соглашения об именовании, уровне исходников и Javadoc, благодаря которым незнакомый код читается
> как остальной репозиторий. Выполняется в каждом модуле на `validate`, до компилятора.

## Зачем

Разработчик, ещё не отгружавший продакшен-Java, пишет код, который компилируется, проходит свой тест
и всё равно читается как «чей-то первый сервис»: `if` без скобок, проглоченное исключение, `3600`
посреди выражения, `System.out.println` там, где место логгеру, Javadoc, чей `@param` называет
параметр, переименованный два коммита назад. Ничего из этого компилятор не ловит, а указывать на это
руками на ревью стоит старшему часа в день и не учит ничему, что запоминается.

Этот модуль превращает такие соглашения в вывод сборки: одно и то же сообщение, в одном и том же
месте, каждый раз, через секунды после сохранения файла — и сборку, которая стоит, пока это не
исправят.

Два принципа не дают ему стать тем, что все отключают:

1. **Он никогда не требует того, что форматтер IntelliJ по умолчанию отменит.** Проект не поставляет
   собственной схемы стиля для IDE, поэтому «стиль» — это то, что IntelliJ делает из коробки: отступ
   4 пробела, отступ продолжения 8, поле на 120 колонок, скобки в стиле K&R с `} else {` в одну
   строку, `case` с отступом внутри `switch`, не более двух подряд пустых строк. Каждое правило про
   пробелы кодирует ровно это, из-за чего **Reformat Code (`Ctrl+Alt+L` / `Cmd+Alt+L`) — законное
   исправление всего, что сборка сообщает о раскладке**, а IDE в принципе не может внести нарушение.
2. **Каждая проверка заслуживает место, ловя настоящую ошибку.** Правила, выражающие один лишь вкус,
   не включены — см. [что эта конфигурация намеренно не
   проверяет](#что-эта-конфигурация-намеренно-не-проверяет), где они перечислены с причинами, чтобы
   никто не выводил их заново.

## Быстрый старт

Включать нечего. Корневой pom применяет плагин ко всем модулям, поэтому:

```bash
mvn validate          # только стиль, несколько секунд, без компиляции
mvn verify            # стиль идёт первым, до компилятора и тестов
```

Отказ называет файл, строку, правило и что делать:

```
[ERROR] .../OrderService.java:88:9: 'if' construct must use '{}'s. [NeedBraces]
[ERROR] .../OrderService.java:94:36: '3600' is a magic number. [MagicNumber]
[ERROR] .../OrderService.java:23: Line is longer than 120 characters (found 134). [LineLength]
```

Имя в скобках — это правило. Ищите его в
[`checkstyle.xml`](src/main/resources/ru/ludwigandreas/checkstyle/checkstyle.xml): каждое правило там
снабжено комментарием о том, зачем оно, — это и есть ответ на вопрос «почему сборке это важно».

Пропустить на один локальный прогон:

```bash
mvn verify -Dcheckstyle.skip=true
```

`checkstyle.skip` — для локального цикла. Пайплайн, который его выставляет, — это пайплайн без
стилевого шлюза.

## Кто чем владеет

Репозиторий покрывают три инструмента, и они намеренно не пересекаются; когда правило могло бы жить в
двух, оно уходит к тому, который в состоянии увидеть проблему.

| Инструмент | Что видит | Чем владеет |
|---|---|---|
| [`architecture-rules`](../architecture-rules/README.md) (ArchUnit) | Скомпилированный байткод: типы, члены, зависимости | Структуру: слои, циклы пакетов, что может пересекать границу, где допустим фреймворк, изоляцию модулей, число соавторов у класса |
| **`checkstyle-rules`** (этот модуль) | Текст исходника и его синтаксическое дерево | Форматирование, именование, соглашения уровня исходника, корректность Javadoc, ресурсные bundle |
| SonarQube | Поток данных внутри тел методов | Ошибки и безопасность: null-безопасность, инъекции, неверное использование криптографии, утечки ресурсов, когнитивную сложность, закомментированный код |

Конкретно этот модуль реализует проверки, которые ArchUnit
[явно не смог выразить](../architecture-rules/README.md#what-this-library-deliberately-does-not-check):
только-ASCII в содержимом исходника и всё остальное, что живёт в символах файла, а не в его
скомпилированной форме.

## Что проверяется

112 правил. Группы ниже говорят, что защищает каждая; сам конфигурационный файл несёт полное
обоснование по каждому правилу.

### Инварианты уровня файла

| Правило | Что предотвращает |
|---|---|
| `NewlineAtEndOfFile` (lf) | Последнюю строку, чья следующая правка выглядит как диф из двух строк |
| `FileTabCharacter` | Файл, выровненный только в том редакторе, который его написал |
| `LineLength` (120) | Строки, которые нельзя просмотреть рядом; строки package/import и голые URL исключены |
| `TrailingWhitespace`, `ConsecutiveBlankLines` | Невидимые символы и разрывы сверх двух пустых строк, которые оставляет IntelliJ |
| `FileLength` (2000) | Файл, переставший быть единицей чего бы то ни было |

### Ресурсные bundle

Локализация здесь первоклассна — пользовательский текст живёт в i18n-bundle, — поэтому сборка держит
bundle вместе:

| Правило | Что предотвращает |
|---|---|
| `UniqueProperties` | Дублированный ключ, где второй молча перекрывает первый |
| `Translation` | Ключ, добавленный в `messages.properties` и забытый в `messages_ru.properties`, из-за чего русскоязычный пользователь видит в рантайме сырой код сообщения |

### Текст исходника

| Правило | Что предотвращает |
|---|---|
| `NonAsciiSourceText` | Зашитый пользовательский текст (и «кракозябры»): не-ASCII место в bundle. Подавлено в тестах, где утверждение обязано выписать ожидаемую локализованную строку |
| `ConsoleOutput` | `System.out`/`System.err`: ни уровня, ни отметки времени, ни идентификатора корреляции и невозможность выключить в продакшене |
| `PrintStackTrace` | Стек, выброшенный в stderr, и объявление проблемы обработанной |
| `AuthorTag` | `@author`, который git и так знает и который врёт после первой чужой правки |
| `UntrackedTodo` (предупреждение) | `TODO` без ключа задачи — пожелание, а не пункт на доске |

### Импорты

`AvoidStarImport`, `UnusedImports`, `RedundantImport`, `IllegalImport` — последнее отвергает
внутренности JDK (`sun.*`, `jdk.internal.*`), Commons Lang 2, API JUnit 3/4, просачивающиеся в
кодовую базу на JUnit 5, и логгирующие API в обход фасада SLF4J, который настраивает модуль
наблюдаемости.

### Именование

Стандартные соглашения Java, которых ожидают и собственные инспекции IntelliJ: имена пакета, типа,
метода, члена, параметра, локальной переменной, константы и параметра типа, плюс
`AbbreviationAsWordInName` (никаких `parseXMLToDTO`). `log`/`logger` — допустимое имя константы, а
параметры типа могут быть длиной до трёх букв, чтобы `BaseRepository<E, ID>` был законным.
Соглашения о **суффиксах** типов («контроллер заканчивается на `Controller`») сюда не входят: они
структурные, и `architecture-rules` проверяет их по байткоду.

### Пробелы и переносы — зеркало IntelliJ

`Indentation` (4 / 8 / case 4 / throws 8), `WhitespaceAround`, `WhitespaceAfter`,
`NoWhitespaceBefore`, `NoWhitespaceAfter`, `ParenPad`, `TypecastParenPad`, `MethodParamPad`,
`GenericWhitespace`, `EmptyForIteratorPad`, `EmptyForInitializerPad`, `SeparatorWrap` (перенесённая
цепочка вызовов начинается с точки; список аргументов оставляет запятую), `EmptyLineSeparator`,
`AnnotationLocation`. Всё это — ровно то, что выдаёт Reformat Code.

### Блоки и скобки

`LeftCurly`, `RightCurly` (`} else {` в одну строку), `NeedBraces`, `EmptyBlock`, `EmptyCatchBlock`,
`AvoidNestedBlocks`.

`NeedBraces` — самое ценное правило файла для новичка: `if` без скобок, у которого потом появляется
второй оператор, — хрестоматийный способ отгрузить ошибку, читающуюся как правильный код, потому что
отступы врут. `EmptyCatchBlock` — на втором месте: проглоченное исключение труднее всего
диагностировать в продакшене, потому что нигде и ничем оно не зафиксировано. Если поймать и ничего не
делать действительно правильно, назовите переменную `ignored` или `expected`, и правило отступит.

### Соглашения кодирования

Ошибки, которые компилируются: `StringLiteralEquality` (`==` на строках работает в тестах и падает на
значениях с провода), `EqualsAvoidNull`, `EqualsHashCode` (одно без другого ломает каждый `HashMap`,
куда тип когда-либо попадёт, включая внутренности Hibernate), `CovariantEquals`,
`MissingSwitchDefault`, `FallThrough`, `DefaultComesLast`, `SimplifyBooleanExpression`,
`SimplifyBooleanReturn`, `EmptyStatement`, `ModifiedControlVariable`, `OneStatementPerLine`,
`MultipleVariableDeclarations`, `ArrayTypeStyle`, `UpperEll`, `ModifierOrder`, `RedundantModifier`,
`ExplicitInitialization`, `UnusedLocalVariable`, `UnnecessaryParentheses`, семейство
`UnnecessarySemicolon*`, `IllegalInstantiation`, `IllegalCatch`/`IllegalThrows` (только `Throwable` и
`Error` — граница фреймворка законно ловит `Exception`), `NoFinalizer`, `NoClone`, `MagicNumber`,
`HiddenField`, `NestedIfDepth`, `NestedTryDepth`.

### Дизайн и размер классов

`VisibilityModifier`, `FinalClass`, `HideUtilityClassConstructor` (точки входа Spring исключены),
`InterfaceIsType`, `MutableException`, `OneTopLevelClass`, `OuterTypeFilename`,
`OverloadMethodsDeclarationOrder`, `MethodLength` (100), `ParameterNumber` (8),
`CyclomaticComplexity` (15), `ThrowsCount` (3). Потолки — растяжки, а не цели.

### Javadoc

Намеренно разделён надвое:

- **Корректность — всегда ошибка.** `JavadocMethod` (`@param` обязан называть существующий параметр,
  `@return` не должен стоять у `void`-метода), `JavadocStyle` (корректный HTML, первое предложение,
  заканчивающееся точкой, — именно его инструмент поднимает в каждую сводную таблицу),
  `InvalidJavadocPosition`, `NonEmptyAtclauseDescription`, `AtclauseOrder`, `JavadocContentLocation`.
  Документация, которая врёт, хуже, чем её отсутствие.
- **Наличие — предупреждение** (см. уровни ниже): `MissingJavadocType`, `MissingJavadocMethod` и
  `JavadocSummaryPresent` для блока Javadoc, состоящего из одних тегов.

**Отсутствующий** `@param` намеренно не ошибка. Требование тега на каждый параметр порождает
`@param name имя` — тег, который удовлетворяет инструмент и не сообщает читателю ничего.

## Уровни серьёзности

| Свойство | По умолчанию | Покрывает |
|---|---|---|
| (всё остальное) | `error` | Валит сборку на `validate` |
| `checkstyle.docs.severity` | `warning` | Отсутствующий Javadoc на публичных типах и методах, Javadoc без сводки, TODO без задачи |
| `checkstyle.package.info.severity` | `ignore` | `JavadocPackage` — по одному `package-info.java` на пакет |

Документационный уровень сообщается, но не ломает сборку, поэтому конфигурацию можно принять, не
написав сначала бэклог документации. Поднимите его, когда публичный API модуля будет покрыт:

```bash
mvn verify -Dcheckstyle.docs.severity=error
```

Выставьте в корневом pom, чтобы закрепить, или в `ignore`, чтобы заглушить уровень целиком.

## Как подавить проверку

Все три формы ниже заставляют назвать правило; ни одна не может выключить всё.

```java
@SuppressWarnings("checkstyle:MagicNumber")                  // всё объявление
public int backoffSeconds() { ... }

// CHECKSTYLE.OFF: IllegalCatch - обёртка повторов обязана видеть любой отказ, включая Error
} catch (Throwable e) {
    // CHECKSTYLE.ON: IllegalCatch

// SUPPRESS CHECKSTYLE VisibilityModifier - внедряется Hibernate, конструктора для внедрения нет
@Autowired(required = false)
DbCoreMetrics metrics;                                       // покрывает эту строку и две следующие
```

Всегда пишите причину. Подавление с причиной — решение, с которым ревьюер может согласиться;
подавление без причины — тихо удалённое правило.

Файловые подавления живут в
[`checkstyle-suppressions.xml`](src/main/resources/ru/ludwigandreas/checkstyle/checkstyle-suppressions.xml)
и ограничены двумя видами записей: сгенерированные исходники (Q-типы QueryDSL, реализации MapStruct —
код, который никто не может править) и те конкретные проверки, **причина существования** которых в
тесте не работает. В остальном тесты держатся того же стандарта, что и продакшен-код: их читают
намного чаще, чем пишут.

## Настройка IDE

Две вещи, обе разовые:

1. **Импортировать нечего.** Пользуйтесь стилем Java по умолчанию из IntelliJ. В этом и весь смысл
   конфигурации: `Ctrl+Alt+L` (Reformat Code) и `Ctrl+Alt+O` (Optimize Imports) всегда дают файл,
   который сборка принимает.
2. **`.editorconfig` в корне репозитория** подхватывается автоматически (IntelliJ, VS Code, Eclipse).
   Он повторяет умолчания, чтобы они путешествовали вместе с репозиторием, и поднимает единственную
   настройку, где фабричное умолчание IntelliJ и соглашение действительно расходятся: IDE
   сворачивает пять импортов одного пакета в звёздочный импорт, который отвергает `AvoidStarImport`,
   поэтому пороги подняты недосягаемо высоко.

Необязательно, но полезно: плагин **Checkstyle-IDEA**, направленный на
`checkstyle-rules/src/main/resources/ru/ludwigandreas/checkstyle/checkstyle.xml`, с областью
сканирования «All sources including tests». Он показывает те же сообщения прямо в редакторе по мере
набора — цикл обратной связи куда короче сборки.

## Использование в другом сервисе

Конфигурация публикуется jar-ом, чтобы сервис ниже по течению не копировал XML:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-checkstyle-plugin</artifactId>
    <version>3.6.0</version>
    <dependencies>
        <dependency>
            <groupId>com.puppycrawl.tools</groupId>
            <artifactId>checkstyle</artifactId>
            <version>10.21.4</version>
        </dependency>
        <dependency>
            <groupId>ru.ludwigandreas</groupId>
            <artifactId>checkstyle-rules</artifactId>
            <version>1.0.0</version>
        </dependency>
    </dependencies>
    <configuration>
        <!-- Разрешается из classpath плагина, поэтому никаких путей в другой репозиторий. -->
        <configLocation>ru/ludwigandreas/checkstyle/checkstyle.xml</configLocation>
        <suppressionsLocation>ru/ludwigandreas/checkstyle/checkstyle-suppressions.xml</suppressionsLocation>
        <includeTestSourceDirectory>true</includeTestSourceDirectory>
        <violationSeverity>error</violationSeverity>
        <propertyExpansion>docs.severity=warning</propertyExpansion>
    </configuration>
    <executions>
        <execution>
            <id>checkstyle-validate</id>
            <phase>validate</phase>
            <goals><goal>check</goal></goals>
        </execution>
    </executions>
</plugin>
```

Сервис с собственными подавлениями направляет `suppressionsLocation` на свой файл; сами правила
форкать не стоит. Этот репозиторий — исключение: он ссылается на файлы по пути, а не через jar,
потому что Maven разрешает зависимости плагинов из локального репозитория, а не из реактора, и ссылка
на jar заставила бы чистый клон падать, пока кто-нибудь не установит этот модуль первым.

## Что эта конфигурация намеренно не проверяет

Некоторые правила выглядят уместными здесь, но таковыми не являются. Их рассмотрели и отклонили;
причины записаны, чтобы никто не выводил их заново.

| Не проверяется | Почему и чьё это |
|---|---|
| **Порядок** импортов | Раскладка IntelliJ по умолчанию ставит сторонние импорты первыми, а `javax`/`java` последними — это специфичное для IDE упорядочивание, которое ни одна модель групп Checkstyle не воспроизводит точно. Закрепив одно, каждый `Optimize Imports` перетасовывал бы файл в ошибку сборки. IDE держит порядок бесплатно |
| `OperatorWrap` (перенесённый `&&` в конце строки или в начале следующей?) | Форматтер применяет свой ответ только когда сам переносит строку, а существующий перенос оставляет как есть, — поэтому любая настройка сообщает о строках, которые Reformat Code не исправляет. Чистый вкус, ничего не ломается ни так, ни эдак |
| `NPathComplexity` | Перемножает ветвления, поэтому N последовательных невложенных `if` дают 2^N: самый понятный способ написать таблицу диспетчеризации набирает тысячи, а по-настоящему запутанный метод с тремя вложенными условиями — меньше. `CyclomaticComplexity` и `NestedIfDepth` измеряют то, что нужно |
| `BooleanExpressionComplexity` | Считает операторы, а не запутанность: список из восьми типов через `\|\|` набирает хуже, чем `a && !b \|\| c && d`, который читатель как раз не может вычислить в уме. Когнитивная сложность — вотчина SonarQube, и у него есть её настоящая мера |
| Закомментированный код | Любая регулярка под него («строка комментария, оканчивающаяся на `;`») попадает и в прозу, заканчивающуюся точкой с запятой, а правило, кричащее «волк» на комментарий, объясняющий **почему**, учит людей перестать читать вывод. SonarQube в `java:S125` вместо этого разбирает комментарий как Java |
| Связность классов (`ClassFanOutComplexity`, `ClassDataAbstractionCoupling`) | `architecture-rules` уже ограничивает соавторов структурно. Запуск обоих означает два инструмента, сообщающих об одной проблеме двумя разными числами |
| Суффиксы имён типов, слои, запрещённые зависимости | Структурное. `architecture-rules` видит байткод и может выразить это как следует |
| Правила безопасности, null-безопасность, утечки ресурсов | Требуют анализа потока данных. SonarQube |

## Внедрение в кодовую базу, которая старше конфигурации

Этот репозиторий привели к нулю нарушений до включения шлюза, и такой порядок предпочтителен: сборка,
которая отгружается красной, учит всех её игнорировать. В большой кодовой базе, где это непрактично:

1. Запустите `mvn checkstyle:checkstyle -Dcheckstyle.failOnViolation=false` и прочитайте
   `target/checkstyle-result.xml` по модулям.
2. Сначала исправьте механические группы — они безопасны и составляют большую часть списка: длина
   строк, неиспользуемые импорты, отсутствующие скобки, избыточные инициализации, Javadoc, больше не
   соответствующий сигнатуре.
3. На остаток добавьте **датированные файловые** записи в собственный файл подавлений сервиса, а не
