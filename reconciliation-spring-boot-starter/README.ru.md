# reconciliation-spring-boot-starter

[English](README.md) | [Русский]

Входящий близнец [`outbox-spring-boot-starter`](../outbox-spring-boot-starter). Outbox захватывает
локальные строки и выталкивает состояние **наружу**; этот модуль захватывает локальные строки и
затягивает состояние **внутрь**. Всё между "проснуться" и "записать исход" у них — одна и та же
машина, и она живёт в [`job-core`](../job-core), общем для обоих.

## Задача

Сервисы этой платформы держат локальные записи, отражающие состояние, которым владеют внешние
системы, и каждый сервис пишет собственный цикл опроса на `@Scheduled`. Каждый такой цикл заново
реализует одни и те же пять стадий, и **по-настоящему различается только стадия 3**:

| № | Стадия | Меняется? | Чья ответственность |
|---|---|---|---|
| 1 | Расписание и выбор лидера | Нет | модуль |
| 2 | **Спрос** — каким локальным записям сейчас нужно внешнее состояние | Данными, но не формой | вы пишете запрос, модуль его выполняет |
| 3 | **Забор** — по одной / пачками / постранично / асинхронная задача | **Да. Единственная реальная вариация** | вы пишете fetcher |
| 4 | **Сверка** — идемпотентно применить внешнее состояние, не затирая более новое | Меняется отображение | вы пишете reconciler, модуль даёт защитные ограждения |
| 5 | Повторы, backoff, карантин, метрики, аудит | Нет | модуль |

Автор сервиса пишет запрос спроса, fetcher и reconciler. Всё операционное — это `application.yaml`, и
оно одинаково во всех сервисах.

### Для чего этот модуль **не** предназначен: файл как источник истины

Если синхронизируемые данные приходят **большим файлом**, а не набором ключей, которые сервис уже
знает, нужен [`file-ingest-spring-boot-starter`](../file-ingest-spring-boot-starter), и разница здесь
не в масштабе.

Этот модуль работает **от потребности**: этап 2 спрашивает, каким *локальным* записям нужно внешнее
состояние, а этап 3 забирает его *по ключу*. Файл переворачивает это: источник истины - сам файл, а его
ключи неизвестны до чтения. `Fetcher.Paged` соединяет полученные результаты с потребностью, поэтому
**запись из файла, для которой нет локальной строки, была бы молча отброшена** - ровно та ошибка,
ради предотвращения которой существует модуль массовой загрузки.

Постраничная запись стадирования этого модуля (`sync_inbox_record` с `attempts`, `next_attempt_at`,
`locked_by` и `version`) уместна для нескольких тысяч расходящихся записей, каждой из которых нужен
свой бюджет повторов, и неуместна для десяти миллионов строк в день: пооперационный учёт обошёлся бы
дороже самой загрузки.

`Fetcher` объявлен `sealed` намеренно. Файл - не пятая форма выборки.

## Быстрый старт

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>reconciliation-spring-boot-starter</artifactId>
</dependency>
```

```java
@ReconciliationTask("billing-status")
public class BillingStatusTask implements SyncTask<Order, String, BillingRecord> {

    private final OrderRepository orders;
    private final BillingClient billing;          // интерфейс @LudwigRestClient

    @Override public String name() { return "billing-status"; }

    @Override public DemandProvider<Order, String> demand() {
        return new DemandProvider<>() {
            @Override public List<Order> demand(DemandRequest request) {
                return orders.findByStatusIn(NOT_SETTLED, request.maxRecords());
            }
            @Override public Optional<Order> byKey(String key) {
                return orders.findByBillingId(key);
            }
        };
    }

    @Override public Function<Order, String> localKey() { return Order::getBillingId; }
    @Override public KeyCodec<String> keyCodec()        { return KeyCodec.ofString(); }
    @Override public Class<BillingRecord> externalType() { return BillingRecord.class; }

    @Override public Fetcher<String, BillingRecord> fetcher() {
        return (Fetcher.Batched<String, BillingRecord>) billing::statusesFor;
    }

    @Override public ExternalStamp stampOf(BillingRecord record) {
        return ExternalStamp.ofTimestamp(record.changedAt());
    }

    @Override public Reconciler<Order, BillingRecord> reconciler() {
        return (order, record, context) -> {
            if (record.status().equals(order.getStatus())) {
                return ReconcileResult.unchanged();
            }
            order.setStatus(record.status());
            orders.save(order);
            return ReconcileResult.applied("status -> " + record.status());
        };
    }
}
```

```yaml
ludwig:
  reconciliation:
    tasks:
      billing-status:
        fetch:    { shape: batched, batch-size: 200, max-concurrency: 4 }
        schedule: { fixed-delay: 30s, initial-delay: 10s, run-timeout: 5m }
        demand:   { max-records-per-run: 5000, freshness-target: 2m }
        rest-client: billing
```

Это вся интеграция. Ни `@EnableScheduling`, ни библиотеки блокировок, ни цикла повторов.

## Основная абстракция: потоки внешних записей, адресуемых ключом

Объединение состоит в том, чтобы перестать моделировать *вызов* и начать моделировать **поток внешних
записей, адресуемых ключом корреляции**. Все четыре формы забора дают ровно это и отличаются только
тем, как движок их обходит:

```
Demand(Set<K>) ──┬─ PerItem   → параллельный веер, ограниченный max-concurrency
                 ├─ Batched   → chunk(batch-size) → веер
                 ├─ Paged     → обход страниц, чекпойнт курсора, join со спросом
                 └─ JobFetcher→ submit / poll / collect через несколько тиков
                              ↓
                    Stream<FetchOutcome<K,O>>    // Found | NotFound | Failed
                              ↓
                    стейджинг (по умолчанию) или прямое применение, по записи, по транзакции
```

`Fetcher` — запечатанный (`sealed`) интерфейс с четырьмя `non-sealed` под-интерфейсами. Запечатан
намеренно: движок обязан знать каждую форму, которую его могут попросить обойти, а пятая, добавленная
снаружи, молча провалилась бы в отсутствие поведения. **Расширение здесь — это выбор формы, а не
изобретение новой**: эти четыре и есть то, что по-настоящему различается между интеграциями.

### `NotFound` — не ошибка

`FetchOutcome.NotFound` — полноправный исход, отличный от `Failed`, со своей политикой на задачу и
своей метрикой. Это важно, потому что "партнёр не знает этот id" обычно **навсегда**: запись удалили
на их стороне, id когда-то ввели с опечаткой, это тестовая строка, — а ошибки повторяются.
Классификация как сбой даёт запись, которая повторяется вечно, исчерпывает бюджет, уходит в карантин и
порождает алерт; помноженное на backlog, это самая частая причина безудержных циклов повторов в
системах такого класса.

| `not-found` | Что происходит |
|---|---|
| `ignore` (по умолчанию) | Учитывается в `reconciliation.records.not_found`, ничего не пишется |
| `mark-missing` | Стейджится строка без payload и вызывается `Reconciler.reconcileMissing`, чтобы "исчез наверху" могло что-то значить для домена |
| `fail` | Трактуется как повторяемый сбой. Верно только для партнёра, который отвечает 404 на "ещё не готово" |

Пакетный fetcher сообщает о not-found тем, что **не кладёт ключ в возвращаемую map**. Он не должен
бросать исключение, возвращать `null` или подставлять заглушку — движок делает это отображение один
раз, централизованно, чтобы отдельному fetcher'у не нужно было об этом помнить.

## Две фазы: сначала записать, потом применить

Забор и применение в одной транзакции — это то, что делает такие задачи хрупкими: одна плохая запись
отравляет весь проход, а повтор снова дёргает партнёра ради записей, которые уже у вас есть. Режим по
умолчанию — `staged`.

`sync_inbox_record` — одна таблица на все задачи, с ключом `task_name`. Проход применения захватывает
строки через `SELECT … FOR UPDATE SKIP LOCKED`, применяет каждую **в собственной транзакции** и
записывает исход. Это даёт четыре вещи:

- повтор по записи **без ещё одного обращения к партнёру**;
- воспроизводимую запись того, что именно сказал партнёр;
- dead-letter по записи, а не падение всего прохода;
- ритм применения, независимый от ритма забора: задача может опрашивать раз в пять минут и при этом
  разгребать отложенные записи каждые десять секунд.

Стейджевая строка бывает одного из трёх **видов**, потому что три вещи разделяют этот жизненный цикл,
но не потребителя:

| Вид | Когда пишется | Кто потребляет |
|---|---|---|
| `RECORD` | партнёр вернул состояние | проход применения |
| `MISSING` | партнёр не знает ключ, при `mark-missing` | проход применения, через `reconcileMissing` |
| `FETCH_FAILURE` | вызов упал | проход **забора**, как талон backoff |

Именно третий вид приводит к тому, что ключ, на котором партнёр стабильно давится, перестаёт
запрашиваться: он откатывается по backoff, как всё остальное, и в итоге уходит в карантин — заметно, —
вместо того чтобы запрашиваться на каждом проходе вечно и без результата.

### `mode: direct`

Доступен, и это явный opt-in. Он применяет данные на месте, без строки, что дешевле и **строго хуже во
всех режимах отказа**: повтор снова дёргает партнёра, а короткое замыкание по идемпотентности и защита
от устаревшей записи недоступны обе, потому что обе отвечаются из истории применённых записей, а
истории нет. Reconciler, используемый в режиме direct, обязан делать собственную проверку порядка. Что
режим direct сохраняет — это изоляцию транзакций по записи.

## Защитные ограждения

| Аспект | Механизм |
|---|---|
| **Двойной опрос в HA** | Аренда прохода на задачу через `RunLock` из `job-core` — захват в БД с `FOR UPDATE SKIP LOCKED`, как в outbox. Ни ShedLock, ни новых зависимостей |
| **Перекрывающиеся проходы** | Нереентерабельный охранник в `SelfSchedulingLifecycle`, `run-timeout` в роли TTL аренды и сборщик зависших записей для проходов, чей владелец умер |
| **Защита от устаревшей записи** | Движок отвергает внешнее состояние, которое по собственной метке времени партнёра старее уже применённого для этого ключа. Локальные записи идут через JPA, чтобы оптимистичная блокировка `db-core` их видела |
| **Идемпотентное применение** | Нормализованный payload хэшируется; неизменившийся хэш даёт `Unchanged` без записи, без обновления `updated_at` и без строки аудита |
| **Изоляция по записи** | Одна транзакция на запись, в отдельном бине, чтобы прокси Spring действительно её применял. Сбой помечает запись, а не проход |
| **Ядовитые записи** | Счётчик попыток, экспоненциальный backoff с джиттером, терминальный статус `QUARANTINED`, возврат в очередь оператором |
| **Watermark / дельта-опрос** | `sync_task_state` держит курсор и watermark на задачу и уровень; `incremental`-задача получает watermark как `updated-since` |
| **Уровни приоритета** | Спрос делится на быстрый проход `hot` и медленный обход `cold` с раздельными расписаниями |
| **Backpressure** | `max-concurrency` на задачу, квоты и рейт-лимиты уровня партнёра, а также собственный bulkhead именованного REST-клиента |
| **Корректная остановка** | Доживание через `SmartLifecycle` с таймаутом; текущие элементы завершаются, а не бросаются посреди захвата |

### Почему защита от устаревшей записи — в движке

Ответы партнёра приходят вразнобой: медленный повторённый вызов, пачка, обогнавшая поштучный забор,
два инстанса, забирающих один ключ в одну секунду, — и применение более старого последним молча
откатывает локальную запись. Эта ошибка не даёт **ни исключения, ни строки в логе, ни упавшей
метрики**. Оставить её каждому reconciler'у — значит получить корректность только там, где автор об
этом подумал.

Токены версии сравниваются на равенство (одинаковый токен означает ту же запись), но **никогда на
порядок**: ничто не гарантирует, что токены партнёра сортируются в порядке выдачи, а сравнение `"10"` и
`"9"` как текста даёт обратный результат. Порядок определяет только метка времени. Задача, чей партнёр
не публикует ни того, ни другого, не получает общей защиты, и модуль говорит об этом прямо, а не
притворяется.

### Почему хэш payload берётся от нормализованной формы

Потому что вопрос звучит "это та же запись, что и в прошлый раз?", а большинство партнёров не
сериализуют одинаково дважды. Порядок ключей в JSON-объекте не значим, и многие серверы его не
стабилизируют, так что хэш сырых байтов объявит изменившейся каждую пересериализованную запись —
запись в БД, обновление `updated_at`, строка аудита и событие наружу, на каждом опросе, вечно. Ключи
объектов рекурсивно сортируются перед хэшированием. **Порядок массивов не трогается**: массивы
упорядочены по определению, и партнёр, переставивший список, сказал нечто иное.

## Ресурсы уровня партнёра: квоты и рейт-лимиты

**Ограничение параллелизма принадлежит внешнему сервису, а не задаче.** Две задачи, бьющие в одного
партнёра, делят его бюджет, поэтому квоты и рейт-лимиты — именованные ресурсы верхнего уровня, на
которые задачи ссылаются по имени.

```yaml
ludwig:
  reconciliation:
    quotas:
      partner-exports:
        max-concurrent: 5
        lease-ttl: 15m
        heartbeat-interval: 2m
        acquire-timeout: 0s
        fifo: true
        reclaim: verify-remote
        max-lifetime: 6h
    rate-limits:
      partner-api: { permits: 100, per: 1m }
```

**Квота** — распределённый арендуемый считающий семафор поверх `sync_quota_lease` и
`sync_quota_waiter`. Bulkhead из Resilience4j работает в пределах JVM и не может выразить "5
одновременных на кластер": три реплики, каждая соблюдающая лимит в пять, дают пятнадцать.

Взятие слота выполняется под **транзакционной advisory-блокировкой** PostgreSQL по имени квоты:
посчитать живые слоты и затем вставить один — это read-modify-write, и два инстанса, делающие это в
один момент, оба увидели бы место и оба его заняли, то есть ровно то, что квота обязана
предотвращать, — в месте, где это заметить труднее всего.

### Три правила, делающие аренду безопасной

Все три обязательны, и каждое предотвращает конкретный невидимый отказ:

1. **Heartbeat; никогда не доверять живости.** Слот занят, только пока его срок в будущем. Без этого
   **один сбой навсегда уменьшает квоту на единицу**, и после достаточного числа сбоев интеграция
   останавливается совсем — без ошибки где бы то ни было, потому что изнутри это неотличимо от
   занятого партнёра. Это худший режим отказа в проекте; у него есть отдельный тест, убивающий
   держателя аренды.
2. **Проверить перед возвратом.** Истёкшая аренда **не** означает, что удалённая работа остановилась.
   По умолчанию `reclaim: verify-remote` сначала опрашивает handle и забирает слот только если задача
   терминальна или пережила `max-lifetime`, отменяя её удалённо там, где реализован `cancel`.
   `reclaim: on-expiry` существует для партнёров без эндпойнта статуса и **может превысить заявленный
   партнёром лимит** — опишите это там, где описана интеграция.
3. **Сначала аренда квоты, потом разрешение рейт-лимитера.** Иначе задача тратит разрешения на работу,
   которую ей не позволено начать.

Квоты по умолчанию **честны по FIFO**. Без очереди "кто получит следующий свободный слот" решает тот
тик, который попал первым, и задача с тридцатисекундным ритмом выигрывает практически каждую гонку у
пятиминутной — более медленная может голодать бесконечно, притом что каждое отдельное взятие выглядит
корректным. Неудавшаяся попытка остаётся в очереди, так что следующая сохраняет уже выжданную позицию.
`reconciliation.quota.oldest_waiter.age` — то единственное число, которое говорит, верно ли размерена
квота; коэффициент насыщения, прижатый к 1.0, выглядит одинаково и когда очередь разгребается за
секунды, и когда она не двигалась час.

`acquire-timeout` по умолчанию `0s`: проходу, не получившему слот, нечего делать, кроме как вернуться
на следующем тике, а ожидание занимает поток планировщика ровно столько, сколько насыщенный партнёр
остаётся насыщенным. Ненулевое значение заставляет взятие повторяться до дедлайна, и это оправдано
только для вызывающего, чья окружающая работа уже чего-то стоила — разрешение рейт-лимитера, наполовину
собранный запрос, — и для которого сдаться на пару сотен миллисекунд раньше дороже.

**Рейт-лимиты действуют на инстанс**, а не на кластер, и это осознанный компромисс, названный прямо:
рейт-лимитер задаёт темп вызовам, которые этот процесс вот-вот сделает, а его координация стоила бы
обращения к БД на *каждый вызов*. Делите опубликованную партнёром частоту на число реплик. Квоту так
решить нельзя, потому что она считает долгоживущую удалённую работу, где стоимость координации
пренебрежима, а ошибка означает больше задач у партнёра, чем он разрешает.

## Форма async-job

Некоторые партнёры отвечают на запрос идентификатором задачи; её опрашивают до завершения, а затем
забирают результат. Это растягивается на несколько тиков, обязано переживать перезапуски и всё это
время удерживает удалённый ресурс.

```
PENDING_SUBMIT → SUBMITTED → RUNNING → SUCCEEDED → COLLECTING → COLLECTED
       │             │           │          │            │
       └─────────────┴───────────┴──────────┴────────────┴──→ FAILED | EXPIRED | CANCELLED
       │
       └──→ ORPHANED
```

```yaml
partner-bulk-status:
  fetch: { shape: async-job, submit-batch-size: 500 }
  quota: partner-exports
  rate-limit: partner-api
  rest-client: partner
  job:
    submit:  { fixed-delay: 1m, max-concurrent-submits: 2 }
    poll:    { fixed-delay: 30s, backoff-multiplier: 1.5, max-interval: 5m, honour-retry-after: true }
    collect: { fixed-delay: 1m, max-concurrency: 1 }
    max-lifetime: 6h
    on-ambiguous-submit: assume-submitted
```

**Три планировщика, каждый со своим ритмом и параллелизмом.** Опросить сотню идущих задач дёшево и
нужно часто; забрать один результат дорого и нужно редко. Общее расписание означает либо что опросы
замедлены до темпа сборки результатов — и задача, завершившаяся две минуты назад, замечается через
двадцать, — либо что сборка наследует параллелизм опросов и эндпойнт результатов получает десять
одновременных многомегабайтных загрузок.

### Порядок записей, который нельзя переставлять

1. `INSERT sync_remote_job (state = PENDING_SUBMIT, idempotency_key = <uuid>)`, **взять аренду
   квоты**, commit.
2. Отправить запрос, передав ключ идемпотентности, если партнёр его учитывает.
3. `UPDATE … state = SUBMITTED, external_handle = …`, commit.

Если POST прошёл, а инстанс умер до шага 3, наивный перезапуск отправит запрос повторно — сожжёт слот
квоты и, возможно, запустит **оплачиваемую удалённую задачу, которая уже идёт**. Шаг 1 — это то, что
оставляет улику: строка `PENDING_SUBMIT` превращает "мы понятия не имеем" в "ситуация неоднозначна, и
вот ключ, по которому можно спросить". Коммит строки после вызова или взятие слота после вызова теряют
это. Любое отклонение от порядка невидимо в тестах и дорого в продакшене.

### Разрешение неоднозначной отправки

Строка, застрявшая в `PENDING_SUBMIT` дольше `submit-grace-period`, **неоднозначна, а не потеряна**.

1. **Спросить.** Если fetcher реализует `listActive()`, найти задачу с ключом идемпотентности этой
   строки и принять её handle. Сопоставление идёт по ключу, никогда по позиции или времени: два
   инстанса, отправивших запросы одновременно, дают две активные задачи, и принятие не той привяжет
   строку к чужой работе, оставив настоящую бесхозной.
2. **Применить политику**, если спросить нельзя:

| `on-ambiguous-submit` | Поведение | Верно для |
|---|---|---|
| `assume-submitted` | Пометить `ORPHANED`, держать слот до `max-lifetime`, не отправлять повторно | Всего дорогого или оплачиваемого. Ошибка стоит одного потерянного слота и запоздавшей синхронизации |
| `resubmit` | Закрыть строку, чтобы следующий проход запустил новую задачу | Только для дешёвых и по-настоящему идемпотентных отправок. Иначе один сбой превращается в две идущие задачи |

Безопасного значения по умолчанию для всех партнёров нет, поэтому ключ **обязателен** для
`shape: async-job`, и контекст без него не стартует.

### Принимать, а не перезапускать

При перезапуске нетерминальные строки задач захватывает тот инстанс, который опрашивает следующим;
владелец переписывается при каждом захвате. Удалённая задача продолжает идти, а новый владелец
возобновляет heartbeat **существующей** аренды вместо того чтобы освободить её и взять новый слот, что
на мгновение посчитало бы одну задачу дважды. Спрос, покрытый любой нетерминальной задачей — включая
`ORPHANED`, — исключается из прохода отправки, так что ничего не отправляется дважды. Закрытие задачи и
есть то, что делает её спрос снова доступным; отдельного флага возврата в очередь нет, потому что
второй источник истины о том, что ещё нужно синхронизировать, оказался бы устаревшим.

### Истечение

Задача, пережившая `max-lifetime`, отменяется удалённо там, где это поддерживается, помечается
`EXPIRED`, и её аренда освобождается — сначала отмена, потом закрытие, чтобы партнёру, который умеет
останавливаться, сказали об этом до того, как система перестанет считать работу. Без жёсткого предела
задача, которую партнёр тихо бросил, держит слот вечно, пока её аренда идеально продлевается: утечка,
которую heartbeat обнаружить не может, потому что heartbeat работает.

## Конфигурация

Привязывается из `@ConfigurationProperties("ludwig.reconciliation")`.

### Приоритет

**Задача, затем `defaults`, затем встроенное значение модуля — по полю, а не по блоку.** Задача,
задавшая только `retry.max-attempts`, сохраняет интервал и множитель из defaults, а не роняет весь
блок. Слияние выписано в `TaskSettingsResolver`, а не оставлено relaxed binding, **потому что Spring
его не делает**: `defaults` и `tasks.billing-status` для биндера — два несвязанных объекта, и сервис,
предположивший обратное, обнаружил бы, что его defaults молча игнорируются.

Cron и fixed-delay наследуются парой, так что задача, задавшая `cron`, не подхватит `fixed-delay` из
defaults и не станет противоречивой.

### Настройки задачи

| Свойство | По умолчанию | Значение |
|---|---|---|
| `enabled` | `true` | Работает ли задача. Отключённая задача всё равно валидируется |
| `mode` | `staged` | `staged` или `direct` |
| `not-found` | `ignore` | `ignore`, `mark-missing` или `fail` |
| `fetch.shape` | — | Обязательно. Должно совпадать с интерфейсом fetcher'а |
| `fetch.batch-size` | `100` | Ключей на вызов, `batched` |
| `fetch.page-size` | `500` | Записей на страницу, `paged` и сборка результата задачи |
| `fetch.max-concurrency` | `4` | Вызовов в полёте у этой задачи |
| `fetch.checkpoint` | `true` | Сохраняет ли постраничный обход свой курсор |
| `fetch.submit-batch-size` | `500` | Ключей на отправленную задачу |
| `schedule.fixed-delay` \| `schedule.cron` | `1m` | Когда идёт горячий проход |
| `schedule.initial-delay` | = fixed-delay | Первый запуск после старта |
| `schedule.run-timeout` | `15m` | TTL аренды прохода. Должен превышать бюджет повторов |

### Что перечитывается, а что требует перезапуска

Настройки читаются там, где используются, поэтому что именно подхватит работающий процесс, зависит от
того, куда попадает значение. Эта матрица — часть контракта:

| Перечитывается — вступает в силу на следующем проходе | Требует перезапуска |
|---|---|
| `retry.*` (калькулятор строится заново на каждый исход) | `fetch.shape` |
| `demand.max-records-per-run`, `demand.freshness-target` | `schedule.*` и `cold-schedule.*` (проход планируется один раз, на старте) |
| `fetch.batch-size`, `fetch.page-size`, `fetch.max-concurrency` | `apply.fixed-delay` (по той же причине) |
| `not-found`, `apply.batch-size` | `mode` (staged/direct меняет назначение схемы) |
| `rate-limits.*` (новая конфигурация лимитера применяется по имени) | `quotas.*` (число слотов читается при взятии из привязанной map) |
| `endpoint.allow-destructive-operations` | Добавление или удаление задачи, квоты, рейт-лимита |

Всё из правой колонки меняет то, что *связывается*, а этот модуль связывает один раз на старте
намеренно: расписание, способное измениться под идущим проходом, — это расписание, о котором никто не
может рассуждать во время инцидента.

### Валидация на старте

`ReconciliationConfigurationValidator` отказывается стартовать на конфигурации, корректной по
отдельности и неверной в целом, и сообщает **все** проблемы за один проход:

- задача ссылается на несуществующую квоту, рейт-лимит или REST-клиент;
- `shape: async-job` без блока `job` или без `on-ambiguous-submit`;
- `run-timeout` короче собственного бюджета повторов задачи;
- `lease-ttl` меньше `2 × heartbeat-interval` или `max-lifetime` меньше `lease-ttl`;
- бин `@ReconciliationTask` без конфигурации или настроенная задача без бина;
- бин, у которого аннотация и `name()` расходятся, или два бина с одним именем;
- fetcher, чей интерфейс противоречит настроенному `fetch.shape`.

Каждое сообщение говорит **что сломается**, а не что неверно, потому что читающий его человек в этот
момент выкатывает релиз и ему нужно решить, откатываться ли.

## Наблюдаемость

Метрики размечены тегом `task`, а где уместно — `quota`.

| Метрика | Тип | О чём говорит |
|---|---|---|
| `reconciliation.freshness.lag` | gauge | **SLO-метрика.** Секунды сверх `freshness-target` задачи |
| `reconciliation.run` | timer | Длительность прохода, теги `tier` и `outcome` |
| `reconciliation.records.fetched` | counter | Записей, вернувшихся от партнёра |
| `reconciliation.records.settled` | counter | Тег `outcome`: applied, unchanged, rejected, deferred, missing, failed, quarantined |
| `reconciliation.records.not_found` | counter | С тегом применённой политики |
| `reconciliation.records.quarantined` | gauge | Текущая глубина карантина |
| `reconciliation.staged.depth` / `.oldest.age` | gauge | Очередь, ждущая применения |
| `reconciliation.fetch.duration` / `.apply.duration` | timer | На исходящий вызов / на запись |
| `reconciliation.quota.in_flight` / `.limit` / `.saturation` | gauge | Занятость слотов |
| `reconciliation.quota.oldest_waiter.age` | gauge | Сколько ждёт очередь |
| `reconciliation.quota.acquire.wait` | timer | Тег `acquired` |
| `reconciliation.quota.lease.reclaimed` | counter | **Алертить на любое устойчиво ненулевое значение** |
| `reconciliation.job.duration` / `.polls` / `.settled` | timer / summary / counter | С тегом терминального состояния |
| `reconciliation.job.ambiguous_submit` | counter | Теги `adopted`, `orphaned` или `resubmitted` |

**Два сигнала, достойных алерта:**

- **`reconciliation.freshness.lag`** — единственная метрика, описывающая то, ради чего модуль
  существует. Любое другое число может выглядеть здоровым, пока она растёт: задача, чей запрос спроса
  перестал что-либо находить, ничего не забирает, мгновенно завершается успехом и вечно показывает
  идеальную долю успешных проходов. Метрика определена как худшее из *возраста самой старой записи,
  всё ещё в конвейере* и *времени с последнего завершённого прохода*, минус собственный
  `freshness-target` задачи, — так что она равна нулю, пока задача укладывается в заявленный бюджет, и
  один порог алерта работает для задач, чья допустимая несвежесть различается на часы.
- **`reconciliation.quota.lease.reclaimed`** с устойчиво ненулевой скоростью означает либо утечку
  аренд, либо дублирование удалённой работы. И то и другое невидимо во всём остальном, и и то и другое
  ухудшается само.

Gauge регистрируются на поставщиках и **опрашиваются**, а не выставляются изнутри проходов. Gauge,
записываемая только во время прохода, продолжает показывать последнее здоровое значение задачи,
которая вообще перестала запускаться, — то есть ровно тот отказ, который метрика свежести и призвана
ловить.

**Трассировка.** У каждого прохода есть run id, проставляемый на каждую стейджевую строку и каждое
событие аудита, и correlation id, привязанный на время прохода. С
`observability-spring-boot-starter` на classpath этот id уходит в исходящие вызовы fetcher'а, так что
одно взаимодействие с партнёром прослеживается от начала до конца.

**Аудит.** `ReconciliationAuditLogger` — открытый SPI с реализациями `Slf4j` и `Persisting`.
Записываются: начало и конец прохода, переходы исходов по записям, переходы состояний задач, взятие,
освобождение и возврат аренды, а также каждое действие оператора. Одна плоская таблица
`sync_audit_record`, а не пять оформленных: у аудита почти всегда спрашивают "что происходило вокруг
этой задачи, по порядку" — а пять таблиц означают пять запросов и ручное слияние в тот момент, когда
кто-то выясняет, почему партнёра вызвали дважды.

## Эксплуатация: эндпойнт actuator `reconciliation`

```
GET  /actuator/reconciliation                    обзор: все задачи и квоты
GET  /actuator/reconciliation/{task}             детали: настройки, курсор, задачи в полёте, карантин
POST /actuator/reconciliation/{task}             {"action": "...", ...}
```

| Действие | Параметры | Эффект |
|---|---|---|
| `run` | `tier` | Запускает проход сейчас. Вернёт `ran: false`, если проход уже шёл |
| `dry-run` | `tier` | Забирает то, что забрал бы проход, и отчитывается по исходам, **ничего не записывая**: ни стейджевой строки, ни применения, ни watermark |
| `backfill` | `keys` | Забирает явный список ключей через запятую, минуя запрос спроса. Сохраняет все ограждения и **не** двигает watermark |
| `reset-cursor` | `tier` | Очищает курсор и watermark |
| `requeue-quarantined` | — | Возвращает записи из карантина в очередь со **сброшенными** счётчиками попыток |
| `requeue-job` | `jobId` | Возвращает в очередь записи, собранные этой задачей |
| `cancel-job` | `jobId`, `confirm` | **Разрушительно.** Помечает задачу истёкшей; проход обслуживания отменит её удалённо и освободит слот |
| `release-lease` | `leaseId`, `confirm` | **Разрушительно.** Принудительно освобождает слот квоты |

Счётчики попыток при возврате в очередь сбрасываются намеренно: оператор возвращает записи, потому что
что-то *починили*, и запись заслуживает целого бюджета против новых условий, а не той единственной
попытки, что оставалась от старого.

Разрушительные действия требуют **одновременно**
`ludwig.reconciliation.endpoint.allow-destructive-operations=true` и `confirm=true` в самом вызове:
среда, где они допустимы, и момент, когда они задуманы, — разные решения. Оба могут развести картину
мира этой системы и партнёра; принудительное освобождение аренды, в частности, означает, что
настроенный лимит теперь может быть превышен. Каждый изменяющий вызов аудируется с указанием
вызывающего. Защищайте эндпойнт через
[`security-spring-boot-starter`](../security-spring-boot-starter), как любой другой.

## Runbook

**Партнёр недоступен.** Заборы падают, ключи накапливают талоны `FETCH_FAILURE` и откатываются по
backoff; ничего не теряется и ничего не применяется неверно. Следите за
`reconciliation.freshness.lag`. Когда партнёр вернётся, ключи в пределах бюджета восстановятся сами;
ушедшим в карантин нужен `requeue-quarantined`. **Не** перезапускайте поды, чтобы "сбросить" это —
состояние backoff в базе, а перезапуск лишь потеряет работу в полёте.

**У квоты нет свободных слотов.** Откройте `GET /actuator/reconciliation` и посмотрите на `holders`
квоты. Если у них есть `jobId`, задачи действительно идут — сверьте их возраст с `max-lifetime`. Если
нет, или их владельцы — уже несуществующие инстансы, значит проход возврата либо не работает, либо
корректно отказывается возвращать слот, не сумев проверить удалённое состояние; посмотрите
`reconciliation.quota.lease.reclaimed` и логи на "could not verify lease". `release-lease` — последнее
средство, и оно может превысить лимит партнёра.

**Задача осиротела.** Её отправку не удалось подтвердить, а партнёр не предлагает списка активных
задач. Она держит слот до `max-lifetime`, и по её ключам ничего не будет отправлено повторно.
Проверьте у партнёра, выполнялась ли задача. Если нет — `cancel-job`, чтобы освободить слот и вернуть
спрос. Если да — оставьте: `max-lifetime` закроет её.

**Записи в карантине.** `GET /actuator/reconciliation/{task}` покажет выборку с `lastError`. Устраните
причину, затем `requeue-quarantined`. Карантин `FETCH_FAILURE` означает, что падал *вызов* по этому
ключу; карантин `RECORD` — что падал *reconciler*.

**Отставание свежести растёт, но ничего не падает.** Обычная причина — запрос спроса перестал что-либо
находить. Проверьте `reconciliation.records.fetched`: задача, забирающая ноль записей и сообщающая об
успешных проходах, — это ровно тот отказ, ради которого метрика и существует.

## Миграция самописного цикла на `@Scheduled`

Типичный цикл выглядит так:

```java
@Scheduled(fixedDelay = 30_000)
public void syncBillingStatuses() {
    for (Order order : orders.findByStatusIn(NOT_SETTLED)) {
        try {
            billing.statusFor(order.getBillingId())
                   .ifPresent(record -> apply(order, record));
        } catch (Exception e) {
            log.warn("sync failed for {}", order.getId(), e);
        }
    }
}
```

1. **`findBy…` становится `DemandProvider.demand`**, и добавьте `byKey`, перечитывающий одну запись:
   проходу применения нужна свежая, а не снимок, который вернул запрос.
2. **Вызов клиента становится `Fetcher`.** Если у партнёра есть пакетный эндпойнт — `Fetcher.Batched`,
   и цикл удаляется; если нет — `Fetcher.PerItem` и `max-concurrency`.
3. **Тело `apply` становится `Reconciler`.** Возвращайте `Unchanged`, когда ничего не изменилось:
   старый цикл почти наверняка писал безусловно.
4. **Удалите `try/catch`, `@Scheduled` и любой `@SchedulerLock`.** Повторы, backoff, карантин, выбор
   лидера и метрики теперь конфигурация.
5. **Реализуйте `stampOf`**, если партнёр публикует метку времени изменения. Этот шаг легче всего
   пропустить и он даёт больше всего: он превращает ответы, пришедшие вразнобой, из невидимой ошибки в
   отклонённую запись.
6. **Объявите `freshness-target`.** Так задача говорит, что для неё значит "работает".

Ожидайте, что Java сократится примерно втрое, а операционное поведение станет строго лучше: у старого
цикла не было ни backoff, ни изоляции, ни выбора лидера, ни способа понять, отстаёт ли он.

## Схема (только PostgreSQL)

Семь таблиц, поставляются как `db/changelog/reconciliation/reconciliation-changelog.xml` и
применяются `ReconciliationLiquibaseAutoConfiguration` как независимый бин `SpringLiquibase` рядом с
собственным changelog приложения. Поставьте `ludwig.reconciliation.liquibase.enabled=false`, чтобы
включить их в свой master changelog.

| Таблица | Что хранит |
|---|---|
| `sync_inbox_record` | Стейджевые внешние записи, маркеры отсутствия и талоны сбоев забора |
| `sync_task_state` | Курсор и watermark на задачу и уровень |
| `sync_remote_job` | Асинхронные задачи и всё нужное, чтобы продолжить их вести |
| `sync_quota_lease` | Занятые слоты квот |
| `sync_quota_waiter` | Очередь перед каждой квотой |
| `sync_audit_record` | Сохранённый аудит |
| `job_run_lock` | (из `job-core`) Аренды проходов по задачам |

Индексы частичные везде, где частичен запрос: индекс захвата покрывает только захватываемые статусы,
так что на задаче, применившей десять миллионов записей и имеющей сорок в ожидании, он остаётся
пропорционален очереди, а не истории.

## Расширение

Всё — бины с `@ConditionalOnMissingBean` по умолчанию: `ReconciliationMetrics`,
`ReconciliationAuditLogger`, `PayloadCodec`, `DemandKeys`, `CorrelationIdSource`, `RestClientPresence`,
`DatabaseQuota`, `RateLimitRegistry` и каждый сервис движка. Опубликуйте свой бин, и модуль
посторонится. **Добавление интеграции никогда не требует правок этого стартера.**

Всё отключаемо: `ludwig.reconciliation.enabled: false` для модуля, `enabled: false` для задачи.

## Тестирование

`mvn test` запускает:

- **Модульные** — привязку свойств и приоритет слияния, каждый случай отказа валидатора, кривую
  backoff и окно её джиттера, идемпотентность и нормализацию хэша payload, отклонение устаревшей метки,
  политики `NotFound`, нарезку спроса и постраничный обход курсора.
- **ArchUnit** — пакет SPI не зависит от реализации и не содержит Spring-обвязки; сущности через него
  не выставляются; `@Scheduled` не используется нигде.
- **Интеграционные** (Testcontainers PostgreSQL) — схема применяется из поставляемого changelog и
  сверяется с JPA-маппингами через `ddl-auto=validate`; ровно один проход при удерживаемой аренде;
  изоляция сбоя по записи; исчерпание бюджета повторов → карантин → возврат в очередь; постраничный
  обход, прерванный посередине и продолженный с чекпойнта; продвижение и монотонность watermark;
  соблюдение квоты двумя инстансами; продление heartbeat; **убитый держатель аренды посреди задачи, где
  verify-remote отказывается отдавать слот ещё идущей задачи**; честность FIFO между двумя задачами с
  общей квотой; сбой между отправкой и коммитом без повторной отправки при `assume-submitted`; принятие
  задачи через `listActive()`; истечение задачи с удалённой отменой; и принятие идущей задачи вместо
  повторной отправки.

Интеграционным тестам нужен запущенный демон Docker.

## Аудит

У этого модуля больше нет собственного механизма аудита. `ReconciliationAuditLogger` и `Slf4jReconciliationAuditLogger` удалены, и `SyncAuditRecord` со
своим репозиторием тоже - в этом репозитории его никогда ничего не писало
(`PersistingReconciliationAuditLogger`, на который ссылался javadoc, не существовал), а строки,
которые развёртывание могло записать своим логгером, миграются в `audit_event` changeset'ом
`audit-003` модуля аудита. Его журнал теперь идёт через
единственный в платформе `AuditSink`, который развёртывание направляет в лог, в таблицу `audit_event`
(только на добавление), в SIEM через транзакционный outbox или в несколько мест сразу - см.
[`audit-core`](../audit-core) and [`audit-spring-boot-starter`](../audit-spring-boot-starter).

Запись `AuditEvent` остаётся, **переименованная в `ReconciliationAuditEvent`**, чтобы её и конверт
платформы можно было импортировать в один файл, с сохранённым перечислением `Category` (`RUN`,
`RECORD`, `JOB`, `LEASE`, `OPERATOR`). `Builder.build()` теперь возвращает `AuditEvent` платформы
напрямую - поэтому ни одна точка вызова в модуле не обросла `.toAuditEvent()`; `buildTyped()`
возвращает запись этого модуля для вызывающего, которому нужны её именованные компоненты.

`Category` становится **атрибутом**, а не `audit_event.category`. Эта колонка называет подсистему, а
те пять - вид события внутри неё; объединение заставило бы одну колонку означать две разные вещи в
зависимости от строки. Миграция `audit-003` отображает её так же, поэтому перенесённая строка и новая
имеют одинаковую форму.

Исход выводится из имени события - `.failed`, `.timed-out` и `.reclaimed` это сбои, `.quarantined` и
`.skipped` - частичные - а не переносится, потому что у записи никогда не было компонента исхода, и
добавление его означало бы обход всех точек вызова ради того, что все они уже говорят именем.

**Что заметит развёртывание:** логгера `ru.ludwigandreas.reconciliation.audit` больше нет; журнал - в `ru.ludwigandreas.audit` с
`category=reconciliation`. Таблица `sync_audit_record` не удаляется - сверьте по ней миграцию и
удалите её сами.
