# История изменений

Здесь записаны все значимые изменения платформы. Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версии — [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

**Один файл на весь реактор.** У всех модулей одна и та же `${revision}`, и выпускаются они
вместе, поэтому тридцать отдельных файлов были бы тридцатью копиями одного списка. Запись
описывает, что изменилось *для потребителя платформы*, и называет модуль там, где это важно.

**Две локали, один набор заголовков.** В `CHANGELOG.md` те же заголовки уровня `##`, в том же
порядке. Сборка с `-Prelease` падает, если в любом из двух файлов нет заголовка для выпускаемой
версии, — то же правило, которое репозиторий уже применяет к `README.md` и `README.ru.md`.

**Релиз — это тег.** Версию вычисляет GitVersion по истории git и передаёт Maven как
`-Drevision=<вычисленное>`; `.mvn/maven.config` — только запасной вариант для копии репозитория
без тегов. Запись версии в этот файл релиз не выпускает, и добавление заголовка сюда — тоже.

## [2.0.0]

**Мажорный** выпуск: он содержит бинарно несовместимые изменения опубликованных API, каждое из которых
помечено ниже как **BREAKING**. Прочитайте эти записи, прежде чем переводить потребителя с `1.1.x`.

### Added

- **Сведения о происхождении сборки в каждом артефакте сервиса и в каждой строке лога.**
  `ludwig-service-parent` теперь упаковывает `META-INF/build-info.properties` (группа, артефакт, имя, версия,
  время сборки и номер сборки CI, если сборке передан `-Dludwig.ci.build-number`) рядом с `git.properties`,
  а `observability-spring-boot-starter` читает оба файла при старте в новую запись `BuildIdentity`.
  Сокращённый коммит пишется в каждое событие лога — `service.commit.id` (`ecs`), `ServiceCommitId` (`otel`),
  `commit_id` (`flat`), — а одно событие `Application identity:` при старте несёт полный коммит, ветку, время
  сборки, номер сборки CI и признак «грязного» дерева. Поле, которое не удалось определить, опускается и
  никогда не пишется как `unknown`. **Агрегатору логов со строгим шаблоном индекса нужно добавить маппинг
  нового поля до того, как сервис с этим полем начнёт писать в общий индекс.** `BuildIdentity` намеренно
  отделена от `ServiceIdentity`, поэтому ничто из неё не становится тегом метрики. В `/actuator/info`
  появляется раздел `build`.
- **`observability-spring-boot-starter`: `ludwig.observability.build.*`** — шесть свойств с определённым
  происхождением сборки; каждое по умолчанию берётся из упакованных ресурсов и может быть задано явно
  артефактом, собранным иным способом.
- **`architecture-rules`: группа правил `logging`**, включена по умолчанию: ни один тип вне модуля
  наблюдаемости не реализует `Encoder` или `Layout` из Logback, ни один тип не повторяет идентичность
  сборки, и ни один продакшен-класс не запускает процесс операционной системы и не зависит от JGit.
  Собственный `logback-spring.xml` сервиса это не затрагивает. Третье правило сообщает о *каждом* запуске
  процесса, потому что по байткоду нельзя сказать, какая программа запускается; законный запуск
  исключается по имени в самом правиле.
- **`scripts/check_build_metadata.sh`**, запускается гейтом: падает, когда `ludwig-service-parent` перестаёт
  быть настроен на выпуск любого из двух ресурсов с происхождением.
- **`odata-filter-spring-boot-starter`: обнаружение политики фильтрации.** Клиент может спросить, по чему
  ему разрешено фильтровать, вместо того чтобы выяснять это, отправляя фильтры и читая отказы, — а это была
  единственная альтернатива и ровно то поведение, для которого `odata.filter.rejected` описан как сигнал
  алерта. `GET <base-path>/<entity>` возвращает пути свойств, которые вызывающий может назвать, тип каждого,
  разрешённые на нём операторы, пригодность для сортировки и пределы, которые применит сервер. Выключено,
  пока не задан `odata.filter.metadata.base-path`, и вдобавок включается для каждой сущности отдельно через
  `@FilterPolicy(metadataName = ...)`; сущность, которую никто не опубликовал, отдаёт 404, а не пустой
  документ. Документ фильтруется по вызывающему — путь, которого его роли не допускают, отсутствует, а не
  помечен запрещённым, и ни одного имени роли в нём нет, — и он является проекцией разрешённой политики,
  поэтому не может расойтись с тем, что принимает путь запроса. Он намеренно не называется `$metadata` и не
  претендует на CSDL.
- **`odata-filter-spring-boot-starter`: `odata.filter.metadata.served`** — счётчик с тегом сущности, чтобы
  отличать клиентов, спросивших по-человечески, от прощупывающих.
- **`audit-core`: категория аудита `query`.** Чтение фильтруемой коллекции вызывающим, отделённое от
  `access`, где записываются решения авторизации. «Разрешено ли было alice искать» и «что именно alice
  искала» — разные вопросы, и расследованию обычно нужно их соединить, а не найти смешанными.
- **У `odata-filter-spring-boot-starter` появился архитектурный тест.** Его не было, поэтому общая
  библиотека правил ArchUnit — включая всю группу `audit`, предмет которой именно этот модуль — к нему
  никогда не применялась. Два правила там выключены как названный долг, с причиной в точке выключения:
  `cycles.modules-are-free-of-cycles` и
  `configuration-properties.configuration-properties-are-validated`.
- **`architecture-rules`: `audit.audit-types-produce-audit-events`.** Падает, если тип в пакете `audit`
  какого-либо модуля не производит `AuditEvent`. Два существующих правила ловили только модуль, который
  объявил что-то *лишнее* — второй SPI, второй логгер, — но не тот, который не объявил ничего и при этом не
  вызывал приёмник; именно так журнал этого модуля не доходил ни до чего при зелёной сборке.
- **`odata-filter-spring-boot-starter`: один вызов выполняет отфильтрованную, отсортированную и
  посчитанную страницу.** `ODataQueryExecutor` применяет предикат, сортировку, смещение, лимит и — если
  вызывающий не прислал `$count=false` — подсчёт, а `ODataSearch` позволяет репозиторию добавить свои
  предикаты (туда идёт область данных) и изменить запрос строк (туда идёт fetch join), не написав ни
  одного из этих четырёх шагов. Оба примерных сервиса потеряли поле `PathBuilder`,
  `orderSpecifiers(Sort)`, рефлексивный `orderSpecifier(String, boolean)` с подавлением непроверяемого
  приведения, вызов `PageableExecutionUtils` и приватный `count` — всё это они несли одинаково.
  Исполнитель также отказывается от корня запроса, чей алиас отличается от того, по которому строится
  предикат: в JPQL такое расхождение никогда не падало — оно соединяло таблицу с собой и возвращало
  молчаливо неверные строки.
- **`odata-filter-spring-boot-starter`: `ODataPaths` открывает обход динамического пути** для
  репозитория, который должен вести запрос сам, но всё ещё нуждается в выражениях сортировки `$orderby`.
- **`odata-filter-spring-boot-starter`: `$count` реализован.** `$count=false` пропускает запрос
  количества, и тогда ответ не несёт итога. Ранее модуль документировал этот параметр как намеренно
  игнорируемый на том основании, что флаг, с которым никакой код ничего не делает, ничего вызывающему не
  даёт, — и это было верно, пока запрос здесь никто не выполнял.
- **`odata-filter-spring-boot-starter`: `ODataQueryOptions`** несёт пять параметров запроса как один
  параметр контроллера, описываемый springdoc, вместо пяти объявлений `@RequestParam` на эндпоинт и
  записей `XSearchCriteria`, которые в каждом сервисе были структурно одинаковыми.
- **`web-core-spring-boot-starter`: `PageResponse.offset`.** Применённое абсолютное смещение строк,
  чтобы вызывающий, листающий невыровненным `$skip`, мог прочитать свою позицию из ответа.
- **`architecture-rules`: `persistence.dynamic-paths-are-not-hand-built`.** Падает, если сервис строит
  `PathBuilder` из QueryDSL для имени свойства, присланного вызывающим, вместо того чтобы взять
  разрешение у модуля, который его проверил.
- **`file-action-spring-boot-starter`: единственный на платформе путь для файла, загруженного
  пользователем и выполняющего бизнес-действие.** Человек перетаскивает таблицу - создаются заказы.
  Сервис пишет типизированную `RowBinding`, одну из двух запечатанных форм обработчика и блок YAML;
  модуль владеет приёмом загрузки, пределом размера, который проверяется по ходу чтения тела,
  определением формата по магическим байтам, сохранением до разбора, заявкой на идемпотентность по хешу
  содержимого, швом антивируса, читателем таблиц с ограниченной памятью, жизненным циклом
  `UPLOADED/VALIDATED/APPLIED` поверх конверта операции из `web-core`, политикой фиксации, постраничным
  ресурсом отклонённых строк и скачиваемой аннотированной книгой, генерируемым шаблоном, отложенным
  исполнением по лизу, удержанием и аудитом. Чтение недоверенного XLSX идёт только через SAX-путь
  `XSSFReader` POI, с пределами степени сжатия, числа элементов и суммарного распаковываемого объёма,
  решаемыми по каталогу ZIP до разбора любого XML; `.xls` отклоняется, потому что у `HSSFWorkbook` нет
  потокового режима и его поддержка сделала бы объём памяти функцией файла пользователя. Рассчитано на
  интерактивную загрузку - по умолчанию 25 МиБ и 100 000 строк, - а файл крупнее отклоняется сообщением,
  называющим `file-ingest-spring-boot-starter`.
- **Два решения, которые стенд обязан принять сам.** У `commit-policy` нет значения по умолчанию, потому
  что `PER_ROW` молча применил бы две трети проводки, а `ALL_OR_NOTHING` отклонил бы четыреста контактов
  из-за одного опечатанного адреса, и что именно неверно - зависит от домена; действие без неё не
  запускается. `ludwig.file-action.scanning.mode` по умолчанию `required`, так что приложение без бина
  `FileScanner` тоже не запустится: отсутствие сканирования должно быть выбором, сделанным вслух, а не
  пробелом, которого никто не замечает.
- **`RuleGroup.UPLOADS` в `architecture-rules`.** `MultipartFile` допустим только в
  `file-action-spring-boot-starter`. До этого изменения в репозитории не было ни одного, и первый сервис,
  которому понадобилась бы загрузка, написал бы предсказуемые ошибки: отсутствие предела до чтения тела,
  `getBytes()`, DOM-чтение книги и 400 с тремя тысячами ошибок по строкам.
- **Работающий `product-import` в `crud-service-example`.** Таблица товаров становится товарами через
  `ProductService`: импорт - это другой способ входа в действие, которое сервис уже выполняет, а не его
  вторая реализация со своей таблицей.
- **Единый контракт предпочтений вызывающего в `web-core`.**
  `ru.ludwigandreas.webcore.preference` разрешает локаль и зону вызывающего из его сохранённой
  настройки, затем из заголовков запроса, затем из конфигурации - и публикует обе в
  `LocaleContextHolder`. Маппер добирается до него, указав `UserPreferenceFormatter` в
  `@Mapper(uses = ...)`, после чего MapStruct подбирает преобразования по типам: ни одна подпись
  отображения не меняется и ни одной аннотации `@Mapping` не добавляется. Вне маппера это
  `UserPreferences.current()`, а `UserPreferences.bind()` переносит захваченные предпочтения
  вызывающего в рабочий поток.
- **`user-settings-spring-boot-starter` отдаёт сохранённую половину.** Сервис, объявивший
  `WellKnownSettings.LOCALE` и `TIMEZONE`, теперь получает их учёт в каждом ответе, а не только их
  хранение. Значение считается выбором пользователя лишь тогда, когда его `SettingLayer` специфичнее
  `PLATFORM`: настройка, которую никто не трогал, не перебивает `Accept-Language` вызывающего.
- **Два правила ArchUnit** в новой группе `RuleGroup.PRESENTATION`: никому нельзя вызывать
  `Locale.getDefault()`, `TimeZone.getDefault()`, `ZoneId.systemDefault()` и
  `Clock.systemDefaultZone()`, и никому нельзя объявлять второй тип, держащий пару
  «локаль и зона вызывающего».

- **`notification-service`: уведомления в интерфейсе, единственный пассивный канал.** Получателю,
  который не хочет ни письма, ни чата, ни вебхука, всё равно можно что-то сообщить. `IN_APP` — канал
  доставки, как и остальные: тот же контракт запроса, та же раскладка шаблонов, та же работа с
  настройками и списком подавления, — но он помечен как `PASSIVE`, и эта пометка является обязательным
  аргументом конструктора `ChannelType`, поэтому новый канал нельзя добавить, не решив этот вопрос.
  Пассивность означает, что канал не прерывает: тихие часы его не откладывают, потому что никого не
  нужно будить. Доставка завершается в момент записи элемента — провайдера, который мог бы её принять,
  нет. Читателем выступают «Входящие»: список, счётчик непрочитанного, отметка одного или всех
  прочитанными, отметка увиденным и отклонение, — каждая операция ограничена вызывающим и никогда не
  принимает владельца параметром, так что один вызывающий не прочитает чужие входящие, поменяв путь.
  Чужой элемент и отсутствующий — оба 404, намеренно неразличимо. Любой переход идемпотентен.
- **`notification-service`: объявления платформы.** Одно объявление, адресованное всем или всем с
  некоторой ролью, вместо отдельного уведомления каждому. В этом и состоит замысел: уведомление
  разворачивается при записи (N строк, у каждой один читатель), объявление — при чтении (одна строка,
  N читателей), поэтому публикация на всю организацию — постоянное число запросов, и её очистка тоже.
  Получатель видит объявления, допускаемые его ролями, отклоняет их по одному, и отклонение — строка,
  которая существует только для тех, кто действительно отклонил. Содержимое хранится по одной записи
  на поддерживаемую локаль. Аудитория разрешается один раз при публикации по настроенному списку
  разрешённых, поэтому роль, которую никто не авторизовал, нельзя взять целью; коды ролей там же
  приводятся к единому виду — объявление с целевой ролью, не совпавшее ни с кем, и было найденным
  дефектом. Категория может дополнительно рассылаться письмами, и это длительная операция, которая
  сообщается через единственный на платформе конверт `OperationResponse`, отменяется кооперативно и
  отвечает 202, потому что остановка лишь запрошена, а уже зафиксированные отправки не отзываются.
  Видимость — это окно, и срок хранения привязан к его концу, а не к созданию: объявление,
  опубликованное на следующий квартал, не вычистят до того, как оно появится, а показываемое сейчас
  не исчезнет из-под читающих его людей.
- **Оба сервиса публикуют свой документ OpenAPI в дерево исходников**, в
  `docs/api/<artifactId>.openapi.yaml`, порождая его из настоящего контекста приложения, а не записывая
  руками. Смысл — в обозримости: иначе HTTP-поверхность сервиса существует только внутри запущенного
  процесса, и изменение, расширившее ответ, убравшее поле или поменявшее код статуса, ревьюеру не
  показывает ничего. По одному `ApiDocumentIT` на сервис перегенерирует документ на `verify` и роняет
  сборку, когда закоммиченная копия расходится с тем, что сервис отдаёт; обычная сборка его никогда не
  перезаписывает, поэтому обновление осознанно, а diff всегда запрошен. Каждый документ сначала
  приводится к каноническому виду — члены каждого объекта отсортированы, `servers` удалён, — потому что
  порядок обхода обработчиков в springdoc не обещан стабильным, а неотсортированный вывод давал бы
  diff-ы из одних перестановок. Эти документы описывают то, что сервисы отдают сейчас; они намеренно
  **не** являются базой совместимости — за неё для jar-ов по-прежнему отвечает
  `scripts/check_api_baseline.sh`. Чтобы это стало возможным, `crud-service-example` получил springdoc,
  что заодно впервые включило там кастомайзер из `odata-filter-spring-boot-starter`: поисковый
  эндпоинт эталонного сервиса теперь документирует свои пять опций запроса OData, как того и требовала
  возможность `odata-query-contract`, но проверить это было нечем.

### Changed

- **`observability-spring-boot-starter`: формат консоли по умолчанию теперь зависит от активного профиля.**
  JSON везде, читаемый текст в профиле `local` — то есть сервис, запущенный с
  `--spring.profiles.active=local`, получает текстовую консоль там, где раньше получал JSON. Явно заданное
  `ludwig.observability.logging.json.enabled` по-прежнему побеждает в любую сторону, поэтому сервис, уже
  задающий его для `local`, не затронут и может убрать переопределение.
- **`observability-spring-boot-starter`: текстовый формат больше не шаблон Spring Boot по умолчанию.** При
  выключенном JSON каждая строка теперь несёт `[имя/версия@коммит env=... instance=...]` и
  `[correlation id,trace id,span id]`; раньше смена формата всё это теряла. Шаблон, заданный через
  `logging.pattern.console` / `logging.pattern.file`, и любой аппендер с вручную настроенным энкодером
  остаются как есть.
- **`observability-spring-boot-starter`: `spring.main.banner-mode` по умолчанию `off`, когда формат — JSON.**
  Spring Boot печатает баннер прямо в стандартный вывод, в обход системы логирования, поэтому раньше
  структурированный поток открывался семью строками ASCII-графики. Явно заданный `spring.main.banner-mode`
  побеждает.
- **`ludwig-service-parent`: `git.properties` сужен до пяти ключей** — идентификатор коммита, сокращённый
  идентификатор, ветка, время коммита, признак «грязного» дерева. Раньше в нём были ещё имя и адрес
  электронной почты автора коммита, имя хоста сборки и URL удалённого репозитория — и всё это отдавал
  `/actuator/info`. Сборка без git-репозитория теперь не упаковывает `git.properties` вовсе, а не кладёт
  пустой файл.
- **`ludwig-service-parent`: задан `maven.build.timestamp.format`** с точностью до дня, потому что он
  определяет время сборки в `build-info.properties`, а время с полной точностью давало бы каждой сборке
  одного коммита свой дайджест образа. Сервис, который читает `${maven.build.timestamp}` для собственных
  нужд, наследует этот формат и должен переопределить свойство.
- **BREAKING для базы, в которой эти changeset'ы уже применены, — каждый changeset Liquibase в
  платформе теперь formatted SQL.** Все 84 changeset'а в 13 модулях перенесены из XML-словаря
  изменений Liquibase в файлы `--liquibase formatted sql`: по одному changeset'у на файл, имя
  `NNNN-<slug>.sql`, идентификатор `<prefix>-NNNN-<slug>` и автор `ludwig-<prefix>`, так что имя файла
  и строка в `DATABASECHANGELOG` не могут расходиться. В каждом модуле остаётся один корневой
  XML-changelog, содержащий только элементы `<include>` и комментарии, — он остаётся XML потому, что у
  парсера formatted SQL в Liquibase 4.27 нет директивы include. **Путь каждого корневого changelog'а
  сохранён**, поэтому ни одна строка `<include>` у потребителя, ни настройка
  `spring.liquibase.change-log`, ни свойство модуля не меняются. Потребитель вместо этого видит сам
  DDL — в файле, а не словарь, который его порождает; к тому же 46 из этих changeset'ов и так
  оборачивали сырой блок `<sql>`, то есть репозиторий уже был наполовину на SQL, без правила, что
  когда применять.

  **Заодно исправлены четыре пространства имён идентификаторов**, поскольку автор теперь выводится из
  префикса: `ingest-` стал `file-ingest-`, `usrset-` — `user-settings-`, схема `0004-N-` в
  `notification-service` — `notification-00NN`/`ludwig-notification`, как у пяти её соседей, а тестовый
  changelog reconciliation — `reconciliation-test-`. Порядковые номера перенумерованы так, чтобы быть
  уникальными и возрастающими внутри модуля: это закрыло два changeset'а с номером `003` и два с
  номером `004` в `crud-service-example` и номер `004b` в `reconciliation`.

  **Если база уже применила XML-changeset'ы**, следующий старт упадёт на несовпадении контрольной
  суммы, а не на испорченной схеме. Восстановление — `liquibase clearChecksums` и обычный `update`; для
  четырёх переименованных пространств имён выше в строках `DATABASECHANGELOG` нужно также обновить
  `ID`, `AUTHOR` и `FILENAME`, иначе эти changeset'ы выполнятся повторно. Изменение сделано на
  зафиксированном основании, что такого развёртывания нет.

- **Каждый changeset теперь объявляет `dbms:postgresql` и явный rollback.** Rollback — либо настоящий
  SQL, либо `--rollback NOT REQUIRED`, который Liquibase разбирает в тот же пустой rollback, что и
  `<rollback/>` в XML; у 37 из 84 его не было вовсе, так что «необратим по природе» ничем не отличалось
  от «никто не подумал». Объявление диалекта приводит к тому, что на не-PostgreSQL changeset будет
  пропущен, а не упадёт на середине схемы. Rollback у `pat-0002` теперь удаляет и
  `ux_ludwig_pat_key_id`, который XML-версия оставляла.

- **BREAKING — `odata-filter-spring-boot-starter`: `ODataFilterProperties` переехал из `..config..` в
  `..properties..`.** Меняется только импорт. Это был единственный класс, державший всю проблему циклов
  пакетов в модуле: `core`, `web` и `policy` читали связанные свойства, а связывание бинов в `config`
  ссылается на каждый пакет модуля, — и эти три входящих ребра замыкали **двадцать** различных циклов через
  `config`, то есть все циклы, какие в модуле были. Один перенос убрал все двадцать. Классы
  автоконфигурации намеренно остались в `config`: полное имя класса автоконфигурации — это API
  конфигурации, ведь развёртывание отключает его через `spring.autoconfigure.exclude=...` в YAML, чего не
  проверяет ни один компилятор, поэтому переименование того пакета молча сломало бы исключение во время
  выполнения.
- **`odata-filter-spring-boot-starter`: связанные свойства проверяются при старте.** `maxDepth`,
  `maxPageSize`, `defaultPageSize`, `maxNestedPropertyDepth` и `maxExpressionLength` должны быть не меньше
  1, и ни одно из них раньше не проверялось. `max-page-size` равный 0 принимался, а затем ронял *каждый*
  запрос при первом же обращении с сообщением про `$top` — указывая оператору на вызывающего, а не на
  строку конфигурации, которая это вызвала. `hibernate-validator` взят **optional**, поэтому до потребителя
  не доходит; у каждого потребителя в репозитории он уже есть.
- **`odata-filter-spring-boot-starter`: его `ArchitectureTest` больше ничего не отключает как долг.**
  `cycles.modules-are-free-of-cycles` и
  `configuration-properties.configuration-properties-are-validated` были выключены, когда у модуля впервые
  появился архитектурный тест; оба включены.
- **`odata-filter-spring-boot-starter`: применение фильтра записывается в единственный `AuditSink` из
  `audit-core`**, категория `query`, вместо публикации только как события Spring, которое каждый
  потребитель должен был пересылать сам. Событие по-прежнему публикуется как внутренний хук. Падает ли
  запрос при недоступном приёмнике — решает `AuditFailurePolicy` из конфигурации развёртывания: этот модуль
  не оборачивает вызов приёмника ни в какой `try`/`catch`.
- **BREAKING — `odata-filter-spring-boot-starter`: `ODataQueryExecutor`, `ODataSearch` и `ODataPage`
  переехали из `..querydsl..` в `..execution..`.** `core` уже зависел от `querydsl`, поэтому исполнитель,
  зависящий от `core` изнутри `querydsl`, давал цикл пакетов — внесённый предыдущим изменением и поймынный
  новым архитектурным тестом этого. Меняется только импорт.
- **`odata-filter-spring-boot-starter`: `FilterSummary` живёт в `..ast..`**, а не в `..audit..`. Он
  описывает фильтр, а не понятие аудита, и новое правило аудита справедливо требует, чтобы тип в пакете
  `audit` производил конверт платформы.
- **BREAKING — `odata-filter-spring-boot-starter`: `ODataFilterService.parse` принимает
  `ODataQueryOptions`** вместо четырёх позиционных параметров — двух `String` и двух `Integer`. Старая
  сигнатура позволяла переставить `filter` и `orderBy` или `top` и `skip` и всё равно скомпилироваться.
- **BREAKING — `odata-filter-spring-boot-starter`: `ODataQuery.predicate()` возвращает
  `Optional<Predicate>`** и пуст, если вызывающий не прислал `$filter`, тогда как раньше возвращался
  `Expressions.TRUE`. Всегда истинный предикат неотличим от настоящего предиката вызывающего — именно
  поэтому `export-spring-boot-starter` дописывал безусловный `AND true` к каждому отчёту без фильтра.
- **BREAKING — `odata-filter-spring-boot-starter`: `ODataQueryArgumentResolver` и
  `odata.filter.web.argument-resolver-enabled` удалены.** Резолвер был помечен `@Deprecated` и выключен
  по умолчанию без замены; замена — `ODataQueryOptions`. Та его половина, что читала запрос, сохранена
  дословно, включая алиасы параметров без префикса `$`.
- **BREAKING — `web-core-spring-boot-starter`: итоги в `PageResponse` допускают null** (`Long`,
  `Integer`) и отсутствуют в JSON, когда вызывающий отказался от подсчёта. Канонический конструктор
  получил `offset` и сменил типы итогов; поддерживаемый вход — фабричные методы, и они совместимы на
  уровне исходников, кроме нового `of(List, long, int, Long)`.
- **`LocaleContextHolder.getTimeZone()` теперь отвечает зоной вызывающего в потоке запроса.** Раньше
  он отвечал `TimeZone.getDefault()` - зоной контейнера, - потому что `AcceptHeaderLocaleResolver`
  является обычным `LocaleResolver` и никогда не публикует `TimeZoneAwareLocaleContext`. **Всё, что
  форматировало дату через holder Spring, меняет вывод**: `@JsonFormat` без явной зоны,
  преобразование `@DateTimeFormat`, аргумент-дата, подставляемый в сообщение. Это и есть задуманное
  исправление - и всё же изменение поведения, о котором стоит прочитать до обновления.
  `ludwig.web.preferences.enabled=false` возвращает прежнее поведение в точности.
- **`Content-Language` несёт регион, который запросил вызывающий.** Запрос `ru-RU` к сервису,
  поддерживающему `ru`, теперь получает `Content-Language: ru-RU`, а не `ru`. Тело по-прежнему
  отрисовывается из бандла `ru`, к которому `MessageSource` откатывается сам; регион сохраняется
  потому, что JDK держит первый день недели и разделители чисел как данные *региона*, и сужение
  `ru-RU` до `ru` выдаёт русскому пользователю американский календарь.
- **`export-spring-boot-starter` отрисовывает отчёт в зоне вызывающего.**
  `SecurityReportCaller.zone()` был жёстко заданным `ZoneId.of("UTC")`, что давало ошибку в пять
  часов в каждой строке для пользователя в Екатеринбурге. `ReportCaller` получает `preferences()`, а
  `locale()` и `zone()` становятся `default`-методами над ним: для вызывающего это совместимое по
  исходникам дополнение, а реализациям этого интерфейса теперь нужно предоставить новый метод. Явный
  `timeZone` в запросе отчёта по-прежнему побеждает.


### Removed

- **BREAKING — `odata-filter-spring-boot-starter`: компоненты `rawFilter` и `resolvedPredicate` записи
  `FilterAppliedEvent`.** Оба были литеральными значениями вызывающего дословно: `rawFilter` — строка
  `$filter` как прислана, `resolvedPredicate` — `predicate.toString()`, — поэтому фильтр по полю с
  электронной почтой, телефоном или номером документа помещал это значение туда, где кто-то слушал. Их
  заменил `FilterSummary` с путями свойств и операторами и без значений в любом виде: не хешированных, не
  обрезанных, не собранных.

### Fixed

- **`observability-spring-boot-starter`: запасной источник версии, который не мог сработать.**
  `ServiceIdentityResolver` обращался к свойству окружения `build.version`, которое никто не публиковал.
  Теперь он читает `build.version` из `META-INF/build-info.properties`, так что сервис, запущенный из
  распакованной раскладки, сообщает свою версию.
- **Два правила ArchUnit, которые сообщали об успехе, ничего не проверяя.**
  `noPrivateCaffeineCache` из `RuleGroup.CACHING` и `noPrivateDeadLetterRecoverer` из
  `RuleGroup.KAFKA` были написаны как `noClasses().should(notDependOnClassesThat(..))`. `noClasses()`
  оборачивает условие в `never()` из ArchUnit, который инвертирует каждое событие, а помощники из
  `ArchitectureConditions` сообщают только о нарушениях - поэтому оба давали ноль находок на коде,
  который их заведомо нарушал. Теперь оба используют `classes().should(..)`, причина написана в каждом
  из мест, а новый `PresentationRulesTest` проверяет, что правило *называет нарушившие классы*, а не
  только что оно выполнилось: именно такая форма теста и поймала бы это.

## [1.1.0]

**Базовая линия совместимости API.** Всё, что опубликовано под этой версией, — тот пол, с которым
сравнивается каждый последующий выпуск: потребитель может зафиксировать `1.1.0` и знать, что
именно вправе изменить `1.1.x` или `1.2.x`.

### Added

- **Проверка совместимости API для каждой публикуемой библиотеки.** `revapi-maven-plugin`
  выполняется на фазе `verify` для каждого модуля, унаследованного от корня реактора, и сравнивает
  скомпилированный API модуля с последним выпуском тех же координат в `ludwig.repo.releases`.
  Разрешением служит приращение версии: мажорное допускает двоично несовместимое изменение,
  минорное — совместимое, патч — только эквивалентный API. Два сервиса не сравниваются: их
  потребляют как образы, а не как jar-файлы.
- **Контракт устаревания.** У `@Deprecated` обязательны и `since`, и `forRemoval`, а в Javadoc
  обязателен тег `@deprecated`, называющий замену. Обеспечивают два правила Checkstyle —
  `DeprecationWithoutSince` и `MissingDeprecated` — на фазе `validate`.
- **Javadoc-архивы**, прикрепляемые под `-Pci` рядом с уже существующими архивами исходников, для
  каждого библиотечного модуля. Некорректный Javadoc — сломанный `{@link}`, неизвестный тег,
  `@param` с несуществующим параметром — теперь ломает сборку; отсутствующий Javadoc остаётся на
  прежнем уровне предупреждений.
- **`CHANGELOG.md` и `CHANGELOG.ru.md`** — эта пара, вместе с правилом enforcer, которое ломает
  релизную сборку, если в любом из файлов нет заголовка для выпускаемой версии.
- **`gitversion.yml` и стадия вычисления версии в Jenkins**, чтобы версия бралась из истории git,
  а не набиралась руками в файле.
- **`scripts/check_image_pins.sh`**, подключённый к `scripts/gate.sh`: каждая ссылка на образ
  контейнера в `Jenkinsfile`, в YAML и в Markdown обязана нести дайджест `sha256`, а не только тег.

### Changed

- **Релиз выпускается тегом**, а не правкой `.mvn/maven.config`. Этот файл сохраняет значение
  `-Drevision` только как локальный запасной вариант для копии без тегов; пользовательское
  свойство из командной строки его перекрывает — на этом приоритете и построен CI.
- **Каждый плагин сборки объявляет версию.** `requirePluginVersions` добавлено в enforcer и в корне
  реактора, и в `ludwig-service-parent`, а плагины, которые Maven и Spring Boot раньше подключали
  без версии — `maven-jar-plugin`, `maven-resources-plugin`, `maven-clean-plugin`,
  `maven-install-plugin`, `maven-deploy-plugin`, `maven-site-plugin`, — зафиксированы. Собственный
  ответ Maven на незакреплённый плагин — предупреждение, которое печаталось в каждой сборке этого
  репозитория и на которое никто не реагировал.

### Fixed

- Двадцать некорректных Javadoc-ссылок в одиннадцати модулях, найденных включением doclint: три
  ссылки на константы перечисления во вложенном типе, семь заголовков `<h2>` внутри Javadoc члена
  класса, где неявный предшествующий заголовок — `<h3>`, три ссылки на переименованный или
  удалённый API (`JiraClientBuilder#meterRegistry`, `request.IssueUpdate`, `AuthorityCache`) и
  несколько ссылок `{@link #getXxx()}` на аксессоры, порождаемые Lombok.
