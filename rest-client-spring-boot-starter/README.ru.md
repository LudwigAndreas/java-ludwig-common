# rest-client-spring-boot-starter

*[English](README.md) · **Русский***

Исходящий HTTP как конфигурация. Сервис объявляет столько независимых HTTP-клиентов, сколько у него
зависимостей, прямо в `application.yaml`, и каждый получает собственный пул соединений, таймауты,
аутентификацию, политику Resilience4j, сериализацию, логирование, метрики и аудит. Ничто в описании
клиента не требует `@Configuration`-класса в потребляющем сервисе.

Дальше клиент используется тем из трёх способов, который подходит вызову: декларативный интерфейс,
внедрённый `RestClient`/`WebClient` или обращение к реестру. Все три идут через один конвейер, поэтому
ведут себя одинаково.

## Быстрый старт

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>rest-client-spring-boot-starter</artifactId>
    <version>1.0.0</version>
</dependency>
```

Две зависимости с по-настоящему разными требованиями — одна медленная и с машинной
аутентификацией, другая быстрая и с ключом, — и больше ничего:

```yaml
ludwig:
  rest-client:
    defaults:                 # наследуется каждым клиентом; ключи клиента перекрывают
      connect-timeout: 2s
      read-timeout: 10s
      resilience:
        retry: { max-attempts: 3, wait-duration: 200ms, exponential-backoff-multiplier: 2.0, randomized-wait-factor: 0.5 }
        circuit-breaker: { failure-rate-threshold: 50, sliding-window-size: 100, wait-duration-in-open-state: 30s }
    clients:
      billing:                # длинный сокетный таймаут + OAuth2 client credentials
        base-url: https://billing.internal/api/v1
        read-timeout: 120s
        auth:
          type: oauth2-client-credentials
          registration-id: billing-sa
        resilience:
          bulkhead: { max-concurrent-calls: 20 }
      pricing:                # короткий таймаут + статический bearer из секрета
        base-url: https://pricing.internal
        read-timeout: 800ms
        auth:
          type: bearer
          token: ${PRICING_TOKEN}
        resilience:
          retry: { max-attempts: 1 }
```

Теперь у `billing` сокетный таймаут 120 секунд, машинный токен, который кэшируется, обновляется
заранее и перевыпускается один раз на 401, три попытки с джиттером, размыкатель по окну в 100 вызовов
и ограничение в 20 одновременных вызовов. У `pricing` — таймаут 800 миллисекунд, статический токен и
полное отсутствие повторов. Ни один из них не может повлиять на другой: отдельные пулы, отдельные
размыкатели, отдельные разрешения.

Вызов:

```java
@LudwigRestClient("billing")
public interface BillingApi {

    @GetExchange("/invoices/{id}")
    Invoice invoice(@PathVariable UUID id);
}
```

```java
@Service
class OrderService {

    private final BillingApi billing;                 // декларативный интерфейс
    private final RestClient pricing;                 // внедрение по квалификатору

    OrderService(BillingApi billing, @Qualifier("pricing") RestClient pricing) { ... }
}
```

и, когда зависимость выбирается во время выполнения:

```java
registry.rest("billing").get().uri("/invoices/{id}", id).retrieve().body(Invoice.class);
registry.reactive("pricing").get().uri("/prices/{sku}", sku).retrieve().bodyToMono(Price.class);
```

## Какую проблему этот стартер убирает

Каждый сервис в контуре разговаривает с несколькими другими, и в каждом заводится своя версия одного
и того же файла: `@Configuration`-класс, собирающий `RestTemplate` или `RestClient`,
`ClientHttpRequestFactory` с таймаутами, которые кто-то выбрал в 2023-м, интерсептор, добавляющий
токен, где-то `@Retryable` и — если сервис писали после инцидента — размыкатель.

Шесть копий этого файла в шести сервисах — это шесть разных ответов на одни и те же вопросы, и
различия не видны, пока не становится поздно:

- **Таймауты общие там, где не должны.** Один бин `RestTemplate` или общесистемные умолчания
  означают, что таймаут медленной зависимости становится таймаутом быстрой. Обычный итог — 120 секунд
  везде и сервис, висящий две минуты на health-check.
- **Пулы общие там, где не должны.** Насыщенная зависимость забирает соединения, нужные остальным
  пяти, и плохой день одного партнёра превращается в отказ всего.
- **Повторы настроены без размыкателя.** Три попытки от каждого вызывающего к сервису, который уже
  падает, — это тройная нагрузка в худший возможный момент.
- **Повторы применяются к POST.** Таймаут чтения говорит, что ответ не пришёл; он ничего не говорит о
  том, обработал ли партнёр запрос. Задвоенный платёж находят через недели.
- **Секрет попадает в лог.** Логирование тела включили во время инцидента, и никто не выключил.
- **Метрики размечены развёрнутыми URI.** `/invoices/7f3a…` даёт новый временной ряд на каждого
  клиента, и реестр растёт, пока процесс не умрёт.

Ни одна из этих вещей не сложна, если делать её один раз. Проблема в том, чтобы сделать её правильно
шесть раз и удержать правильной по мере расхождения шести сервисов. Этот стартер превращает их из
свойств исходника в свойства развёртывания.

| | |
|---|---|

## Три модели программирования

### 1. Декларативные интерфейсы — основная модель

Интерфейс с HTTP-аннотациями Spring, привязанный к именованному клиенту:

```java
@LudwigRestClient("billing")
public interface BillingApi {

    @GetExchange("/invoices/{id}")
    Invoice invoice(@PathVariable UUID id);

    @PostExchange("/invoices")
    Invoice create(@RequestBody NewInvoice invoice);
}
```

Прокси регистрируется как бин, поэтому интерфейс внедряется как любой другой сотрудник. Он находится
без всяких аннотаций на приложении: сканируются пакеты под `@SpringBootApplication`. Интерфейсы,
живущие в другом месте — например, в общем артефакте контрактов, — подключаются через
`@EnableLudwigRestClients(basePackageClasses = BillingApi.class)`.

Возвращаемые типы должны соответствовать режиму клиента, и несоответствие — это ошибка **на старте**,
называющая интерфейс, метод и клиент:

```
ru.example.BillingApi does not match its client's mode:
  - invoice returns Mono, but client 'billing' is mode=sync. Set mode: async on the client, or
    return a value type.
```

### 2. Внедряемые `RestClient` / `WebClient`

Каждый `sync`-клиент — это ещё и бин `RestClient` с именем `<name>RestClient` и квалификатором
`<name>`; каждый `async` — точно так же `WebClient`:

```java
OrderService(@Qualifier("billing") RestClient billing) { ... }
```

Это правильная модель для по-настоящему разового вызова — одиночного `HEAD`, потоковой загрузки,
запроса, форма которого не ложится в метод интерфейса.

### 3. Обращение к реестру

```java
RestClient billing = registry.rest("billing");
WebClient pricing = registry.reactive("pricing");
```

Для кода, выбирающего зависимость во время выполнения, и для тестов. Запрос ненастроенного клиента
падает сразу, перечисляя настроенные; запрос блокирующего представления реактивного клиента
отклоняется, а не молча блокирует event loop.

### Программные переопределения

Всё, чего не выражают свойства, — это бин `LudwigRestClientCustomizer` (или
`LudwigWebClientCustomizer`). Они выполняются **после** всех настроек из YAML, что и делает их
переопределением:

```java
@Bean
LudwigRestClientCustomizer partnerMediaTypeCustomizer() {
    return new LudwigRestClientCustomizer() {
        @Override public boolean supports(String clientName) { return "partner".equals(clientName); }

        @Override public void customize(String clientName, RestClient.Builder builder) {
            builder.messageConverters(converters ->
                converters.add(0, new PartnerVendorMediaTypeConverter()));
        }
    };
}
```

## Приоритет

Пять уровней, снизу вверх. Они описаны здесь, потому что именно в них ошибаются, когда настройка «не
применяется»:

1. **Встроенные умолчания** — `ClientPropertiesMerger.builtInDefaults()`, единственное место, где
   записаны собственные мнения стартера.
2. **Блок `defaults`** — то, что это развёртывание хочет для каждого клиента.
3. **Блок самого клиента** — то, что нужно этой зависимости.
4. **Бины-кастомайзеры** — то, чего не выражают свойства.
5. **Заголовки конкретного запроса** — `X-Ludwig-Retry`, `X-Ludwig-Max-Attempts`.

Уровни 1–3 — это явное глубокое слияние, а не relaxed binding. Правила неоднородны, и эта
неоднородность намеренна:

| Что | Правило | Почему |
|---|---|---|
| Скаляры | Верхний слой выигрывает, если не `null` | Все скаляры — обёртки, поэтому «не упомянуто» выразимо |
| Вложенные блоки | Сливаются по полям | Задав `retry.max-attempts`, вы сохраняете унаследованный backoff |
| Списки | **Заменяются** | `retry-on-status: [503]` означает 503 и ничего больше |
| Списки `additional-*` | **Складываются** | «умолчания плюс мои» — отдельная интенция, и ей нужен отдельный ключ |
| Объявленный блок `bulkhead` / `rate-limiter` | **Включает политику** | Написать `max-concurrent-calls: 20` и не получить переборку — молчаливый no-op; явный `enabled: false` всё равно побеждает |
| Карты (`default-headers`) | Сливаются по ключу | «заголовки платформы плюс мои» — единственное, что здесь имеют в виду |
| `base-url` | **Никогда не наследуется** | Общий базовый URL неверен для всех клиентов, кроме одного |
| `auth.relay-enabled` | **Никогда не наследуется** | Проброс чужого токена — решение по каждой зависимости |

## Переопределения на уровне запроса

Два заголовка, поглощаемые конвейером и никогда не уходящие партнёру:

| Заголовок | Эффект |
|---|---|
| `X-Ludwig-Retry: true` | Повторять запрос, даже если метод не идемпотентен. Вызывающий утверждает, что сделал запрос безопасным для повтора — ключ идемпотентности, уникальное ограничение. |
| `X-Ludwig-Retry: false` | Подавить повтор, который иначе произошёл бы. |
| `X-Ludwig-Max-Attempts: 2` | Понизить лимит попыток для этого запроса. Только понизить: место вызова не должно перекрывать решение о ёмкости, принятое для развёртывания. |

## Порядок декораторов и почему повтор внутри размыкателя

```
RateLimiter → Bulkhead → CircuitBreaker → Retry → TimeLimiter → [аутентификация → отправка]
```

Одинаков для `sync` и `async` и не настраивается. У любого другого порядка есть конкретный отказ:

- **Повтор внутри размыкателя.** Обратный вариант — размыкатель внутри повтора — означает, что каждая
  попытка берёт разрешение и записывает результат, и логический вызов из трёх попыток тратит три
  ячейки окна на опыт одного вызывающего. Хуже того, это не останавливает усиление: повтор умножает
  нагрузку на зависимость ровно тогда, когда она этого меньше всего выдержит, и остановить это может
  только размыкатель *над* повтором, отклоняющий вызов до первой попытки. Как только он разомкнут,
  три попытки превращаются в ноль.
- **Переборка снаружи повтора.** Внутри один логический вызов брал бы и отпускал разрешение на каждой
  попытке, и ограничение параллелизма перестало бы ограничивать число вызовов в полёте — единственное,
  ради чего оно существует.
- **Ограничитель частоты снаружи всего.** В любом другом месте он тратит разрешения на попытки и на
  вызовы, которые размыкатель всё равно отклонил бы, так что партнёр видит частоту, кратную
  настроенной.
- **Ограничитель времени внутри всего.** Он ограничивает одну попытку. Вокруг повтора он ограничивал
  бы весь вызов, что уже делает `retry.max-elapsed-time`, и отмена первой попытки выглядела бы как
  дедлайн всего вызова.

Размыкатель берёт одно разрешение и записывает один результат на **логический** вызов, поэтому его
окно считает то, что испытал вызывающий, а детектор медленных вызовов измеряет время, которое
вызывающий действительно ждал. Аутентификация находится внутри повтора — именно это делает
`401 → обновление → повтор` вообще возможным.

### Что считается отказом

По умолчанию размыкатель записывает 408, 429, 500, 502, 503 и 504. Он намеренно **не** записывает
400, 401, 403, 404, 409 и 422: клиентская ошибка означает, что этот сервис отправил то, что партнёр
отверг, — значит, партнёр здоров, и размыкание выводит работающую зависимость из строя из-за бага в
вызывающем. Это самый частый способ, которым размыкатель делает инцидент хуже.

Отказ аутентификации и отклонённый вызов тоже не являются отказом зависимости и не записываются.

### Замечание о Resilience4j

Размыкатель, переборка, ограничитель частоты и ограничитель времени — это собственные объекты
Resilience4j, создаваемые в общих реестрах, привязанных к Micrometer, и названные по имени клиента,
так что `resilience4j.circuitbreaker.state{name="billing"}` стоит рядом с
`ludwig.restclient.requests{client="billing"}`.

**Повтор — собственный** и построен на `IntervalFunction` из Resilience4j ради экспоненциального
backoff с джиттером. Декоратор `Retry` не выражает одновременно трёх вещей, нужных этой политике:
паузы, взятой из заголовка `Retry-After`, бюджета по настенным часам на весь вызов и реактивного
пути, разделяющего решения с блокирующим, а не повторяющего их. Видимое следствие — метрики
`resilience4j.retry.*` для этих клиентов не публикуются; публикуется
`ludwig.restclient.retries{client,reason}`, одинаково в обоих режимах.

## Аутентификация

`auth.type` выбирает стратегию. Семь поставляются; восьмая — это бин.

| Тип | Ключи | Примечания |
|---|---|---|
| `none` | — | По умолчанию |
| `basic` | `username`, `password` | Отклоняется по plain HTTP на не-loopback хост |
| `bearer` | `token` **или** `token-supplier`, `scheme` | Ровно один из двух; оба — ошибка старта |
| `api-key` | `key`, `header-name` **или** `query-param-name`, `value-prefix` | Форма с query предупреждает: секрет в URI попадает в access-лог каждого прокси |
| `oauth2-client-credentials` | `registration-id`, `refresh-skew`, `scopes` | Кэшируется, обновляется заранее, single-flight, перевыпуск один раз на 401 |
| `oauth2-token-relay` | `relay-enabled`, `fail-when-no-token` | См. ниже |
| `custom` | `authenticator` | Делегирует названному бину `ClientAuthenticator` |

### Кэширование токена

Токен `oauth2-client-credentials` кэшируется и обновляется за `refresh-skew` (30 с) до заявленного
истечения — без запаса токен, истекающий через 200 мс, используется для вызова длиной 300 мс, и отказ
выглядит как беспорядочный 401 без всякой закономерности.

Обновление — **single-flight**. Наивный кэш прекрасно ведёт себя в тесте и плохо в продакшене: в
момент истечения все запросы в полёте одновременно обнаруживают, что токен устарел, и сервис с 200
параллельными вызовами отправляет 200 запросов к серверу авторизации в одну и ту же миллисекунду, раз
за время жизни токена. Здесь первый вызывающий выпускает токен, а остальные присоединяются к этому
одному результату.

401 отбрасывает кэшированный токен и даёт **одну** дополнительную попытку вне бюджета повторов —
преждевременно истёкший токен не транспортный отказ и не должен тратить бюджет, предназначенный для
него. Второй 401 — это уже настоящий отказ авторизации, и он сообщается как 401.

### Проброс токена — самый опасный тип

`oauth2-token-relay` передаёт учётные данные пользователей этого сервиса третьей стороне. Иногда это
ровно то, что нужно — шлюз, вызывающий ресурсный сервер от имени пользователя, — а иногда это партнёр
с рабочим пользовательским токеном, который он не должен был увидеть. Три защиты, ни одну нельзя
отключить:

1. `auth.relay-enabled: true` должен стоять **на клиенте**. Это единственный ключ, который слияние
   отказывается наследовать из `defaults`, чтобы девять клиентов не получили его случайно.
2. Без входящего токена вызов **падает**, а не уходит анонимно. Анонимный вызов превращает «этот
   пользователь не аутентифицирован» в «вызов удался с теми правами, что партнёр даёт анонимам» —
   изменение привилегий, которое нигде не вызывает ошибки.
3. Клиент с пробросом в сервисе, не настроенном как ресурсный сервер, отклоняется на старте, потому
   что он мог бы только всегда падать.

### Рецепт: новый способ аутентификации

Опубликуйте один бин. В этом стартере ничего не меняется.

```java
/** Подпись запросов HMAC, как требует один партнёр. */
public class HawkAuthenticationProvider implements ClientAuthenticationProvider {

    @Override public String type() { return "hawk"; }

    @Override public Class<? extends ClientAuthProperties> propertiesType() {
        return HawkProperties.class;               // ваш собственный изменяемый JavaBean
    }

    @Override public ClientAuthenticator create(String clientName, ClientAuthProperties properties) {
        HawkProperties hawk = (HawkProperties) properties;
        Mac mac = Mac.getInstance("HmacSHA256");   // дорогая работа — здесь, а не на каждом запросе
        mac.init(new SecretKeySpec(hawk.getKey().getBytes(UTF_8), "HmacSHA256"));

        return new ClientAuthenticator() {
            @Override public void authenticate(AuthRequest request) {
                String nonce = UUID.randomUUID().toString();
                String payload = request.method() + "\n" + request.uri().getPath() + "\n" + nonce;
                String signature = Base64.getEncoder().encodeToString(mac.doFinal(payload.getBytes(UTF_8)));
                request.headers().set("Authorization",
                        "Hawk id=\"" + hawk.getId() + "\", nonce=\"" + nonce + "\", mac=\"" + signature + "\"");
            }

            @Override public String describe() { return "hawk(id=" + hawk.getId() + ")"; }
        };
    }
}
```

```java
@Bean
ClientAuthenticationProvider hawkAuthProvider() { return new HawkAuthenticationProvider(); }
```

```yaml
ludwig:
  rest-client:
    clients:
      partner:
        base-url: https://partner.example.com
        auth:
          type: hawk
          id: ${HAWK_ID}
          key: ${HAWK_KEY}
```

Блок `auth` привязывается к `HawkProperties` дважды к одному экземпляру — сначала из
`ludwig.rest-client.defaults.auth`, затем из блока клиента, — поэтому пользовательский тип наследует
из блока умолчаний ровно так же, как встроенный.

Провайдер, чей `type()` совпадает с одним из встроенных имён, **заменяет** встроенный: так сервис
меняет смысл «bearer», не обходя этот модуль.

Там, где целый провайдер избыточен — один клиент, один аутентификатор, никаких новых свойств, —
используйте `type: custom` с `auth.authenticator: mySigner` и опубликуйте бин `ClientAuthenticator`.

### Метрики

| Метрика | Теги | О чём говорит |
|---|---|---|
| `ludwig.restclient.requests` (таймер) | `client`, `method`, `uri`, `status`, `outcome`, `exception` | RED-метрики по зависимости. `uri` — это **шаблон**, ограниченный `metrics.max-uri-tags` |
| `ludwig.restclient.retries` | `client`, `reason` | Попытки сверх первой. Делённые на число запросов — доля повторов, самый ранний признак деградации, потому что повторы ещё успешны |
| `ludwig.restclient.circuitbreaker.transitions` | `client`, `from`, `to` | Считается, а не только измеряется: датчик со скрейпом раз в 15 с пропускает размыкатель, открывшийся и закрывшийся между ними |
| `ludwig.restclient.auth.token.refreshes` | `client`, `type` | Реально выпущенные токены. Сильно чаще одного за время жизни — кэш не работает |
| `ludwig.restclient.calls.notpermitted` | `client`, `policy` | Вызовы, которые сервис отказался делать. Сброс нагрузки, а не ошибки |
| `ludwig.restclient.listener.failures` | `client`, `listener`, `callback` | Слушатель бросил исключение, и оно было поглощено |
| `ludwig.restclient.audit.failures` | `client` | Приёмник аудита бросил исключение |
| `ludwig.restclient.pool.{leased,pending,available,max}` | `client` | Только транспорт Apache. Важен `pending`: он ноль в здоровом состоянии и растёт за секунды до роста задержки |

Собственные метрики Resilience4j — `resilience4j.circuitbreaker.state`, `resilience4j.bulkhead.available.concurrent.calls`, `resilience4j.ratelimiter.available.permissions` и остальные — привязываются к `MeterRegistry` приложения этим модулем и размечаются именем клиента. Размыкатель, открывшийся без метрики, — это изменение состояния, на которое никто не может настроить алерт.

Таймер получается из собственного клиентского наблюдения Spring с изменёнными тегами — поэтому
метрика и клиентский спан описывают один обмен и несут один и тот же шаблон URI. Кардинальность URI
ограничивается фильтром `UriCardinalityLimitingMeterFilter` из observability-spring-boot-starter —
той же реализацией, что защищает `http.server.requests`.

Ни один секрет, токен, значение заголовка или развёрнутый URI не попадает ни в один тег.

### Трассировка и correlation

Контекст трассировки W3C распространяется собственной инструментацией Spring. Correlation id
платформы распространяется интерсептором `CorrelationPropagatingRequestInterceptor` из
observability-spring-boot-starter — этот модуль его подключает, а не переписывает. Для реактивных
клиентов, где у того модуля аналога нет, небольшой фильтр отправляет тот же id из того же источника
под тем же именем заголовка.

### Структурированное логирование

По клиенту, в логгер `ludwig.restclient.<client>`, так что одну зависимость можно поднять до DEBUG
во время инцидента, не задевая остальные девять, — а при наличии observability-spring-boot-starter и
без перезапуска.

| `logging.level` | Что пишется |
|---|---|
| `none` | Ничего. Метрики и трассы всё равно фиксируют вызов |
| `basic` (по умолчанию) | Метод, шаблон URI, статус, длительность, попытка |
| `headers` | То же плюс заголовки с маскированием |
| `body` | То же плюс тела с маскированием и ограничением размера |

Две независимые задвижки, и это намеренно: `logging.level` решает, *что* пишется, и это решение о
данных; уровень SLF4J решает, *пишется ли*, и это операционное решение. Их объединение означало бы,
что включение отладки для клиента включает и логирование тел.

Успешные вызовы пишутся на INFO, неуспешные — на WARN.

**Тела никогда не «протекают» в лог потоком.** Тело материализуется, только если ответ неуспешен или
клиент явно попросил уровень `body`, **и** заявленный `Content-Length` меньше 256 КиБ. Ответ без
`Content-Length` — а именно так выглядит потоковый ответ — не буферизуется никогда. Следствие названо,
а не скрыто: клиент, качающий большие ответы, не увидит тел в логах.

Умолчания маскирования: заголовки `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`,
`X-Api-Key`, `X-Auth-Token`, `Api-Key`; JSON-поля `password`, `secret`, `token`, `access_token`,
`refresh_token`, `id_token`, `client_secret`, `pin`, `otp`, `card_number`, `cvv`. Маскирование полей
обходит разобранный документ, поэтому `"name":"password"` выживает, а `"password":"hunter2"` — нет;
регулярное выражение делает ровно наоборот. Чтобы добавить к умолчаниям, используйте
`additional-redacted-headers` / `additional-redacted-fields`; задание `redacted-headers` их заменяет.

Само маскирование теперь — `Redactor` из `audit-core`, общий для всей платформы: структурный обход JSON,
замена form-encoded тела целиком и маркер усечения переехали туда без изменений, вместе с обоснованием и
тестами, которые их доказывали. Здесь остался `ClientRedactor` — привязка к клиенту, то есть *какие* имена
маскирует этот клиент; это конфигурация конкретного партнёра, и её место рядом с клиентом.

Список клиента может только **расширить** то, что маскируется, но не сузить: он композируется с
правилами `ludwig.audit.redaction`, действующими для всего развёртывания, а не заменяет их — поэтому поле
тела с именем `client_secret` маскируется независимо от того, назвал ли его список этого клиента. Сужение —
это операция, которая протекает, и модуль не должен иметь возможности отменить правило платформы.

### Рецепт: слушатель

```java
/** Запоминает остаток квоты партнёра, чтобы дашборд показал его до того, как нас начнут душить. */
@Component
public class QuotaListener implements RestClientListener {

    private final AtomicInteger remaining = new AtomicInteger(-1);

    @Override public boolean supports(String clientName) { return "partner".equals(clientName); }

    @Override public void onResponse(OutboundRequest request, OutboundResponse response) {
        List<String> header = response.headers().get("X-RateLimit-Remaining");
        if (header != null && !header.isEmpty()) {
            remaining.set(Integer.parseInt(header.get(0)));
        }
    }

    @Override public void onRetry(OutboundRequest request, int nextAttempt, long waitMillis, String cause) {
        log.info("повторяем {} {} (попытка {}, ждём {} мс): {}",
                request.method(), request.uriTemplate(), nextAttempt, waitMillis, cause);
    }

    @Override public int getOrder() { return 0; }
}
```

Слушатель, бросивший исключение, **никогда не ломает вызов**: исключение логируется один раз на класс
слушателя и считается в `ludwig.restclient.listener.failures`. Позволить интеграции с дашбордом
завалить платёж — не та сделка, которую эта платформа заключает; следствие в том, что слушатель не
может ничего обеспечивать. Колбэки выполняются на вызывающем потоке (`sync`) или на потоке Reactor
(`async`), поэтому блокирующий слушатель замедляет каждый вызов — отдавайте работу исполнителю.

### Аудит

Включается по клиенту. Отличается от логирования и не является его громкой версией: аудиторская
запись хранится, её читают люди не из дежурной смены, и в ней никогда не должно быть ни секрета, ни
полезной нагрузки.

Аудируются ли вообще вызовы партнёра, с какой частотой выборки и какие его заголовки разрешены —
остаётся здесь, по именованному клиенту, потому что это факты об отношениях с этим партнёром. В
`ludwig.audit` переехали назначение, политика отказов и retention.

```yaml
ludwig:
  rest-client:
    clients:
      billing:
        audit:
          enabled: true
          sampling-probability: 0.1
          include-response-headers: [X-Request-Id]
          sink: mySiemAuditSink        # необязательно; имя бина, по клиенту
```

Запись несёт: клиент, метод, **шаблон** URI, статус, исход, длительность, число попыток, correlation
id, trace id, субъект, отметку времени, разрешённые заголовки и тип отказа. Ни развёрнутого URI, ни
тел, и только те заголовки, которые названы явно, — список разрешённых, потому что список запрещённых
хорош ровно настолько, насколько его последний раз дополняли.

Выборка применяется **только к успешным вызовам**. Отказы, отклонённые вызовы и ошибки аутентификации
пишутся всегда: редкие события — это то, ради чего аудит существует.

Записи идут в единственный в платформе `AuditSink` с `category=outbound-call` — в лог, в таблицу
`audit_event` (только на добавление), в SIEM через транзакционный outbox или в несколько мест сразу.
`NOT_PERMITTED` записывается с исходом `DENIED`, а не как сбой: вызов отклонён собственной политикой
сервиса и ничего не сломалось, а это различие реагирующему на инцидент нужно первым.

**`AuditEventEmitter` и `LoggingAuditEventEmitter` удалены, а `audit.emitter` стал `audit.sink`.** Это
были два из девяти механизмов аудита, накопившихся в платформе; см. [`audit-core`](../audit-core).
Свойство переименовано, а не сделано алиасом, намеренно: алиас позволил бы свойству, называющему бин
типа, которого больше нет на classpath, выглядеть учтённым. `audit.sink` остаётся **по клиенту**, потому
что сервису вполне законно бывает нужно отправлять журнал одного партнёра в API вендора, а остальное — в
приёмник платформы.

`OutboundCallAudit` остаётся поверхностью авторства и получил `toAuditEvent()`; всё, что он говорил о
том, что может содержать запись исходящего вызова, по-прежнему верно и лежит там же.

«Приёмник аудита не должен уметь завалить платёж» по-прежнему верно для этой категории и по-прежнему
обеспечивается — `FailurePolicyAuditSink`, который разрешает `ludwig.audit.failure.by-category` и для
`outbound-call` логирует и продолжает. Ушёл `catch` в `AuditRecorder`: держать его ещё и здесь означало бы
подменять то, что настроило развёртывание, решением, зашитым в библиотеке, — а именно это и делали девять
отдельных механизмов. Счётчик, делавший молча теряющий приёмник заметным, теперь общий для платформы и с
тегом категории — `ludwig.audit.sink.failures{category="outbound-call"}` — вместо
`RestClientMeters.auditFailure`, который остаётся как публичный API, но здесь больше не инкрементируется.

**Что заметит развёртывание:** логгера `ludwig.restclient.audit` больше нет; записи — в
`ru.ludwigandreas.audit` с `category=outbound-call`.

## Ошибки

| Исключение | Смысл | Кто чинит |
|---|---|---|
| `RestClientResponseException` | Партнёр ответил статусом отказа | Зависит от статуса |
| `RestClientTimeoutException` | Дедлайн истёк. Запрос **мог** быть обработан | Мы или они |
| `RestClientConnectionException` | Запрос до них не дошёл | Сеть |
| `RestClientAuthenticationException` | Мы не смогли получить или использовать секрет | Мы |
| `RestClientCallNotPermittedException` | Наша собственная политика отказалась делать вызов | Мы — сбрасываем нагрузку |

Каждое несёт имя клиента и correlation id — в сообщении, а не только в полях, потому что сообщение
это то, что пишет аппендер и цитирует алерт.

`RestClientResponseException` несёт статус, маскированные заголовки, усечённый фрагмент тела и — для
`application/problem+json` — разобранный `ProblemDetail` с сохранёнными расширениями.

Партнёр, чей конверт ошибки не по RFC 9457, обрабатывается публикацией переводчика:

```java
@Component
public class PartnerErrorTranslator implements ResponseErrorTranslator {

    @Override public boolean supports(String clientName) { return "partner".equals(clientName); }

    @Override public RuntimeException translate(ErrorContext context) {
        if (context.statusCode() != 409 || context.body() == null) {
            return null;                                   // не моё — передаём следующему
        }
        return new DuplicateOrderException(readOrderId(context.body()));
    }
}
```

Переводчики вызываются в порядке `@Order`, побеждает первый непустой ответ; встроенный идёт последним,
поэтому переводчик сервиса всегда получает право первого отказа.

При наличии `web-core-spring-boot-starter` исключение, вышедшее за пределы контроллера, рендерится
как штатный problem-документ платформы: 5xx, таймаут, отказ соединения или отклонённый вызов
становятся `upstream-unavailable` (503); 429 остаётся 429; а **4xx становится 500**, потому что 422 от
billing означает, что этот сервис отправил billing что-то неверное, и проброс обвинил бы вызывающего
в дефекте, которого он не совершал.

Обработка ошибок применяется к `retrieve()` и намеренно не применяется к `exchange()`: тот, кто
запросил сырой обмен, хочет сырой ответ, включая 404, который он собирается трактовать как пустой
результат.

## Запасные ответы

```yaml
ludwig:
  rest-client:
    clients:
      billing:
        resilience:
          fallback:
            handler: cachedInvoiceFallback         # на все методы
            methods:
              BillingApi#invoice: cachedInvoiceFallback
```

Запасной ответ срабатывает только на отказ, означающий, что *вызов не удалось сделать или завершить*.
Он **не** срабатывает на 4xx — партнёр ответил, и подмена 403 закэшированными данными это способ
выпустить дефект авторизации — и на отказ аутентификации, который заставил бы сломанное развёртывание
выглядеть здоровым ровно столько, сколько живут устаревшие данные. Запасные ответы применяются к
декларативным интерфейсам; разовый вызов через `RestClient` получает исключение.

## Транспорты

| `transport` | Пул | HTTP/2 | Примечания |
|---|---|---|---|
| `http-client` (по умолчанию) | Не настраивается | Да | Собственный JDK. Ручек пула не существует; блок `pool` помечается как проигнорированный, а не выглядит работающим |
| `apache` | Полностью настраивается | Нет | Выбирайте, когда важен пул. Классический клиент только HTTP/1.1 |
| `reactor-netty` | Настраивается | Да | Подразумевается `mode: async`; недоступен для `sync` |

Пулы никогда не разделяются между именованными клиентами — два клиента, смотрящие на один хост, всё
равно получают два пула, потому что смысл разделения в том, чтобы насыщенная зависимость не съедала
разрешения, нужные другой.

`compression: true` значит одно и то же на всех трёх: Apache и Reactor Netty декодируют прозрачно, а
для JDK стартер сам объявляет и декодирует gzip/deflate.

### TLS

По клиенту: truststore, keystore (mTLS), протоколы (по умолчанию TLSv1.3 и TLSv1.2), наборы шифров,
проверка имени хоста. Общесистемный `javax.net.ssl.trustStore` не выражает двух клиентов, доверяющих
разным внутренним УЦ, а это обычный случай при более чем одном партнёре.

`tls.trust-all: true` и `tls.hostname-verification: false` требуют **двух** переключателей и проверки
профиля:

```yaml
ludwig:
  rest-client:
    allow-trust-all: true                  # верхний уровень, отдельно от клиента
    production-profiles: [prod, production]
    clients:
      sandbox:
        tls: { trust-all: true }
```

и контекст всё равно откажется стартовать, если активен любой из `production-profiles`. Один
переключатель — это переключатель, который кто-то щёлкает во время инцидента и не возвращает обратно;
второй, названный иначе и находящийся на верхнем уровне, означает, что YAML с ноутбука разработчика
нельзя просто скопировать в развёртывание.

### Перезапуск против перечитывания

Ключи с пометкой **нет** действительно перечитываются. Раз в секунду на клиента конвейер
перечитывает привязанные `@ConfigurationProperties` и пересобирает то, что является чистой функцией
от них — решение о повторе, логгер обмена, списки маскирования, регистратор аудита, — и
переконфигурирует живой ограничитель частоты через собственные `changeLimitForPeriod` /
`changeTimeoutDuration` из Resilience4j. Поэтому вместе с `hot-reload-spring-boot-starter`,
обновлением через actuator или продлением аренды Vault поднять уровень логирования или снизить число
повторов во время инцидента — это изменение конфигурации, а не выкат.

Вызов, уже находящийся в полёте, сохраняет политику, с которой начал: логический вызов не должен
менять правила на полпути к решению, повторяться ли ему. А конфигурация, ставшая невалидной, —
класс из `retry-on-exception`, которого больше нет, — оставляет в силе предыдущую и пишет
предупреждение, а не роняет клиента.

Два ключа внутри в остальном перечитываемых блоков всё же требуют перезапуска:
`rate-limiter.limit-refresh-period`, потому что его смена означает выбрасывание текущего цикла, и
`retry-on-exception`, потому что список классов разрешается один раз.

Всё остальное требует перезапуска, и причина всегда одна: значение запечено в объект, созданный один
раз, — пул соединений, `SSLContext`, базовый URL, аутентификатор, окно размыкателя. Смена этих
значений под работающим клиентом оставила бы половину вызовов на старом объекте.

## Проверка на старте

Bean Validation проверяет по одному полю, что ловит отрицательный размер пула и пропускает все
интересные ошибки. Ниже — отношения, и каждое даёт поведение, которое проявляется редко и почти не
атрибутируется спустя недели, поэтому под падает:

- клиент без `base-url` или `base-url` в `defaults`
- секреты по plain HTTP на не-loopback хост
- бюджет повторов, в который не влезают две попытки, из-за чего `max-attempts` — ложь
- `request-timeout` не больше `connect-timeout`
- ограничитель времени у `sync`-клиента; пул-переборка или ожидание переборки у `async`
- `trust-all` без второго переключателя или при активном production-профиле
- keystore без пароля
- неизвестный `auth.type`; `bearer` с токеном и поставщиком одновременно
- проброс токена без `relay-enabled` или в сервисе, не являющемся ресурсным сервером
- размыкатель, у которого `minimum-number-of-calls` больше окна, — он никогда не откроется
- ожидание ограничителя частоты длиннее read-timeout
- движок, класс исключения или модуль Jackson, которых нет в classpath

Предупреждения — логируются, но не фатальны — покрывают блок пула на транспорте JDK, `http2` на
Apache, API-ключ в query-параметре, 4xx в списке отказов размыкателя и повторы неидемпотентных методов
по умолчанию.

Все проблемы сообщаются вместе. Развёртывание с тремя ошибками должно занять один выкат, а не три.

## Чего он намеренно не делает

- **Нет service discovery и балансировки.** `base-url` — это URL. В этом контуре это имя сервиса
  Kubernetes или шлюз, и оба уже балансируют; второй балансировщик внутри клиента сделал бы
  распределение трафика функцией двух систем.
- **Нет кэширования ответов.** Кэширование — доменное решение об устаревании, а не транспортное.
- **Нет подписи запросов сверх поставляемых схем.** Для этого есть SPI аутентификатора.
- **Нет повтора при потоковом теле запроса.** Тело `sync`-запроса буферизуется, чтобы повтор мог его
  отправить снова; клиент, загружающий большие файлы, должен отключить повторы или работать с
  транспортом напрямую.
- **Нет кластерного ограничения частоты.** Ограничитель работает на процесс. Настраивать надо квоту
  партнёра, делённую на число реплик, и пересматривать при масштабировании.
- **Нет аннотаций в духе `@Retryable`.** Устойчивость — свойство зависимости, а не метода, и место
  вызова не должно иметь возможности не согласиться с развёртыванием в том, как достигается
  зависимость.

```

├── core            реестр, runtime и оба конвейера выполнения

├── transport       JDK / Apache / Reactor Netty, TLS, прокси, датчики пула

```

То, что `spi` не зависит ни от чего внутри модуля, проверяется правилом ArchUnit: SPI, залезающий в
реализацию, невозможно реализовать снаружи, не притащив реализацию с собой, — а человек, который
добавит такой импорт, будет добавлять совершенно разумный вспомогательный метод.
