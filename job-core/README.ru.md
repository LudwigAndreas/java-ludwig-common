# job-core

[English](README.md) | [Русский]

Механика, из которой собран каждый планируемый воркер этой платформы, работающий поверх базы данных -
в одном месте, чтобы каждой её части было **по одной**, а не по одной на модуль.

Собственных задач у модуля нет. Он существует потому, что
[`outbox-spring-boot-starter`](../outbox-spring-boot-starter) и
[`reconciliation-spring-boot-starter`](../reconciliation-spring-boot-starter) - это одна и та же
машина, направленная в противоположные стороны: одна захватывает локальные строки и выталкивает
состояние наружу, другая захватывает локальные строки и затягивает состояние внутрь, - а всё между
"проснуться" и "записать исход" у них одинаковое. Две разошедшиеся копии кривой backoff - это ровно
та ошибка, которую модуль предотвращает: она проявляется спустя месяцы как "другой сервис
восстанавливается после недоступности партнёра иначе, чем этот", и указать при этом не на что.

## Что внутри

| Часть | Что это |
|---|---|
| `BackoffPolicy` / `BackoffCalculator` | Экспоненциальный backoff с множителем, потолком и джиттером, вычисляемый для сохраняемого `next_attempt_at`, а не проспанный внутри вызова |
| `ScheduleSpec` / `SelfSchedulingLifecycle` / `ScheduledJob` | База `SmartLifecycle`, которая планирует себя на внедрённом `TaskScheduler`, отказывается выполняться дважды одновременно, гасит исключения и доживает текущий проход до конца при остановке |
| `SkipLockedClaim` | Запрос `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *`, построение и выполнение |
| `ClaimOwner` / `JobInstanceIdentity` | Строка, которую процесс пишет в колонки `locked_by` / `owner` |
| `RunLock` / `JdbcRunLock` | Арендуемое кластерное взаимное исключение для именованной единицы планируемой работы |

## Backoff

```java
BackoffCalculator backoff = new BackoffCalculator(
        new BackoffPolicy(Duration.ofSeconds(2), 2.0, Duration.ofMinutes(10), 0.3));

message.setNextAttemptAt(Instant.now().plus(backoff.nextDelay(message.getAttempts())));
```

`attempt` - это счётчик попыток с единицы **после** только что произошедшего сбоя: первый сбой
передаёт `1` и получает `initialInterval`.

resilience4j-core используется только как функция интервала, никогда как `@Retry` или
`Retry.decorateSupplier`. Те повторяют *внутри вызова*, удерживая поток и соединение с базой, пока
спят; здесь же следующее время готовности записывается в строку, и её подхватывает следующий тик -
именно это переживает перепланирование пода посреди backoff.

**Джиттер - не украшение.** Без него все записи, упавшие из-за минутной недоступности партнёра,
становятся готовыми ровно в один момент и сразу на всех инстансах, и только что вернувшийся партнёр
опрокидывается всем накопленным трафиком и падает снова. Значение `0` делает кривую
детерминированной - это нужно тестам на форму кривой и тестам, проверяющим точные времена готовности;
в продакшене разумный диапазон - около `0.2`-`0.3`.

## Планирование

```java
public class BillingStatusPoller extends SelfSchedulingLifecycle {

    public BillingStatusPoller(TaskScheduler scheduler) {
        super("billing-status", scheduler,
                ScheduleSpec.fixedDelay(Duration.ofSeconds(30), Duration.ofSeconds(10)),
                Duration.ofSeconds(20));
    }

    @Override
    protected void runOnce() {
        // один проход; исключения пусть всплывают - база залогирует, какая задача упала
    }
}
```

Либо, когда тело уже живёт в сервисном бине, `new ScheduledJob(name, scheduler, spec, drainTimeout,
service::pollOnce)`.

Четыре свойства базового класса несущие:

- **Не `@Scheduled`.** Эта аннотация принимает интервал как атрибут, то есть либо строку-плейсхолдер,
  заново разбираемую из конфигурации, уже связанной в `Duration`, либо SpEL - и в любом случае требует,
  чтобы *приложение-потребитель* включило `@EnableScheduling`. Стартер, который молча ничего не делает,
  если сервис об этом забыл, не является plug-and-play, а симптом - растущий backlog без единой ошибки.
- **Фиксированная задержка, никогда не фиксированная частота.** Фиксированная частота продолжает
  запускать проходы, пока предыдущий ещё идёт, так что задача, начавшая выполняться дольше своего
  интервала, накапливает перекрывающиеся проходы до исчерпания пула - ровно тогда, когда система уже
  под нагрузкой. Фиксированная задержка деградирует более редкими запусками, что видно и безвредно.
- **Нереентерабельность.** Cron-расписание не защищает от перекрытия, как и "запустить сейчас" из
  actuator, пришедшее посреди прохода. Повторный вход - это залогированный no-op, а не второй
  параллельный проход логики захвата, которая рассчитана на одного исполнителя в инстансе.
- **Доживание при остановке.** `stop()` отменяет расписание *без прерывания* и затем ждёт до
  `drainTimeout`. Прерывание бросило бы строки посреди захвата: они остались бы помеченными как
  обрабатываемые, принадлежащими несуществующему процессу, и вернулись бы в работу только когда
  сборщик зависших заметит их спустя минуты. Держите `drainTimeout` заметно меньше grace period
  остановки контейнера, иначе под будет убит посреди доживания и смысл теряется.

`runNow()` использует тот же охранник нереентерабельности и возвращает, действительно ли проход
выполнился, - именно это должна вызывать и показывать операция actuator "запустить проход".

## Захват строк

```java
List<OutboxMessage> claimed = SkipLockedClaim.claim(entityManager, OutboxMessage.class,
        "outbox_message",
        "status = 'PROCESSING', locked_at = now(), locked_by = :lockOwner",
        "t.status IN ('PENDING', 'FAILED') AND t.next_attempt_at <= :now",
        "t.created_at, t.id",
        batchSize,
        Map.of("lockOwner", lockOwner, "now", Instant.now()));
```

строит и выполняет

```sql
UPDATE outbox_message
   SET status = 'PROCESSING', locked_at = now(), locked_by = :lockOwner
 WHERE id IN (SELECT t.id FROM outbox_message t
               WHERE t.status IN ('PENDING', 'FAILED') AND t.next_attempt_at <= :now
               ORDER BY t.created_at, t.id
               LIMIT :jobClaimLimit
               FOR UPDATE SKIP LOCKED)
RETURNING *
```

Три вещи в этом запросе не стилистические:

- **Блокирующая конструкция стоит на подзапросе, а не на `UPDATE`.** PostgreSQL не позволяет
  прикрепить её к `UPDATE`, а блокировки строк, которые берёт `UPDATE`, *блокирующие*. Подзапрос -
  это то, что заставляет второй поллер перешагивать через строки, которые захватывает первый, вместо
  того чтобы встать за ними в очередь: разница между "N инстансов делят работу" и "N инстансов
  работают по очереди".
- **`RETURNING *`, а не второй `SELECT`.** Один round trip и никакого окна, в котором строка уже
  захвачена, но ещё не прочитана. Поэтому же запрос выполняется как возвращающий результат:
  `executeUpdate()` отбросил бы возвращённые строки.
- **Тотальный `ORDER BY`.** Без него PostgreSQL вправе вернуть готовые строки в любом порядке, и
  backlog может бесконечно морить голодом собственную голову. Симптом - "в основном всё хорошо, но
  несколько записей устарели на дни" - очень трудно связать с отсутствующей сортировкой.

Вызывающая сторона передаёт написанные ею самой фрагменты и связывает каждое значение как параметр;
имя таблицы и фрагменты приходят из кода модуля, никогда из конфигурации или запроса. Перегрузок две,
потому что JPA связывает `:name`, а обычный JDBC - `?`, и попытка одного переписывать плейсхолдеры
другого - это то, как однажды калечится строковый литерал.

## Run lock

```java
Optional<RunLockHandle> held = runLock.tryAcquire("billing-status", Duration.ofMinutes(5));
if (held.isEmpty()) {
    return;                       // этот проход у другого инстанса; вернёмся на следующем тике
}
try (RunLockHandle lease = held.get()) {
    // ... периодически: if (!lease.renew(Duration.ofMinutes(5))) { немедленно остановиться; }
}
```

Это **аренда**, а не блокировка. Блокировка, удерживаемая умершим процессом, удерживается вечно, а
"задача тихо перестала запускаться после того, как под убили" - не то, на что что-либо алертит:
расписание продолжает срабатывать, каждый тик отказывается работать, и backlog растёт за метрикой, на
которую никто не смотрит. Поэтому каждое взятие истекает, а держатель, который хочет сохранить
аренду, обязан продолжать об этом заявлять.

Два следствия, под которые обязан проектироваться вызывающий код:

1. **Владение арендой никогда не является доказательством того, что вы ею всё ещё владеете.** `renew`
   возвращает, ваша ли она ещё. Держатель, у которого продление не удалось, был вытеснен и обязан
   остановиться *немедленно*, а не доделать пачку: другой инстанс уже переделывает этот проход.
2. **`tryAcquire` никогда не блокирует.** Планируемой задаче, не получившей аренду, нечего ждать, а
   блокировка заняла бы поток планировщика на всё время прохода другого инстанса.

Продление обусловлено совпадением не только `owner`, но и `run_id`. Аренда, которая истекла, была
взята другим инстансом и вернулась к этому, считается **потерянной**, а не всё ещё удерживаемой:
строка владельца совпала бы, но работа, которую этот процесс наполовину сделал, уже не относится к
авторитетному проходу.

Каждая операция с арендой выполняется на собственном коротком JDBC-соединении с autocommit, а не через
`EntityManager` вызывающей стороны. Включение её в транзакцию вызывающего сделало бы аренду невидимой
для остальных до коммита этой транзакции и откатило бы её вместе с упавшим проходом - то есть упавший
проход молча отдал бы аренду, которую должен был удерживать достаточно долго, чтобы записать причину
падения.

## Схема (только PostgreSQL)

Одна таблица, `job_run_lock`, поставляется как `db/changelog/job-core/job-core-changelog.xml` и
применяется `JobCoreLiquibaseAutoConfiguration` как независимый бин `SpringLiquibase` рядом с
собственным changelog приложения. Поставьте `ludwig.job-core.liquibase.enabled=false`, чтобы вместо
этого включить его в свой master changelog.

`expires_at` - единственный источник истины для "удерживается ли аренда": держатель, переставший
продлевать, перестаёт быть держателем без какого-либо участия с его стороны.

## Конфигурация (`ludwig.job-core.*`)

| Свойство | По умолчанию | Значение |
|---|---|---|
| `ludwig.job-core.enabled` | `true` | Главный выключатель автоконфигурации модуля |
| `ludwig.job-core.owner` | имя хоста + случайный суффикс | Идентичность, записываемая в колонки владельца блокировки |
| `ludwig.job-core.liquibase.enabled` | `true` | Применяет ли модуль собственный changelog |

Намеренно крошечная. Всё, что меняется от задачи к задаче - расписания, размеры пачек, бюджеты
повторов, - настраивается модулем, которому задача принадлежит, под его собственным префиксом.
`BackoffPolicy` и `ScheduleSpec` являются value-типами, а не классами `@ConfigurationProperties`,
именно поэтому: связывание их здесь загнало бы всех потребителей в один префикс свойств.

Идентичность инстанса **не** стабильна между перезапусками, и относиться к ней как к стабильной
нельзя. Перезапущенный под - это новый владелец; подхват работы, оставленной предыдущим, - это явный
шаг возврата, а не побочный эффект совпадения имён.

## Подключение

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>job-core</artifactId>
</dependency>
```

Версии приходят из `ludwig-bom`; здесь не указывайте ни одной. Из рантайм-зависимостей только Spring
Context, Spring Boot autoconfigure, Jakarta Persistence API (compile-scope, ради JPA-варианта
помощника захвата - собственных сущностей модуль не отображает и сканирования сущностей не навязывает),
resilience4j-core и SLF4J. Liquibase опционален.

## Тестирование

`mvn test` запускает модульный набор: кривую роста backoff и окно её джиттера, валидацию
`ScheduleSpec`, а также нереентерабельность, гашение исключений и доживание при остановке у базового
жизненного цикла. `JdbcRunLock` проверяется на настоящем PostgreSQL интеграционными тестами его
потребителей - там, где конкурирующие инстансы и есть то, что аренда обязана пережить.
