# idempotency-spring-boot-starter

**Единственное в платформе хранилище дедупликации работы**: захват переданного вызывающей стороной ключа в
пределах области (scope), чтобы одно и то же действие нельзя было выполнить дважды. Вынесено из
`notification-service`, где примитив был написан и где его собственный README называл его кандидатом на
вынесение №1 — *«одна из двух возможностей, которых у платформы пока нет… без неё этот сервис начинает
отправлять дважды в тот момент, когда запускается более чем в одной реплике»*.

Вся корректность заключена в одном выражении, и всё остальное в модуле построено на нём:

```sql
INSERT INTO idempotency_claim AS t (…)
VALUES (…)
ON CONFLICT (scope, idempotency_key) DO UPDATE SET
    request_id = CASE WHEN <reclaimable> THEN EXCLUDED.request_id ELSE t.request_id END,
    …                                     -- по одному присваиванию такой формы на каждый столбец
RETURNING request_id, state, fingerprint, lease_expires_at, expires_at, response_*
```

## Для чего это и шесть вещей, которыми это не является

Модуль отвечает ровно на один вопрос: **«я уже выполнил эту работу?»** — о ключе, который нам передали.
`IdempotencyStore` сознательно узок, и граница — самое важное в этом README, потому что «идемпотентность» в
этом репозитории называет семь разных механизмов, и только два из них относятся сюда.

| № | механизм | где живёт | здесь? |
|---|---|---|---|
| 1 | **захват ключа вызывающей стороны в области** | **этот модуль** | **да — это и есть примитив** |
| 2 | **передача ключа вниз по вызову, чтобы дедуплицировала дальняя сторона** | `IdempotencyHeaders`, `crud-service-example` | **да — как документированный помощник** |
| 3 | дедупликация при публикации — `OutboxMessageRepository.findByIdempotencyKey` | `outbox-spring-boot-starter` | нет |
| 4 | ключ как столбец бизнес-агрегата — `ExportReportRun.findByIdempotencyKey` | `export-spring-boot-starter` | нет |
| 5 | дедупликация по естественному ключу — ограничение уникальности `(bucket, key, etag)` | `file-ingest-spring-boot-starter` | нет |
| 6 | классификация повторов по RFC 9110 — `IdempotentMethods`, `HttpMethod.isIdempotent()` | `rest-client`, `jira-client` | нет |
| 7 | «побеждает последняя запись» по версии | `identity-projection`, `user-settings` | нет |

Механизмы 3–7 **не изменены**; см. [Что модуль сознательно не поглощает](#что-модуль-сознательно-не-поглощает)
— почему каждый из них является правильным локальным ответом и был бы испорчен универсальным хранилищем.

## Выражение и почему любая альтернатива неверна

Выражение находится в `ru.ludwigandreas.idempotency.sql` — единственном документированном исключении модуля
из правила «только QueryDSL», огороженном тестом `SqlConfinementTest`. Ни `ON CONFLICT`, ни `RETURNING` не
существуют в JPQL, а QueryDSL-JPA генерирует JPQL.

Вся ценность в том, что это **одно** выражение:

- **Прочитать-затем-вставить** — очевидная реализация, и именно она неверна для того случая, ради которого всё
  это существует. Две реплики, обрабатывающие одну и ту же запись at-least-once, обе читают «строки нет», обе
  вставляют, и одна получает нарушение ограничения, обрывающее транзакцию, которая к этому моменту уже
  записала настоящую работу. Кроме того, это отказывает *молча*: при низкой нагрузке выглядит идеально.
- **`DO NOTHING`** не возвращает строку при конфликте, поэтому проигравшему пришлось бы делать повторный
  SELECT — а в `READ COMMITTED` повторный SELECT всё ещё может не увидеть строку, вставляющая транзакция
  которой не закоммичена. `DO UPDATE` заставляет проигравшего **заблокироваться на блокировке строки
  победителя** и затем прочитать закоммиченного победителя. Ни исключения, ни отката, ни двойного выполнения.
- **Уникальный индекс и есть обеспечение**, а не проверяющий код. Ничто в Java не даёт того, что даёт
  `uk_idempotency_claim_key`.

Одно уточнение по сравнению с перенесённым выражением: ветка конфликта также **перезахватывает** свободный
захват — окно которого прошло, аренда держателя истекла или он был помечен `FAILED`. Истечение решается внутри
выражения, а не оставляется очистке, потому что очистка асинхронна и выполняется на одной реплике по
расписанию: иначе TTL означал бы «TTL плюс сколько-то до следующего запуска очистки». У каждого столбца
присваивание при конфликте имеет одну и ту же форму — именно это делает утверждение «живой захват остаётся
нетронутым» верным для всей строки, а не для тех столбцов, о которых кто-то не забыл.

## Два режима захвата

Один режим не может обслужить оба типа вызывающих, и **выбор обязателен в каждой точке вызова** — значения по
умолчанию нет, потому что неверный выбор — это ошибка корректности, проявляющаяся только при конкурентности.

| | `TRANSACTIONAL` | `STANDALONE` |
|---|---|---|
| транзакция | транзакция вызывающего (эквивалент `MANDATORY`) | своя собственная (эквивалент `REQUIRES_NEW`) |
| жизненный цикл | коммитится вместе с работой; откат освобождает ключ | `IN_PROGRESS → COMPLETED \| FAILED`, коммитится независимо, с арендой |
| что говорят дубликату | «сделано, вот идентификатор владеющего запроса» | «сделано, вот ответ» или «в процессе, вернитесь позже» |
| мёртвый держатель | невозможен — захват не был закоммичен | его аренда истекает, и ключ снова можно захватить |
| для | консьюмера, у которого вся единица работы — одна транзакция | HTTP-фильтра и любой работы, выходящей за одну транзакцию или делающей внешние вызовы |

`TRANSACTIONAL` отказывает, а не деградирует, когда транзакция не открыта. Деградация до независимого коммита
— именно тот отказ, ради предотвращения которого режим существует, и он всплыл бы только как ключ, который
нельзя повторить, после какого-то несвязанного откота, спустя дни.

`STANDALONE` нуждается в аренде по той же причине, что и `RunLock`: процесс, умерший посреди запроса, оставил
бы `IN_PROGRESS` навсегда, а **ключ, застрявший в процессе, — это вызывающий, который никогда не сможет
повторить**, что хуже предотвращаемого двойного выполнения, потому что это навсегда. Захват `FAILED` можно
перезахватить сразу: неудачная попытка не должна блокировать повтор, ради которого она и существует.

Два режима — это две транзакционные границы, выраженные через `TransactionTemplate`, а не через
`@Transactional`, потому что режим — значение времени исполнения, а `@Transactional` применяется прокси
вокруг вызовов, приходящих *извне* бина. Метод `claim`, делегирующий аннотированному
`claimTransactionally` на `this`, обошёл бы прокси молча и только при конкурентности. Два выхода из этой
ловушки — второй бин, единственная цель которого быть «кем-то другим» (чем и был `LockLeaseService` в
`notification-service` и что удалил `job-core`), либо объявление границы там, где принимается решение.

## HTTP-поверхность

Выключена по умолчанию (`ludwig.idempotency.http.enabled`). Фильтр, который начал бы дедуплицировать каждый
подходящий эндпоинт в момент появления модуля в classpath, изменил бы поведение работающих API как побочный
эффект обновления зависимости.

Эндпоинт включается аннотацией `@Idempotent` на обработчике либо сопоставлением пути и метода в конфигурации —
для эндпоинтов, которыми сервис не владеет. Четыре пути:

| ключ | ответ |
|---|---|
| **новый** | обработчик выполняется, его ответ сохраняется в захвате |
| **завершённый** | сохранённый ответ **воспроизводится**, ничего не выполняется |
| **в процессе** | `409` с `Retry-After` — не ответ, которого ещё не существует, и не второе выполнение |
| **несовпадение отпечатка** | `422` с указанием ключа и **никогда** ответ первого запроса |

Захват **FAILED** — не пятый путь: выражение перезахватывает его, поэтому повтор неудавшегося запроса приходит
как новый ключ.

**Воспроизведение ответа — то, чего не может флаг «дубликат»**, и именно оно делает возможность реальной для
API. Вызывающему, который повторил `POST` после таймаута, нужен исходный `201` и его тело — что было создано,
где оно, каков его идентификатор, — а не булево «вы это уже сделали».

Две вещи, которые фильтр отказывается сохранять, потому что воспроизвести их было бы хуже, чем не
воспроизводить:

- **обрезанное** тело (больше `max-stored-response`) — это правдоподобно выглядящий ответ без конца;
- **4xx или 5xx**, который к тому же трактуется как *работа не выполнена*: захват помечается `FAILED`, ключ
  освобождается. Сохранённый 5xx сделал бы временный сбой постоянным для этого ключа, а сохранённый 4xx
  отклонил бы повтор **исправленного** клиентом запроса как несовпадение отпечатка вместо того, чтобы дать ему
  успешно пройти.

2xx, ответ которого оказался слишком большим, завершает захват — работа выполнена и не должна повторяться, — а
последующий дубликат получает `409 ludwig.idempotency.error.not-replayable` без `Retry-After`. Это отдельный
код, а не тот же 409, специально: двум случаям нужно противоположное от вызывающего, и `Retry-After` здесь
породил бы вежливый бесконечный цикл.

409 и 422 — это документы RFC 9457, отрендеренные через **собственную** `ProblemDetailFactory` и бандлы
`web-core`. Модуль не поставляет ни одного `@RestControllerAdvice`; фильтр находится вне обработки исключений
Spring на уровне обработчика, поэтому он выполняет те же два шага, что и общий advice, над теми же бинами,
получая ту же форму документа — на языке вызывающего и в UTF-8.

## Отпечаток запроса

**Требование корректности, а не приятное дополнение.** Без него клиент, переиспользующий ключи, молча получает
ответ чужого ресурса: сбой целостности данных, который выглядит как «API вернул чужие данные» — с чистым
access-логом, кодом 200 и без единой ошибки где-либо.

- **Хэш**, а не тело. Дешевле, и это избавляет от таблицы, накапливающей полезные нагрузки запросов, — к
  которой пришлось бы применять правила редактирования из `audit-core` и проверку прав у каждого читателя.
- JSON-тело **канонизируется** (ключи объектов сортируются, пробелы отбрасываются, параметры
  `charset`/`boundary` игнорируются) перед хэшированием. Хэширование сырых байтов объявило бы повтор,
  пересериализовавший тело, несовпадением и отклонило бы его с 422 — превратив страховочную сетку в аварию.
- **Порядок массива сохраняется.** JSON-массив упорядочен по спецификации, и модуль не вправе решать иначе за
  чужую полезную нагрузку. Ошибка здесь означала бы принять действительно другой запрос за дубликат, а это
  единственный отказ хуже отклонённого повтора.
- Захват **без** сохранённого отпечатка никогда не даёт несовпадения, поэтому релиз, выпущенный до включения
  отпечатков, не начинает отклонять те самые повторы, ради которых он был сделан.

## Дедупликация на стороне консьюмера

`IdempotentRecordFilterStrategy` захватывает `topic:partition:offset` — или настроенный заголовок — до
выполнения тела слушателя, в режиме `TRANSACTIONAL`.

Именно `RecordFilterStrategy`, а не аспект, и вторая причина — несущая: аспект притащил бы
`spring-boot-starter-aop` в каждого консьюмера, а стратегия фильтрации выполняется **внутри вызова контейнера
слушателя**, то есть внутри транзакции контейнера, когда та настроена. Захват, закоммиченный вне транзакции
слушателя, оставил бы ключ занятым для работы, которая затем откатилась, и повторную доставку, которую Kafka
непременно выполнит — смещение тоже не было закоммичено, — отбросили бы как дубликат. **Сообщение никогда не
было бы доставлено, и ничто об этом не сказало бы.**

```java
factory.setRecordFilterStrategy(idempotentRecordFilterStrategy);
factory.getContainerProperties().setTransactionManager(transactionManager);
```

Стратегия сознательно не подключается ко всем слушателям. Некоторые слушатели дедуплицировать **нельзя**:
проекция, сходящаяся по значению — сравнение отметок времени в identity-projection, воспроизведение в
user-settings, — уже корректна при повторе, и захват перед ней добавил бы таблицу, запись и точку отказа ради
гарантии, которая уже была.

Ключ по умолчанию — координаты записи, идентифицирующие **доставку**, а не сообщение, что и есть правильное
значение по умолчанию для at-least-once. `key-header` нужен, когда продюсер переопубликовывает одно логическое
событие на новое смещение; только продюсер знает, что две записи — одно событие. Никогда не message key
записи: он идентифицирует целый набор связанных записей партиции и свёл бы все события об одной сущности к
первому.

## Очистка по retention и почему TTL — параметр корректности

Исходный javadoc `IdempotencyStore.purgeExpired` уже говорил главное: *«должно выполняться ровно на одной
реплике — это одна из задач, ради которых существует распределённая блокировка»*. Тогда блокировка тоже
находилась в `notification-service`; теперь она принадлежит `job-core`, поэтому очистку поставляет этот модуль,
а не каждый потребитель: модуль, владеющий TTL, обязан владеть и тем, что делает TTL правдой.

`SelfSchedulingLifecycle` + `RunLock`, по образцу `ExportRetentionPurge`, **пакетно, с продлением аренды между
пакетами**. Первый запуск после сокращения TTL может иметь миллионы строк к удалению, и одно выражение по всем
из них зафиксировало бы самый старый идентификатор транзакции, остановило autovacuum на таблице, получающей
вставку на каждый защищённый запрос, и держало блокировки на её горячем пути. Потерянная аренда останавливает
прогон; пакеты независимы, поэтому остальные выполнятся на следующем тике.

**TTL — это окно, в котором распознаётся повтор.** Его сокращение превращает дубликаты в двойные выполнения, а
не в экономию места. Он задан щедро (24 часа — принятый минимум для HTTP `Idempotency-Key`) и настраивается
по областям, потому что консьюмеру Kafka обычно нужно **больше**, чем retention его топика, а HTTP-вызывающему
редко нужно больше суток.

Если очистка не успевает, она говорит об этом на уровне `warn`, называя ручки — больший пакет или меньший
интервал, но никогда не более короткий TTL.

## Бэкенды

| | Postgres (по умолчанию) | Redis |
|---|---|---|
| `TRANSACTIONAL` | да | **нет** |
| `STANDALONE` | да | да |
| очистка | задача этого модуля | Redis истекает ключи сам |
| перезахват брошенного захвата | взаимно исключающий (блокировка строки) | best-effort (побеждает последний записавший) |

**Захват в Redis не транзакционен с записью в БД, которую он защищает.** Это не ограничение реализации, а
свойство Redis: захват коммитится в другой системе, чем работа, поэтому никакое расположение двух вызовов не
делает их одним атомарным действием. Поэтому он обслуживает только `STANDALONE` — и бросает исключение вместо
деградации, потому что подмена транзакционного захвата standalone-захватом оставляет ключи занятыми для
работы, которая откатилась. Падение между захватом и коммитом оставляет ключ занятым для работы, которой не
было, и это ограничено арендой, а не TTL.

Приемлемо для HTTP-фильтра перед обработчиком, который сам идемпотентен. **Неприемлемо для случая
консьюмера** — того самого, ради которого примитив и был написан. Эта оговорка стоит в javadoc класса
`RedisIdempotencyStore`, а не только здесь, потому что команда, берущая Redis, делает это ради
производительности в тот момент, когда правит конфигурацию, и эта страница — не то, что она читает.

## Наблюдаемость

| метрика | теги | означает |
|---|---|---|
| `ludwig.idempotency.claims` | `scope`, `outcome` | попытка захвата |
| `ludwig.idempotency.replays` | `scope` | сохранённый ответ воспроизведён вместо повторного выполнения |
| `ludwig.idempotency.claims.failed` | `scope` | захват освобождён для повтора |
| `ludwig.idempotency.fingerprint.mismatches` | `scope` | **клиент переиспользует один ключ для разных запросов** |
| `ludwig.idempotency.purged` | — | захваты, удалённые по истечении окна |

**Счётчик несовпадений — тот, по которому стоит настраивать алерт.** Все остальные метрики описывают трафик:
дубликаты и воспроизведения — здоровое следствие повторов, и развёртывание без них скорее имеет выключенную
возможность, чем идеальных клиентов. Несовпадение означает, что клиент сломан, и со стороны клиента это
выглядит как редкий 422, о котором никто не сообщит.

`scope` — единственный тег, из набора, фиксированного на момент развёртывания. Ключ, идентификатор запроса и
вызывающий сознательно никогда не теги: все три неограниченны, и любой из них превратил бы бэкенд метрик в
хранилище временных рядов на запрос. Интересный вопрос о дубликате — обычно *кто его отправил*, и он относится
к аудиторскому следу.

## Аудит

Два события, через единственный `AuditSink` из `audit-core`, в категории `idempotency`:

- **воспроизведение**, потому что вызывающий получил ответ, который сервис не производил для этого вызова.
  Когда позже спросят, почему в логе один заказ, а у клиента два подтверждения, ответом будет эта запись;
- **несовпадение отпечатка**, записанное как `DENIED`, а не `FAILURE`: сервис отказал намеренно и отказал
  верно, а «мы им отказали» и «мы сломались» ведут к противоположным расследованиям.

Не по строке на каждый успешный захват: это была бы строка на каждый запрос к каждому защищённому эндпоинту,
похоронившая два значимых события под трафиком, который уже есть в access-логе. Ни одно из событий не несёт
тело запроса или отпечатки — публикация отпечатка позволила бы читателю следа подтвердить догадку о содержимом
запроса.

`IdempotencyAuditEvent` — типизированная поверхность авторства с `toAuditEvent()`, точно как
`IngestAuditEvent` и `ExportAuditEvent`. Модуль не объявляет собственного SPI аудита, логгера с именем
`*.audit` и маски редактирования.

## Что модуль сознательно не поглощает

Четыре из пяти механизмов ниже — **правильный локальный ответ**, и универсальное хранилище испортило бы каждый:
лишняя таблица, лишняя запись на горячем пути и вторая вещь, которая может отказать. Этот раздел существует,
чтобы следующий читатель списка не «дозакончил работу».

**3. Дедупликация при публикации** — `findByIdempotencyKey` и `OutboxProperties.Idempotency` в
`outbox-spring-boot-starter`. Поиск по уникальному столбцу собственной строки outbox, где **возврат
существующего сообщения *и есть* контракт**. Нечего захватывать и негде.

**4. Ключ как столбец бизнес-агрегата** — `ExportReportRun.findByIdempotencyKey` в
`export-spring-boot-starter`. Ключ принадлежит прогону. Вторая таблица добавила бы запись на путь создания
прогона и строку, способную пережить или опередить прогон, который она описывает, ради гарантии, которую уже
даёт уникальный столбец самого прогона.

**5. Дедупликация по естественному ключу** — ограничение уникальности `(bucket, key, etag)` в
`file-ingest-spring-boot-starter`. **Никто не передаёт ключ**; идентичность выводится из данных, что строго
сильнее, чем доверять вызывающему дважды прислать одну и ту же строку. Именно поэтому *исправленная повторная
загрузка* корректно не пропускается — ключ от вызывающего это бы скрыл.

**6. Классификация повторов по RFC 9110** — `IdempotentMethods` в rest-client и `HttpMethod.isIdempotent()` в
jira-client. Другой вопрос с другим ответом: *«можно ли повторить этот метод»*, а не *«выполнял ли я эту
работу»*. `GET` идемпотентен и не имеет работы для дедупликации; `POST` с таким ключом повторяем именно
**потому**, что он его несёт. Два механизма встречаются на `IdempotencyHeaders.KEY`, и это всё их
отношение.

**7. «Побеждает последняя запись» по версии** — сравнение отметок времени в identity-projection,
воспроизведение в user-settings. Сходимость по значению не нуждается ни в ключе, ни в хранилище.

### Одно небольшое дублирование, оставленное за рамками

`IdempotentMethods` (rest-client) и `HttpMethod.isIdempotent()` (jira-client) — это одна и та же таблица RFC
9110, написанная дважды. Это настоящая, но гораздо меньшая задача — один enum или одна статическая таблица в
общем месте — и она относится к **политике повторов**, а не к дедупликации работы. Её сознательно не влили в
этот модуль: механизм 6 в списке «не здесь» выше, и его поглощение сделало бы границу модуля тем самым, что
этот README защищает целым разделом.

## Структура модуля и растяжка

**Один модуль здесь верен**, в отличие от `audit-core`, которому пришлось разделиться. Проверка: ничто выше
`db-core` не нуждается в хранилище. Самые низкоуровневые потребители дедупликации работы — сервисы и
помощники вокруг outbox, а все они уже стоят над `db-core`, `job-core` и `web-core`, поэтому модуль зависит
от всех трёх напрямую. `mvn -pl db-core -am verify` собирает только `web-core` и `db-core` — это и есть
доказательство.

**Растяжка**, указанная и в POM, и здесь: если `rest-client-*` или `hot-reload-*` когда-нибудь понадобится
хранилище, модуль **обязан** быть разделён на `idempotency-core` (SPI, ключ, отпечаток, без внутренних
зависимостей репозитория) и стартер. Реактор Maven игнорирует scope, поэтому цикл иначе появился бы в самый
неподходящий момент — как падение реактора во время чьего-то несвязанного изменения. `SqlConfinementTest`
сегодня проверяет отсутствие этих зависимостей.

## Конфигурация

См. YAML в [англоязычном README](README.md#configuration): ключи и значения по умолчанию одни и те же.
Существенное:

- `ttl` — **параметр корректности**, а не настройка производительности;
- `http.enabled` и `kafka.enabled` выключены по умолчанию, и включение их — решение о поведении API, а не об
  оптимизации;
- `http.methods` — это `POST` и `PATCH` и сознательно не `PUT`/`DELETE`: они уже идемпотентны по RFC 9110, так
  что их повтор безопасен без ключа, а сохранённое воспроизведение скрыло бы от второго вызывающего настоящее
  изменение состояния;
- `http.replayed-headers` — белый список, а не «всё кроме». Воспроизведение всех заголовков означало бы
  воспроизведение `Date`, всего, что добавил прокси, и — в худшем случае — `Set-Cookie`, то есть передачу
  второму вызывающему сессии первого.

## Переход с локального хранилища

Changelog несёт `idempotency-002-migrate-notification-idempotency`, переносящий `notification_idempotency` в
`idempotency_claim`. Он `runAlways="true"` с предусловием `tableExists` и двумя анти-джойнами — та же форма,
что установили `audit-002`/`audit-003`, и по той же причине: порядок между двумя бинами `SpringLiquibase` — не
порядок регистрации их автоконфигураций, а changeset, помеченный как выполненный, больше никогда не
рассматривается.

**Почему строки переносятся, а не таблица начинается пустой:** каждый ключ в старой таблице — это захват на
работу, которая была выполнена. Пустая таблица означает, что каждый ключ «в полёте» — дубликат, на который
сервис подействует второй раз, один раз, во время того самого развёртывания, которое его переносит. Для
`notification-service` это второе письмо или второе сообщение в чат реальному человеку — как побочный эффект
внедрения модуля, чья цель это предотвращать.

Отображение и то, что сознательно отсутствует: `state` становится `COMPLETED` (именно это означала каждая
строка той таблицы — у неё не было столбца состояния, потому что её единственным режимом был транзакционный);
`fingerprint`, `lease_expires_at` и столбцы ответа остаются **null**, потому что сфабрикованный отпечаток
отклонил бы те самые повторы, ради распознавания которых эти строки существуют; `created_at` и `expires_at`
переносятся, поэтому перенесённый захват истекает точно тогда, когда истёк бы, а не продлевается молча на
целый TTL.

**Второй** анти-джойн — тот, который важен на живом развёртывании: между одной загрузкой и следующей запрос
может захватить те же `(scope, key)` через новую таблицу, и этот захват новее и авторитетнее. Вставка старой
строки нарушила бы ограничение уникальности и обрушила бы всю миграцию, а с ней и запуск приложения.

Потребитель, включающий этот changelog в свой master changelog — как делает `notification-service`, —
получает детерминированный порядок и может удалить старую таблицу в том же развёртывании. См. там
`0006-fold-idempotency-into-starter.xml`, предусловие которого и есть та сверка, которую иначе оператор
выполнял бы глазами.

## Тесты

Интеграционные, против настоящего PostgreSQL, потому что всё несущее здесь — это поведение Postgres, когда две
транзакции встречаются на одной строке, и потому что **однопоточный тест ничего не доказывает**:
прочитать-затем-вставить его проходит.

| набор | что закрепляет |
|---|---|
| `IdempotencyStoreIT` | N потоков на один ключ → один победитель и его идентификатор, возвращённый каждому проигравшему; откат в `TRANSACTIONAL` освобождает ключ и повтор проходит; `TRANSACTIONAL` без транзакции отклоняется; дубликаты `IN_PROGRESS`/`COMPLETED`/`FAILED`; аренда мёртвого держателя истекает; истёкшую аренду нельзя продлить; граница TTL в ±1 секунду; области — пространства имён; очистка избирательна |
| `IdempotencyHttpIT` | повторённый `POST` воспроизводит исходный `201`, его тело и `Location`, **и обработчик выполняется один раз**; пересериализованный повтор всё ещё повтор; переиспользованный ключ даёт `422`, и первый ответ *не* возвращается; дубликат «в процессе» даёт `409` с `Retry-After`; неудавшийся запрос освобождает ключ; 5xx не сохраняется; один ключ на двух эндпоинтах — два захвата |
| `ConsumerDedupIT` | одна и та же запись дважды даёт один эффект; слушатель с откатом получает запись снова; ключ продюсера, переиспользованный для другой полезной нагрузки, отклоняется |
| `RetentionPurgeIT` | очистка проходит несколько пакетов и не трогает живые захваты; реплика, не получившая аренду, не удаляет **ничего** |
| `NotificationMigrationIT` | каждая старая строка попадает в общую таблицу с сохранённым окном и владельцем, и количества сходятся; миграция идемпотентна; более новый захват её переживает |
| `SqlConfinementTest` | SQL и JDBC остаются внутри `…idempotency.sql`; пакет `api` не видит реализацию; нет `@RestControllerAdvice`; нет SPI аудита; нет зависимости от `rest-client` или `hot-reload` |
| `RequestFingerprintTest` | порядок ключей, пробелы и `charset` не влияют; порядок массива влияет; некорректное тело всё равно даёт отпечаток |

Границы TTL и аренды закрепляются **подвижными часами**, а не ожиданием. Это возможно только потому, что
каждое решение в модуле принимается против внедрённого `Clock`, а мгновение передаётся в выражение параметром,
вместо того чтобы выражение вызывало `now()` базы: механизм, истечение которого нельзя проверить на границе, —
это механизм, истечение которого принято на веру.

```bash
mvn -pl idempotency-spring-boot-starter -am verify   # unit + architecture + integration
mvn -pl db-core -am verify                           # доказывает отсутствие цикла
```
