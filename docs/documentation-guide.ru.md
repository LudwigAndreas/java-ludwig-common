# Написание документации для `ludwig-common`

**[English](documentation-guide.md)** · **Русский**

Для кого: для всех, кто добавляет модуль, изменяет существующий или пишет инструкцию по эксплуатации (runbook). Здесь описано, что должно содержаться в README модуля, в каком порядке идут разделы и как поддерживать документацию в актуальном состоянии.

## 1. Где находится документация

| Документ | Расположение | Для кого | Как поддерживается в актуальном состоянии |
|---|---|---|---|
| README модуля | `<module>/README.md` + `<module>/README.ru.md` | разработчики, аналитики, администраторы | изменение, затрагивающее модуль (задача OpenSpec) |
| Обзор платформы и карта модулей | `README.md` (корень репозитория) | все | изменение, добавляющее или удаляющее модуль |
| Руководство разработчика | [`docs/developer-guide.md`](developer-guide.md) | разработчики | проверка при ревью |
| Процесс разработки и выпуска | [`docs/runbook.md`](runbook.md) | разработчики, менеджеры релизов | проверка при ревью |
| Руководство администратора | [`docs/admin-guide.md`](admin-guide.md) | администраторы платформы, SRE | проверка при ревью |
| Руководство аналитика | [`docs/analyst-guide.md`](analyst-guide.md) | системные аналитики | проверка при ревью |
| Области данных и сопоставление ролей | [`docs/data-scope-configuration.md`](data-scope-configuration.md) | разработчики, администраторы | проверка при ревью |
| Контракты HTTP и событий | `docs/api/*.openapi.yaml`, `docs/api/*.asyncapi.yaml` | аналитики, потребители | генерируется; `ApiDocumentIT` завершает сборку с ошибкой при расхождении |
| Требования к поведению | `openspec/specs/<capability>/spec.md` | аналитики, проверяющие | этап архивирования OpenSpec |
| Примечания к выпускам | `CHANGELOG.md` + `CHANGELOG.ru.md` | потребители | `-Prelease` завершает сборку с ошибкой, если запись отсутствует хотя бы в одном из файлов |
| Что контролируется автоматически, а что нет | [`docs/harness-enforcement.md`](harness-enforcement.md) | разработчики, проверяющие | проверка при ревью |
| Правила работы агентов | `docs/agent-operations.md`, `docs/agent-state.md`, `docs/code-index.md` | агенты программирования | проверка при ревью |
| Манифест модулей | `PROJECT_INDEX.md`, `project-index.json` | все | генерируется командой `scripts/manifest.sh build` |

Javadoc описывает контракт каждого публичного типа и метода. README не дублирует Javadoc: в нём объясняется, как компоненты взаимодействуют, как ими пользоваться и почему они устроены именно так.

## 2. Правила для каждого документа

1. **Описывайте только текущее состояние.** Не используйте формулировки «раньше», «больше не», «было заменено на», «сначала мы попробовали», «это исправляет ошибку, при которой». История относится к `CHANGELOG.md`, архиву OpenSpec (`openspec/changes/archive/`) и Git. Читателю нужно знать, что делает модуль и почему; сведения о том, как он к этому пришёл, не помогают в эксплуатации.
2. **Указывайте причину, а не историю.** «При остановке выполняется ожидание завершения текущего опроса, поэтому при последовательном развёртывании заявленные строки не остаются без обработки до истечения `stale-timeout`» — это объяснение причины. «До версии 1.1 строки оставались без обработки» — это история.
3. **Обе локали обновляются в рамках одного изменения.** В `README.md` и `README.ru.md` должны быть одинаковые разделы в одинаковом порядке и одинаковый смысл. Обновление README только на одном языке считается незавершённым изменением (правило для задач по модулям в `openspec/config.yaml`). Каждый файл начинается со строки переключения языка.
4. **В ссылках на образы указывайте дайджест.** Используйте формат `name:tag@sha256:...`, в том числе в примерах. Скрипт `scripts/check_image_pins.sh` проверяет блоки кода и встроенный код в каждом README; обычный текст не проверяется.
5. **В таблицах свойств указывайте значения по умолчанию.** Каждое свойство `ludwig.*`, которое использует модуль, должно присутствовать в таблице конфигурации с указанием значения по умолчанию и назначения. Если свойства нет в таблице, оно не поддерживается.
6. **Вместо пропуска раздела указывайте «не применимо».** Отсутствующий раздел «Аудит» выглядит так, будто об этом никто не подумал; формулировка «Не применимо: эта библиотека не изменяет состояние» показывает, что решение принято осознанно.
7. **Фиксируйте известные пробелы.** Если модуль должен выдавать метрику, индикатор работоспособности или событие аудита, но не делает этого, укажите это в разделе «Наблюдаемость» или «Аудит» в подразделе **«Известные пробелы»**. Пробел, зафиксированный в README, — это задача в бэклоге; незадокументированный пробел становится неожиданностью в production.

## 3. Шаблон README модуля

Разделы должны идти в указанном порядке. Заголовки должны точно совпадать с приведёнными ниже, чтобы читатель мог быстро переходить между документацией разных модулей.

```markdown
# <artifactId>

**English** · [Русский](README.ru.md)

<Один абзац: что делает модуль и когда он нужен сервису. Без исторических сведений.>

| | |
|---|---|
| Роль | library / starter / service / contract / build tooling / test support |
| Зависит от (в репозитории) | ссылки или «ничего» |
| Используется | ссылки (из PROJECT_INDEX.md) |
| Интерфейсы | REST / Kafka / gRPC / actuator / отсутствуют |

## Использование
Фрагмент зависимости, минимальная рабочая конфигурация, затем основной API. Примеры кода компилируются.

## Конфигурация
| Свойство | По умолчанию | Назначение |
Одна таблица для каждого свойства `ludwig.<module>.*`. Если таблица большая, сгруппируйте свойства по подразделам.

## Развёртывание
Что должно существовать до начала работы модуля: схема БД (путь к changelog Liquibase и способ его применения), топики, бакеты, секреты, сетевой доступ, образ (для сервисов). Если развёртывание не требуется: «Развёртывание не требуется: <причина>».

## Наблюдаемость
- Метрики — таблица: название, тип, теги, назначение.
- Логи — имена логгеров, что записывается на каждом уровне и что никогда не записывается.
- Трассировки — создаваемые спаны/наблюдения, распространение контекста.
- Проверки работоспособности — индикаторы и группа проверок, к которой они относятся.
- Рекомендуемые оповещения — выражение или условие и объяснение его важности.
- Известные пробелы — что должно отслеживаться, но не отслеживается.

## Аудит
Какие категории/действия `AuditEvent` записывает модуль, с каким результатом и когда, а также какие данные редактируются или маскируются. Либо: «Не применимо: <причина>».

## Runbook
| Симптом | Вероятная причина | Что делать |
Конкретные симптомы, которые видит оператор (метрика, строка лога, HTTP-статус), а не абстрактные режимы отказа. В каждом пункте «Что делать» должно быть действие, включая SQL-запрос или команду, если они нужны.

## Тестирование
Как тестируется модуль, для чего требуется Docker и что должен самостоятельно тестировать использующий его сервис.

## Проектные решения
Краткий список правил, которые могут показаться неожиданными, с объяснением причин. Только окончательные решения.
```

В `README.ru.md` используется тот же порядок и следующие заголовки: `Использование`, `Конфигурация`, `Развёртывание`, `Наблюдаемость`, `Аудит`, `Runbook`, `Тестирование`, `Проектные решения`. Строки таблицы: `Роль`, `Зависит от (в репозитории)`, `Используется`, `Интерфейсы`. Строка переключения языка: `*[English](README.md) · **Русский***`.

Необязательные разделы добавляются между **«Использование»** и **«Конфигурация»**, если они нужны модулю (например, «Маршрутизация», «Схема», «Точки расширения»). Обязательные разделы сохраняют установленный порядок.

### Чего не должно быть в README

- Истории изменений и заметок о миграции для прошлых выпусков (они размещаются в `CHANGELOG.md` под заголовком выпуска, в котором появилось изменение).
- Контента, генерируемого в другом месте: списка модулей из `PROJECT_INDEX.md`, документов API из `docs/api/`.
- Копии требования из `openspec/specs/`. Вместо этого добавьте ссылку на него.

## 4. Как написать запись в runbook

Запись в runbook предназначена для оператора, который в 03:00 получил оповещение и не располагает контекстом.

| Нужно | Не нужно |
|---|---|
| Начинайте с наблюдаемого оператором симптома: оповещения, метрики, сообщения лога или HTTP-статуса | Начинать с внутреннего компонента, в котором произошёл сбой |
| Приводите запрос или команду для подтверждения причины | Писать «проверьте базу данных» |
| Указывайте, безопасно ли повторять действие | Заставлять оператора гадать, приведёт ли повторный запуск к дублированию данных |
| Указывайте, когда и кому эскалировать проблему (команде, отвечающей за модуль) | Заканчивать словом «разберитесь» |

Пример:

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Увеличивается `ludwig_outbox_deadlettered_total` | Получатель отклоняет данные либо был недоступен дольше, чем допускает бюджет повторных попыток | Выполните `SELECT destination, last_error, count(*) FROM outbox_message WHERE status = 'DEAD_LETTER' GROUP BY 1, 2;`. Исправьте получателя, затем поставьте сообщения в очередь повторно: `UPDATE outbox_message SET status = 'PENDING', attempts = 0, next_attempt_at = now(), locked_at = NULL, locked_by = NULL WHERE status = 'DEAD_LETTER' AND destination = '<dest>';`. Сообщение отправляется повторно с тем же заголовком `ludwig-idempotency-key`, поэтому потребитель с включённой дедупликацией отбрасывает копию, которую уже обработал. |

Общеплатформенные процедуры (развёртывание, откат, ротация секретов, миграции БД) описаны в [`docs/admin-guide.md`](admin-guide.md); README модулей должны ссылаться на этот документ, а не повторять его содержимое.

## 5. Контрольный список для изменения, затрагивающего модуль

- [ ] Обновлены `README.md` и `README.ru.md`, разделы совпадают.
- [ ] Каждое новое свойство `ludwig.*` добавлено в таблицу конфигурации с указанием значения по умолчанию.
- [ ] Каждая новая метрика добавлена в таблицу наблюдаемости; новые сценарии отказа описаны в runbook.
- [ ] Новые действия аудита добавлены в раздел «Аудит».
- [ ] В `CHANGELOG.md` и `CHANGELOG.ru.md` добавлена запись под `## [Unreleased]`.
- [ ] Если изменился HTTP-интерфейс или поверхность событий: заново сгенерированы документы в `docs/api/` (`ApiDocumentIT`, см. [`docs/api/README.md`](api/README.md)).
- [ ] Если модуль добавлен или удалён: обновлена карта модулей в корневом `README.md` и выполнена команда `scripts/manifest.sh build`.
- [ ] Скрипт `scripts/check_image_pins.sh` проходит успешно.
