# Published API documents

Two documents per service, generated from the service's real Spring application context and committed
here: an OpenAPI document for its HTTP surface, and an AsyncAPI document for its Kafka surface (what it
reads, what it publishes through the outbox, the platform envelope headers, and its clusters). The
AsyncAPI document comes from Springwolf plus `asyncapi-spring-boot-starter`.

| Document | Service | Generated by |
|---|---|---|
| `crud-service-example.openapi.yaml` | `crud-service-example` | `ApiDocumentIT` in that module |
| `notification-service.openapi.yaml` | `notification-service` | `ApiDocumentIT` in that module |
| `crud-service-example.asyncapi.yaml` | `crud-service-example` | `AsyncApiDocumentIT` in that module |
| `notification-service.asyncapi.yaml` | `notification-service` | `AsyncApiDocumentIT` in that module |

A service without one kind of surface is listed here instead, with a line of the form
``- `<service>`: no asyncapi surface``. `scripts/api-docs.sh missing`, part of `scripts/gate.sh`, fails on
a service that has neither the document nor that line. No service is listed today.

## These files are generated. Do not edit them

A hand edit fails the build exactly as drift does, because from the comparison's point of view the
two are indistinguishable and wrong for the same reason. To change a document, change the code it
describes.

To refresh every document after a deliberate change, or check that none has drifted:

```bash
scripts/api-docs.sh refresh
scripts/api-docs.sh check
```

To refresh one (the failing test prints this command, with its own IT name):

```bash
mvn -pl :<artifactId> verify -Dit.test=ApiDocumentIT -DfailIfNoTests=false -Dludwig.apidocs.write=true
```

Then **read the diff** before committing it. The diff is the point of the whole arrangement: it is
the only place a reviewer can see that a response grew a field, lost one, or changed its status code.

An ordinary `mvn verify` never rewrites these files. It regenerates into
`target/<kind>/<artifactId>.<kind>.yaml`, compares, and fails with the command above if the two
differ - so a build leaves a clean tree clean, and a stale document cannot be committed unnoticed.

## Why they are canonicalized

Each document is re-serialized before it is written: every object's members sorted by key, and the
server addresses removed - the whole `servers` block of an OpenAPI document, and in an AsyncAPI document,
whose servers are the cluster names, each server's `host` replaced by its name (AsyncAPI requires a host). The canonicalization is
`test-support`'s `PublishedDocument`, shared by every document IT.

Sorting is what makes the comparison worth having. springdoc builds the document by walking handler
mappings, and nothing guarantees that walk is in the same order on another JVM or after a class is
renamed. Without sorting, unrelated changes would produce diffs that are pure reordering - and the
first time that happens somebody refreshes without reading the diff, at which point the check is
decorative. Member order carries no meaning in OpenAPI. Array order does (`required`, `enum`,
`parameters`), so arrays are left exactly as generated.

`servers` is derived from the request the document was fetched with, so it would describe the test
harness rather than any deployment. Committing `http://localhost` would be a claim about where the
service runs that this document is in no position to make.

## Publishing to Nexus

Other teams fetch a versioned document from the platform's Maven repositories:

```bash
scripts/api-docs.sh publish --version <v>             # check, then upload
scripts/api-docs.sh publish --version <v> --dry-run   # print the uploads only
```

Each document is published as `ru.ludwigandreas:<service>:<v>:yaml:<kind>`, for example
`ru.ludwigandreas:crud-service-example:1.4.0:yaml:asyncapi`. The repository is the one libraries deploy
to, `ludwig.repo.{releases,snapshots}.{id,url}` in the root POM, and the snapshots one when `<v>` ends in
`-SNAPSHOT`. Credentials come from your `settings.xml`. `publish` refuses to upload while any document is
missing or stale.

The document itself carries `info.version: current`, not the release version: a version inside the file
would turn every release into drift. The Nexus coordinate is the version.

## What these documents are not

**Not a compatibility baseline.** They describe what the services currently serve. Nothing fails
because a diff is backwards-incompatible for a consumer - that would need a versioning policy for
HTTP surfaces, which this repository has not decided. `scripts/check_api_baseline.sh` is the
different, existing thing: it guards *Java* API compatibility for library modules.

**Not the error contract's source.** Every error is an RFC 9457 problem document produced by
`web-core`'s single advice, not returned from a controller, so the problem schema is declared by hand
in each service's `OpenApiConfig` and attached to every operation as its `default` response. A
document inferred from return types alone would describe only the happy paths, and a generated client
would have no type able to read a failure.

**Not exhaustive across the platform.** Only services have documents. A starter contributes to a
document - `odata-filter-spring-boot-starter`'s customizer is what puts the five OData query options
into `crud-service-example`'s - but it does not have one of its own.

## A new service

A new service with no documents fails `scripts/api-docs.sh missing` in the gate until it gains both ITs
and their documents, or is listed above as having no such surface. The services are read from
`project-index.json`, so the script needs no edit.
