**[English](runbook.md)**· **Русский**

Этот файл отвечает на четыре вопроса и ни на что другое: **как мне добавить функцию, как исправить ошибку, как

## 0. Пять вещей, которые удивляют людей

Прочтите их прежде всего. Каждый из них кого-то покусал.

1. **Релиз - это git tag.** Никто нигде не редактирует версию. `.mvn/maven.config" - это запасной вариант для
   проверки без тегов, он должен оставаться "-SNAPSHOT", правило enforcer не выполняет сборку, если это не так,
   а перехватчик вообще отказывается редактировать файл.
2. **Нет кода без изменения OpenSpec.** Это не соглашение — рабочий процесс, с помощью которого создается репозиторий.
   вокруг. Раздел 2.
3. **Интеграционный тест должен называться `…IT` или `…IntegrationTest`, иначе он не запустится.** Surefire
   исключает эти названия и запускает тесты с отказоустойчивостью при `verify`. Тест под названием `FooTest`, для которого требуется
   Postgres, запускается с помощью surefire и завершается ошибкой на компьютере без Docker.
4. **Выбирайте модули по параметру `-pl :artifactId`, а не по директории.** Директории могут перемещаться, и при этом любая
   команда, основанная на пути, перестает работать.
5. **API опубликованной библиотеки заморожен на уровне последней выпущенной версии.** Удаление открытого метода приведет к сбою сборки, если только это не разрешено при повышении версии *и* если в предыдущей версии было предупреждение об этом.
   оно. Раздел 5.

## 1. Настройка

| Нужно | Зачем |
|---|---|
| JDK 17 | `maven.compiler.release=17`. Более новая версия JDK в `JAVA_HOME` в целом подходит; Lombok и Byte Buddy установлены перед Spring Boot именно для того, чтобы это было возможно |
| Maven 3.9+ | `requireMavenVersion` обеспечивает его наличие для сервисов |
| **Docker запущен**| Каждый интеграционный тест выполняется с помощью Testcontainers. Без демона они не пропускаются — они *выдают ошибку*, и команда `mvn clean install` завершается с ошибкой на `test-support` |
| Больше ничего не нужно | Не нужно импортировать стиль оформления кода из IDE: правила Checkstyle соответствуют стандартным настройкам IntelliJ, поэтому Reformat Code всегда создает чистый файл |

```bash
git clone <repo> && cd java-ludwig-common
mvn clean install          # ~полный реактор, включая интеграционные тесты
```

Если все прошло успешно, значит, все готово. Если возникли проблемы с Testcontainers, запустите Docker — без него не обойтись.

> **Один нюанс, касающийся переформатирования.** `Reformat Code` в `pom.xml` безопасен, за исключением случаев, когда речь идёт о
> `<propertyExpansion>`, где перенос строки имеет семантическое значение. Оба случая записаны как `&#10;`
> с комментарием, объясняющим, почему так сделано. Если вы когда-нибудь увидите
> `No enum constant …SeverityLevel.WARNING PACKAGE.INFO.SEVERITY=IGNORE`, знайте, что именно это и произошло.

## 2. Добавление функции

### 2.1 Branch

```bash
git switch develop && git pull
git switch -c feature/short-description
```

`feature/*` и `feature-*` распознаются `gitversion.yml`. Название ветки не влияет на
выпущенную версию, оно определяет только номер SNAPSHOT во время работы над проектом.

### 2.2 Создайте change перед кодом

```bash
openspec new change add-short-description
```

Артефакты, в таком порядке — интерфейс командной строки подскажет, какой из них будет следующим:

| Артефакт | Когда требуется | Что это такое |
|---|---|---|
| `proposal.md` | всегда | Почему, какие изменения, какие возможности, влияние |
| `design.md` | когда изменение добавляет модуль, пересекает границу модуля или затрагивает общий контракт | Решения и их альтернативы. Место, где можно записать, почему бы и нет |
| `specs/<capability>/spec.md` | всегда | Требования и сценарии в виде дельт по сравнению с `openspec/specs/` |
| `tasks.md` | всегда | Список реализаций, каждая задача с собственной командой проверки |

```bash
openspec validate add-short-description     # перед тем как объявить о готовности
```

**Зачем это нужно, если можно просто написать код:**спецификация — это независимая проверка
реализации. Если один и тот же человек пишет и то, и другое за один проход, это уже не проверка. Затраты реальны, но и польза тоже. Не пропускайте этот этап из-за «небольшого изменения» — именно в небольших изменениях кроется опасность разрастания непроверенных областей.

### 2.3 Где находится код

| Если это… | Каталог | Родительский POM | Также |
|---|---|---|---|
| библиотека или стартовый набор | `sources/<name>/` | корень реактора `common` | import `ludwig-bom`; declare `<relativePath>../../pom.xml</relativePath>` |
| исполняемый сервис | `services/<name>/` | `ludwig-service-parent` | поставляется в виде образа |
| инструменты для сборки | `build/<name>/` | корень реактора | `checkstyle-rules`, `architecture-rules`, BOM, родительский модуль |

`<relativePath>` не является необязательным. По умолчанию в Maven используется путь `../pom.xml`, который на один уровень ниже и представляет собой каталог без POM-файла.
При этом Maven не выдает ошибку, а просто находит родительский модуль в `~/.m2` и выполняет сборку на основе устаревшего `common`.

`scripts/manifest.sh layout` выдает ошибку, если модуль находится не в том каталоге, который соответствует его роли, и шлюз запускает его.

### 2.4 Прежде чем добавлять зависимость между модулями

Проверьте: *зависит ли модуль, от которого я завишу, от моего модуля напрямую или
опосредованно?*

```bash
scripts/manifest.sh module sources/<your-module>   # в обе стороны
```

Реактор DAG должен оставаться ациклическим. `cache-spring-boot-starter` имеет **ноль** зависимостей внутри репозитория, что позволяет `security-spring-boot-starter` использовать его. `ModuleIndependenceTest` завершает сборку с ошибкой, если эта зависимость нарушена.

### 2.5 Запустите проверку

```bash
scripts/gate.sh --change add-short-description <your-module>
```

Она сама определяет **зависимые** модули внутри репозитория и собирает их. Это направление позволяет выявить критические изменения, но его часто игнорируют.
Опция `-am` собирает *зависимости* модуля, то есть делает противоположное. `scripts/gate.sh --list <module>` выводит команды, не выполняя их.

Изменения в `ludwig-bom` или `ludwig-service-parent` не требуют более узкой проверки, чем `mvn clean install`, и скрипт заменяет её, а не позволяет выполнить частичную проверку.

### 2.6 Откройте пул-реквест

Целевой репозиторий — `develop`. После слияния `develop` выполняет сборку и тестирование. IFT развертывается вручную до тех пор, пока не будут выполнены этапы, описанные в разделе 4.4.

## 3. Исправление ошибки

Аналогично разделу 2, но с двумя отличиями:

- Создайте ответвление от ветки `develop` с названием `fix/…`, если только его не нужно выпустить **сейчас**, не дожидаясь следующего
  релиза — это исправление, раздел 6.
- Для изменения по-прежнему требуется запись в OpenSpec. Однострочное исправление требует однострочного предложения; в противном случае оно не будет учтено, потому что исправление без объяснения причин будет отменено следующим
  человеком, который прочитает эту строку и решит, что она выглядит неправильно.

**Сначала напишите тест, который не проходит, в том же изменении.** Исправление без теста — это исправление, которое не работает.

### 3.1 Локальное воспроизведение ошибки

Сервис с локальным приложением работает на вашем компьютере целиком — это его настоящий `main`, с закреплёнными
контейнерами, заменителями для партнёров и начальными данными, — так что для воспроизведения ошибки нужно «запустить его, установить
точку останова и вставить команду `curl`»:

```bash
mvn -pl :notification-service spring-boot:test-run \
    -Dspring-boot.run.main-class=ru.ludwigandreas.notification.местный.LocalNotificationApplication
```

В логе запуска выводится каждый адрес, команда готовности для вызова сервиса при каждом вызове, а также команда, из-за которой партнёр выходит из строя. `notification-service` — это эталонный пример:
см. раздел «Локальный запуск» в [его README](../services/notification-service/README.ru.md#Что-запускается),
а также [`test-support-local`](../sources/test-support-local/README.ru.md) для добавления того же функционала в другой
сервис.

## 4. Версии, ветки и IFT

### 4.1 Никто не вводит версию вручную

GitVersion считывает историю git, а конвейер передаёт ответ в Maven в виде `-Drevision=…`.
Суффикс определяет конвейер, а не GitVersion:

| HEAD | Версия | Передаётся в |
|---|---|---|
| имеет тег | `1.3.0` | `ludwig.repo.releases`, а в продакшене |
| не имеет тега, любая ветка | `1.3.0-SNAPSHOT` | `ludwig.repo.snapshots` |

Собственные пререлизные метки GitVersion (`1.3.0-alpha.4`) намеренно отключены во всех ветках.
Они соответствуют стандарту SemVer и **не** являются моментальными снимками Maven, поэтому Maven публикует их в репозитории релизов как неизменяемые артефакты, и они удовлетворяют требованию `requireReleaseDeps` в потребителе.
Метка, которая для человека выглядит как пререлиз, а для Maven — как релиз, — это худшее из двух зол.

### 4.2 Что вычисляет каждая ветка

Из `gitversion.yml`:

| Ветка | Инкремент | После `v1.2.0` нетегированный коммит выглядит так |
|---|---|---|
| `master` / `main` | Патч | `1.2.1-SNAPSHOT` |
| `develop` | Минор | `1.3.0-SNAPSHOT` |
| `feature/*` | Наследуется от исходной ветки | то же, что и в исходной ветке |
| `hotfix/*` | Патч | `1.2.1-SNAPSHOT` |
| `release/*` | Нет | содержит номер, с которым была создана ветка |

`release/*` настроен, и **приведенный ниже процесс его не использует.** Это сделано для того, чтобы при переходе на стабилизационную ветку в дальнейшем не требовалось вносить изменения в конфигурацию.

### 4.3 Запрос на более высокий инкремент

По умолчанию инкремент ветки равен единице.  Чтобы запросить больший инкремент, добавьте маркер в сообщение о коммите — это значения по умолчанию для GitVersion, и в этом репозитории они не переопределяются:

```
+semver: major      (или "breaking")
+semver: minor      (или "feature")
+semver: patch      (или "fix")
+semver: none       (или "skip")
```

**Это влияет только на номер SNAPSHOT.** В случае сборки с тегами тег *является* версией.  Таким образом, основная задача маркера — следить за тем, чтобы номер SNAPSHOT в ветке develop не менялся между релизами. Это важно, потому что именно по этому номеру API-шлюз проверяет внесенные изменения (раздел 5).

> Сам GitVersion был настроен и прошел проверку схемы, но **никогда не применялся** к этому > репозиторию — на компьютере, на котором был создан файл `gitversion.yml`, не было Docker. Первый
> запуск конвейера также является первым реальным тестированием этого метода. Если вычисленное число выглядит неправильным, то это
> место для поиска, а не на стороне Maven.

### 4.4 IFT

**IFT запускает `development".** Каждое слияние с "development" создает "x.y.z-SNAPSHOT" и повторно развертывает IFT.
Нет ветки выпуска и нет кандидата на выпуск.

> ### ⚠ Эта часть представляет собой готовый процесс и еще НЕ настроена
>
> В текущей версии Jenkinsfile сборка и тестирование в ветке develop выполняются, а затем процесс останавливается. Оба
> `Publish artifacts` и `Push image` содержат `when { branch 'master' }`, поэтому при сборке в ветке develop не публикуется
> jar-файл со снимком состояния и не отправляется образ, а этап развертывания IFT вообще отсутствует.
>
> Два конкретных изменения делают остальную часть этого раздела верной:
>
> 1. расширьте эти два этапа до `when { anyOf { branch 'master'; branch 'develop' } }`, чтобы при слиянии в ветке develop
>    создавались артефакты с пометкой `-SNAPSHOT` и образ со снимком состояния;
> 2. добавьте этап `Deploy to IFT`, `when { branch 'develop' }`, на котором развертывается образ, только что отправленный на предыдущем
>    этапе.
>
> До тех пор, пока не будут реализованы оба этапа, IFT развертывается вручную, и фраза «при каждом слиянии IFT развертывается заново» описывает намерение,
> а не работу конвейера. Этот примечание останется здесь до тех пор, пока не будут реализованы оба этапа.

Что это дает: единое место для поиска, отсутствие необходимости синхронизировать ветки и обратная связь по результату слияния
в рамках одной сборки.

Чего это стоит, если говорить прямо, чтобы никого не удивлять: **IFT никогда не тестирует артефакты, которые запускаются на продакшене.** Он тестирует коммит. Между подписанием IFT и тегом `develop` ветка может переместиться. Если этот промежуток когда-то станет важнее, чем простота, то решением станет ветка `release/*`, которую уже настроил `gitversion.yml` — это изменение процесса, а не инструментария.

## 5. Что можно и что нельзя менять в опубликованном API

Это самая сложная часть, и именно из-за неё у людей, которые её не читали, возникают проблемы при сборке.

### 5.1 Правило

Каждая jar-библиотека, вложенная в корневой репозиторий реактора, при `verify` сравнивается с последней версией с теми же
координатами. **Приращение версии — это разрешение:**

| Приращение | Разрешения |
|---|---|
| major | изменение, нарушающее работу бинарных файлов |
| minor | изменение, несовместимое с исходным кодом, но совместимое с бинарными файлами |
| patch | эквивалентный API |

Таким образом, удаление открытого метода из `audit-core` в патче приводит к ошибке, и в сообщении об ошибке указывается метод и
приращение, которое позволило бы это сделать.

Обратите внимание на асимметрию: фильтр не пропускает слишком маленькое приращение и никогда не пропустит слишком большое.  Команда, которая меняет основную версию при каждом релизе, делает фильтр бесполезным, и ни один инструмент этого не заметит — только журнал изменений.

### 5.2 Где это можно узнать

На этапе разработки, а не во время релиза.  SNAPSHOT на этапе разработки — это незначительное изменение, поэтому изменение, нарушающее работу бинарного файла, приведет к сбою при сборке на этапе разработки.  Если ваше изменение действительно нарушает работу, укажите это с помощью `+semver: major`, и сборка пройдет успешно, потому что теперь вы об этом заявили, а в этом и заключается весь смысл.

### 5.2a HTTP-интерфейс — это совсем другое, и он проверяется по-другому

Все вышесказанное касается совместимости с **Java** API и относится к jar-файлам — библиотекам и стартовым пакетам.  **HTTP**-интерфейс сервиса вообще не проверяется: revapi сравнивает байт-код, а в байт-коде сервиса нет никаких указаний на то, что из ответа исчезло какое-то поле в формате JSON.

Вместо этого для каждого сервиса создается фиксированный документ в папке `docs/api/`, который генерируется на основе собственного Spring-контекста сервиса с помощью `ApiDocumentIT` и проверяется при `verify`. Сборка завершается с ошибкой, если
зафиксированная копия и работающая служба не совпадают, что означает:

- **В запросе на вытягивание, который изменяет HTTP-интерфейс службы, содержится сравнение этого интерфейса.** Это то, что нужно читать при проверке. Расширенный ответ, удалённое поле, изменённый код состояния и новая конечная точка — всё это можно увидеть только здесь и больше нигде.
- **Обновление выполняется намеренно.** `mvn -pl :<artifactId> verify -Dit.test=ApiDocumentIT
  -DfailIfNoTests=false -Dludwig.apidocs.write=true`, а затем прочтите полученный результат. При обычной сборке файл не перезаписывается, поэтому отсутствие изменений в выводе команды `git status` имеет смысл.

Обратите внимание на то, чего эта команда **не делает**: она не отклоняет обратно несовместимые изменения, в отличие от описанного выше случая с инкрементной версией. В этом репозитории нет политики управления версиями для HTTP-интерфейсов, поэтому документ делает изменения видимыми, а решение остаётся за разработчиком.
В `docs/api/README.md` говорится то же самое, но более подробно.

### 5.3 Устаревание

```java
/**
 * …
 *
 * @deprecated вместо этого используйте {@link Replacement#doThing()}
 */
@Deprecated(since = "1.3.0", forRemoval = false)
public void oldThing() { … }
```

Оба элемента обязательны, и без них Checkstyle выдает ошибку `validate`:

- `since` — пользователь, читающий просто `@Deprecated`, не может понять, идет ли речь об одном выпуске или о пяти.
- `forRemoval` — без этого предупреждения компилятора об удалении не будет, поэтому `false` — это утверждение, а не значение по умолчанию.
- тег Javadoc `@deprecated` должен **указывать на замену** или сообщать об ее отсутствии. Если в описании устаревания не указано, что использовать вместо него, проблема ложится на того, кто это читает.

### 5.4 Удаление чего-либо

Три условия, все они обязательны:

1. **Исходная версия уже содержала**`@Deprecated(forRemoval = true)`. Если объявить что-то устаревшим и удалить в том же релизе, ничего не получится: в исходной версии нет предупреждения, поэтому удаление неотличимо от необъявленного удаления.
2. **Обновление** версии является **major**.
3. Запись в `revapi.differences` в корневом POM-файле реактора с обоснованием, в котором указан выпуск
   с объявлением об устаревании:

```json
{
  "code": "java.method.removed",
  "old": "method void ru.ludwigandreas.audit.AuditSink::legacyRecord(…)",
  "justification": "Устаревший метод, который будет удален в версии 1.4.0; удален в версии 2.0.0. Замена: record(AuditEvent)."
}
```

Удаление, для которого никто ничего не писал, приводит к сбою сборки, независимо от указанной версии.

> **Правило, которое записано, но не проверяется:** устаревший API должен просуществовать как минимум до выхода одного
> *минорного* релиза, прежде чем его удалят. Никто не следит за его соблюдением — шлюз сравнивает одну сборку с одной
> базовой версией, и два артефакта не могут определить, сколько релизов их разделяет. Это комментарий рядом с
> конфигурацией revapi и запись в `docs/harness-enforcement.md`, сделанная намеренно, а не
> правило, которое выглядит как обязательное, но таковым не является.

### 5.5 Если шлюз сообщает о чем-то, что не является критическим изменением

Ответ зависит от того, о чем идет речь:

- **`java.missing.newClass`** — тип, который revapi не смог загрузить. Обычно это можно исправить, устранив причину. (зависимость в области видимости `provided`, которую не удалось разрешить). Исправьте это там. Если проигнорировать класс, который revapi *мог бы*
  прочитать, то некорректный анализ превратится в незаметный.
- **`externalClassExposedInAPI` / `nonPublicPartOfAPI`** — уже исключены на глобальном уровне. Эти исключения вычисляются только на основе нового архива и не являются утверждениями о совместимости двух версий.

Проверка на любое новое исключение: **код, сравнивающий два архива, остается активным; код, вычисленный на основе одного архива, не является утверждением о совместимости.** Добавьте его с обоснованием или не добавляйте.

## 6. Выпуск

### 6.1 Минорное обновление или патч

```bash
# 1. Разрабатываемая ветка зеленая, и IFT не выявила проблем. 
# 2. Напишите запись в журнал изменений — для ОБЕИХ локализаций, с одинаковым заголовком. 
#    ## [1.3.0] в CHANGELOG.md и CHANGELOG.ru.md
# 3. Объедините разрабатываемую ветку с основной через пул-реквест.
# 4. Пометьте коммит слияния тегом. 
git switch master && git pull
git tag -a v1.3.0 -m 'Release 1.3.0'
git push origin v1.3.0
# 5. Объедините ветку master с веткой develop, чтобы тег появился в её истории. 
```

Вот и вся процедура. Конвейер распознаёт тег, удаляет `-SNAPSHOT`, добавляет `-Prelease`
и развёртывает код в репозиторий релизов.

`-Prelease` не устанавливает версию — он *принудительно* устанавливает конкретную версию, без зависимостей от SNAPSHOT,
а также заголовок журнала изменений для этой версии **в обоих языковых разделах**, указывая на тот, в котором его нет. Если пропустить
шаг 2, сборка завершится ошибкой на этапе `validate`, до того как что-либо будет скомпилировано.

### 6.2 Основной выпуск

То же самое, но с двумя дополнениями:

- Где-то в истории с момента последнего выпуска есть коммит с сообщением `+semver: major`, поэтому в
  разработке SNAPSHOT уже используется значение `2.0.0-SNAPSHOT`, и шлюз API проверял его, пока вы
  работали.
- Каждое удаление сопровождается записью `revapi.differences` (раздел 5.4).

Тег "Version 2.0.0". Именно по этому тегу и будет произведено решающее изменение.

### 6.3 Исправление

```bash
git switch master && git pull
git switch -c исправление/краткое описание
# исправление + тест + изменение OpenSpec + запись в журнале изменений в обеих локалях
# PR в master
git switch master && git pull
git tag -a версии 1.2.1 -m "Hotfix 1.2.1"
git push origin v1.2.1
git checkout develop && git merge master # ВСЕГДА. Не пропускайте.
```

**Обратное слияние - это шаг, о котором забывают**, и симптомом является то, что исправление исчезает в
следующем выпуске, потому что в "разработке" его никогда не было.

> **Известный пробел, поскольку IFT отслеживает "разработку":** исправление, направленное непосредственно в "master"**, не проходит
> через IFT.** Такова цена простой модели среды. Для чего-либо большего, чем
> однострочное исправление, либо сначала объедините его в "development" и дайте IFT его увидеть, либо разверните ветку исправления в
> IFT вручную, прежде чем добавлять теги. Принимайте решение обдуманно; не обнаруживайте его впоследствии.

### 6.4 Что публикуется в релизе

При использовании параметра `-Pci` каждый jar-файл, родительским элементом которого является корневой jar-файл реактора, публикует свой **jar-файл, свернутый POM, jar-файл `-sources`
 и jar-файл `-javadoc`**. При использовании команды `mvn clean install` по умолчанию не создаются два последних jar-файла, поэтому локальный цикл выполняется быстро. Сервисы не публикуют ни один из этих файлов — они поставляются в виде образов, привязанных по имени, версии **и**`sha256`
дайджест.

### 6.5 Откат

Отменить публикацию невозможно. Выпущенная версия неизменна, в этом и смысл. Откатите изменения: исправьте и добавьте следующий патч. Если релиз настолько плох, что его нужно откатить, повторно разверните образ с предыдущим дайджестом — он указан в манифесте предыдущего релиза, поэтому в каждой ссылке на образ есть такой дайджест.

## 7. Гейт в одном месте

```bash
scripts/gate.sh --change <name> <module> [<module> …]   # запускает все, что указано ниже
scripts/gate.sh --list <module>                          # или просто выводит список
```

По порядку, вручную:

```bash
scripts/check_image_pins.sh        # каждая ссылка на образ содержит дайджест
scripts/check_api_baseline.sh      # неразрешимый базовый дайджест — это не отсутствие базового дайджеста
scripts/manifest.sh build          # только если изменился POM
mvn -q validate                    # Checkstyle + enforcer, для каждого модуля
mvn -pl :<touched> -am verify
mvn -pl :<each in-repo dependent> -am verify
openspec validate <change>
```

`mvn test` сам по себе не запускает **ни одного** интеграционного теста. `mvn verify` запускает.

Локальные обходные пути, никогда не используются в конвейере и в файлах:
`-Dcheckstyle.skip=true`, `-Djacoco.skip`, `-Denforcer.skip`, `-DskipTests`, `-Drevapi.skip=true`.
