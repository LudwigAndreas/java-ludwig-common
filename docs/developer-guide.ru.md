# Руководство разработчика

**[English](developer-guide.md)** · **Русский**

Для инженеров, которые разрабатывают платформенные модули или сервисы на их основе. Процесс работы (ветки, OpenSpec, gate, версии и релизы) описан в [runbook.md](runbook.md) и здесь не повторяется; в этом руководстве рассматривается, что нужно создавать и каким требованиям это должно соответствовать. Авторитетные правила для каждого модуля находятся в его собственном README.

## 1. Архитектура на одной странице

```text
build/      артефакты сборки: ludwig-bom, ludwig-service-parent, ludwig-grpc-api-parent,
            architecture-rules, checkstyle-rules, jacoco-aggregate
sources/    библиотеки (*-core), стартеры (*-spring-boot-starter), контракты (*-grpc-api),
            средства поддержки тестирования (test-support*)
services/   запускаемые сервисы: crud-service-example (эталонный пример), notification-service
```

| Тип | Соглашение об именовании | Родительский модуль | Содержимое |
|---|---|---|---|
| Библиотека Core | `<name>-core` | корень reactor | обычные Java-контракты и алгоритмы; Spring — только если без него нельзя обойтись, автоконфигурация запрещена |
| Стартер | `<name>-spring-boot-starter` | корень reactor | автоконфигурация, `@ConfigurationProperties`, changelog Liquibase, пакеты сообщений, метрики |
| Контракт | `<service>-grpc-api` | `ludwig-grpc-api-parent` | только файлы `.proto` |
| Поддержка тестирования | `test-support*` | корень reactor | фикстуры, используемые в области `test` |
| Сервис | любое имя | `ludwig-service-parent` | приложение, `deploy/`, `Dockerfile`, если он поставляется вместе с сервисом |

**Зависимости направлены вниз и никогда не образуют циклов.** `audit-core`, механизмы `job-core`, `cache-spring-boot-starter`, `test-support` и `pat-core` намеренно не зависят от других модулей внутри репозитория, чтобы их могли использовать все остальные. Перед добавлением зависимости проверьте оба направления: `scripts/manifest.sh module sources/<module>`. `PROJECT_INDEX.md` — сгенерированная карта проекта.

**Используйте примитивы платформы вместо собственной реализации:**

| Задача | Используйте | Никогда не используйте |
|---|---|---|
| Запланированный обработчик с хранением состояния в БД | `job-core`: `SelfSchedulingLifecycle`, захват задач через `SKIP LOCKED`, `RunLock` | циклы с `@Scheduled`, advisory locks |
| Публикация события | `outbox-spring-boot-starter`, предварительно объявив тип события | `KafkaTemplate.send` внутри транзакции |
| Получение события | фабрику контейнеров `messaging-spring-boot-starter` | самодельную фабрику или обработчик ошибок |
| Дедупликация по ключу, переданному вызывающей стороной | `idempotency-spring-boot-starter` | последовательность «прочитать, затем вставить» |
| Запись аудита | `AuditSink` из `audit-core` | собственный SPI или таблицу аудита модуля |
| Кэширование | `cache-spring-boot-starter` с объявленной целью использования | отдельный экземпляр Caffeine для конкретного модуля |
| Ответ об ошибке | маппер исключений `web-core` + пакет сообщений | `@RestControllerAdvice` |
| Длительная HTTP-операция | контракт операций из `web-core` (`OperationResponse`, `202` + `Location`) | собственный формат опроса статуса |
| Исходящие HTTP- или gRPC-вызовы | именованные клиенты `rest-client` / `grpc-client` | `new RestTemplate()` |
| Файлы в объектном хранилище | `object-storage-spring-boot-starter` | прямое использование AWS SDK |

## 2. Создание библиотеки или стартера

1. **Сначала опишите изменение в OpenSpec** (`openspec new change <name>`), добавив спецификацию возможностей, на которые будут опираться другие модули. См. [runbook.md §2](runbook.md#2-adding-a-feature).
2. **Создайте `sources/<name>/pom.xml`**, указав корень reactor в качестве родителя и `<relativePath>../../pom.xml</relativePath>`. Версии берутся из `ludwig-bom`; не объявляйте их вручную.
3. **Добавьте модуль** в `<modules>` корневого `pom.xml`, в `ludwig-bom` и в зависимости `build/jacoco-aggregate`; затем запустите `scripts/manifest.sh build`, чтобы пересоздать `PROJECT_INDEX.md`.
4. **Структура пакетов:** `ru.ludwigandreas.<name>`; автоконфигурация находится в `...autoconfigure` и перечисляется в `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.
5. **Конфигурация:** одно дерево `@Validated @ConfigurationProperties("ludwig.<name>")` с подключённым configuration processor. Все значения по умолчанию задаются в этом классе, а не в YAML. Если настройки по отдельности допустимы, но несовместимы друг с другом, валидатор должен отклонить запуск и сразу сообщить обо всех проблемах.
6. **Условное подключение:** стартер, присутствующий в classpath, не должен менять или ломать приложение, если его функции не включены (`openspec/specs/starter-conditional-wiring`). Упорядочивайте автоконфигурации с помощью `after`/`before`, если одна зависит от бинов другой.
7. **Хранение данных:** добавьте changelog Liquibase в `db/changelog/<name>/` внутри JAR. Используйте changeset-файлы в формате SQL с заголовками Liquibase и именами `NNNN-<slug>.sql` (`id` вида `<prefix>-NNNN-<slug>`, автор `ludwig-<prefix>`); корневой XML-файл должен содержать только include-директивы. Документируйте строку include, которую добавляет сервис. Не редактируйте уже выпущенный changeset — создавайте новый. Формат проверяет `scripts/check_migrations.sh`.
8. **Ошибки и тексты:** коды ошибок имеют вид `ludwig.<name>.error.<reason>`. Все пользовательские строки должны находиться в `i18n/ludwig-<name>-messages.properties` и `i18n/ludwig-<name>-messages_ru.properties` с идентичными наборами ключей (`openspec/specs/i18n-bundles`).
9. **Метрики:** используйте Micrometer как необязательную зависимость и интерфейс `<Name>Metrics` с реализацией `Noop`, которая регистрируется всегда, чтобы вызывающий код мог безусловно записывать метрики. Имена метрик должны начинаться с `ludwig.<name>.`; наборы тегов должны быть ограниченными (никогда не используйте ID пользователя, ключ или имя шаблона).
10. **Состояние здоровья:** если модуль управляет очередью необработанных задач или внешним соединением, добавьте `HealthIndicator` и укажите, в какую группу readiness он входит.
11. **Аудит:** изменения состояния и решения по безопасности должны отправлять `AuditEvent` через внедрённый `AuditSink`; см. §5.
12. **Тесты:** модульные тесты размещайте рядом с кодом; тесты с Testcontainers называйте `*IT` или `*IntegrationTest` и используйте `test-support`; добавьте архитектурный тест с `architecture-rules`.
13. **README.md и README.ru.md** создайте по шаблону из [documentation-guide.md](documentation-guide.md) в рамках того же изменения.

## 3. Создание нового сервиса

1. Создайте `services/<name>/pom.xml`, указав `ludwig-service-parent` в качестве родителя (и `<relativePath/>`, если сборка должна работать за пределами этого reactor).
2. Возьмите `crud-service-example` за основу структуры: `web` → `service` → `repository`; DTO, доменные модели и entity-модели сопоставляются через MapStruct; для запросов используйте QueryDSL, для типизированных свойств — `settings`.
3. Явно добавьте `observability-spring-boot-starter`; он не подключается транзитивно.
4. **Группа readiness:** включите `db` и любой индикатор очереди:
   ```yaml
   management.endpoint.health.group.readiness.include: readinessState, db, <yourIndicator>
   ```
   Проверка liveness должна проверять только процесс; отказ внешнего партнёра никогда не должен приводить к перезапуску pod'ов.
5. **Публикуемые документы API:** добавьте `ApiDocumentIT` для OpenAPI и, если сервис взаимодействует с Kafka, `AsyncApiDocumentIT`. Оба теста должны использовать `PublishedDocument` из `test-support`; сохраните полученный результат в `docs/api/` (см. [api/README.md](api/README.md)).
6. **Развёртывание:** используйте образ, собираемый через Jib из родительской конфигурации, либо многоэтапный `Dockerfile`, в котором базовые образы закреплены по digest. Добавьте манифест в `deploy/k8s/` по образцу `notification-service` (пробы, ресурсы, `PodDisruptionBudget`, секреты через `secretKeyRef`).
7. **Локальный запуск:** добавьте `test-support-local` и `Local<Name>Application` в `src/test`, как это сделано в `notification-service`.
8. Пути endpoint'ов должны иметь версию (`/api/v1/...`); в сегменте, обозначающем ресурс, нельзя использовать дефисы: `/server/info`, а не `/server-info`.

## 4. Создание модуля gRPC-контракта

Создайте `sources/<service>-grpc-api/`, указав `ludwig-grpc-api-parent` в качестве родителя: POM должен содержать родительскую конфигурацию и `artifactId`. Файлы proto размещайте в `src/main/proto/ludwig/<service>/v1/` и задавайте `package ludwig.<service>.v1`, `java_package = "ru.ludwigandreas.<service>.grpc.v1"` и `java_multiple_files = true`. Для каждого RPC укажите `idempotency_level`; стартер клиента повторяет только те вызовы, которые контракт определяет как безопасные для повтора. Для длительных операций используйте `ludwig/operation/v1/operation.proto`. Проверку выполняют `scripts/check_protos.sh` и `scripts/manifest.sh layout`. Пример: [catalog-grpc-api](../sources/catalog-grpc-api/README.md).

## 5. Контрольный список наблюдаемости и аудита для любого нового модуля

Модуль нельзя считать завершённым, пока оператор не сможет понять, работает ли он, не читая его исходный код.

| Вопрос оператора | Что должен предоставлять модуль |
|---|---|
| Выполняется ли работа? | Счётчик обработанных элементов с разбивкой по результату |
| Успевает ли он обрабатывать поступающие задачи? | Gauge размера очереди и **возраста самой старой задачи**; когда очередь пуста, значение должно быть нулевым |
| Возникают ли ошибки? | Счётчик ошибок с ограниченным набором причин; строка журнала уровня `WARN`/`ERROR` с идентификатором корреляции |
| Завис ли он? | Для worker-процессов — время последнего успешного выполнения или счётчик запусков (`job-core` сам по себе этого не предоставляет) |
| Доступны ли зависимости? | Индикатор состояния; включайте его в readiness только тогда, когда без этой зависимости сервис не может обслуживать запросы |
| Кто и что изменил? | `AuditEvent` для каждой мутации состояния, инициированной человеком или внешней системой |
| Какое оповещение должно срабатывать? | Таблица «Recommended alerts» в README с именами метрик Prometheus |

События аудита: категория берётся из `AuditCategories` (если подходящей нет, добавьте её в `audit-core`), действие имеет формат `<category>.<verb>`, субъект определяется через `ActorResolver` или `Actor.system()`. Не помещайте персональные данные в атрибуты иначе как через `Redactor`. Если запись аудита для мутации состояния не удалась, операция завершается ошибкой в соответствии с политикой отказа sink. Наблюдательное событие при ошибке записи журналируется и отбрасывается.

Известные пробелы в существующих модулях перечислены в [admin-guide.md §9](admin-guide.md#9-known-operational-gaps); не копируйте шаблоны из этого списка.

## 6. Соглашения, проверяемые сборкой

| Правило | Средство проверки |
|---|---|
| Форматирование, именование, Javadoc | `checkstyle-rules` на фазе `validate` |
| Слои, циклические зависимости, хранение данных, Kafka, REST-пути, журналирование | тесты `architecture-rules` |
| Покрытие не менее 70% инструкций / 60% ветвей (сервисы) | проверка JaCoCo в `ludwig-service-parent` |
| Публичный API библиотеки нельзя нарушать без повышения major-версии | revapi, `scripts/check_api_baseline.sh` |
| Каждая ссылка на образ закреплена по digest | `scripts/check_image_pins.sh` |
| Changeset'ы — SQL с единообразным форматированием и структурой | `scripts/check_migrations.sh` |
| Модуль находится в каталоге, соответствующем его роли | `scripts/manifest.sh layout` |
| Опубликованные документы API соответствуют коду | `ApiDocumentIT`, `AsyncApiDocumentIT`, `scripts/api-docs.sh` |

То, что описано в документации, но не проверяется автоматически, перечислено в [harness-enforcement.md](harness-enforcement.md). Запустите все проверки командой `scripts/gate.sh --change <name> <module>`.

## 7. Тестирование

- `mvn test` запускает только модульные тесты; `mvn verify` запускает также интеграционные тесты и требует Docker.
- Используйте `@LudwigPostgresTest`, `@LudwigKafkaTest`, `@LudwigLocalStackTest`. Контейнеры совместно используются в пределах JVM, поэтому очищайте состояние через `DatabaseCleaner` в `@BeforeEach`.
- Для тестов с учётом безопасности используйте `test-support-security` (`TestPrincipalBuilder`, `JwtDecoder`, отклоняющий все запросы).
- Управляйте временем с помощью `TestClock`; никогда не используйте `Thread.sleep`.
- См. [test-support](../sources/test-support/README.md).

## 8. Создание документации и инструкций по эксплуатации

Следуйте [documentation-guide.md](documentation-guide.md): используйте единый шаблон README для каждого модуля; включайте обе локали в одно изменение; описывайте только текущее состояние (история хранится в git и `CHANGELOG.md`); вместо пропуска раздела пишите «Не применимо»; для каждого рекомендуемого оповещения добавляйте запись в runbook.
