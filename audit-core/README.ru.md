# audit-core

[English](README.md) | [Русский]

**Единственный** в платформе конверт аудита, его SPI-приёмник и пакет редактирования (маскирования).

Модуль появился потому, что таких механизмов было девять. Каждый стартер этого репозитория, которому
надо было записать, что он сделал, изобретал для этого свой механизм, и каждое такое решение было
локально разумным: модулю нужно место для журнала, SPI с поставляемой реализацией по умолчанию - это
идиоматичный ответ, а тот, кто писал шестой, не мог видеть остальные пять. В итоге получилось девять
SPI, семь реализаций на SLF4J, три постоянных хранилища с тремя разными схемами и три разных маркера
редактирования. Аудитор, спрашивающий "покажите всё, что этот человек делал в прошлый вторник", имел
девять мест для поиска, в трёх форматах, и одно из них существовало только в лог-файле, который уже
ротировали.

| Было | Стало |
|---|---|
| `ExportAuditSink` + `Slf4jExportAuditSink` | `AuditSink`; `ExportAuditEvent.toAuditEvent()` |
| `IngestAuditLogger` + `Slf4jIngestAuditLogger` | `AuditSink`; `IngestAuditEvent.toAuditEvent()` |
| `HotReloadAuditLogger` + `Slf4jHotReloadAuditLogger` | `AuditSink`; `HotReloadAuditEntry.toAuditEvent()` |
| `OutboxAuditLogger` + `Slf4jOutboxAuditLogger` | SPI сохранён (см. ниже); `OutboxTransitionAudit.toAuditEvent()` |
| `ReconciliationAuditLogger` + `Slf4jReconciliationAuditLogger` | `AuditSink`; `ReconciliationAuditEvent.toAuditEvent()` |
| `AuditEventEmitter` + `LoggingAuditEventEmitter` | `AuditSink`; `OutboundCallAudit.toAuditEvent()` |
| `AccessAuditLogger` + `Slf4jAccessAuditLogger` | `AuditSink`; `AccessDecision.toAuditEvent()` |
| `SettingsAuditRecorder`, писавший свою таблицу | вызывающая сторона `AuditSink` |
| `SecretRedaction`, `HeaderRedactor`, `SettingsRedaction` | четыре `SensitivityClassifier` + один `Redactor` |
| `AuditorProvider` из `db-core` | **без изменений**, но питается от того же `ActorResolver` |

## Два модуля, и почему

`audit-core` не зависит **ни от чего в этом репозитории**, и добавлять такую зависимость нельзя.

Модули, которым журнал нужнее всего, находятся ниже всех в стеке: `security-spring-boot-starter`
записывает решения авторизации, `rest-client-spring-boot-starter` - исходящие вызовы,
`hot-reload-spring-boot-starter` - перезагрузки конфигурации. Все три лежат ниже `db-core`. Реакторный
граф Maven игнорирует scope, поэтому даже `optional`- или `provided`-ребро отсюда к `db-core` стало бы
циклом в тот момент, когда аудит понадобился бы чему-либо выше `db-core`. Поэтому всё, что требует базы
данных, планировщика или outbox, живёт в [`audit-spring-boot-starter`](../audit-spring-boot-starter) -
это та же форма core/starter, которую репозиторий уже применяет для `db-core` и
`web-core-spring-boot-starter`.

Редактирование живёт здесь, в `ru.ludwigandreas.audit.redaction`, а не в третьем модуле, потому что этот
модуль уже гарантирует отсутствие внутренних зависимостей - а это единственное свойство, которое дал бы
отдельный `redaction-core`. Следствие стоит назвать, потому что оно выглядит странно, пока не знаешь
причины: модуль, импортирующий модуль *аудита* только ради пакета редактирования, - это задуманная схема,
а не ошибка. `observability-spring-boot-starter` именно так и делает, ради одного `Redaction.MASK`, чтобы
оператору не приходилось учить два маркера; `web-core-spring-boot-starter` может сделать то же для
маскирования problem-документа.

## Конверт

```java
public record AuditEvent(
        UUID id,                        // назначается при построении; ключ идемпотентности при отправке
        Instant occurredAt,
        String category,                // "export", "ingest", "access", "settings", "outbound-call", ...
        String action,                  // "run.completed", "access.denied", "setting.changed"
        Actor actor,                    // subject, principalType, displayName, onBehalfOf
        Resource resource,              // type, id, name
        AuditOutcome outcome,           // SUCCESS | FAILURE | DENIED | PARTIAL, + reason
        String correlationId,
        String traceId,
        Map<String, Object> attributes) // всё специфичное для модуля, уже отредактированное
```

Выведен из `AccessDecision` в `security-spring-boot-starter`, а не придуман заново: эта запись уже была
здесь самым близким к универсальному конвертом - субъект, тип ресурса, идентификатор ресурса, действие,
исход, причина.

Три правила действуют для каждого события в платформе.

**`attributes` редактируется при построении, никогда в приёмнике.** Правило началось в модуле
hot-reload, чей `AuditingSourceChangeListener` объяснил причину: редактирование "сознательно
применяется в точке построения записи аудита, а не оставляется каждой реализации логгера, чтобы
пользовательский логгер, пишущий в базу или отправляющий в SIEM, не мог про него забыть". Приёмник,
который *может* получить неотредактированное событие, - это приёмник, который однажды запишет его куда-то
навсегда.

**События модулей - подтипы по духу, а не замена.** `ExportAuditEvent`, `OutboundCallAudit`,
`AccessDecision`, `IngestAuditEvent` и `ReconciliationAuditEvent` сохраняют типизированную форму в точке
вызова - тринадцать компонентов, собранных позиционно, читаются, а тринадцать записей, положенных в
`Map<String, Object>`, нет - и каждая получила `toAuditEvent()`. Типизированная запись - это поверхность
авторства; `AuditEvent` - поверхность передачи и хранения.

**Никаких полезных нагрузок, никогда.** Правило, которое `AccessDecision` и `OutboundCallAudit`
формулировали каждый для себя, обобщено: журнал аудита хранится годами и читается людьми, которым не
положен доступ к данным, которые он охраняет, поэтому он записывает, *какой* объект затронут, и никогда -
что было внутри.

## Приёмники

```java
public interface AuditSink {
    void record(AuditEvent event);
}
```

Один метод, потому что "приёмник аудита, которому можно задавать вопросы, соблазнительно было бы и
читать, а журнал, который читает сама аудируемая система, - это журнал, который она однажды начнёт
фильтровать" (`ExportAuditSink`, когда он был одним из девяти). Чтение - это query API в стартере,
отдельный тип с отдельным набором вызывающих.

| Приёмник | Где | Что делает |
|---|---|---|
| `Slf4jAuditSink` | здесь | Одна структурированная строка на событие в логгер `ru.ludwigandreas.audit` |
| `NoopAuditSink` | здесь | Отбрасывает - для теста или развёртывания, маршрутизирующего иначе |
| `CompositeAuditSink` | здесь | Веером; несколько сразу - это нормальная конфигурация |
| `JpaAuditSink` | стартер | Таблица `audit_event`, только на добавление |
| `OutboxAuditSink` | стартер | Доставка в SIEM ровно один раз через транзакционный outbox |

Добавить этот модуль в сервис достаточно, чтобы получить работающий журнал:
`AuditCoreAutoConfiguration` связывает SLF4J-приёмник, композит и политику отказов без базы данных и без
планировщика. Это сделано намеренно - модуль ниже `db-core` не может взять стартер, и если бы связывание
жило только там, каждому такому модулю пришлось бы связывать приёмник самому, а именно так девять из них
и получили девять механизмов.

### Реализация *может* бросать исключение, и это новое

Каждый из семи заменённых SPI говорил "не должен бросать", и каждый был прав относительно тех событий,
которые несли. Старое правило всё равно было неверным как правило платформы, потому что делало
незаписанное изменение состояния молчаливой нормой.

Выживет ли вызывающая сторона, решает `AuditFailurePolicy`, применяемая `FailurePolicyAuditSink`,
которую любое связывание в платформе ставит перед настоящим приёмником:

| Категория | Политика по умолчанию | Почему |
|---|---|---|
| `settings` | `FAIL_OPERATION` | Изменение настройки или согласия, зафиксированное без строки аудита, - именно то, что журнал существует, чтобы сделать невозможным; и его запись уже идёт внутри транзакции вызывающего, так что переброс откатывает изменение, а не сообщает об изменении, которое осталось |
| всё остальное | `LOG_AND_CONTINUE` | Отказ запроса из-за сбоя записи аудита превращает сбой аудита в сбой сервиса, а операционная реакция на это неизменно - выключить журнал |

Модуль не должен оборачивать `record` своим `try`/`catch`. Это подменяет настроенную развёртыванием
политику политикой, зашитой в библиотеке. (`AuthorizationDeniedAuditListener` - единственное исключение в
платформе, и его javadoc объясняет: он защищает решение авторизации от *слушателя*, а не вызывающего от
приёмника.)

Каждый сбой доходит до `AuditSinkFailureListener` при любой политике, иначе приёмник с
`LOG_AND_CONTINUE`, падающий со времён изменения схемы, - это предупреждение в логе, которое никто не
читает, и первым заметит аудитор, спрашивающий, почему пропал месяц. Стартер связывает это со счётчиком
Micrometer.

## Редактирование

Две задачи, разделённые, потому что три заменённых реализации выглядели как три редактора, а были тремя
*классификаторами*, питающими одно действие маскирования:

| Классификатор | Правило | Откуда |
|---|---|---|
| `KeyNameSensitivityClassifier` | Имя ключа совпадает с шаблоном именования секретов | hot-reload |
| `ProvenanceSensitivityClassifier` | Значение вообще пришло из Vault, как бы ни называлось | hot-reload |
| `ConfiguredNamesSensitivityClassifier` | Развёртывание назвало его, сверка без учёта регистра | rest-client |
| `DeclaredSensitivityClassifier` | Определение говорит, что это персональные данные | user-settings |

Они **композируются объединением** - `SensitivityClassifier.anyOf` - и никогда порядком приоритета.
Значение, чувствительное по происхождению и безобидное по имени (ключ Vault с именем `timeout`),
чувствительно; и наоборот, безобидное по происхождению, но названное `client_secret`, тоже. Любое
правило, позволяющее одному классификатору снять флаг, поставленный другим, - это правило, которое
протекает; цена ошибки объединения - замаскированный таймаут в строке лога. Нужны все четыре: эвристика
находит секрет, который никто не настроил, настроенный список - единственное, что поймает учётные данные
в поле `x-partner-key`, а декларация - единственное, что знает, что поле `mobile` персональное.

`Redactor` - половина маскирования, и покрывает все формы, которые платформа записывает: скаляры, карты
атрибутов с рекурсивным обходом, мультикарты заголовков, **JSON-тела с обходом структуры** и
form-encoded тела, заменяемые целиком.

Структурный обход JSON принадлежал `HeaderRedactor` и сохранён целиком вместе с обоснованием, потому что
слияние по наименьшему общему знаменателю, сводящее всё к маскированию скаляров, было бы регрессом, а не
консолидацией:

> Редактирование тела структурно, а не текстуально. Регулярное выражение по сырому JSON также совпало бы
> со строкой `"password"`, встречающейся как *значение*, и пропустило бы поле, вложенное на три объекта
> вглубь. Разбор и обход дерева медленнее и правильны, и работают только когда вызывающий явно включил
> логирование тел - а это единственное место, где быть медленным и правильным очевидно верный выбор.

### Одна маска

`Redaction.MASK` - это `***REDACTED***`, и это `static final` без **какого-либо свойства, которое его
меняет**. Обе половины пришли из `SettingsRedaction`, чей аргумент был лучшей формулировкой решения по
безопасности в этом репозитории и ничто в нём не перестало быть верным:

> Фиксированный маркер, а не хеш и не усечение. Хеш обратим для любого значения из небольшого множества
> - а большинство настроек таковы, и номер телефона уж точно - а усечение раскрывает именно ту часть
> идентификатора, которая идентифицирует. Ни то, ни другое не стоит удобства отладки, которое даёт,
> потому что строка аудита уже записывает, какая настройка изменилась, когда и кем, а именно это в
> журнале и читают.
>
> Маркер сознательно не настраивается. Развёртывание, способное его изменить, могло бы выставить пустую
> строку, и тогда отредактированное значение и никогда не заданное становятся одной и той же строкой.

Выбор одного был **миграцией данных**, а не изменением константы: `[redacted]` не только логировался, он
**сохранялся** в `user_setting_audit.old_value` и `new_value`. Changeset `audit-004` переписывает эти
строки; без него таблица писала бы одно понятие двумя способами и никакой запрос не отличил бы
"отредактировано по старому правилу" от "пользователь, у которого значение настройки буквально строка
`[redacted]`". `****` и `***REDACTED***` только логировались и не требуют ничего.

Вторая константа-маска где-либо ещё в репозитории ломает сборку - правилом **Checkstyle**
(`SecondRedactionMask`), а не ArchUnit, потому что маска - это *значение* строковой константы, а ArchUnit
читает байт-код, где `JavaField` его не раскрывает. Парное правило про SPI аудита живёт в ArchUnit, где
имя и форма типа действительно структура. То же разделение труда, что и везде здесь:
`architecture-rules` владеет структурой, `checkstyle-rules` - текстом исходников.

## Один ответ на вопрос "кто действует"

Их было два. `SpringSecurityAuditorProvider` из `db-core` штамповал `created_by` / `last_modified_by` в
строки сущностей; рекордер аудита в `user-settings` вызывал `SecurityPrincipals.currentSubject()`. Когда
два пути к одному ответу расходятся, `last_modified_by` строки и событие аудита, описывающее это же
изменение, называют одного человека по-разному, и соединения, нужного аудитору, не существует.

`ActorResolver` теперь единственное разрешение, а штамповка полей в `db-core` питается от него через
`ActorResolverAuditorProvider` в стартере. **Сама штамповка не изменилась.** `AuditedEntity` и
`AuditorProvider` отвечают на вопрос "кто последним тронул эту строку", а это не журнал событий, и
складывание их вместе изменило бы маппинг каждой сущности платформы без выигрыша.

Три резолвера, от наиболее специфичного:

| Резолвер | Где | Когда выигрывает |
|---|---|---|
| `PrincipalActorResolver` | `security-spring-boot-starter` | `LudwigPrincipal` есть на classpath - только он умеет извлечь из него субъекта |
| `SpringSecurityActorResolver` | здесь | Spring Security есть, а `LudwigPrincipal` нет |
| `ActorResolver.unattributed()` | здесь | Нет ни того, ни другого - пакетный обработчик, тест; события тогда несут `Actor.system()` |

Все три сделаны взаимоисключающими **по classpath**, через `@ConditionalOnMissingClass` с именами классов
строками, а не упорядоченными по приоритету автоконфигураций. Это результат двух неудачных попыток, и обе
стоит знать, потому что ни одна о себе не заявляла:

- `@ConditionalOnClass` на **методе** `@Bean` был признан выполненным на classpath без Spring Security, и
  контекст затем не поднялся с `NoClassDefFoundError`. Условие должно быть на уровне *класса*, на вложенной
  `@Configuration`, чтобы класс, упоминающий резолвер, вообще не загружался.
- `@AutoConfiguration(afterName = ...)` с именем security-стартера **не** заставил его резолвер выиграть у
  бина, объявленного этим вложенным классом. Выигрывал более простой резолвер, `Authentication.getName()`
  на токене с `LudwigPrincipal` отвечал `toString()` объекта, и собственный идентификатор администратора
  молча превращался в `system` в каждом событии аудита - неверное значение в журнале, который хранится
  годами, а не ошибка.

Взаимное исключение по classpath невозможно испортить изменением порядка - поэтому оно и поставляется.
Развёртывание, которому нужно другое, публикует свой `ActorResolver`; все три ему уступают.

## Конфигурация

Все свойства под `ludwig.audit` и связываются одним классом `AuditProperties`, который живёт здесь, хотя
его блоки `jpa`, `outbox`, `retention` и `liquibase` описывают возможности, реализуемые только стартером.
Два класса `@ConfigurationProperties` на один префикс - это способ получить свойство, связанное в одном
из них и молча проигнорированное в другом; описание возможности не стоит этому модулю ни одной
зависимости.

```yaml
ludwig:
  audit:
    enabled: true
    source-system: ${spring.application.name}      # записывается как автор каждой строки
    slf4j:
      enabled: true
    failure:
      default-policy: LOG_AND_CONTINUE
      by-category:
        settings: FAIL_OPERATION
    redaction:
      key-name-heuristic: true
      key-name-pattern:                            # заменяет поставляемый
      sensitive-provenance-prefixes: [ "vault:", "vault-lease:" ]
      sensitive-names: [ ]                         # всегда чувствительные ключи, поля, заголовки
```

*Шаблон* редактирования настраивается там, где *маска* - нет. Асимметрия намеренна: расширять то, что
считается чувствительным, всегда безопасно.

## Что делает модуль

```java
// 1. Сохраните свою типизированную запись. Добавьте toAuditEvent().
public record ExportAuditEvent(UUID runId, RunStatus status, ...) {
    public AuditEvent toAuditEvent() {
        return AuditEvent.builder()
                .category(AuditCategories.EXPORT)
                .action("run." + status.name().toLowerCase(Locale.ROOT))
                .actor(principalId == null ? Actor.system() : Actor.of(principalId))
                .resource(new Resource(RESOURCE_TYPE, runId.toString(), definitionKey))
                .outcome(degradedStages.isEmpty() ? AuditOutcome.success()
                        : AuditOutcome.partial("degraded stages: " + ...))
                .correlationId(correlationId)
                .attributes(attributes)
                .build();
    }
}

// 2. Внедрите AuditSink. Не объявляйте SPI, не перехватывайте, не оборачивайте.
audit.record(new ExportAuditEvent(...).toAuditEvent());
```

## Вне области, как решение

**Хеш-цепочка или подпись для доказательства неизменности.** Это настоящая возможность, и она
сознательно не построена наполовину. Ей нужны управление ключами и инструмент проверки, чтобы что-то
значить, а половина - цепочка, которую никто не проверяет - хуже, чем ничего, потому что выглядит как
гарантия. Стартер заявляет другое: принудительный append-only - ни один путь в коде не обновляет строку и
ни один не удаляет её вне очистки по retention, причём `SnapshotImmutabilityListener` из `db-core`
отклоняет попытку, а не соглашение вежливо просит.

**Проверку того, что модуль аудирует то, что должен.** "Каждое изменение состояния порождает событие"
требует знать, какие методы меняют состояние, а это семантическое суждение, которого не сделает никакое
структурное правило. Правило ArchUnit проверяет то, что *является* структурой: что когда модуль
аудирует, он аудирует через этот тип.
