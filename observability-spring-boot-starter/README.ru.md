# observability-spring-boot-starter

*[English](README.md) · **Русский***

Основа наблюдаемости, на которой стоит каждый сервис в этом репозитории: распределённая трассировка с
экспортом по OTLP, единый correlation id, проходящий через HTTP и Kafka и попадающий в каждую строку
лога, структурированные JSON-логи с trace-, span- и correlation-идентификаторами, RED-метрики на
каждом HTTP-эндпоинте с ограниченной кардинальностью тегов, разделённые liveness и readiness, а также
уровни логирования, которые меняются без перезапуска.

Достаточно добавить зависимость — и сервис собран так же, как любой другой сервис в контуре: без
`@Bean` для сэмплера, без `logback-spring.xml`, без фильтра, копирующего заголовок в MDC, и без
`MeterFilter`, защищающего от взрыва кардинальности, о котором никто не вспомнил.

## Быстрый старт

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>observability-spring-boot-starter</artifactId>
    <version>1.0.0</version>
</dependency>
```

Укажите коллектор. Это и есть вся настройка:

```yaml
spring:
  application:
    name: product-catalog

management:
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
  tracing:
    sampling:
      probability: 0.1
```

Теперь запрос порождает такую строку лога — один JSON-объект, уже разобранный на поля:

```json
{"@timestamp":"2026-09-16T09:12:13.481Z","log.level":"INFO","log.logger":"com.example.OrderService",
 "process.thread.name":"http-nio-8080-exec-3","message":"order 4711 accepted",
 "trace.id":"0af7651916cd43dd8448eb211c80319c","span.id":"b7ad6b7169203331",
 "correlation.id":"0af7651916cd43dd8448eb211c80319c","service.name":"product-catalog",
 "service.version":"1.4.2","service.environment":"prod","service.node.name":"catalog-7d9f-xk2",
 "labels":{"tenant":"acme"}}
```

такой ответ:

```console
$ curl -i -H 'X-Correlation-Id: order-4711' localhost:8080/api/v1/orders/4711
HTTP/1.1 200
X-Correlation-Id: order-4711
X-Trace-Id: 0af7651916cd43dd8448eb211c80319c
```

и такие метрики — размеченные идентичностью сервиса и ограниченные по построению:

```
http_server_requests_seconds_bucket{service="product-catalog",environment="prod",version="1.4.2",
  uri="/api/v1/orders/{id}",method="GET",status="200",outcome="SUCCESS",le="0.1"} 412
```

## Какую проблему этот стартер убирает

Каждый из шести пунктов ниже — это то, что каждый сервис выводил заново, и выведенные решения между
собой не совпадали. Дорого обходится именно это: не сама работа, а то, что в контуре оказывается
четыре написания заголовка с correlation id, три формы лога, два имени одного и того же сервиса и
частота сэмплирования, которую нельзя поменять без выкатки.

**Три столпа ничем не были связаны.** Метрики Micrometer по модулям существовали — и это всё. От
медленного эндпоинта на дашборде нельзя было перейти к трассе, а от трассы — к логам, потому что между
ними не было общего идентификатора. Этот модуль делает trace id полем лога, correlation id — тегом
спана, а идентичность сервиса — одной и той же строкой во всех трёх сигналах.

**Каждый сервис изобретал свою корреляцию.** Обычно это был фильтр, копирующий `X-Request-Id` в MDC,
обычно без валидации, обычно забывающий восстановить MDC после запроса — и всегда обрывающийся на
первом исходящем вызове. Через Kafka идентификатор не проходил вовсе.

**Логи были текстом.** Pattern layout приходится разбирать обратно регулярным выражением, которое
живёт в другом месте и ломается в первый же раз, когда в сообщении встретится перевод строки — то
есть в первый же раз, когда что-нибудь залогирует стектрейс.

**Liveness и readiness были одним эндпоинтом.** Сервис, потерявший базу, — *не готов*, но совершенно
*жив*; отвечая на обе пробы одним агрегатом, он заваливал и liveness, и Kubernetes перезапускал его по
кругу, что базу починить не могло никак.

**Кардинальность метрик ничем не ограничивалась.** `http.server.requests` размечается шаблоном URI и
потому безопасен — ровно до первого запроса, который не сопоставился ни с одним обработчиком и внёс
свой сырой путь. Дальше сканер уязвимостей разгоняет количество временных рядов, пока реестр не съест
всю кучу.

**Смена уровня логирования означала перезапуск.** То есть уничтожение того самого процесса, в котором
воспроизводился симптом.

## Что вы получаете из коробки

| Область | Что настроено | Почему это не поведение фреймворка по умолчанию |
|---------|---------------|--------------------------------------------------|
| Трассировка | Экспортёр OTLP, распространение W3C, parent-based сэмплирование по доле | Boot даёт механику; выбор, единый для всего контура, остаётся на вас |
| Переопределение сэмплирования | `X-Ludwig-Force-Trace` заставляет протрассировать один запрос | Без своего `Sampler` невозможно в принципе |
| Гигиена спанов | Серверные спаны `/actuator/**` отбрасываются на экспорте | Иначе пробы в бэкенде численно перевешивают реальный трафик |
| Корреляция | Один id на входящем и исходящем HTTP, на входящем и исходящем Kafka и в MDC | В Spring Boot отсутствует полностью |
| Логи | JSON, наборы полей ECS/OTel/flat, маскирование, усечение | В Boot 3.3 структурированного логирования нет |
| Метрики | Теги идентичности, ограничение кардинальности URI, SLO-гистограмма, исключение путей проб | Boot убрал `max-uri-tags`; остального там не было никогда |
| Аннотации | `@Timed`, `@Counted`, `@Observed` действительно работают | Micrometer поставляет аспекты и не регистрирует ни одного |
| Пробы | Liveness и readiness разделены, graceful shutdown | В Boot выключено по умолчанию |
| Уровни логов | `logging.level.*` применяются из отслеживаемого файла или секрета Vault | Иначе нужен перезапуск либо вызов actuator в каждой реплике |

## Correlation id против trace id

Это не одно и то же, и одно не заменяет другое.

**Trace id** идентифицирует одно распределённое исполнение. Он существует, только когда трассировка
включена и только если запрос попал в выборку — при доле сэмплирования 10% у 90% запросов пригодного
trace id нет вообще.

**Correlation id** идентифицирует единицу *бизнес*-работы. Он есть у 100% запросов, потому что его
никогда не отсекает сэмплирование, он переживает повтор, который получает собственную новую трассу, и
его может прислать вызывающая сторона, связав работу, о которой этот сервис ничего не знает.

Отсюда и разделение: поддержка называет correlation id, инженеры открывают trace id, а когда запрос
приходит без correlation id, эти два значения намеренно делаются равными — trace id принимается за
correlation id, и тогда любое из двух значений можно вставить в любой из двух инструментов.

### Как он путешествует

| Переход | Механизм |
|---------|----------|
| Входящий HTTP | `X-Correlation-Id`, затем `X-Request-Id`, затем trace id, затем сгенерированный |
| Исходящий HTTP | Добавляется в каждый `RestTemplate`, собранный из автоконфигурированного билдера |
| Исходящий Kafka | Заголовок записи, добавляется обёрткой над управляемой Spring фабрикой продюсеров |
| Входящий Kafka | Читается из заголовка записи в MDC на время работы слушателя |
| Логи | Ключ MDC `correlationId`, публикуется отдельным полем JSON |
| Трассы | Тег спана `correlation.id`, чтобы id из тикета находил трассу |
| Ответ | Заголовки `X-Correlation-Id` и `X-Trace-Id` |

Входящие значения считаются недоверенным вводом, потому что таковыми и являются. Значение длиннее
лимита или содержащее что-либо вне `[A-Za-z0-9_.:-]` **заменяется целиком**, а не чинится: `\r\n`,
дошедший до заголовка ответа, — это уязвимость расщепления ответа, а значение без ограничения длины
умножает объём логов одного запроса на то число, которое выбрал вызывающий.

## Структурированное логирование

**JSON включён по умолчанию.** Это осознанное и слегка спорное решение: стартер, у которого
структурированное логирование надо включать, — это стартер, включить который забудет каждый сервис.
Цена ложится на разработчика, читающего консоль локально, поэтому в профиле `local` шаблона сервиса
должно стоять:

```yaml
ludwig:
  observability:
    logging:
      json:
        enabled: false
```

Выберите набор полей, который ваш агрегатор уже понимает, — и сопоставление на приёме не понадобится:

| `field-set` | Имена | Для чего |
|-------------|-------|----------|
| `ecs` (по умолчанию) | `@timestamp`, `log.level`, `trace.id` | Elasticsearch, OpenSearch |
| `otel` | `Timestamp`, `SeverityText`, `TraceId` | Коллектор OpenTelemetry |
| `flat` | `timestamp`, `level`, `trace_id` | Loki и стеки без собственной схемы |

Энкодер устанавливается до того, как приложение что-либо залогирует: он срабатывает сразу после
инициализации системы логирования в Spring Boot, поэтому баннер, список профилей, миграции Liquibase и
любая ошибка на старте уже идут в JSON. Смена формата позже оставила бы поток, наполовину состоящий из
текста и наполовину из JSON, — а большинство шипперов обрабатывают это, выбрасывая ту половину, под
которую они не настроены.

### Работа с MDC

Записи MDC по умолчанию вкладываются в объект `labels`. Если их разложить на верхний уровень,
прикладной ключ с именем `message` или `service.name` перезапишет структурное поле с тем же именем — а
в Elasticsearch ключ, тип значения которого расходится с типом в маппинге, портит шаблон индекса для
всех сервисов, пишущих в этот индекс.

MDC — открытая карта, поэтому всё, что туда когда-либо кладут, попадает в каждую последующую строку
этого потока. Если сервис складывает туда данные уровня запроса, задайте список разрешённых ключей:

```yaml
ludwig:
  observability:
    logging:
      json:
        mdc-include-keys: [tenant, correlationId, traceId, spanId]
```

Значения, в ключе которых встречается `password`, `secret`, `token`, `credential`, `authorization` или
`apikey`, заменяются на `***`. Это подстраховка, а не средство защиты — секретам вообще не место в
MDC, — но агрегатор логов худшее место, где можно об этом узнать, поскольку это единственная система, в
которой ищет вся компания.

### Структурированные аргументы

Пары «ключ-значение» из SLF4J 2.x становятся полями верхнего уровня и маскируются по тем же правилам:

```java
log.atInfo().addKeyValue("orderId", id).addKeyValue("amount", total).log("order accepted");
```

## RED-метрики

Метрика — `http.server.requests`; этот модуль добавляет всё то, что делает её безопасной и пригодной
для агрегации.

**Ограничение кардинальности — самая важная настройка здесь.** Сверх `max-uri-tags` различных URI
последующие записываются как `OTHER`, а не отбрасываются, поэтому количество запросов и доля ошибок
остаются верными, а тег перестаёт расти:

```yaml
ludwig:
  observability:
    metrics:
      http:
        max-uri-tags: 100
```

**Гистограммы, а не перцентили на стороне клиента.** Micrometer умеет считать p99 внутри процесса; это
число верно для одной реплики и лишено смысла после агрегации, потому что среднее из p99 четырёх
реплик — не p99 всего кластера, и смещено оно *вниз*, то есть скрывает инциденты. Вместо этого
экспортируются корзины, а перцентиль считается на этапе запроса:

```yaml
ludwig:
  observability:
    metrics:
      http:
        slo: [50ms, 100ms, 200ms, 500ms, 1s, 2s, 5s, 10s]
```

Идентичность добавляется общими тегами, а не оставляется скрейперу, потому что `job` и `instance` —
это точка зрения цели скрейпа: их нет у всего, что отправляется push-ом, они теряются при федерации
рядов в центральное хранилище и они не несут версии — так что вопрос «p99 сдвинулся из-за релиза?»
задать вообще невозможно.

## Трассировка одного конкретного запроса

При доле сэмплирования 10% с подавляющей вероятностью запрос, на который только что пожаловался
пользователь, в выборку не попал. Обычные способы это исправить — поднять общую долю, то есть
увеличить затраты на весь контур и выкатить изменение, — либо попросить пользователя повторять попытку,
пока не повезёт.

Вместо этого:

```console
$ curl -H 'X-Ludwig-Force-Trace: true' https://catalog.internal/api/v1/orders/4711
```

**По умолчанию это выключено и требует явного согласия**, потому что любой, кто может выставить этот
заголовок, может заставить сервис трассировать 100% своего трафика в бэкенд с тарификацией за спан:

```yaml
ludwig:
  observability:
    tracing:
      sampling:
        trusted-force-header: true   # только там, где периметр срезает или авторизует заголовок
```

Переопределение действует только там, где трасса *начинается*. Запрос, пришедший с решением о
сэмплировании от вызывающей стороны, это решение сохраняет: переопределение записало бы потомка,
родитель которого никогда не экспортировался, и трасса выглядела бы начинающейся с середины цепочки
вызовов.

## Уровни логирования без перезапуска

Если на classpath есть [`hot-reload-spring-boot-starter`](../hot-reload-spring-boot-starter/README.md),
ключи `logging.level.*` из отслеживаемого файла или секрета Vault применяются к работающей системе
логирования:

```yaml
ludwig:
  hotreload:
    files:
      - path: /etc/config/logging.yml
```

```yaml
# /etc/config/logging.yml — правится во время инцидента: без перезапуска, без потери состояния
logging:
  level:
    com.example.payments: DEBUG
```

Удаление ключа **возвращает логгеру уровень, который был у него на старте**. Без этого реальная
последовательность такова: кто-то в три часа ночи поднимает болтливый пакет до DEBUG, на следующий день
удаляет строку — и сервис продолжает писать на DEBUG, в полном объёме, в тарифицируемый конвейер, до
следующего перезапуска, который может случиться через несколько недель. Симптомом будет счёт за логи, и
ничто не укажет на причину.

## Пробы

Liveness и readiness разделены, и в этом разница между корректной выкаткой и циклом перезапусков.
Сервис, потерявший базу, *не готов* и при этом совершенно *жив*; ответ на обе пробы из одного агрегата
приводит к тому, что его убивают и перезапускают по кругу, а базу это починить не может.

```console
$ curl localhost:8080/actuator/health/liveness    # процесс завис? перезапусти меня
$ curl localhost:8080/actuator/health/readiness   # могу обслуживать? направляй трафик
```

Graceful shutdown включён с окном в 30 секунд, чтобы запросы в обработке завершались, а не обрывались
посреди ответа: иначе рядовая выкатка выглядит как всплеск 502 на стороне клиентов, неотличимый от
настоящего инцидента.

`management.endpoints.web.exposure.include` по умолчанию равен `health,info,metrics,prometheus,loggers`.
`env`, `configprops`, `heapdump` и `threaddump` исключены намеренно: они раскрывают учётные данные и
содержимое памяти, и стартер не должен становиться причиной того, что они стали доступны.

## Конфигурация

Всё перечисленное ниже — *значения по умолчанию*, публикуемые как источник свойств с самым низким
приоритетом. Любое значение, заданное в `application.yml`, переменной окружения или системным
свойством, побеждает, и сервису для этого не нужно знать о существовании этого модуля.

| Свойство | По умолчанию | Примечание |
|----------|--------------|------------|
| `ludwig.observability.enabled` | `true` | Главный выключатель |
| `ludwig.observability.service.name` | `${spring.application.name}` | Проставляется одинаково в метрики, спаны и логи |
| `ludwig.observability.service.version` | манифест jar | `Implementation-Version`, иначе `build.version` |
| `ludwig.observability.service.environment` | первый активный профиль | Догадка; в деплое задавайте явно |
| `ludwig.observability.service.instance` | `$HOSTNAME` | В Kubernetes — имя пода |
| `ludwig.observability.tracing.excluded-paths` | `/actuator/**` | Отбрасывается на экспорте, не на сэмплировании |
| `ludwig.observability.tracing.sampling.trusted-force-header` | `false` | См. выше — включайте осознанно |
| `ludwig.observability.correlation.header-name` | `X-Correlation-Id` | |
| `ludwig.observability.correlation.additional-inbound-headers` | `[X-Request-Id]` | Проверяются по порядку |
| `ludwig.observability.correlation.max-length` | `128` | Не положительное значение — ошибка на старте |
| `ludwig.observability.correlation.allowed-pattern` | `[A-Za-z0-9_.:-]+` | Не подходящие значения заменяются |
| `ludwig.observability.logging.json.enabled` | `true` | Выключайте в профиле `local` |
| `ludwig.observability.logging.json.field-set` | `ecs` | `ecs`, `otel` или `flat` |
| `ludwig.observability.logging.json.max-message-length` | `16384` | `0` отключает усечение |
| `ludwig.observability.logging.levels.revert-on-removal` | `true` | |
| `ludwig.observability.metrics.http.max-uri-tags` | `100` | Отрицательное значение — ошибка на старте |
| `ludwig.observability.metrics.http.slo` | `50ms…10s` | Те задержки, которые вы действительно обещаете |

Везде, где у Spring Boot уже есть своё свойство, используется именно оно —
`management.tracing.sampling.probability`, `management.otlp.tracing.endpoint`, `management.endpoints.*`.
Этот модуль никогда не вводит второе имя для ручки, у которой имя уже есть.

## Чего он намеренно не делает

- **Не заменяет трассировку Spring Boot.** Экспортёр, пропагаторы, мост Micrometer и процессор спанов —
  всё это Boot. Этот модуль настраивает её под контур; добавляет он ровно то, о чём у Boot нет мнения.
- **Не инструментирует WebClient.** Реактивного стека нет на classpath этого модуля. Trace-контекст
  по-прежнему распространяется собственной инструментацией Boot; заголовок correlation id — нет, для
  него нужен `ExchangeFilterFunction`, читающий `CorrelationContext`.
- **Не перехватывает продюсеров, созданных вне управляемой Spring фабрики.** У кода, который сам
  конструирует `KafkaProducer`, нет точки подключения; ему следует читать
  `CorrelationContext.currentId()` и выставлять заголовок самостоятельно.
- **Не экспортирует логи по OTLP.** Логи идут в stdout как JSON, чтобы их забрал агент на узле, — так
  устроен любой существующий конвейер логов в Kubernetes.

## Связь с остальными модулями

- [`web-core-spring-boot-starter`](../web-core-spring-boot-starter/README.md) — получает от этого модуля
  реализацию `TraceIdProvider`, поэтому `traceId` в документе RFC 9457 — это идентификатор того спана,
  который был в области видимости в момент отказа, а не то, что оказалось в некотором ключе MDC.
- [`hot-reload-spring-boot-starter`](../hot-reload-spring-boot-starter/README.md) — через свой SPI
  наблюдателя обеспечивает смену уровней логирования на лету.
- Обе зависимости **опциональны**. Стартер работает и без любой из них.

## Замечание по сборке

В отличие от большинства модулей здесь, actuator, мост трассировки, экспортёр OTLP и реестр Prometheus
**не** являются опциональными зависимостями. Стартер, экспортёр которого приходится собирать в каждом
сервисе, возвращает эту сборку в каждый pom — то самое дублирование, ради устранения которого модуль и
существует. Деплой, который экспортирует иначе, исключает ненужное: одно задокументированное исключение
в одном месте вместо пяти правильных зависимостей в пятидесяти pom-файлах.

Точки интеграции — Spring MVC, Spring Kafka, web-core, hot-reload — все опциональны, поэтому батч-воркер
без сервлет-контейнера и без брокера всё равно получает метрики, логи и трассы, не получая при этом ни
того, ни другого.
