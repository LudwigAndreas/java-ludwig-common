# common-utils

*[English](README.md) · **Русский***

Общие вспомогательные средства платформы. На сегодня это одна вещь: обёртка повторов для вызовов,
которые падают так, что повторить стоит.

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>common-utils</artifactId>
</dependency>
```

```java
Charge charge = RetryingCall
        .with(new RetryPolicy()
                .retryOn(SocketTimeoutException.class, ConnectException.class)
                .withMaxRetries(3)
                .withDelay(200, TimeUnit.MILLISECONDS)
                .withIncreasingDelay(true))
        .withMetrics(meterRegistry, "payment-gateway-charge")
        .get(() -> gateway.charge(request));
```

---

## Что сюда относится, а что нет

Это единственный модуль платформы вообще без предметной области: ни Spring, ни JPA, ни веб-стека, ни
представления о том, что такое сервис. Единственная его зависимость — опциональный Micrometer, и так и
останется намеренно: модуль, от которого может зависеть любой другой модуль, не должен тянуть за собой
ничего.

Поэтому планка для добавления сюда высокая. Помощник уместен здесь, если он действительно общего
назначения **и** ему негде больше жить. Всё, что знает про хранение, — в `db-core`, всё про HTTP — в
`web-core-spring-boot-starter`, всё про идентичность — в `security-spring-boot-starter`. «Utils» — не
категория; так называется модуль, для содержимого которого никто не решил, куда его деть, и
единственный способ этого избежать — держать модуль таким, чтобы его можно было прочитать за один
присест.

## Повтор вызова

Два типа. `RetryPolicy` говорит, **когда** повторять и **сколько** ждать; `RetryingCall` выполняет
операцию по этой политике.

### Политика

| Метод | Действие |
|---|---|
| `retryOn(Class…)` | повторять, когда вызов бросает это исключение или его наследника |
| `retryIf(Predicate<Throwable>)` | повторять, когда так решит предикат — для «на этот HTTP-статус да, а на тот нет» |
| `retryOnResult(Predicate<Object>)` | повторять при **успешном** возврате с неудовлетворительным значением |
| `withMaxRetries(int)` | попытки **после** первой; `0` (по умолчанию) означает «без повторов» |
| `withDelay(long, TimeUnit)` | фиксированная пауза между попытками |
| `withIncreasingDelay(boolean)` + `withDelayFactor(double)` | экспоненциальный backoff, коэффициент по умолчанию `2.0` |
| `withMaxDelay(long, TimeUnit)` | потолок, чтобы экспонента не убежала |
| `enabled(boolean)` | выключить повторы, не разбирая место вызова |

`retryOnResult` стоит пояснить. Масса API сообщает о неуспехе возвращаемым значением, а не
исключением: пустое тело, поле статуса, `null` из ещё не прогретого кэша, — и без этого метода у
каждого такого места вызова вырастает рукописный цикл. С ним «повторять, пока ответ не станет
пригодным» — такая же однострочная запись, как «повторять, пока вызов падает».

**По умолчанию не повторяется ничего.** У свежей `RetryPolicy` `maxRetries = 0` и пустой список
повторяемых исключений, поэтому обёртывание вызова без настройки политики ничего не меняет. Это
намеренно: опасное умолчание здесь — щедрое. Повтор неидемпотентного вызова превращает одно двойное
списание в четыре, и обёртка, делающая это без явного указания, была бы ловушкой.

### Выполнение

```java
RetryingCall.with(policy).run(() -> sink.publish(event));          // без результата
RetryingCall.with(policy).get(() -> client.fetch(id));             // с результатом
RetryingCall.with(policy).call(() -> callable.call());             // java.util.concurrent.Callable
```

Все три принимают лямбду, которая может бросить проверяемое исключение, — именно это позволяет
обернуть те вызовы, которым повторы и нужны, без `try`/`catch` в каждом месте.

### Что бросается наружу

Неповторяемая ошибка или ошибка, пережившая все попытки, пробрасывается **как есть**.
`RuntimeException` возвращается неизменным; проверяемое исключение заворачивается в
`RuntimeException` с числом попыток в сообщении. Обёртка ничего не проглатывает и не подставляет
значение по умолчанию: помощник, возвращающий `null` после исчерпания попыток, превратил бы громкий
отказ в `NullPointerException` где-то совсем в другом месте.

Исчерпание попыток на предикате **результата** — все вызовы успешны, ни один не вернул приемлемого
значения — бросает `RetryExhaustedException`: пробрасывать нечего, а возврат последнего
неудовлетворительного значения выглядел бы как успех.

Ловится `Throwable`, включая `Error`, а не `Exception`. Обёртка общего назначения обязана **видеть**
всё, что может произвести обёрнутый вызов; дальше политика решает, что повторяемо, а неповторённое
пробрасывается, а не проглатывается. Сужение catch позволило бы `Error` пройти мимо слушателя и
метрик по пути наружу — ровно тогда, когда оператор больше всего хочет его увидеть.

### Прерывание

Прерывание во время паузы backoff восстанавливает флаг прерывания потока и бросает исключение. Оно не
проглатывается с продолжением сна — именно так штатное завершение превращается в зависание.

## Наблюдаемость

Инструментирование подключается явно, а Micrometer — опциональная зависимость: вызов без
`withMetrics(...)` не публикует ничего, а сервис без Micrometer в classpath всё равно собирается.

| Метрика | Тип | Теги |
|---|---|---|
| `retry.attempts` | счётчик, +1 на каждую попытку | `operation` |
| `retry.call` | таймер, одна запись на вызов | `operation`, `outcome` (`success`/`failure`), `exception` |

`operation` — имя, которое передаёте вы, то есть ограниченный серверный словарь, а не то, чем
управляет вызывающая сторона. Пара метрик делает отвечаемым полезный вопрос: `retry.attempts`,
делённое на число `retry.call`, — это среднее число попыток на операцию, и его рост является самым
ранним предупреждением о деградации зависимости, задолго до того, как она начнёт падать совсем.

`RetryListener` закрывает то, чего метрики не дают:

```java
RetryingCall.with(policy)
        .withListener((attempt, exception, result) ->
                log.warn("Повтор {} вызова списания", attempt, exception))
        .get(() -> gateway.charge(request));
```

Он вызывается **перед** каждым повтором и получает либо исключение, либо неудовлетворительный
результат, который повтор вызвал, — но никогда оба сразу.

## Сборка и тесты

```bash
mvn -pl common-utils test
```

Семь тестов: решения политики (какие исключения, какие результаты, как растёт задержка и где она
упирается в потолок), поведение обёртки при пробросе и метрики — проверяемые против
`SimpleMeterRegistry`, а не мока, чтобы значения тегов были теми же, что увидел бы дашборд.
