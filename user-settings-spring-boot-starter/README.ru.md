# user-settings-spring-boot-starter

*[English](README.md) · **Русский***

Платформенный движок пользовательских настроек, предпочтений и согласий — тех данных, которыми
OIDC-провайдер не владеет. Модуль даёт хранилище, послойное разрешение значений, кэш, валидацию, журнал
изменений и реестр согласий; потребляющий сервис даёт **перечень самих настроек** — типизированными
константами в собственном коде.

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>user-settings-spring-boot-starter</artifactId>
</dependency>
```

```java
public final class AccountSettings {

    public static final SettingDefinition<ZoneId> TIMEZONE = SettingDefinition
            .of("user.timezone", ZoneId.class)
            .defaultValue(ZoneId.of("UTC"))
            .category("locale")
            .userEditable(true)
            .build();
}

@Bean
SettingDefinitionSource accountSettings() {
    return SettingDefinitionSource.of(AccountSettings.TIMEZONE);
}
```

```java
ZoneId zone = settings.get(PrincipalRef.user(subject), AccountSettings.TIMEZONE);
```

## Ограничение, ради которого модуль устроен именно так

Движок настроек должен быть переиспользуем на платформах с совершенно разными наборами настроек.
Очевидный путь к этому — сделать схему данными: таблица ключей, типов и значений по умолчанию,
редактируемая в рантайме. Именно так сервис настроек и превращается в EAV-хранилище, которое уже никто не
отрефакторит: каждый ключ — строковый литерал, каждое значение в точке вызова нетипизировано,
переименование — это поиск и надежда, а удаление вообще непроверяемо.

**Поэтому схема — это код, а общим остаётся только движок.** `SettingDefinition<T>` — артефакт времени
компиляции того сервиса, который его объявил: на него ссылаются, а не пишут строкой, он типизирован в
каждой точке вызова, виден в «найти использования» и переименовывается рефакторингом. Хранилище под ним
остаётся универсальным — значение это текст плюс дискриминатор типа, преобразуемый на границе через
`SettingValueConverter`, — и такой размен допустим **только потому, что по значению настройки никто не
джойнит, не фильтрует и не строит отчёты**. Индекса на колонке значения нет и не будет. Не переносите
этот приём на данные, по которым кто-то отчитывается.

Цена честная: добавление настройки требует деплоя объявившего её сервиса. Взамен ни один сервис никогда
не получит настройку, которой он не понимает.

## Два режима, один интерфейс чтения

Сервис, который настройки *читает*, обычно не тот же, что ими *владеет*, и общей базы у них нет.

| | Режим владельца | Режим проекции |
|---|---|---|
| Владеет таблицами | да | держит реплику |
| `SettingsLookup` | да | да — тот же интерфейс |
| `SettingsWriter` | да | **бина нет вовсе** |
| `ConsentService` | чтение и запись | только чтение |
| Публикует события | через транзакционный outbox | нет |
| Потребляет события | нет | да |

```yaml
# Сервис учётных записей, который ими владеет
ludwig.user-settings.owner.enabled: true

# Сервис уведомлений, который их читает
ludwig.user-settings.projection.enabled: true
```

Ни один режим не включён по умолчанию, и сервис обязан назвать свой. Разумного умолчания здесь нет:
предположить владельца — значит заставить читающий сервис писать в чужие таблицы, а предположить проекцию
— молча отклонять каждую запись во владеющем сервисе. Включение обоих сразу — ошибка старта.

Поскольку оба режима публикуют один и тот же `SettingsLookup`, потребляющий сервис пишется один раз и не
знает, в каком режиме работает: перевод его из одного в другой — изменение конфигурации.

`SettingsWriter` в режиме проекции намеренно **отсутствует**, а не присутствует и бросает исключение. Код,
который его инжектит, не поднимется в неверном режиме — вместо того чтобы упасть на первом пользователе,
попытавшемся сохранить предпочтение.

## Разрешение значения

Пять слоёв, от самого частного к самому общему:

```
USER  →  ROLE  →  TENANT  →  PLATFORM  →  DEFAULT
```

| Слой | Откуда берётся | Кто задаёт |
|---|---|---|
| `USER` | строка для субъекта | сам субъект или администратор |
| `ROLE` | строка на каждую роль субъекта | администратор |
| `TENANT` | строка тенанта либо значение из конфигурации | администратор / конфигурация |
| `PLATFORM` | только конфигурация — чтобы поддавалась горячей перезагрузке | эксплуатация |
| `DEFAULT` | сам `SettingDefinition` | разработчик |

Каждое разрешённое значение сообщает, **какой слой его дал**:

```java
ResolvedValue<ZoneId> zone = settings.getAll(ref).resolved(AccountSettings.TIMEZONE);
zone.value();    // Europe/Moscow
zone.layer();    // TENANT
zone.scopeId();  // acme
```

Голое значение отвечает на вопрос «какой у пользователя часовой пояс» и не отвечает на вопрос «почему» —
а именно его задают и экран настроек («унаследовано от организации»), и инженер, разбирающий обращение.

**Порядок внутри слоя ролей — это политика**, отданная `SettingScopeResolver`: у пользователя с тремя
ролями, каждая из которых задаёт один и тот же ключ, побеждает та роль, которую резолвер вернул первой.
Поставляемый резолвер сохраняет порядок, полученный от `AuthorityLookup`. «По алфавиту» и «самая
разрешающая» одинаково защитимы и ни одна не универсальна, поэтому движок не выбирает за вас.

### `getAll` — это один запрос

```java
ResolvedSettings all = settings.getAll(ref);   // один запрос к настройкам, все настройки
```

Набор областей — субъект, каждая его роль, тенант, платформа — вычисляется **до** обращения к данным,
поэтому источники спрашиваются один раз обо всех сразу. Наивная реализация, идущая по слоям до первого
попадания, даёт запрос на слой на настройку; этот N+1 и был бы главным дефектом производительности
модуля, и SPI `SettingValueSource` устроен так, что выразить его нельзя.

`get(ref, definition)` идёт по тому же пути, поэтому чтение пяти настроек подряд или одной настройки в
цикле по получателям всё равно стоит один запрос. Есть интеграционный тест, который считает JDBC-statement
и требует ровно одного.

Уточнение, что именно считается «одним»: **один запрос к таблицам настроек**. Слой ролей спрашивает у
`AuthorityLookup`, какие роли есть у субъекта, и в инсталляции, где роли лежат в базе, это второй запрос —
отдаваемый из кэша прав на любом прогретом запросе и уже сделанный авторизацией самого запроса. Модуль
настроек своих запросов к нему не добавляет.

**Используйте `getAll`, когда нужна больше чем одна настройка одного субъекта** — страница, веерная
рассылка, выгрузка.

### Ограничение по тенанту обязательно

Поиск никогда не пересекает границу тенанта, и перегрузки, способной выполниться без ограничения, не
существует:

- у каждой хранимой строки `tenant_id` не-nullable, поэтому предикат — обычное равенство, а не
  `tenant = ? OR tenant IS NULL`;
- `SettingsSubject` — внутренний ключ — невозможно сконструировать без тенанта;
- поиск, для которого тенант определить не удалось, **отклоняется** (`TenantUnresolvableException`), а не
  выполняется без ограничения;
- администратор читает в границах **своего** тенанта, а не тенанта цели, поэтому межтенантное чтение
  ничего не находит, а не находит данные и лишь затем получает отказ;
- кэш ключуется по субъекту **и** тенанту, поэтому ответ одного тенанта никогда не отдаётся другому.

Код вне запроса — воркер очереди, планировщик — не имеет security-контекста, из которого взять тенант, и
обязан использовать перегрузки с `SettingsSubject`, называя тенант, который ему и так известен:

```java
settings.getAll(new SettingsSubject(PrincipalRef.user(subject), tenantId));
```

## Объявление настроек

```java
SettingDefinition.of("user.timezone", ZoneId.class)   // ключ и тип обязательны
        .defaultValue(ZoneId.of("UTC"))
        .category("locale")        // группировка для UI и тег метрики записи
        .userEditable(true)        // по умолчанию false: самостоятельное редактирование — решение
        .pii(false)                // true прячет значение везде, кроме таблицы настроек
        .validator(SettingValidator.range(1, 100))
        .jsonEncoded(false)        // true — хранить значение как JSON, см. ниже
        .description("...")
        .build();
```

Ключи — сегменты в нижнем регистре через точку (`^[a-z][a-z0-9]*([.-][a-z0-9]+)*$`), и это требование, а
не рекомендация: ключ — идентификатор на проводе, он попадает в события, строки аудита и таблицы
проекции, а инсталляция, допускающая и `User.TimeZone`, и `user.timezone`, получила бы две настройки,
которые любой человек назвал бы одной.

### Что проверяется на старте

Реестр собирается из всех предоставленных `SettingDefinitionSource` и проверяется до окончания подъёма
контекста. Каждый из этих случаев — деплой, который должен упасть, а не пользователь, который об этом
узнает:

| Проверка | Почему это фатально |
|---|---|
| дубль ключа с другим объявлением | победитель зависел бы от порядка бинов |
| тип, который нечем конвертировать | упало бы на первой записи — у того, кто её сделал |
| значение по умолчанию, не проходящее собственную валидацию | все чтения успешны и возвращают значение, которое модуль отказался бы сохранить |
| значение по умолчанию, не переживающее цикл «сохранить-прочитать» | значение изменится при первом же сохранении |

Один и тот же ключ, объявленный **идентично** двумя источниками, допустим — чтобы определение,
порождённое фабрикой (по одному отказу на категорию уведомлений), могло встречаться в нескольких списках.

Единственное, что нельзя перенести на старт, — определение, которого никто не предоставил: проверять
нечего. Обращение к нему падает громко и конкретно, с `UnknownSettingException`, а не разрешается в
значение по умолчанию, маскируясь под проблему с данными.

### Типы значений

Встроенные: `String`, `Boolean`, `Integer`, `Long`, `Double`, `BigDecimal`, `Instant`, `Duration`,
`LocalTime`, `ZoneId`, `Locale`, `UUID` и любой `enum`.

Всему прочему нужен либо бин `SettingValueConverter` ровно для этого типа, либо `jsonEncoded(true)` на
определении. JSON **не** является автоматическим запасным вариантом, и это намеренно: иначе ни один тип
никогда не оказался бы неконвертируемым, и «определение, тип которого нечем кодировать» перестало бы быть
ошибкой старта.

`ZoneId` хранится идентификатором региона (`Europe/Moscow`), а не смещением: смещение не переживает
переход на летнее время. Разбор `Boolean` строгий — `Boolean.parseBoolean` превращает любую нераспознанную
строку в `false`, а хранимое `"yes"`, молча ставшее «отписан», — ровно тот класс ошибок, которого у этого
модуля быть не должно.

## Запись

```java
writer.set(ref, AccountSettings.TIMEZONE, ZoneId.of("Europe/Moscow"));
writer.reset(ref, AccountSettings.TIMEZONE);
writer.setAll(ref, List.of(
        SettingUpdate.of(AccountSettings.TIMEZONE, ZoneId.of("Europe/Moscow")),
        SettingUpdate.reset(AccountSettings.LOCALE)));

// административно, на другой области
writer.setForScope(adminSubject, SettingScope.tenant("acme"), AccountSettings.TIMEZONE, zone);
```

Каждая запись валидирует, аудирует, публикует и инвалидирует кэш — в этом порядке и в одной транзакции.
Массовое обновление проверяет **все** изменения до записи **любого**, поэтому форма настроек, отклонившая
одно поле, оставляет пользователя перед экраном, соответствующим хранимому состоянию, — и сообщает обо
всех отказах, а не только о первом.

`reset` не записывает значение по умолчанию. Он убирает собственное значение субъекта, чтобы нижние слои
снова его давали; запись умолчания «приколола» бы настройку к текущему значению и последующее изменение
умолчания тенанта её бы не затронуло — то есть ровно противоположное тому, о чём просит «сбросить».

Сброс оставляет **надгробие** (tombstone), а не удаляет строку. Именно это делает проекцию устойчивой к
нарушению порядка: без строки не с чем было бы сравнить опоздавшее событие «установлено», и значение
вернулось бы с того света. Надгробия вычищает задача ретенции.

Две конкурентные записи одной настройки сталкиваются на уникальном ограничении, и одна получает
`DataIntegrityViolationException`. Оно намеренно пробрасывается, а не ретраится: иначе значение
проигравшего затёрло бы значение победителя по правилу «побеждает последний», которого никто не выбирал.

### Кто что может писать

Субъект может читать и писать **свои** настройки. Всё остальное требует настроенного административного
права **и** совпадения тенанта. Правило реализовано внутри модуля, а не в каждом вызывающем коде: правило,
переписываемое на каждом эндпоинте, — это правило, которое один из эндпоинтов однажды нарушит, и это будет
тот эндпоинт, который берёт идентификатор субъекта из пути и передаёт его дальше не глядя.

`userEditable(false)` запрещает редактировать значение *субъекту*. Администратора это не касается: «этому
пользователю нельзя менять» и «менять нельзя никому» — разные утверждения.

**Административные чтения чужих настроек аудируются**, независимо от того, были ли они отданы из кэша.
Собственные чтения — нет: строка на каждый просмотр страницы похоронила бы те, что действительно важны.

## Согласия

Согласие — не настройка. Настройка это текущее состояние, которое предполагается перезаписывать; согласие
это свидетельство, которое предполагается накапливать. Общий интерфейс означал бы общую модель хранения, а
модель, подходящая настройке — upsert на месте, побеждает последний, — уничтожает единственное, ради чего
согласие и хранят.

```java
consents.grant(ref, ConsentGrant.builder()
        .consentKey("marketing.email")
        .textVersion("2026-01-v3")     // обязательно
        .locale("ru-RU")
        .evidenceIp(request.getRemoteAddr())
        .evidenceUserAgent(request.getHeader(USER_AGENT))
        .build());

consents.revoke(ref, grant);                       // новая строка, никогда не обновление
consents.currentState(ref).isGranted("marketing.email");
consents.currentState(ref).isGrantedForVersion("marketing.email", "2026-02-v4");
consents.stateAsOf(ref, whenTheEmailWentOut);      // «докажите, на что он соглашался на дату X»
```

**Только добавление, и это обеспечено трижды.** `UserConsentEntity` наследует `SnapshotEntity` из
db-core, поэтому `SnapshotImmutabilityListener` отклоняет любой `@PreUpdate`; триггер в базе отклоняет
любой `UPDATE` в обход ORM; и ни один путь кода в модуле строку согласия не обновляет. «Только
добавление» — это утверждение, которое делают аудиторам, а утверждение, обеспеченное одной лишь
договорённостью, делать не стоит. Триггер защищает `UPDATE` и намеренно не защищает `DELETE`, чтобы
политику хранения всё-таки можно было исполнить.

**Версия текста обязательна**, потому что без неё запись отвечает на вопрос «согласился ли?», но не на
вопрос «на что именно?» — а защитой является только второе. Согласие на `v3` ничего не говорит про `v4`.

**Текущее состояние выводится, а не хранится.** Ни таблицы текущих согласий, ни булевой колонки: и то и
другое было бы второй копией факта, который уже есть в журнале, и однажды эти две копии разойдутся — а
применительно к согласиям это особенно плохая позиция. За свою жизнь субъект накапливает единицы решений,
поэтому свернуть их на чтении дешевле, чем поддерживать согласованность сводки.

Первичный ключ назначает владелец, и каждая проекция переиспользует его дословно, поэтому повторно
доставленное событие натыкается на ключ, а не добавляет вторую копию того же решения.

## Режим проекции

Потребитель в точности повторяет дисциплину `identity-projection-spring-boot-starter` и по тем же
причинам:

- **Идемпотентность.** Событие настройки несёт полное состояние одной строки; событие согласия несёт
  первичный ключ владельца. Повторное применение любого из них ничего не меняет.
- **Устойчивость к порядку.** Kafka упорядочивает только внутри партиции, а события субъекта переезжают
  между партициями при масштабировании топика. Событие старее хранимого отбрасывается по сравнению
  `occurredAt` с хранимым `changed_at` — без этой проверки повтор восстановил бы предпочтение, которое
  пользователь уже изменил, и пользователь увидел бы, как настройки самопроизвольно откатываются.
- **Инвалидация после коммита.** Кэш чистится после коммита транзакции проекции. Чистка внутри неё
  открывает окно, в котором другой поток перечитывает старую строку и заново кладёт в кэш устаревшее
  значение, — и чистка всё равно бы произошла, даже если бы транзакция откатилась.
- **Ручное подтверждение.** Модуль поднимает собственный контейнер слушателя с `AckMode.MANUAL`.
  Запись, которую применили или намеренно отбросили, подтверждается; запись, применение которой
  *упало*, — нет, и контейнер доставляет её повторно. При пакетном подтверждении смещение сдвинулось бы в
  любом случае, и изменение, потерянное из-за недоступности базы, было бы потеряно навсегда.
- Неразбираемое сообщение отбрасывается: его повтор будет падать так же всегда. Неизвестный этому реплике
  тип события игнорируется — именно это позволяет владельцу добавить пятый тип события, не согласовывая
  релиз.

Диспетчеризация идёт по заголовку `event-type`, который пишет Kafka-диспетчер outbox, а не угадывается по
форме полезной нагрузки: угадывание работает, пока два типа не пересекутся, а затем молча применяет не тот.

| Тип события | Полезная нагрузка | Когда публикуется |
|---|---|---|
| `UserSettingChanged` | `UserSettingChangedEvent` | значение установлено, изменено или сброшено на любой области |
| `ConsentGranted` | `ConsentChangedEvent` | согласие дано |
| `ConsentRevoked` | `ConsentChangedEvent` | согласие отозвано |

Ключ упорядочивания — область (`tenant/LAYER/scopeId`), поэтому все изменения одного пользователя, одной
роли или одного тенанта доставляются в том порядке, в котором были сделаны.

## Наполнение новой проекции: backfill

Поток изменений несёт **изменения**. И больше ничего. Для поддержания реплики в актуальном состоянии это
ровно то, что нужно, а для её создания — ровно то, что не нужно, и разрыв между этими двумя задачами —
самый частый способ получить от модуля неверный ответ.

Рассмотрим случай, ради которого вся эта функциональность и появилась. Сервис, который никогда не читал
настройки, теперь должен читать `user.timezone` — настройку, существующую два года и уже используемую
другими. Объявление ничего не стоит:

- это константа из общего jar с определениями, поэтому новый сервис импортирует тот же
  `SettingDefinition`, который объявляет владелец;
- реестр принимает один и тот же ключ, объявленный несколькими источниками, если объявления идентичны, и
  падает на старте с указанием обоих, если они разошлись;
- **миграции нет.** Настройка — это строка в `user_setting_value`, а не колонка. Добавление сороковой
  настройки в сервис, читавший тридцать девять, не меняет его схему никак.

Затем сервис стартует, и его реплика пуста. Каждый пользователь, который два года назад выставил часовой
пояс и с тех пор его не трогал, не порождает ни одного события — значит новый сервис разрешит значение в
умолчание определения ровно для тех людей, кто настроил его наиболее осознанно, и нигде ничего об этом не
сообщит.

### Почему очевидные обходные пути не закрывают разрыв

**Перечитывание топика с самого начала** работает, и попробовать это дешевле всего: проекция
идемпотентна и терпима к порядку, поэтому переигранные события либо вставляются, либо отбрасываются как
устаревшие. Ограничение — ретенция. Топик, хранящий семь дней, даст вам семь дней *изменений*, а не
текущее состояние.

**Компактификация лога здесь не работает**, и об этом стоит сказать прямо, потому что именно к ней
тянутся в первую очередь. Kafka-диспетчер outbox использует ключ упорядочивания как ключ записи, а для
настроек этот ключ — `tenant/LAYER/scopeId`, то есть *субъект*, а не субъект вместе с настройкой. Значит
компактифицированный топик сохранит для каждого субъекта последнюю изменённую настройку и выбросит
остальные. Ключ по настройке сделал бы компактификацию рабочей и отнял бы упорядоченность по субъекту, на
которую опирается проекция; эта сделка выигрышна, но это изменение контракта событий, а не настройка
брокера.

### Что делает backfill вместо этого

`SettingsBackfillService` читает текущее состояние владельца и переопубликовывает его как обычные события
`UserSettingChanged` и события согласий, так что проекция приходит в нужное состояние по единственному
пути, который у неё есть, — без второго консьюмера, без формата импорта и без скопированных руками
таблиц.

```java
@RequiredArgsConstructor
class SettingsRunbook {

    private final SettingsBackfillService backfill;

    void seedNewConsumer() {
        // Один тенант, одна настройка: случай нового потребителя.
        backfill.backfill(SettingsBackfillRequest.forSettings("acme", "user.timezone"));

        // Всё по одному тенанту: реплика, пересобранная после неудачного релиза.
        backfill.backfill(SettingsBackfillRequest.forTenant("acme"));

        // Все тенанты, ограниченными порциями, чтобы за долгим прогоном можно было наблюдать.
        SettingsBackfillResult result = backfill.backfill(SettingsBackfillRequest.builder()
                .batchSize(1000)
                .maxRows(100_000)
                .build());
        if (!result.complete()) {
            // Запустите ещё раз. Никакого курсора переносить не нужно.
        }
    }
}
```

Бин существует в режиме владельца без каких-либо настроек, и это сделано намеренно: момент, когда бин
понадобился оператору, — плохой момент узнавать, что сначала нужен редеплой.

### Почему это безопасно запускать в любое время

**Каждое переопубликованное событие несёт исходный `changed_at` владельца в качестве `occurredAt`.** На
этой одной строке держится всё. Проекция сравнивает её с тем, что у неё есть, и отбрасывает всё, что не
новее, — поэтому backfill против уже актуальной реплики создаёт много трафика и не меняет ничего. Не
нужно предварительно отвечать на вопрос «а сейчас уже безопасно?» — именно это свойство делает операцию
пригодной во время инцидента.

Оно же делает её возобновляемой простым повторным запуском. Прерванный прогон оставил после себя
корректные события для строк, до которых дошёл; повторный начинает с начала, а проекция их отбрасывает.

Ещё три решения, о которых стоит знать:

- **Надгробия переопубликовываются как удаления.** Реплика, наполненная только живыми строками, но ранее
  узнавшая о значении, которое потом сбросили, вечно отдавала бы воскресшее значение.
- **Согласия идут через отдельный метод публикатора, который не выставляет ключ идемпотентности
  outbox.** Обычный путь ставит id согласия этим ключом, чтобы обработчик с гарантией at-least-once не
  поставил решение в очередь дважды, — и для переигрывания это ровно неверно, потому что строка исходной
  публикации может ещё лежать в outbox и поглотить повтор. Отказ от ключа безопасен: проекция ключует
  строки согласий по id владельца и никогда их не обновляет, так что дедупликация живёт у потребителя,
  где ей и место.
- **Ни строк аудита, ни редактирования ПДн.** Backfill ничего не меняет, поэтому запись в журнал изменений
  на каждую строку означала бы миллионы записей о том, что ничего не произошло, — на той самой таблице,
  ради которой существует задача ретенции. А переопубликованное событие несёт значения с флагом ПДн так
  же, как их несло исходное событие изменения: репликация этих данных и есть смысл операции. Инсталляция,
  которая не хочет, чтобы значения настройки покидали владельца, не должна проецировать их вовсе.

### Сканирование, батчи и тенант

Сканирование — keyset-пагинация по первичному ключу с продолжением от последнего прочитанного id.
Сканирование через `OFFSET` заново проходит всё, что уже пропустило, и, что хуже, молча теряет строки,
когда конкурентная запись сдвигает порядок под ним.

Каждый батч — своя транзакция. Backfill может пройти миллионы строк, и делать это в одной транзакции
значило бы держать её открытой минутами против таблиц, которые одновременно обслуживают живые записи.
(Поэтому же публикатор батчей — отдельный бин от сервиса: вызов `@Transactional`-метода на том же объекте
идёт мимо прокси, так что цикл и батч обязаны жить в разных бинах, иначе аннотация ничего не значит.)

`maxRows` — это бюджет, а не потолок: сканирование останавливается после батча, который его пересёк, так
что прогон может опубликовать на один батч больше запрошенного.

Он к тому же **общий на оба сканирования, а настройки сканируются первыми.** Бюджет меньше таблицы
настроек поэтому никогда не дойдёт до согласий, сколько бы раз его ни перезапускали, — повторный прогон
тоже начинает с начала. Если бюджет задан вообще, запускайте обе половины по отдельности:

```java
backfill.backfill(SettingsBackfillRequest.builder()
        .tenantId("acme").maxRows(100_000).includeConsents(false).build());
backfill.backfill(SettingsBackfillRequest.builder()
        .tenantId("acme").maxRows(100_000).includeSettings(false).build());
```

`tenantId` — единственное поле в модуле, которое может быть `null`, и `null` означает «все тенанты».
Пересборка реплики означает пересборку для всех, а оператору, вынужденному сначала перечислить тенанты,
понадобился бы запрос, которого модуль намеренно не предоставляет. REST-эндпоинт это выразить не может: в
его теле нет поля тенанта, а контроллер подставляет тенант самого вызывающего.

### Эндпоинт

```
POST /admin/settings/backfill
```

Монтируется, только если `ludwig.user-settings.web.enabled=true` **и**
`ludwig.user-settings.web.backfill-enabled=true` **и** сервис в режиме владельца. Три условия на один
эндпоинт, потому что это единственный здесь, чей радиус поражения — целый тенант, а не один субъект. Он
требует административного права безусловно: backfill не «про субъекта», поэтому случая самообслуживания,
который мог бы тут примениться, просто нет.

```json
{ "settingKeys": ["user.timezone"], "includeConsents": false, "maxRows": 50000 }
```

```json
{ "settingRows": 41230, "consentRows": 0, "batches": 83, "complete": false }
```

`complete: false` означает, что бюджет строк исчерпан; вызовите ещё раз. Вызов отрабатывает до конца
прежде чем ответить: с заданным `maxRows` это нормально, без него на большой инсталляции — плохая идея.

### Запуск даст всплеск `projection.dropped`

Этот счётчик — признак того, что backfill работает: уже актуальная реплика отвергает всё, что ей
присылают. Любой алерт на устаревшие события должен быть написан с допуском на backfill, иначе он будет
будить дежурного при каждом прогоне.

### Чего backfill не исправит

Backfill переопубликовывает то, что владелец **держит сейчас**. Он не восстановит значение, которое
менялось дважды, пока потребитель лежал: реплика догонит текущее значение, а не промежуточное, которое
она пропустила. Для настроек это правильный ответ — разрешению нужно только текущее состояние. Для
журнала согласий это важнее, и именно поэтому согласия переопубликовываются построчно, а не снимком
текущего состояния: журнал *и есть* история, поэтому переигрывание каждой строки восстанавливает её
целиком.

## Кэширование

SPI `SettingsCache` по образцу `AuthorityCache` из `security-spring-boot-starter`, с реализациями на
Caffeine и no-op и тем же схлопывающим `get(subject, loader)`: конкурентные промахи по одному субъекту
запускают загрузчик один раз, а не по запросу на каждый висящий вызов в момент пиковой нагрузки.

**TTL здесь — решение про производительность, а не окно безопасности.** TTL у `AuthorityCache` — это
срок, в течение которого отозванная роль ещё работает, поэтому он измеряется секундами. Устаревшая
настройка означает, что пользователь недолго видит старое предпочтение, и никаких привилегий за этим не
стоит — поэтому по умолчанию пять минут, и увеличение TTL меняет свежесть на нагрузку, а не удлиняет окно
атаки.

TTL — **не** механизм согласованности. Механизм — инвалидация: после коммита локальной записи и после
коммита спроецированного события. TTL — страховка на случай, когда одно из них пропущено (потерянное
событие, лежавший потребитель), чтобы неверное значение вылечилось само, а не дожило до перезапуска.

Одна запись кэша хранит **весь** разрешённый набор субъекта. Запись на пару (субъект, настройка) сделала
бы `getAll` некэшируемым: странице, которой нужно двадцать настроек, нашлось бы двадцать записей — и всё
равно не было бы способа узнать, что это все.

Запись на области роли, тенанта или платформы чистит кэш целиком. Затронуты «все, у кого есть эта роль», а
перечислить их запись не может, не сходив в каталог, — и такие записи редки и административны.

## Персональные данные и аудит

У определения с `pii(true)` значение **скрывается везде, кроме самой таблицы настроек**: в журнале
изменений, в логах, в документах ошибок и в административных ответах API. И никогда — в теге метрики: ни
одна метрика модуля не тегируется значением настройки или идентификатором субъекта, поскольку и то и
другое даёт неограниченную кардинальность, управляемую вызывающей стороной, а значение вдобавок
опубликовало бы персональные данные в хранилище, до которого не дотянется ни один запрос на удаление.

Скрытие — фиксированный маркер, не хеш и не усечение: хеш обратим для значения из небольшого множества, а
усечение раскрывает ровно ту часть идентификатора, которая идентифицирует.

Отклонённое значение не попадает в документ ошибки **безусловно**, помечено оно как ПДн или нет. Правило,
опускающее его только для помеченных настроек, зависело бы от того, что все определения помечены верно.

Каждое изменение фиксирует кто, когда, какое определение, старое → новое, какой слой и идентификатор
корреляции запроса — то, что связывает строку аудита с логами, трассировками и нижележащими вызовами того
же запроса.

### Ретенция

| Таблица | Срок по умолчанию | Чистится автоматически |
|---|---|---|
| `user_setting_audit` | 365 дней | да, при `retention.enabled=true` |
| надгробия в `user_setting_value` | 30 дней | да, при `retention.enabled=true` |
| `user_consent` | — | **никогда** |

Чистка идёт ограниченными пачками с фиксированной задержкой: одиночное неограниченное удаление годового
объёма держит долгую блокировку и порождает много WAL на таблице, которая к тому же лежит на пути записи
каждого изменения настроек. Каждый проход удаляет не более `batch-size` строк, а планировщик возвращается
за остальными.

**Согласия по расписанию не чистятся никогда.** `SettingsRetentionService.purgeConsents` существует,
работает и не вызывается из модуля ниоткуда. Сколько хранить свидетельства согласия — юридический вопрос
с разным ответом в разных юрисдикциях и для разных согласий, и умолчание, тихо удаляющее их по таймеру,
уничтожало бы ровно то свидетельство, ради которого журнал и спроектирован. Метод вызывает оператор,
действующий по written-политике; планировщик — нет.

## Общеизвестные настройки

**Подключаемый по желанию** пакет определений, общих для платформы:

```java
@Bean
SettingDefinitionSource platformSettings() {
    return WellKnownSettings.source();   // user.locale, user.timezone, тихие часы, дайджест
}

@Bean
SettingDefinitionSource notificationOptOuts() {
    return SettingDefinitionSource.of(
            WellKnownSettings.channelOptOut("billing", "email"),
            WellKnownSettings.channelOptOut("billing", "chat"));
}
```

Ничто из этого не регистрируется автоматически. Автоматическая регистрация заняла бы одну строку и сломала
бы главное обещание модуля: `getAll` возвращает ровно те настройки, которые объявил *этот* сервис. Сервис
с четырьмя собственными настройками вдруг разрешал бы девять, для четырёх из которых у него нет ни экрана,
ни намерения их соблюдать, — а пользователь, отредактировав такую, увидел бы, что его предпочтение
проигнорировано.

Часть из них описывает поведение уведомлений, и **этот модуль не зависит от `notification-service`** —
зависимость направлена в обратную сторону. Предпочтение принадлежит пользователю и живёт рядом с его
остальными настройками; что с ним делает сервис — дело сервиса.

`QuietHours` — одна настройка, а не три (`enabled`, `start`, `end`), потому что в послойном движке каждая
разрешалась бы независимо: пользователь, переопределивший только время окончания, молча унаследовал бы
время начала от тенанта и получил бы окно, которое никто не настраивал.

## Интеграция с платформой

| Модуль | Для чего используется |
|---|---|
| `security-spring-boot-starter` | `PrincipalRef` как ключ поиска, `LudwigPrincipal` для проверки «свой или админ», `AuthorityLookup` для слоя ролей |
| `db-core` | `AuditedEntity`, `SnapshotEntity` и его слушатель неизменяемости, `BaseRepository` |
| `web-core-spring-boot-starter` | каждая ошибка — `LocalizedException`; модуль добавляет bundle сообщений и один `ExceptionProblemMapper` и не поставляет ни одного `@RestControllerAdvice` |
| `outbox-spring-boot-starter` *(опционально)* | события изменений в режиме владельца, в одной транзакции с изменением |
| `observability-spring-boot-starter` *(опционально)* | идентификатор корреляции в каждой строке аудита |
| `odata-filter-spring-boot-starter` *(опционально)* | административный поиск, см. ниже |
| `hot-reload-spring-boot-starter` *(опционально)* | слои умолчаний тенанта и платформы, перезагружаемые без редеплоя |
| `micrometer` *(опционально)* | `SettingsMetrics`, с парной no-op реализацией |

### Административный поиск не может раскрыть значение

Фильтрация OData — это белый список с запретом по умолчанию, и у `value_text` нет `@Filterable` — как и у
полей свидетельств согласия и у старого/нового значения в журнале. Является ли значение персональными
данными — свойство его *определения*, а не колонки (в одной колонке лежат значения всех настроек),
поэтому построчного правила, пропускающего безопасные и задерживающего помеченные, не существует.
Единственный обеспечиваемый ответ — не фильтруемо ни одно значение настройки; потеря невелика, поскольку
«найти всех пользователей с часовым поясом Europe/Moscow» — отчётный вопрос, а эта схема намеренно не
предназначена отвечать на отчётные вопросы.

### Горячая перезагрузка умолчаний

При наличии `hot-reload-spring-boot-starter` слои умолчаний тенанта и платформы читаются через живое
представление, а кэш настроек чистится на каждой перезагрузке — так что «с сегодняшнего дня новые
пользователи получают недельный дайджест» становится правкой, а не релизом. Сами определения **не**
перезагружаются: определение — артефакт времени компиляции, а перезагрузка, способная добавить или
перетипизировать его, и была бы той рантайм-схемой, ради отказа от которой модуль и устроен.

### REST-эндпоинты

Выключены по умолчанию (`ludwig.user-settings.web.enabled`). Сервис должен иметь возможность владеть
формой собственного API — путями, DTO, версионированием, группами OpenAPI, — и стартер, монтирующий
эндпоинты без спроса, решал бы это за него. Они существуют для сервиса, у которого мнения пока нет.

| Метод | Путь | Примечание |
|---|---|---|
| `GET` | `/me/settings` | собственные настройки вызывающего, разрешённые |
| `PUT` | `/me/settings` | массовое обновление; значения — закодированный текст |
| `POST` | `/me/settings/reset` | тело, а не переменная пути: ключи содержат точки |
| `GET` | `/me/settings/consents` | текущее состояние |
| `POST` | `/me/settings/consents/grant` \| `/revoke` | свидетельства берутся из запроса, никогда из тела |
| `GET` | `/admin/settings/subjects/{subject}` | значения ПДн скрыты; чтение аудируется |
| `PUT` | `/admin/settings/scopes/{scopeType}/{scopeId}` | только режим владельца |
| `GET` | `/admin/settings/subjects/{subject}/consents[/as-of?at=…]` | журнал и любой прошлый момент |

Контроллер самообслуживания вообще не берёт субъекта из запроса — там нет переменной пути, которую можно
перепутать, а это более сильная гарантия, чем проверка.

| `ludwig.user-settings.retention.tombstones` | `30d` | срок хранения надгробия сброса |
| `ludwig.user-settings.retention.batch-size` | `500` | строк за проход |
| `ludwig.user-settings.retention.interval` | `1h` | фиксированная задержка между проходами |
| `ludwig.user-settings.metrics.enabled` | `true` | Micrometer вместо no-op метрик |
| `ludwig.user-settings.liquibase.enabled` | `true` | применять поставляемый changelog отдельным `SpringLiquibase` |

Ключи настроек содержат точки, поэтому умолчаниям в конфигурации нужна скобочная нотация:

```yaml
ludwig:
  user-settings:
    platform-defaults:
      "[user.timezone]": Europe/Moscow
    tenant-defaults:
      acme:
        "[user.locale]": ru-RU
```

Настроенное умолчание для настройки, которую не объявляет ни одно определение, пропускается, а не роняет
сервис: конфигурация живёт дольше деплоев, и оставшийся YAML снятой настройки не должен останавливать
запуск.

## Схема

Три таблицы, применяемые отдельным `SpringLiquibase` рядом с changelog самого приложения — тем же
приёмом, что и в `outbox-spring-boot-starter`, с идентификаторами набора изменений в пространстве
`usrset-NNN`.

| Таблица | Что хранит |
|---|---|
| `user_setting_value` | по одному значению на `(тенант, тип области, идентификатор области, ключ)`, плюс надгробия |
| `user_setting_audit` | кто что изменил, когда, с чего на что, на каком слое |
| `user_consent` | журнал согласий, только на добавление |

Одни и те же три таблицы обслуживают оба режима. Проекция — это реплика, а не другая форма, и отдельная
схема означала бы два набора миграций, которые надо вечно держать в согласии, — и ошибку, исправленную
только в одном из них.

Чтобы управлять порядком миграций между модулями, поставьте `ludwig.user-settings.liquibase.enabled=false`
и подключите `classpath:db/changelog/user-settings/user-settings-changelog.xml` из собственного
мастер-changelog.

## Точки расширения

Все бины объявлены через `@ConditionalOnMissingBean`, поэтому каждая из них — замена, а не форк:

| SPI | Когда заменять |
|---|---|
| `SettingScopeResolver` | наследование идёт по группам, оргединицам или чему-то ещё |
| `SettingsTenantResolver` | ваши тенанты — не тенанты модуля безопасности |
| `SettingValueSource` | значения приходят ещё откуда-то, о чём модуль не знает |
| `SettingValueConverter` | тип, которого нет во встроенных, или другая кодировка для имеющегося |
| `SettingsCache` | другая реализация кэша |
| `SettingsMetrics` | другой бэкенд метрик |
| `SettingsEventPublisher` | события уходят не в outbox |

Замена любого из них не затрагивает приоритеты слоёв, кэширование, валидацию и аудит.

## Метрики

| Метрика | Теги |
|---|---|
| `ludwig.user.settings.cache` | `result` = `hit` \| `miss` |
| `ludwig.user.settings.resolution` | — (таймер с гистограммой перцентилей) |
| `ludwig.user.settings.resolution.size` | — (распределение числа настроек на разрешение) |
| `ludwig.user.settings.write` | `category`, `layer`, `action` = `set` \| `reset` |
| `ludwig.user.settings.consent` | `consent`, `decision` |
| `ludwig.user.settings.admin.read` | — |
| `ludwig.user.settings.projection.dropped` | `reason` = `stale` |
| `ludwig.user.settings.value.unreadable` | `layer` |
| `ludwig.user.settings.backfill.published` | `kind` = `setting` \| `consent` |

Падающая доля попаданий в кэш обычно означает, что инвалидация срабатывает чаще, чем должна. Растущий
`projection.dropped` — что владелец переопубликовывает события или топик перепартиционировали; ждите
всплеска при каждом прогоне backfill — это признак его нормальной работы. Растущая
задержка разрешения без изменения трафика — что вырос набор областей на субъекта, как правило роли.

## Тесты

173 теста: модульные — приоритеты слоёв, стартовая валидация, конвертация, схлопывание кэша, политика
доступа, порядок в проекции, постраничный обход backfill и его бюджет строк, отказ контекста подниматься
с испорченным определением; интеграционные на Testcontainers против настоящего PostgreSQL и настоящего
брокера — режим владельца, режим проекции, события вне порядка и повторные, инвалидация после коммита,
изоляция тенантов, неизменяемость согласий против триггера в базе, проверка со счётчиком JDBC-statement,
что `getAll` делает ровно один запрос, и backfill, проверенный по реальным строкам outbox: что он
переопубликовывает сохранённый `changed_at`, а не текущее время, что он переносит надгробия, что он
проходит больше строк, чем помещается в один батч, и что повтор согласия не поглощается ключом
идемпотентности исходной публикации; и `ArchitectureTest` поверх общей библиотеки правил ArchUnit.
