## Context

See proposal.md, "Why". The things the design builds on:

- **OpenAPI.** Each service has its own `ApiDocumentIT`, nearly identical between the two. It fetches
  `/v3/api-docs`, canonicalizes the result (sorted members, no `servers`), writes
  `target/openapi/<id>.openapi.yaml`, and compares that with `docs/api/<id>.openapi.yaml`.
  `-Dludwig.apidocs.write=true` overwrites the committed copy.
- **What the platform already knows about the Kafka surface:**
  - consumers: `ListenerContainerFactoryBuilder.forJsonPayload(name, type, topics)`, plus each
    consumer's cluster and dead-letter cluster from `add-kafka-clusters`
  - producers: outbox routes (event type → transport, cluster, destination)
  - the envelope: `MessageHeaders`
  - clusters: `KafkaClusters`
- **What it does not know:** a producer's payload type.
- **Deployment.** Services have no `distributionManagement`, because `ludwig-service-parent` is not
  parented by the reactor root, and they are not deployed. Libraries deploy to
  `ludwig.repo.{releases,snapshots}.{id,url}`, which are defined in the root POM.

## Goals / Non-Goals

**Goals:**

- One mechanism for both document kinds: generation, canonicalization, drift check and publishing.
- Producer payloads declared once per event type. The topic and cluster come from the routes, which
  already exist.

**Non-Goals:**

- Schema compatibility rules. The check is drift only; see the proposal.

## Decisions

### D1. Springwolf generates, and a platform starter completes

`asyncapi-spring-boot-starter` depends on `springwolf-kafka`, `messaging-spring-boot-starter` and
`outbox-spring-boot-starter`. Springwolf scans `@KafkaListener` and builds the document. The starter
contributes Springwolf customizers that run after the scan:

1. **Envelope.** It sets a headers schema from `MessageHeaders`, plus the configured correlation header
   name, on every message.
2. **Consumers.** For each receive operation it finds the listener's consumer name and adds the cluster
   binding and the dead-letter channel. The dead-letter channel is
   `DeadLetterTopics.forTopic(topic, suffix)` on the dead-letter cluster. The name is found from the
   listener's `containerFactory` bean through a new
   `ListenerContainerFactoryBuilder.consumerNameOf(factory)`: the builder records the name of each
   factory it builds. Today only `messaging-db-spring-boot-starter` knows this mapping, by proxying the
   builder; it can drop its proxy once this method exists.
3. **Producers.** For each declared event type matched by a route whose transport is `kafka` or
   `kafka:<cluster>`, it adds a channel for the destination, a send operation, and a message named after
   the event type. The payload schema is generated by Springwolf's own schema service from the declared
   class.
4. **Servers.** One per cluster in `KafkaClusters`, protocol `kafka`, with the cluster name as host.

- **Alternative, Springwolf's `@AsyncPublisher` on every publishing method:** rejected, by user
  decision. It repeats topic and cluster on every method, so the two can drift apart.
- **Alternative, a generator of our own:** rejected. It would mean owning AsyncAPI serialization and
  schema generation for no gain.

A spike pins the Springwolf version against Boot 3.3.5 and spring-kafka 3.2.4. It confirms three
things: that generic `ConsumerRecord<String, T>` parameters resolve to `T`, the customizer extension
point, and the endpoint that serves the document as YAML or JSON. If any of the three is missing, the
design is revised before group 3.

### Spike outcome (task 1.1)

Springwolf **1.9.0** is the last release built against Spring Boot 3.3.x (3.3.5, this platform's line).
1.10.0 moves to 3.4. Measured against it:

- **`ConsumerRecord<String, T>` is not unwrapped by default.** Without configuration the payload is
  documented as an empty `ConsumerRecord`. `springwolf.payload.extractable-classes[org.apache.kafka.clients.consumer.ConsumerRecord]=1`
  makes it document `T`, verified with a complete record schema. The starter ships this as a default.
- **A customizer runs after the scan, and can add a send operation** whose payload schema Springwolf
  generates (`ComponentsService.resolvePayloadSchema`) from a declared class. This is exactly the
  producer mechanism.
- **Springwolf refuses to build a document without `springwolf.docket.servers`,
  `springwolf.docket.base-package` and `info.title`/`info.version`.** The starter contributes defaults
  with an `EnvironmentPostProcessor`, at lowest precedence so that a service can override any of them:
  - one server per cluster (`default` plus every `ludwig.kafka.clusters` key), protocol `kafka`, with the
    cluster name as host. Canonicalization sets each server's `host` to its name, so the committed document
    carries no address even when a service configures one. *Revised during review:* removing `host`
    instead made the document invalid, because AsyncAPI 3.0 requires it on every server; IntelliJ and
    AsyncAPI Studio both rejected it.
  - base package `ru.ludwigandreas`, so that listeners contributed by platform starters (identity and
    user-settings projections) are part of the service's surface, as they are at runtime
  - title `${spring.application.name}`, and version `current`, because the published Nexus coordinate is
    the real version and a version inside the document would make every release a drift
- **Springwolf adds a Spring `__TypeId__` header schema** to every message. The platform turns type
  headers off, so the envelope customizer replaces those headers.
- The document serializes to YAML through `AsyncApiSerializerService.toYaml`, so the drift test needs no
  HTTP endpoint.

### D2. `OutboxEventTypes`, a registry in outbox

`ru.ludwigandreas.outbox.api.OutboxEventTypes` is a small immutable map, `eventType → Class<?>`, that a
service declares as a bean, for example
`OutboxEventTypes.of(Map.of("ProductCreated", ProductEventPayload.class))`. Several beans are merged. A
type declared twice with different classes fails startup.

`DefaultOutboxEventPublisher` takes it, possibly empty. With `ludwig.outbox.events.require-declared=true`
it refuses an undeclared type, or a payload that is not an instance of the declared class, before
anything is written. The default is `false`, so production behaviour does not change. Each service's
test properties set it to `true`, so the service's own tests are what catch an undeclared producer.

*Revised during implementation:* an event the code publishes down a route by name
(`OutboxEvent.route("product-notifications")`) is declared with that route, via
`OutboxEventTypes.routed(type, payload, route)`. The route is chosen in code at publish time and no
configuration records it, so without this the customizer would document such an event on the default
route - in `crud-service-example`, as a Kafka send for what is a REST call. With `require-declared`, the
publisher also refuses an event whose explicit route differs from the declared one, so the document cannot
contradict the code.

*Revised during implementation:* platform starters that publish through the outbox declare their own
event types next to the publisher bean, inside the class that is already guarded on the optional outbox:
audit (`audit.event`), export (`report.ready`), file-ingest (the run summary) and user-settings
(`UserSettingChanged`, `ConsentGranted`, `ConsentRevoked`). Without them, a service that uses one of these
starters fails its own tests under `require-declared`, and its document leaves those events out.

- **Alternative, the class name in properties:** rejected. A renamed class would break at runtime
  instead of at compile time.

### D3. One document check in test-support

`ru.ludwigandreas.testsupport.docs.PublishedDocument` holds what `ApiDocumentIT` holds today:

- canonicalize: sort object members recursively, keep arrays as generated, drop server addresses (all of
  `servers` for OpenAPI; each AsyncAPI server's `host` replaced by its name)
- write `target/api-docs/<id>.<kind>.yaml`
- compare with `docs/api/<id>.<kind>.yaml`, or overwrite it under `-Dludwig.apidocs.write=true`
- fail with the refresh command

Both services' `ApiDocumentIT` move onto it, and each service gains an `AsyncApiDocumentIT` that fetches
Springwolf's document from the real context the same way. The committed OpenAPI documents must come out
byte-identical, and that is task 2.2's proof.

*Revised during implementation (user decision):* adding Springwolf to a service changes its OpenAPI
document once. Springwolf registers a schema-title model converter in swagger's shared converter
registry, which springdoc also uses, so every schema gains `title:`. That is accepted as a reviewed
one-off refresh of each adopting service's OpenAPI document. Springwolf's own controllers, whose UI
config would otherwise add an `InitialConfig` schema, are kept out by a starter default,
`springdoc.packages-to-exclude=io.github.springwolf`. A service that sets that property itself must
include the package.

Springwolf also flips swagger's JVM-wide `TypeNameResolver` to fully-qualified names while it scans
(`springwolf.use-fqn`, default `true`). A springdoc document generated at the same moment came out with
every schema renamed to its FQN, as notification-service's first refresh showed. The starter defaults
`springwolf.use-fqn=false`, so the shared flag never changes, and AsyncAPI schemas carry simple names,
as the OpenAPI ones do.

### D4. `scripts/api-docs.sh`

- `refresh`: `mvn -pl <services> verify -Dit.test='ApiDocumentIT,AsyncApiDocumentIT'
  -Dludwig.apidocs.write=true`, where the services are those listed by `scripts/manifest.sh` with role
  `service`
- `check`: the same, without `write`. It also fails when a service is missing either document, unless
  the service is listed in `docs/api/README.md` as having no surface of that kind.
- `publish --version <v>`: runs `check`, then one `mvn deploy:deploy-file` per document with
  `-DgroupId=ru.ludwigandreas -DartifactId=<service> -Dversion=<v> -Dpackaging=yaml
  -Dclassifier=openapi|asyncapi -DgeneratePom=false`. The repository id and URL come from the root POM
  through `mvn help:evaluate` on `ludwig.repo.{releases,snapshots}.{id,url}`; the snapshots repository
  is used when `<v>` ends in `-SNAPSHOT`. Credentials are the user's `settings.xml`, as for library
  deploys.
*Revised during implementation:* `gate.sh` runs `scripts/api-docs.sh missing`, which is the
missing-document half of `check` and needs no build. The drift half is each service's own IT, which the
gate already runs whenever a change reaches a service. Running every service's ITs, with their
PostgreSQL containers, on a change to an unrelated module would turn a millisecond check into minutes.
`publish --dry-run` prints the upload commands without running the check.

- **Alternative, attaching the documents to each service's `mvn deploy`:** rejected for now. Services do
  not deploy, and making them deploy is a separate decision.

### Dependency-direction check

New edges:

- asyncapi-starter → messaging, asyncapi-starter → outbox (messaging itself gains only a method)
- crud-service-example → asyncapi-starter, notification-service → asyncapi-starter

Does messaging or outbox depend on the new starter, directly or transitively? Their `inRepoDependents`
(messaging: identity-projection, messaging-db, notification-service, outbox, user-settings; outbox:
audit, crud-service-example, export, file-action, file-ingest, messaging-db, notification-service,
user-settings) do not contain it, and nothing will. The services are leaves: `inRepoDependents` is empty
for both. **No cycle.**

### POM changes

- **`ludwig-bom`:** the Springwolf version (third-party) and the new in-repo artifact.
- **Root `pom.xml`:** `<module>`. No plugin is added: `deploy:deploy-file` and `help:evaluate` resolve by
  prefix, and `maven-deploy-plugin`'s version is already pinned.
- **`ludwig-service-parent`:** none.
- **Service POMs:** the new starter dependency.

### Conventions and their checks

- **"Every service has both documents, or declares that it has no such surface"**: checked by
  `scripts/api-docs.sh check`, a gate script. A document is not bytecode or Java source, so neither
  ArchUnit nor Checkstyle can see it. This is the same reasoning `unify-sql-migrations` recorded for
  changelogs.
- **"Every produced event type is declared"**: checked by the services' own tests running with
  `require-declared=true`. No static check is possible, because the event type is a runtime string.
  That is recorded in the starter README.

## Risks / Trade-offs

- **[Springwolf version churn]** → it is pinned in the BOM, and the spike is the first task.
- **[The documents are generated by tests that need brokers]** → the ITs only start a context. Springwolf
  scans beans and does not connect, but `crud-service-example`'s context needs PostgreSQL. The ITs reuse
  the services' existing test containers.
- **[`publish` runs from a laptop]** → it refuses stale documents, takes an explicit version, and uses
  the same credentials as library deploys. A CI job can call the same script.
- **[An undeclared producer in production]** → it is not refused at runtime by design, and it does not
  appear in the document. The service's tests catch it, as long as a test exercises that publish.

## Migration Plan

Nothing to migrate. Each service gains a document and an IT, and its OpenAPI document is refreshed once
(`title:` on every schema; see D3). Rollback removes the starter dependency and the AsyncAPI documents.
