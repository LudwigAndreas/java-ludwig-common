# identity-projection-spring-boot-starter

*[English](README.md) · **Русский***

Локальный, пригодный для запросов ответ на вопрос «кто этот вызывающий и что ему здесь можно?»,
поддерживаемый в актуальном состоянии из Kafka-потока пользователей OIDC-провайдера — и реализации трёх
SPI модуля [`security-spring-boot-starter`](../../sources/security-spring-boot-starter/README.ru.md) поверх базы
данных.

Подключите оба модуля, и роли перестанут браться из клеймов токена и начнут браться из ваших таблиц:

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>identity-projection-spring-boot-starter</artifactId>
    <version>1.0.0</version>
</dependency>
```

Заглушки модуля безопасности отключаются автоматически (`@ConditionalOnMissingBean`); писать проводку не
нужно.

| SPI | Реализация | Источник |
|---|---|---|
| `AuthorityResolver` | `DatabaseAuthorityResolver` | `security_user` (Kafka), `security_partner` (таблица), `ludwig.identity.service-roles` (конфиг) |
| `DataScopeProvider` | `DatabaseDataScopeProvider` | `security_grant` — явные, при желании срочные гранты |
| `PartnerIdentityResolver` | `DatabasePartnerIdentityResolver` | `security_partner` — подключение и приостановка партнёров без релиза |

## Зачем вообще проекция

Альтернатива — ходить в провайдер идентичности на каждое решение об авторизации, а это добавляет сетевой
хоп и чужой бюджет доступности на самый горячий путь. Другая альтернатива — положить роли в токен, а
именно этого вся конструкция и избегает: почему задержка отзыва прав решает спор, написано в README
модуля безопасности.

Проекция даёт локальный join. «Все агенты в этом тенанте», «у кого ещё есть эта роль» и «как выглядел
этот subject на момент вон той записи аудита» становятся запросами, а не вызовами API.

## Контракт события

```json
{
  "eventId":   "5f1c...",
  "type":      "UPSERT",
  "subject":   "0b7c1b5e-...",
  "displayName": "Anna Schmidt",
  "tenantId":  "tenant-a",
  "roles":     ["CATALOG_ADMIN", "ORDER_AGENT"],
  "email":     "anna.schmidt@example.com",
  "emailVerified": true,
  "alternateEmail": "anna@personal.example",
  "phoneNumber": "+49301234567",
  "phoneVerified": true,
  "chatHandle": "@anna",
  "sourceVersion": "7",
  "occurredAt": "2026-03-01T10:00:00Z"
}
```

Работу делают три свойства этой формы:

**`roles` — полный набор, а не дельта.** Повторное применение того же события даёт ту же строку, а
переигрывание топика с начала сходится к правильному состоянию. Инкрементальные «роль добавлена» / «роль
удалена» оставили бы проекцию навсегда неверной после одного потерянного или задублированного сообщения —
а «навсегда неверной» здесь означает, что у кого-то осталась роль, которой у него больше нет.

**`occurredAt` — ключ упорядочивания, а не время получения.** Kafka упорядочивает внутри партиции, а
события одного пользователя переезжают между партициями при масштабировании топика или смене ключа.
Событие старше того, что уже сохранено, — это норма, а не ошибка, и оно отбрасывается. Без этой проверки
переигрывание молча возвращает роль, отозванную несколько дней назад: отложенное, невидимое повышение
привилегий.

**Неизвестные поля игнорируются.** Схемой владеет провайдер, и он будет её дополнять. Консьюмер, падающий
на новом поле, превращает релиз наверху в инцидент во всех сервисах на топике.

`type` — это `UPSERT`, `DISABLE` или `DELETE`. `DELETE` проецируется как смена статуса, а не как удаление
строки: записи аудита и ссылки `created_by` на этот subject должны продолжать разрешаться, а
пересозданная учётная запись не должна унаследовать историю предыдущей.

### Контактные данные подключаются явно и по умолчанию выключены

Контактные поля сохраняются **только** при `ludwig.identity.contact.enabled`. Иначе их в проекции нет,
а из строк, записанных прежней конфигурацией, они вычищаются: выключение флага затирает строку каждого
пользователя на его следующем событии, а не замораживает уже записанное.

Аргументы работают в обе стороны, и важны обе. Верификация происходит у OIDC-провайдера, поэтому он и
есть единственный источник истины по адресам человека, а сервис, который пишет людям, должен читать
адрес из каталога, а не держать копию, которую ничто не синхронизирует. Но эта проекция реплицируется
в *каждый* сервис, использующий модуль, и всегда заполненная контактная колонка положила бы адрес
человека в базу каждого сервиса эстейта — включая те, которым он незачем, и каждая из них ещё одно
место, до которого должен дотянуться запрос на удаление.

Отсюда флаг: его включает тот сервис, который действительно отправляет людям сообщения, и больше
никто. Индексов на этих колонках нет намеренно — все обращения идут по subject, поэтому индекс ничего
не дал бы и сделал бы дешёвым вопрос *«у какого пользователя этот адрес»* к реплике данных каталога.

`emailVerified` и `phoneVerified` намеренно nullable. Null означает, что провайдер ничего не сказал, и
это другой факт, нежели «сказал нет»: потребитель, решающий, можно ли писать на адрес, обязан их
различать, а трактовка молчания как «не верифицирован» остановила бы все сообщения в тот день, когда
поле появилось.

## Задержка отзыва прав

```
изменение в каталоге -> Kafka -> коммит проекции -> инвалидация кэша прав -> следующий запрос видит его
```

Инвалидация происходит **после коммита**, а не внутри него: инвалидация внутри транзакции открывает окно,
в котором другой поток перечитает старую строку и заполнит кэш устаревшими ролями, — и произошла бы даже
в случае отката транзакции.

Раньше эта дисциплина была `TransactionSynchronization`, который модуль регистрировал вручную, — и это была
*вторая* копия того же хелпера, первую написал `user-settings`. Теперь это один вызов
`cache.evictAfterCommit(ref)` в
[`cache-spring-boot-starter`](../../sources/cache-spring-boot-starter/README.ru.md), где рассуждение записано один раз и
где на случай откатa есть тест.

Поэтому `ludwig.cache.caches.authorities.ttl` (по умолчанию 30s; до консолидации кэшей —
`ludwig.security.authorities.cache.ttl`) — это страховка на случай *пропущенного* события, а не штатный путь
к согласованности. В штатном пути изменение видно на следующем запросе. Кэш объявлен как
`purpose: security`, и именно это ставит на это число потолок при старте — см. `AuthorityCaches`.

## Схема

Поставляется как Liquibase-чейнджлог с неймспейснутыми id чейнджсетов, применяется либо отдельно, либо из
вашего master-чейнджлога (`ludwig.identity.liquibase.enabled=false` — см. сервис-пример).

| Таблица | Что хранит | Кем владеет |
|---|---|---|
| `security_user` (+ `security_user_role`) | проекцию; PK — OIDC `sub` | каталог, через Kafka |
| `security_partner` (+ `security_partner_role`) | реестр партнёров: код, идентификаторы сертификата, статус, роли | вы, с аудитом |
| `security_grant` | явные гранты области доступа к данным, при желании срочные | вы, с аудитом |

`security_user` наследуется от `ExternalEntity` из db-core, потому что это ровно оно и есть — запись, чей
id и жизненный цикл принадлежат другой системе, — а её колонки `source_version`/`source_timestamp` и
сравнивает страж порядка. Хранится только то, что нужно авторизации: это данные каталога, реплицированные
в каждый сервис, использующий модуль, поэтому каждая лишняя колонка — ещё одно место, куда придётся
дотянуться при запросе на удаление персональных данных.

`security_partner` и `security_grant` — наоборот, `AuditedEntity`, потому что их никто не проецирует: их
выдают, и выдаёт конкретный человек, а *кто, что и когда выдал* — первый вопрос аудитора.

## Гранты против политики

И то и другое расширяет область доступа вызывающего, и они складываются
(`CompositeDataScopeProvider` их объединяет), но существуют они ради разных жизненных циклов:

| | Ролевая политика (`ludwig.security.data.policies`) | Строка гранта (`security_grant`) |
|---|---|---|
| Говорит | «агенты видят свои обращения» | «Анна ведёт Берлин, пока Боб в отпуске» |
| Является | правилом о системе | данными о человеке |
| Меняется через | пулл-реквест и деплой | действие администратора |
| Истекает | никогда | `expires_at`, проверяется в запросе |

Грант может только **расширить** то, что разрешает политика. Сужение делается снятием ролей — так вопрос
«почему этот человек это видит?» остаётся отвечаемым чтением двух мест, а не разматыванием цепочки
переопределений.

Срочность — это разница между временной подменой и постоянной привилегией, о выдаче которой никто уже не
помнит; и она проверяется в `WHERE`, а не чем-то, что должно вернуться и прибраться.

## Соседние сервисы

```yaml
ludwig:
  identity:
    service-roles:
      "[spiffe://mesh/ns/orders/sa/orders]":
        - ROLE_CATALOG_READER
```

В конфигурации, а не в таблице, и это намеренно: то, какой сервис какой может вызывать, — часть топологии
развёртывания. Она меняется вместе с кодом и должна ревьюиться в том же пулл-реквесте, что и вызов,
который она авторизует. Никто не выдаёт сервису доступ в рантайме.

## Поведение консьюмера

Контейнер слушателя приходит из `messaging-spring-boot-starter`: `ErrorHandlingDeserializer` вокруг ключа
и значения, экспоненциальная задержка и затем dead-letter топик.

Листенер принимает payload как обычную `String` и десериализует его сам, а не через настроенный
`JsonDeserializer`. Одна из двух исходных причин этого больше не действует — фабрика контейнеров теперь
платформенная, а не модуля, — а вторая стала выбором, а не необходимостью:

- **Неразбираемый payload** → логируется и фиксируется здесь, внутри кода приложения. Ошибка
  десериализации на уровне контейнера была бы помечена как неповторяемая и отправлена в dead-letter топик
  с первой попытки, что, пожалуй, лучше; перевод этого слушателя на типизированный конверт — изменение,
  которое стоит сделать, и оно намеренно не смешано с исправлением ниже.
- **Ошибка при применении** (база недоступна, сработало ограничение) → пробрасывается, смещение не
  фиксируется, и контейнер повторяет с растущими интервалами, а затем отправляет в dead-letter. Повторять
  безопасно, потому что применение события идемпотентно.

Сам payload никогда не логируется. Это данные каталога о человеке.

Каждому сервису нужна **своя consumer group** — общая означала бы, что каждый сервис видит лишь часть
событий.

### Раньше этот модуль терял запись, которую не мог обработать

Он **не объявлял фабрику контейнеров вообще**, поэтому слушатель работал на автоконфигурируемой фабрике
Spring Boot со штатным `DefaultErrorHandler`: десять попыток, без задержек, затем запись в лог и переход к
следующей записи. Запись терялась. Единственным следом была строка в журнале сервиса, который никто не
читает, а в проекции молча отсутствовали данные каталога об одном человеке — что проявляется недели спустя
как уведомление, ушедшее не на тот адрес.

Штатное поведение Boot разумно для приложения, которое ни о чём не задумывалось. Для проекции оно не
разумно, и модуль его не выбирал — он получил его, ничего не объявив. Именно поэтому замена закреплена
правилом ArchUnit `kafka.container-factories-set-an-error-handler`, а не просто исправлена.

Два следствия, о которых стоит знать до развёртывания:

- **Топик `oidc.users.dlt` нужно создать.** Это значение `ludwig.identity.kafka.topic` с суффиксом
  `.dlt`. Dead-letter топик, который автоматически создаётся в dev и отсутствует в production, — это та же
  молчаливая потеря в другой одежде; полное описание условия смотрите в README
  `messaging-spring-boot-starter` и настройте алерты на `ludwig.messaging.dead.lettered` и
  `ludwig.messaging.dropped`.
- **`OidcUserEventListener` больше не принимает `Acknowledgment`.** И не должен: Spring Kafka передаёт его
  только в ручных режимах подтверждения, а у слушателя, объявившего его при платформенном
  `AckMode.RECORD`, этот параметр разрешается как полезная нагрузка, и каждая запись падает с
  `Payload value must not be empty`.

## Конфигурация

```yaml
ludwig:
  identity:
    enabled: true
    grants-enabled: true              # регистрировать DataScopeProvider поверх таблицы грантов
    partner-registry-enabled: true    # регистрировать PartnerIdentityResolver поверх таблицы
    kafka:
      enabled: true
      topic: corp.identity.users
      group-id: my-service-identity-projection
    liquibase:
      enabled: true                   # false, когда чейнджлог включается из вашего master
    contact:
      enabled: false                  # проецировать верифицированные контактные данные, см. выше
    service-roles: {}
```

Всё необязательно. При `kafka.enabled=false` таблицы остаются на месте и продолжают опрашиваться —
удобно для админского сервиса поверх той же схемы или для теста.
