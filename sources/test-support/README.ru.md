# test-support

*[English](README.md) · **Русский***

Одно место для образов контейнеров этой платформы, самих контейнеров и фикстур, нужных интеграционному
тесту. Подключается одной зависимостью с областью `test` и даёт каждому модулю закреплённый по дайджесту
`DockerImageName`, общий на JVM синглтон PostgreSQL/Kafka/LocalStack, подключение через
`@ServiceConnection`, хелпер очистки таблиц между тестами, SMTP- и HTTP-заглушки в процессе и `Clock`,
который тест двигает вручную.

## Зачем

Две проблемы, и вторая крупнее первой.

**Дайджест был выписан двадцать один раз.** Политика безопасности платформы требует, чтобы каждый образ
задавался именем, версией *и* `sha256`-дайджестом, и она верна: тег можно перенаправить на другое
содержимое, и тогда тест незаметно начнёт исполнять что-то другое. Непросчитанное следствие — дайджест
приходится писать всюду, где запускается контейнер. Один литерал `postgres:16-alpine` встречался в
двадцати одном файле в **трёх разных написаниях**: в одну строку, разбитым на две через склейку строк и
разбитым плюс с полным именем класса. `sed` по полному литералу находит первое написание и молча
пропускает остальные два, оставляя половину сборки на одном дайджесте, а половину — на другом. Каждый
новый модуль платил этот налог снова, копируя у соседа.

**За сборку реактора поднималось девятнадцать контейнеров Postgres.** Девятнадцать отдельных
`new PostgreSQLContainer<?>(...)`, большинство — статические поля `@Container`, по одному на тестовый
класс. Старт контейнеров доминировал во времени прогона, а три независимые базовые тестовые
абстракции — `NotificationTestBase`, `FileIngestTestBase` и `PostgresBackedTest`, 416 строк вместе —
изобрели решение одной и той же задачи, причём две из них по пути независимо наткнулись на одну и ту же
неочевидную поломку.

## Что внутри

| Тип | Что это |
|---|---|
| `LudwigTestImages` | `POSTGRES`, `KAFKA`, `LOCALSTACK`, `REDIS` как `DockerImageName` из `images.properties`, с уже применённым `asCompatibleSubstituteFor(...)` |
| `Containers` | По одному контейнеру на образ на JVM, ленивый старт, без остановки |
| `PostgresContainerConfiguration` | `@TestConfiguration`, отдающая Postgres через `@ServiceConnection` |
| `KafkaPropertiesInitializer` | Наводит `spring.kafka.bootstrap-servers` на общий брокер |
| `LocalStackS3Initializer` | Наводит `ludwig.storage.s3.*` на общий LocalStack |
| `LocalStackS3` | Клиент SDK к нему плюс идемпотентные создание и очистка бакета |
| `Containers.redis()` | Общий Redis для общего слоя `cache-spring-boot-starter`. `GenericContainer` и один проброшенный порт, который читается из контейнера, а не предполагается: `Containers.REDIS_PORT` — это порт *внутри* него |
| `@LudwigPostgresTest`, `@LudwigKafkaTest`, `@LudwigLocalStackTest` | Составные аннотации; каждая документирует, что включает и когда её брать не нужно |
| `DatabaseCleaner` | `TRUNCATE ... RESTART IDENTITY CASCADE` всех таблиц, кроме ликвибейзовых |
| `GreenMailFixture`, `WireMockFixture` | SMTP и HTTP в процессе — образа нет, закреплять нечего |
| `TestClock` | Изменяемый `Clock`: `advance(Duration)`, `set(Instant)` и фабрика фиксированного |

## Как включить

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>test-support</artifactId>
    <scope>test</scope>
</dependency>
```

Версия приходит из `ludwig-bom`. Дальше либо составная аннотация:

```java
@LudwigPostgresTest
class SomethingIntegrationTest {
    // контекст уже подключён к запущенному PostgreSQL, закреплённому по дайджесту
}
```

либо импорт конфигурации рядом с `@SpringBootTest`, к которому у модуля есть свои требования:

```java
@SpringBootTest(classes = TestApplication.class)
@Import(PostgresContainerConfiguration.class)
class SomethingIntegrationTest { }
```

Помните: surefire запускает только то, что **не** названо `*IT` или `*IntegrationTest`, а failsafe —
только то, что названо так. Интеграционный тест с другим именем не запустится вообще.

## Путь обновления, ради которого всё это и делалось

В `images.properties` рядом с каждым пином стоят комментарии `# renovate:`:

```properties
# renovate: datasource=docker depName=postgres
ludwig.test.image.postgres = postgres:16-alpine@sha256:cf78e766...
```

Бот зависимостей может открыть пулл-реквест на одну строку со следующим дайджестом. В этом и смысл
properties-ресурса вместо констант в Java-коде: следующий перевыпуск по CVE превращается из «правки в
двадцати одном файле, о которой надо помнить» в «посмотреть и влить».

`LudwigTestImages` отказывается инициализироваться, если у пина нет сегмента `@sha256:` с
64-символьным hex-дайджестом. Фикстура, тихо откатившаяся на голый тег, вернула бы ровно то нарушение
политики, ради предотвращения которого модуль и существует, — и все прогоны остались бы зелёными.

## Чего стоит общий контейнер и где эта цена платится

Контейнер на тестовый класс давал каждому классу пустую базу по построению. Один общий — не даёт. Этот
обмен сделан осознанно: изоляция между тестами становится вопросом **схемы**, а не контейнера, и
`DatabaseCleaner` сводит плату к одной строке в `@BeforeEach`.

```java
@BeforeEach
void reset() {
    new DatabaseCleaner(dataSource).clean();
}
```

Это не про аккуратность. Когда тест проверяет именно разделяемое состояние кластера — аренду, окно
рейт-лимита, строку outbox, — оставшаяся строка не мелочь для уборки, а тест, который проходит или падает
в зависимости от того, что шло до него. `LocalStackS3.clearBucket(...)` — то же самое для S3.

## Конфигурация форков: проверена, а не предположена

Ускорение зависит от того, что несколько тестовых классов делят JVM, поэтому это было проверено, а не
заявлено: ни корневой POM реактора, ни `ludwig-service-parent` не задают `forkCount` или `reuseForks`,
значит действуют значения Maven по умолчанию — **один форк на модуль, переиспользуемый между тестовыми
классами**. Синглтоны действительно разделяются внутри прогона surefire модуля и внутри его прогона
failsafe.

Между модулями они **не** разделяются: каждый модуль — отдельная JVM, поэтому полная сборка реактора
поднимает по одному Postgres на модуль, которому он нужен, а не один на всю сборку. Разработчик, который
поставит `testcontainers.reuse.enable=true` в `~/.testcontainers.properties`, получит и это, потому что
каждый синглтон объявлен с `withReuse(true)`; по умолчанию и в CI это намеренно выключено, так как
переиспользованный контейнер несёт строки предыдущего прогона.

## Чего модуль намеренно не делает

- **Не зависит ни от чего в этом репозитории и не должен начать.** Maven строит DAG реактора по всем
  объявленным зависимостям независимо от области, включая `test` и `optional`. Интеграционные тесты есть у
  одиннадцати модулей, среди них `db-core` и `audit-core`; одна зависимость на соседа здесь замыкает цикл,
  который валит весь реактор. Образец, который скопирован, — `architecture-rules`.
- **Это не `test-jar`.** Обычный jar, потребляемый в области `test`, — то, что репозиторий уже делает, и
  это полностью обходит жизненный цикл `test-jar`.
- **Здесь нет фикстур безопасности.** Им нужен `LudwigPrincipal`, поэтому они живут в
  [`test-support-security`](../../sources/test-support-security/README.ru.md) — там написано, почему разделение не
  является оверинжинирингом.
- **GreenMail и WireMock не контейнеризованы.** Это библиотеки, работающие в процессе. Образа нет, значит
  закреплять нечего, а в процессе они быстрее.
- **Не создаёт ни бакетов, ни топиков.** Эти имена — словарь потребляющего модуля.
- **Нет принудительного порога покрытия** и не выставляется `-Djacoco.skip`. Классы модуля исполняются в
  прогонах одиннадцати других модулей и ни в одном своём, так что порог здесь мерил бы не то. Вместо этого
  есть тесты на два действительно своих свойства: юнит-тест на отказ от пина без дайджеста и
  `PostgresFixtureIntegrationTest`, который поднимает контекст через `@LudwigPostgresTest`, — потому что
  разрешается ли `@ServiceConnection` на имени образа с дайджестом, это факт про проводку Spring, и
  выпустить три составные аннотации, которые ни один тест никогда не запускал, было бы хуже, чем не иметь
  цифры покрытия.
