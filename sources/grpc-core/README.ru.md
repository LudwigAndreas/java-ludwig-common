# grpc-core

*[English](README.md) · **Русский***

То, что два сервиса платформы разделяют, когда говорят по gRPC, - без какого-либо транспорта.

От этого модуля зависят оба стартера gRPC, а сервис может нести только один из них. Поэтому здесь
лежит только то, о чём должны договориться *обе* стороны вызова, - четыре вещи - и ничего, что
открывает сокет.

| | |
|---|---|
| [Ключи метаданных](#ключи-метаданных) | Имена, под которыми передаются идентификатор корреляции, ключ идемпотентности, локаль и часовой пояс |
| [Кодек проблем](#проблема-и-статус---один-факт) | Проблема RFC 9457, представленная как `google.rpc.Status`, и чтение её обратно |
| [Сообщение операции](#сообщение-операции) | Конверт длительной операции в формате передачи |
| [Мост контекста](#мост-контекста) | Состояние потока, восстановленное на том потоке, на котором gRPC доставляет обратный вызов |

Здесь же определено, [что такое модуль контракта](#публикация-контракта).

## Публикация контракта

Контракт gRPC сервиса - отдельный модуль `<service>-grpc-api` в `sources/`, чей родитель -
`build/ludwig-grpc-api-parent`. В нём лежат файлы `.proto` и сгенерированный из них код, и больше ничего.
Вызывающие зависят от этого jar; никто не держит собственную копию сообщений.

Всё остальное даёт родитель - `grpc-protobuf`, `grpc-stub`, `protobuf-java`, этот модуль (чтобы контракт
мог импортировать `ludwig/operation/v1/operation.proto`) и генерацию protobuf, которая запускается в любом
модуле с каталогом `src/main/proto`. POM модуля контракта целиком:

```xml
<parent>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>ludwig-grpc-api-parent</artifactId>
    <version>${revision}</version>
    <!-- Обязательно: без него Maven молча берёт устаревший родитель из ~/.m2. -->
    <relativePath>../../build/ludwig-grpc-api-parent/pom.xml</relativePath>
</parent>
<artifactId>billing-grpc-api</artifactId>
<name>Billing gRPC API</name>
<description>The gRPC contract of billing.</description>
```

и три регистрации: `<module>` в корневом `pom.xml`, запись в `build/ludwig-bom/pom.xml` и зависимость в
`build/jacoco-aggregate/pom.xml`. `scripts/manifest.sh layout`, который запускает gate, падает с именем
модуля, если чего-то из этого нет, если родитель другой, если в модуле есть Java или нет ни одного
`.proto`, - так что десять строк проверяются, а не генерируются.

```proto
syntax = "proto3";

package ludwig.billing.v1;

option java_package = "ru.ludwigandreas.billing.grpc.v1";
option java_multiple_files = true;

service BillingService {
  rpc GetInvoice(GetInvoiceRequest) returns (Invoice) {
    option idempotency_level = NO_SIDE_EFFECTS;
  }
  rpc CreateInvoice(CreateInvoiceRequest) returns (Invoice) {
    option idempotency_level = IDEMPOTENCY_UNKNOWN;
  }
}
```

`scripts/check_protos.sh`, который запускает проверочный шлюз, падает на любом отступлении от этой
формы. Каждое правило на что-то опирается в другом месте:

| Правило | Почему это не дело вкуса |
|---|---|
| `package ludwig.<service>.v<N>` | Версия стоит в пакете, чтобы `v2` можно было обслуживать рядом с `v1` |
| `java_package = ru.ludwigandreas.<service>.grpc.v<N>` | Это единственное исключение сгенерированного кода из покрытия и анализа (`**/grpc/v*/**`); контракт вне него измеряется так, будто его написали вручную |
| `java_multiple_files = true` | Иначе каждое сообщение - вложенный класс одного внешнего класса, названного по файлу, и переименование файла переименовывает все типы |
| каждый `rpc` объявляет `idempotency_level` | Клиент gRPC читает эту опцию, решая, можно ли повторить неудавшийся вызов. `IDEMPOTENCY_UNKNOWN` - допустимый ответ; молчание - нет, потому что оно не должно выглядеть как решение |
| `.proto` лежит только в модуле `-grpc-api` (или здесь) | Proto внутри сервиса заставляет вызывающих зависеть от jar, собираемого как образ |

`protoc` разрешается как артефакт Maven, поэтому сборке не нужен системный компилятор. Его версия -
свойство `protoc.version` корневого POM, которое обязано совпадать с `protobuf.version` в `ludwig-bom`;
тот же скрипт валит шлюз, когда они расходятся.

**Чего скрипт проверить не может:** что `idempotency_level` *правдив* и что изменение опубликованного
proto совместимо на уровне передачи. Первое знает только автор метода. Второму нужен базовый дескриптор
на каждый выпуск, и оно отложено - см. `build/architecture-rules/README.ru.md`.

## Отображение сообщений

Сервис отображает сгенерированное сообщение в свою модель и обратно через MapStruct, как на любой другой
границе моделей: `ludwig-service-parent` кладёт protobuf SPI в путь обработчиков аннотаций, а этот модуль
даёт конфигурацию:

```java
@Mapper(config = ProtobufMapperConfig.class)
public interface ProductMessageMapper {
    ru.ludwigandreas.catalog.grpc.v1.Product toMessage(Product product);
}
```

`ProtobufMapperConfig` оставляет поле сообщения пустым для отсутствующего значения модели (сеттер
построителя бросает исключение на `null`), заполняет повторяющиеся поля через их adder-методы и
преобразует `Instant`/`Duration` в `google.protobuf.Timestamp`/`Duration` и обратно (`ProtobufConversions`).
Остальное делает SPI: построители, наличие через `hasX` (незаданное optional-поле отображается в `null`) и
префиксы `ENUM_NAME_` с константой `UNSPECIFIED`. Рабочий пример - `ProductMessageMapper` в
`crud-service-example`.

## Ключи метаданных

`GrpcMetadataKeys` объявляет каждый ключ один раз. Каждый - это HTTP-заголовок, несущий то же значение,
в нижнем регистре, так что у понятия одно имя на обоих транспортах.

| Ключ | Отражает |
|---|---|
| `authorization` | HTTP `Authorization` |
| `x-correlation-id` | `ludwig.observability.correlation.header-name` (используйте `forHeader`, если развёртывание его переименовало) |
| `idempotency-key` | `IdempotencyHeaders.KEY` |
| `idempotency-replayed` | `IdempotencyHeaders.REPLAYED` |
| `accept-language` | HTTP `Accept-Language`, который читает источник предпочтений web-core |
| `x-time-zone` | заголовок часового пояса web-core |
| `retry-after` | `OperationHeaders.RETRY_AFTER` |

Модули-владельцы не являются зависимостями этого модуля, поэтому литералы повторены здесь; стартеры,
зависящие от обеих сторон, несут тест, утверждающий их равенство.

## Проблема и статус - один факт

Решение о том, *какой* проблемой является исключение, остаётся в `ProblemMapperRegistry` модуля
`web-core`, который питают мапперы всех модулей. `GrpcStatusCodec` начинает с `ProblemDetail`,
произведённого этим конвейером, и меняет только конверт. **Модуль никогда не пишет отображение
исключения, специфичное для gRPC**; действует тот маппер, который он внёс для HTTP.

| Статус проблемы | Код gRPC | | Статус проблемы | Код gRPC |
|---|---|---|---|---|
| 400, 405, 406, 415 | `INVALID_ARGUMENT` | | 413, 429 | `RESOURCE_EXHAUSTED` |
| 401 | `UNAUTHENTICATED` | | 500 | `INTERNAL` |
| 403 | `PERMISSION_DENIED` | | 501 | `UNIMPLEMENTED` |
| 404, 410 | `NOT_FOUND` | | 502, 503 | `UNAVAILABLE` |
| 409, 423 | `ABORTED` | | 504 | `DEADLINE_EXCEEDED` |
| 412, 422 | `FAILED_PRECONDITION` | | | |

Код gRPC - грубый сигнал: на него реагируют политика повторов и предохранитель. Точный ответ едет
рядом, и именно он позволяет вызывающему восстановить проблему в точности:

| Член проблемы | Где он передаётся |
|---|---|
| статус | код выше и точное число в `ErrorInfo.metadata[http_status]` |
| `code` | `ErrorInfo.reason` |
| тип, заголовок | `ErrorInfo.metadata[type]`, `[title]` |
| detail | сообщение статуса и `LocalizedMessage` с его локалью |
| `violations` | `BadRequest.field_violations` |
| retry-after | `RetryInfo.retry_delay` |
| идентификатор корреляции | `ErrorInfo.metadata[correlation_id]` |

`409` - это `ABORTED`, а не `ALREADY_EXISTS`, потому что конфликт здесь столь же часто оказывается
сбоем оптимистичной блокировки, сколь и дубликатом; какой именно - говорит код проблемы.

**В таблице нет ветки по умолчанию.** `GrpcStatusCodes.forProblemStatus` - выражение `switch`,
называющее каждую константу, поэтому статус, добавленный в `web-core`, останавливает компиляцию этого
модуля, пока кто-то не решит, какой у него код gRPC, вместо того чтобы провалиться в `UNKNOWN` и быть
обнаруженным предохранителем вызывающего.

**Что не передаётся никогда:** сообщение исключения, имя класса, трассировка стека. У кодека нет
параметра типа `Throwable` на стороне кодирования, поэтому он не может выдать то, чего ему не дали.
Свободные свойства проблемы тоже не пересылаются - включая член `debug`, который `web-core` может
добавить к 5xx, - а отклонённое значение нарушения пересекает границу, только если его нёс бы и
HTTP-ответ.

Декодирование никогда не бросает исключение на некорректном или чужом статусе. Сбой от сервера не с
этой платформы декодируется в приближение, у которого `fromPlatform()` равно `false`.

## Сообщение операции

`ludwig/operation/v1/operation.proto` - это `OperationResponse` в формате передачи. Метод gRPC,
запускающий, опрашивающий или отменяющий длительную операцию, возвращает `Operation`, построенный
`OperationMessages.toMessage` из того же конверта, который модуль отдал бы `OperationResponses` для
HTTP:

```proto
import "ludwig/operation/v1/operation.proto";

service ExportService {
  rpc StartExport(StartExportRequest) returns (ludwig.operation.v1.Operation) {
    option idempotency_level = IDEMPOTENT;
  }
}
```

```java
return OperationMessages.toMessage(run.toOperationResponse(), Duration.ofSeconds(5));
```

Конверт по-прежнему один, общей таблицы операций нет, и зависимости от хранилища здесь нет.
Собственная таблица запусков модуля и его более богатый жизненный цикл в `detail` остаются ровно
такими, какими были.

**Контракт никогда не объявляет собственное перечисление статусов.** Перечисление в этом proto -
единственное названное исключение из правила словаря операций в `architecture-rules`, и существует оно
только потому, что формат передачи не может импортировать Java-перечисление. Оба переключателя по
статусу в `OperationMessages` называют каждую константу и не имеют ветки по умолчанию, поэтому два
словаря не могут разойтись по недосмотру; нулевое значение proto3 и `UNRECOGNIZED` отвергаются, а не
читаются как `PENDING`, потому что операция, чей статус никто не установил, - это не операция, которая
ждёт.

`retry_after` несёт то, что HTTP-представление кладёт в заголовок `Retry-After`.

## Мост контекста

Платформа хранит личность вызывающего, идентификатор корреляции и предпочтения вызывающего в
переменных потока. Для сервлетного запроса это работает, потому что его обслуживает один поток. У
вызова gRPC такого потока нет: его события доставляет тот поток исполнителя, который свободен.

`ContextRestoringServerInterceptor` выполняет остаток вызова с прикреплённым `Context` gRPC и всеми
`ThreadBinding` в силе **вокруг каждого обратного вызова** и снимает их в обратном порядке после.

Очевидная реализация - установить переменные потока один раз в `interceptCall` - неверна и проходит
любой однопоточный тест. `interceptCall` возвращается раньше, чем пришло сообщение запроса; для унарного
вызова обработчик выполняется позже, внутри `onHalfClose`, на потоке, который исполнитель выберет
тогда. В рабочей среде это обычно другой поток, где контекст безопасности пуст; а поток, на котором
выполнялся `interceptCall`, возвращается в пул с личностью предыдущего вызывающего. Поэтому
`ContextBridgeTest` доставляет обратные вызовы на другом потоке, чем перехватчик, перемежая двух
вызывающих на одном потоке пула.

`ThreadBinding` возвращает поток *таким, каким его нашёл*, а не очищает его, потому что потоки
исполнителя общие и внешней области на том же потоке её значение может быть ещё нужно.

Привязки вносит `grpc-server-spring-boot-starter`; этот модуль восстанавливает все три подсистемы, не
завися ни от одной из них.

## Чего он намеренно не делает

- **Нет транспорта.** Ни Netty, ни канала, ни сервера. `ModuleIndependenceTest` валит сборку, если
  отсюда достижим тип транспорта, тип сервлета или любой модуль платформы, кроме `web-core`.
- **Нет связывания Spring.** Автоконфигурации нет; стартеры сами создают то, что им нужно.
- **Нет проверки сообщений.** Проверка остаётся в сервисном слое и доходит до вызывающего через
  описанное выше отображение проблем.
