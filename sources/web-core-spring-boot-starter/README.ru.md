# web-core-spring-boot-starter

*[English](README.md) · **Русский***

REST-фундамент, на котором стоит каждый сервис этого репозитория: один локализованный конвейер
`ProblemDetail` по [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) (ранее RFC 7807), в который
каждый модуль **вносит вклад**, вместо того чтобы поставлять собственный `@RestControllerAdvice`;
транспортно-нейтральные бизнес-исключения; разрешение локали запроса, связанное с Bean Validation; и
конверт постраничного ответа, не протекающий JSON-формой Spring Data.

Добавьте зависимость — и обычный `@RestController`-сервис отвечает на любой отказ (бизнес-,
валидационный, фреймворочный, security, необработанный) одним документом проблемы на языке
вызывающего, без собственных advice, `MessageSource` и резолвера локали.

## Быстрый старт

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>web-core-spring-boot-starter</artifactId>
    <version>1.0.0</version>
</dependency>
```

Объявите, что отказ **означает**, в сервисном слое, без единого упоминания HTTP:

```java
public class ProductNotFoundException extends LocalizedException {

    public ProductNotFoundException(UUID id) {
        super(ProblemStatus.NOT_FOUND, "error.product.not-found", id);
    }
}
```

Положите его текст в `src/main/resources/i18n/messages[_ru].properties`:

```properties
error.product.not-found.title=Product not found
error.product.not-found=No product exists with id {0}.
```

Бросьте его. Больше подключать нечего:

```console
$ curl -H 'Accept-Language: ru' localhost:8080/api/v1/products/8f3a...
HTTP/1.1 404
Content-Type: application/problem+json
Content-Language: ru

{
  "type": "urn:ludwig:problem:error.product.not-found",
  "title": "Товар не найден",
  "detail": "Товар с идентификатором 8f3a... не существует.",
  "status": 404,
  "instance": "/api/v1/products/8f3a...",
  "code": "error.product.not-found",
  "timestamp": "2026-09-15T18:22:07.411Z",
  "traceId": "0af7651916cd43dd8448eb211c80319c"
}
```

## Проблема, ради устранения которой стартер и существует

Каждый модуль этого репозитория, способный упасть так, что это видит клиент, раньше поставлял
собственный `@RestControllerAdvice`. Выглядит как хорошая инкапсуляция — и не переживает встречи со
вторым модулем. Ломаются две вещи, и они усиливают друг друга.

**Язык.** Advice из библиотеки может отдавать только тот текст, с которым была скомпилирована. Advice
OData-стартера отвечала собственным английским текстом своих исключений, написанным для разработчика:
*«Property 'supplierCost' cannot be used in $filter/$orderby: not annotated @Filterable»* — потому что
единственный bundle, способный это перевести, должен был бы лежать в приложении. Так сервис,
отвечавший на все прочие ошибки на языке вызывающего, имел одну подсистему, отвечающую по-английски.
Единственным выходом было выключить эту advice
(`odata.filter.web.problem-detail-advice-enabled=false`) и вручную переобработать все семь типов её
исключений. Каждый сервис, использовавший модуль, писал одну и ту же advice, и предшественник этого
стартера — `ApiExceptionHandler` в `crud-service-example` — нёс комментарий, прямо об этом
говорящий.

**Форма.** Несколько advice — это несколько мнений о том, что содержит документ проблемы. Одна
выставляла `title` и не выставляла `code`, другая наоборот. Клиент не мог рассчитывать на наличие
`code`, потому что оно зависело от того, какая подсистема отказала.

Лечение — отделить **смысл** от **отрисовки**. Модуль сообщает только то, что означает его отказ: это
400, вот его код, вот поле-нарушитель, — внося `ExceptionProblemMapper`, и поставляет свой текст как
`ProblemMessageBundle`. Отрисовывает всё одна advice, а bundle самого приложения просматривается
раньше любого модульного, поэтому любую формулировку можно переопределить, объявив тот же ключ у
себя. Ни форка, ни настройки, ни переобработки.

```
      модуль                      приложение                      этот стартер
 ┌──────────────────┐          ┌───────────────────┐         ┌────────────────────┐
 │ его исключения   │          │ наследники        │         │ ProblemMapper      │
 │        │         │          │ LocalizedException│         │   Registry         │
 │        ▼         │          │        │          │         │        │           │
 │ ExceptionProblem │──────────┼────────┼──────────┼────────▶│ побеждает первое   │
 │   Mapper (бин)   │          │        ▼          │         │   совпадение       │
 │        +         │          │  i18n/messages    │         │        ▼           │
 │ ProblemMessage   │──────────┼── смотрится ──────┼────────▶│  ProblemMessages   │
 │  Bundle (бин)    │          │    первым         │         │        │           │
 └──────────────────┘          └───────────────────┘         │        ▼           │
                                                             │ ProblemDetail      │
                                                             │   Factory          │
                                                             │        │           │
                                                             │        ▼           │
                                                             │ ApiExceptionHandler│
                                                             └────────────────────┘
```

## Что он отвечает из коробки

| Отказ | Статус | Код |
|---|---|---|
| `LocalizedException` | тот, что он объявил | тот, что он объявил |
| отклонённое `@Valid @RequestBody` | 400 | `ludwig.web.error.validation` + `violations` |
| ограничение на `@RequestParam`/`@PathVariable` | 400 | `ludwig.web.error.validation` + `violations` |
| `ConstraintViolationException` от `@Validated`-бина | 400 | `ludwig.web.error.validation` + `violations` |
| неразбираемое тело | 400 | `ludwig.web.error.malformed-request` |
| отсутствующий или непреобразуемый параметр | 400 | `ludwig.web.error.bad-request` + `parameter` |
| неверный метод | 405 | `ludwig.web.error.method-not-allowed` (сохраняет `Allow`) |
| неверный `Content-Type` | 415 | `ludwig.web.error.unsupported-media-type` |
| ничего приемлемого для `Accept` | 406 | `ludwig.web.error.not-acceptable` |
| неизвестный путь | 404 | `ludwig.web.error.not-found` |
| `AccessDeniedException` внутри диспетчеризации | 403 | `ludwig.web.error.forbidden` |
| `AuthenticationException` внутри диспетчеризации | 401 | `ludwig.web.error.unauthorized` |
| `DataIntegrityViolationException` | 409 | `ludwig.web.error.conflict` |
| `OptimisticLockingFailureException` | 409 | `ludwig.web.error.concurrent-modification` |
| `PessimisticLockingFailureException` | 423 | `ludwig.web.error.concurrent-modification` |
| `QueryTimeoutException` | 503 | `ludwig.web.error.upstream-unavailable` |
| слишком большая загрузка | 413 | `ludwig.web.error.payload-too-large` |
| всё необработанное | 500 | `ludwig.web.error.internal` |

Несколько строк здесь — суть модуля, а не украшение. `AccessDeniedException` и
`AuthenticationException` бросаются `@PreAuthorize` и защитой данных **внутри** диспетчеризации MVC,
после того как цепочка фильтров security уже передала запрос дальше: `AccessDeniedHandler`
приложения их не видит, и без этого они всплывают пятисотками. Нарушение ограничения и отказ
оптимистичной блокировки по умолчанию тоже пятисотки — отклонённый ввод и проигранная гонка записи,
поданные как отказы сервера.

Каждый ответ несёт `Content-Type: application/problem+json` и `Content-Language`, называющий язык, на
котором тело действительно вернулось, — а он не всегда тот, который просили.

## Как это расширять

### Научить его исключению, о котором он не слышал

Один бин. `ExceptionProblemMapper.forType` закрывает обычный случай:

```java
@Bean
ExceptionProblemMapper quotaExceededMapper() {
    return ExceptionProblemMapper.forType(
            QuotaExceededException.class,
            e -> ProblemDefinition.of(ProblemStatus.TOO_MANY_REQUESTS, "error.quota.exceeded", e.limit())
                    .withProperty("limit", e.limit()));
}
```

Мапперы просматриваются в порядке `Ordered`, побеждает первое совпадение. Собственные мапперы
библиотеки регистрируются на `ExceptionProblemMapper.DEFAULT_MODULE_ORDER`, поэтому маппер
приложения — на порядке 0 по умолчанию — перекрывает любой из них, не зная, какое число выбрала
библиотека.

Реестр также идёт по цепочке причин. Исключение, дошедшее до advice, часто не то, которое бросили:
flush JPA заворачивает нарушение ограничения, менеджер транзакций — отказ коммита, прокси —
проверяемое исключение. Обход цепочки означает, что намеренный 409 остаётся 409, когда слой фреймворка
решил его завернуть, а не деградирует до 500. Побеждает более мелкая причина, поэтому обёртка,
которая **сама** отображена, выигрывает у своей отображённой причины.

### Внести текст из модуля

```java
@Bean
ProblemMessageBundle myModuleProblemMessages() {
    return ProblemMessageBundle.of("i18n/ludwig-mymodule-messages");
}
```

Порядок разрешения ключа полный: сначала `MessageSource` приложения, затем внесённые bundle в
объявленном порядке, затем умолчание вызывающего. Так модуль поставляет рабочий текст, а приложение
переформулирует любой его фрагмент, объявив тот же ключ в своём bundle.

### Сообщать собственные нарушения

Доменное правило, невыразимое в Bean Validation, сообщается в той же форме, что и отклонённый
`@NotBlank`, — чтобы у клиента был один путь обработки «отклонено по полям»:

```java
throw new InvalidProductException()
        .withProperty("violations", List.of(
                Violation.of("price", messages.get(...), "PriceBelowCost")));
```

## Локализация

Три бина, которые REST-сервис иначе писал бы сам, все под `@ConditionalOnMissingBean`:

- `MessageSource` поверх `ludwig.web.i18n.basenames`, UTF-8, никогда не откатывающийся к локали
  самого сервера — иначе язык API зависел бы от того, как настроен контейнер;
- `AcceptHeaderLocaleResolver`, ограниченный `supported-locales`, чтобы запросивший язык без bundle
  получил умолчание **целиком**, а не наполовину переведённый ответ;
- `LocalValidatorFactoryBean`, связанный с этим `MessageSource`, — именно он делает сообщения
  ограничений (`{catalog.validation.product.sku.required}`) локализованными. Без него отклонённый
  запрос возвращается с переведённым `title` и английскими сообщениями по полям.

Эта конфигурация объявлена `before` относительно `MessageSourceAutoConfiguration` и
`ValidationAutoConfiguration` Spring Boot, которые обе отступают при наличии бина нужного типа, — так
что она побеждает порядком, а не борьбой. Любой бин того же типа из приложения имеет приоритет, а
`ludwig.web.i18n.enabled=false` возвращает весь вопрос Boot-у.

Держите bundle в ногу: ключ, присутствующий в одной локали и отсутствующий в другой, — это то, как API
начинает отвечать наполовину на одном языке и наполовину на другом. Небольшой тест, сверяющий наборы
ключей между bundle, стоит своих десяти строк.

## Предпочтения вызывающего: язык, часовой пояс и что с ними делает маппер

Разрешение локали выше отвечает лишь на половину вопроса. `LocaleContextHolder.getLocale()` в потоке
запроса корректен, а `LocaleContextHolder.getTimeZone()` возвращал **зону контейнера**: потому что
`AcceptHeaderLocaleResolver` наследует `AbstractLocaleResolver` и никогда не публикует
`TimeZoneAwareLocaleContext`. Каждый `@JsonFormat` без явной зоны, каждое преобразование
`@DateTimeFormat` и каждый аргумент-дата, подставляемый в сообщение, читали именно её - UTC в
дата-центре и зону самого разработчика на ноутбуке. Дефект невидим ровно там, где его бы заметили.

`ru.ludwigandreas.webcore.preference` - единственный ответ платформы на вопрос "на каком языке и в
какой зоне читает этот вызывающий".

### Что пишет маппер

Ничего. Укажите форматтер в `uses`, и MapStruct подберёт преобразования по типам:

```java
@Mapper(componentModel = "spring", uses = UserPreferenceFormatter.class)
public interface ProductMapper {
    ProductResponse toResponse(Product product);   // Instant createdAt -> OffsetDateTime createdAt
}
```

`Instant -> OffsetDateTime` и `Instant -> LocalDate` разрешаются автоматически, в зоне вызывающего.
Ни одна подпись метода отображения не меняется, ни одной аннотации `@Mapping` не добавляется.
Работает это благодаря ограничению: `UserPreferenceFormatter` объявляет **ровно один метод на пару
исходный/целевой тип**. MapStruct выбирает неаннотированный метод из `uses` только по типам, и второй
кандидат на одну пару - это неоднозначность, которую потребляющий модуль обязан разрешить через
`qualifiedByName`, а это означало бы аннотировать форматтер `org.mapstruct.Named` и сделать MapStruct
зависимостью модуля, который полезен и без него. Сервису, которому нужно второе представление той же
пары, следует написать собственную обёртку с `@Named` - там этой аннотации и место.

Вне маппера читайте `UserPreferences.current()`. Это статическое чтение по той же причине, по которой
статичен `SecurityPrincipals.require()`: тот же поиск должен работать из сгенерированного маппера, из
слушателя JPA и из фрагмента репозитория, а ни одно из этих мест не годится для протаскивания
сервиса. Метод никогда не возвращает null и никогда не бросает исключение: у неразрешённого
*презентационного* предпочтения есть корректный консервативный ответ, а исключение превратило бы
косметический пробел в 500 на пути, который всего лишь форматировал дату. Коду, который не должен
приписывать вызывающему предпочтение, которого тот не выражал, предназначен `currentIfResolved()` -
он возвращает пустое значение.

### Откуда берётся ответ

Каждое измерение берётся у первого источника, который на него отвечает, независимо от другого - так
сохранённая зона без сохранённой локали всё равно оставляет выбор языка за `Accept-Language`:

| Порядок | Источник | Отвечает из |
|---|---|---|
| 100 | `StoredUserPreferenceSource` (в `user-settings-spring-boot-starter`) | `user.locale` / `user.timezone`, **только** если разрешённый `SettingLayer` специфичнее `PLATFORM` |
| 200 | `RequestHeaderPreferenceSource` | `Accept-Language` и `ludwig.web.preferences.time-zone-header` |
| последний | `ConfiguredPreferenceSource` | `ludwig.web.i18n.default-locale`, `ludwig.web.preferences.default-zone` |

Два решения в этой таблице стоит знать.

**Сохранённый выбор важнее заголовка запроса.** `Accept-Language` - подсказка, которую отправляет
*браузер*; сохранённая локаль - выбор, который сделал *пользователь*, как правило именно потому, что
браузер присылал не то. Платформа, где браузер молча побеждает, имеет неработающий экран настроек.

**Слои `PLATFORM` и `DEFAULT` воздерживаются.** `SettingsLookup.getAll` всегда отвечает для
объявленного определения, поэтому пользователь, ни разу не открывавший экран настроек, получит `UTC` и
`en` из слоя `SettingLayer.DEFAULT`. Источник, отвечающий из него и при этом стоящий первым в цепочке,
сделал бы UTC всех вызывающих, проигнорировал бы каждый когда-либо отправленный `Accept-Language` и
навсегда сделал бы недостижимыми два источника ниже. `PLATFORM` воздерживается на шаг выше по той же
причине: это конфигурация развёртывания, а `ConfiguredPreferenceSource` уже *и есть* ответ
развёртывания - и стоит он ниже заголовков, где общеразвёрточному значению по умолчанию и место.

Развёртывание, которое с этим не согласно, переупорядочивает бины. Источники - упорядоченные
`@Bean`-ы, а `UserPreferenceSource` публикует три константы порядка, так что замена размещается
*относительно* них, а не на магическом числе.

**Стандартного заголовка запроса для часового пояса не существует** - у `Accept-Language` есть
RFC 9110, у часового пояса нет ничего, - поэтому имя задаётся конфигурацией с документированным
значением по умолчанию, а не константой, выдаваемой за стандарт. Принимаются и `Europe/Moscow`, и
`+03:00`, а непригодное значение игнорируется, а не отклоняется: ответ 400 здесь означал бы провал
корректного в остальном запроса из-за подсказки, которую клиент мог и не присылать.

### Вне потока запроса

```java
UserPreferences captured = UserPreferences.current();          // в потоке запроса
...
try (UserPreferences.Scope scope = captured.bind()) {          // в рабочем потоке
    render(captured);
}
```

Закрытие восстанавливает предыдущий контекст потока, в том числе когда его не было: иначе поток из
пула перенесёт предпочтения одного вызывающего в задачу следующего.

### Чем это не является

Это **не хранилище предпочтений**. `user-settings-spring-boot-starter` владеет хранением, слоями,
валидацией, кэшированием, аудитом и API `/me/settings`; этот пакет объявляет SPI, который тот
реализует, и `web-core` не приобретает зависимости от персистентности - та же конструкция и по той же
причине, что и контракт длительных операций.

Это **не способ спросить про кого-то другого**. Здесь *амбиентный* контекст текущего вызывающего.
Вопрос "каковы предпочтения пользователя X" - это `SettingsLookup.getAll(subject)`; он принимает
субъекта, потому что амбиентного субъекта нет, и именно им должен пользоваться рабочий поток очереди,
рассылающий сообщение сотне получателей. `RecipientPreferences` в `notification-service` имеет
именно такую форму и сознательно не объединён с этим контрактом; правило
`noSecondCallerPreferenceType` из `RuleGroup.PRESENTATION` написано так, чтобы не срабатывать на
форму "по субъекту".

И он держит **два измерения, а не пять**. Всё, что из них выводится, - метод на `UserPreferences`:
`numberFormat()`, `firstDayOfWeek()`, `dateTimeFormatter(FormatStyle)`. Отдельно хранимый
`firstDayOfWeek` может разойтись с хранимой локалью, и тогда календарь начинается с понедельника, а
подсвечена колонка воскресенья. Всё, что не выводится, - это `SettingDefinition` в том модуле,
которому оно нужно.

> Один острый угол, о котором стоит знать: JDK держит первый день недели и разделители чисел как
> данные **региона**, поэтому `WeekFields.of(Locale.forLanguageTag("ru"))` отвечает `SUNDAY`, а
> `ru-RU` - `MONDAY`. Поэтому разрешение отвечает собственным тегом вызывающего, когда поддержан его
> *язык*, а не сужает `ru-RU` до поддержанного `ru`: `MessageSource` сам откатывается к бандлу `ru`,
> так что регион там ничего не стоит и критичен везде остальном. Следствие для потребителя:
> `Content-Language` теперь `ru-RU` там, где раньше было `ru`.

Проверяется ArchUnit, в `RuleGroup.PRESENTATION`: `noAmbientDefaultLocaleOrZone` ломает сборку при
вызове `Locale.getDefault()`, `TimeZone.getDefault()`, `ZoneId.systemDefault()` или
`Clock.systemDefaultZone()`, а `noSecondCallerPreferenceType` - при объявлении второго типа, держащего
эту пару. Сознательно **не** проверяется маппер, который вместо этого пишет
`instant.atOffset(ZoneOffset.UTC)`: он не вызывает ни одного запрещённого метода и всё равно неверен,
а запрет `ZoneOffset.UTC` был бы правилом, которое ошибается чаще, чем срабатывает, - ведь он корректен
в отображении персистентности, в тестовой фикстуре и в записи аудита. Это вопрос ревью.

## Постраничные ответы

```java
@GetMapping
public PageResponse<ProductResponse> search(ProductQuery query) {
    return PageResponse.of(productService.search(query), mapper::toResponse);
}
```

```json
{ "content": [...], "page": 1, "size": 20, "offset": 25, "totalElements": 137, "totalPages": 7 }
```

**`offset` — достоверная позиция, а `page` из неё выводится.** `page` теряет информацию: у смещения,
не кратного `size`, целой страницы нет, поэтому при `size=20` смещения 20 и 25 дают одну и ту же
`page=1`. Клиент, листающий по абсолютному смещению (а `$skip` в OData именно такой и явно не обязан
быть кратным `$top`), не может вычислить следующий запрос по одному номеру страницы. `page` остаётся
для обычного выровненного случая; он никогда не должен быть единственной позицией в конверте.

**`totalElements` и `totalPages` полностью отсутствуют, если вызывающий отказался от подсчёта**
(в OData это `$count=false`), потому что на глубоко листаемой отфильтрованной выборке `SELECT COUNT(*)`
обычно самая медленная часть запроса. Их нет в JSON, а не выставлены в null, поэтому клиент, который
никогда не отказывается, разницы не увидит. Нуль в роли признака не подходит: нуль — настоящий итог.
Для результата, который не является `Page` из Spring Data — а это любой результат без итога, ведь
`Page` всегда его несёт, — используйте `PageResponse.of(content, offset, size, totalElements)`.

`Page` из Spring Data напрямую не возвращается. Его JSON-форма — деталь реализации библиотеки
хранения: она менялась между версиями, а при сериализации выдаёт объект `pageable`, описывающий, как
был выполнен запрос, а не то, о чём просил клиент. Возврат его делает каждого потребителя API
зависимым от выбора библиотеки доступа к данным; Spring Boot 3.3 предупреждает ровно об этом при
старте.

## Длительные операции

Пять модулей этой платформы назвали состояния длительного запуска каждый по-своему, и они
расходились в главном. Выгрузка называла завершённый запуск `SUCCEEDED`, загрузка файлов -
`COMPLETED`. Одно состояние, два слова, в одной платформе и в двух API. Выгрузка отвечала `202`
без `Location`, то есть говорила клиенту "опрашивай", не говоря где. `Retry-After` не отдавал никто,
поэтому каждый клиент выбирал интервал сам - и все выбирали одну секунду.

`ru.ludwigandreas.webcore.operation` - это контракт, который это исправляет. Именно **контракт, а не
фреймворк**: общей таблицы операций за ним нет и не планируется. Четыре модуля уже ведут
свои запуски в таблицах, спроектированных под их собственную предметную область, и общая таблица
продублировала бы все четыре, добавила запись на каждый переход и была бы хуже в каждом из
их запросов. Каждый модуль остаётся со своей таблицей и проецирует её на конверт на своём краю -
и именно это оставляет стартер без зависимости от слоя данных, которой у него быть не должно.

### Словарь

```
PENDING -> RUNNING -> SUCCEEDED | FAILED | CANCELLED
SUCCEEDED -> EXPIRED            (retention удалил результат; запись осталась)
```

`EXPIRED` - терминальное состояние и **не** ошибка; то же верно для `CANCELLED`. Проверяйте
`status.isFailure()`, а не `!= SUCCEEDED`: клиент, считающий ошибкой любое терминальное состояние
кроме `SUCCEEDED`, будет будить дежурного из-за штатной очистки.

Более богатые жизненные циклы этим не заменяются. `COLLECTING`, `PENDING_SUBMIT` и `ORPHANED` из
сверки несут информацию, которую эти шесть констант выразить не могут; они проецируются на
ядро и остаются видны в `OperationResponse.detail()`. Общий словарь, который их бы стёр, был бы
шагом назад, и его бы справедливо отказались принять. Правило
`operations.no-second-operation-vocabulary` в `architecture-rules` аккуратно различает эти два
случая - см. README того модуля.

### Постановка задачи

```java
@PostMapping
ResponseEntity<RunResponse> submit(@Valid @RequestBody RunRequest body) {
    Run run = service.submit(body);
    RunResponse response = response(run);
    return run.isQueued()
            ? OperationResponses.accepted(response.operation(), response,
                    statusUri(run.getId()), OperationLocationHeader.LOCATION)
            : OperationResponses.completed(response.operation(), response);
}
```

`202` с заголовком, указывающим на ресурс статуса, и вызывающая сторона обязана выбрать
заголовок явно:

- **`Location`** - когда операция и есть тот ресурс, который клиент будет читать. Так
  работают и запуск выгрузки, и запрос уведомления.
- **`Operation-Location`** - когда у итогового результата другой URL, чем у монитора статуса:
  долго создаём ресурс, потом читаем созданное.

Значения по умолчанию нет сознательно. Вспомогательный метод, выбирающий сам, выбрал бы
`Location` для всех, а модули, которым нужен второй вариант, об этом бы не узнали.

`200` с эндпоинта постановки - это синхронный быстрый путь, и он разрешён явно: клиенту не
нужно опрашивать то, что уже готово. Контракт требует лишь, чтобы такой `200` нес
*терминальный* конверт.

`202` тоже может нести терминальный конверт, и это осознанно. Ранняя версия
`OperationResponses.accepted` такой ответ отклоняла; уведомления показали, что правило слишком
сильное. Они раскладывают запрос в веер той же транзакцией, которая его принимает, так что
операция-запрос завершена к моменту записи ответа, - и они всё равно отвечают `202`, потому
что создано намерение в очереди, а дойдёт ли что-то до кого-то, решается минутами позже
провайдером, которым этот сервис не управляет. Несущее инвариант требование в том, что
`202` называет ресурс статуса и что заголовок выбрала вызывающая сторона. Терминальный конверт
всё равно должен предъявить свидетельство, так что `202` со `SUCCEEDED` и без результата по-прежнему
отклоняется.

### Опрос

`OperationResponses.poll(...)` возвращает `200` и добавляет `Retry-After`, пока операция не
терминальна. Он **отказывает** в нетерминальном ответе без `Retry-After`, в терминальном
успехе без `result` и в терминальной ошибке без `failure`. Каждый из этих случаев - ошибка
производителя ответа, и каждый был когда-то выпущен в этой платформе, поэтому падение
происходит на первом вызове в первом тесте, а не в интеграции клиента шесть недель спустя.

### Отмена

`202`, а не `204`. Отмена в этой платформе кооперативная: операция останавливается на следующей
проверке своего `Cancellation` на том экземпляре, который её выполняет, так что честно эндпоинт
может сообщить только то, что запрос зафиксирован. `204` утверждал бы, что работа уже
остановлена, а это ложь, на которой клиенты строят логику повторов.

Отмена уже завершённой операции - **не** ошибка. `409` здесь приглашает к циклу повторов за
тем, что никогда не изменится; `OperationResponses.cancellationRequested` возвращает текущий
конверт с его терминальным состоянием.

### Прогресс

У `OperationProgress` **обнуляемый знаменатель**, и это самое главное. Модель прогресса, требующая
знаменатель, заставляет производителя либо врать, либо не отдавать прогресс вовсе: загрузка
файлов не знает числа записей в потоковом файле, пока его не прочитает. Пустой знаменатель
сериализуется как отсутствующее поле, а не как `"total": 0`, что клиент прочитал бы как
"готово, и даже с запасом".

### Идемпотентность: рядом, но не то же самое

Эндпоинт постановки длительной операции должен принимать `Idempotency-Key`, чтобы повторный
вызов возвращал *тот же* идентификатор операции, а не запускал вторую. Чего делать нельзя -
так это смешивать два кода, которые `idempotency-spring-boot-starter` различает сознательно:

| | значение |
|---|---|
| `202` | новая работа принята, вот её идентификатор |
| `409` + `Retry-After` | ваш дубликат наткнулся на работу в полёте; нового не запущено |

Эндпоинт, отвечающий `202` на дубликат, сообщает вызывающему, что запустил второй запуск.

### Сосуществование с вашей собственной advice

Общая advice регистрируется на `Ordered.LOWEST_PRECEDENCE`, и это несущее решение, а не произвол. Она
обрабатывает `Exception`, а Spring возвращает первую advice, которая **вообще** способна обработать
брошенное исключение, — а не ту, у которой самый специфичный обработчик для него. Advice, стоящая
где-либо кроме последнего места, поэтому проглатывала бы каждое исключение, ради отрисовки которого
написана ваша `@RestControllerAdvice`, включая типы, объявленные ею явно. Последнее место означает,
что у всех прочих advice есть право первого отказа.

Ничьи при этом разрешаются в вашу пользу: сортировка Spring устойчива, а бины автоконфигурации
регистрируются после собственных бинов приложения, поэтому `@RestControllerAdvice` без `@Order` всё
равно идёт раньше этой. Поставьте явный `@Order`, если не хотите зависеть от этого.

Если вы хотите отрисовывать **всё** сами, `ludwig.web.problem.enabled=false` убирает advice и
оставляет `ProblemDetailFactory`, `ProblemMessages` и цепочку мапперов доступными для внедрения —
тогда в вашей advice по одной строке на обработчик, а локализованный текст по-прежнему приходит из
bundle каждого модуля.

### Два переключателя, которые лучше не трогать

`include-rejected-value` и `include-exception-message` выключены по умолчанию, и оба сделаны
переключателями, а не проверками профиля, чтобы их включение было решением о развёртывании, которое
можно проаудировать.

Поле, чаще всего не проходящее валидацию, — это же поле, чаще всего содержащее пароль, токен или
номер карты, а тело проблемы — ровно то, что вставляют в тикет. По той же причине `detail` у 500
никогда не цитирует исключение: *«connection refused to db-7.internal:5432»* написано для того, кто
эксплуатирует сервис. Вместо этого клиент получает идентификатор трассировки — в теле, а не только в
заголовке, который консоль браузера прячет, — и именно это делает указание «назовите trace id»
выполнимым.

## Замечания по безопасности

- Advice ловит `AccessDeniedException` раньше, чем это может сделать `ExceptionTranslationFilter`
  Spring Security, и это намеренно: тот фильтр не находится на пути исключения, брошенного внутри
  диспетчеризации. Отрисованный так 401 не несёт заголовка `WWW-Authenticate`; для API, смотрящего в
  браузер, это обычно и нужно, поскольку реакция браузера на этот заголовок — нативное окно ввода
  учётных данных, которого не просит ни один UI на сессиях.
- Ответы 401 и 403 сообщают лишь то, что в доступе отказано. Различение «вам не хватает роли
  редактора» и «эта запись принадлежит другому тенанту» превращает эндпоинт в оракул для перебора
  записей; подробности принадлежат журналу аудита с ключом по субъекту.
- Если присутствует `security-spring-boot-starter`, он вносит маппер, и эти ответы возвращаются под
  кодами `ludwig.security.error.*` — теми же, что пишут его обработчики в цепочке фильтров, чтобы
  клиенту никогда не приходилось знать, какой слой ему отказал.

## Неверховые модули

`LocalizedException`, `ProblemStatus`, `ProblemMessages` и цепочка мапперов не зависят от Spring MVC,
а MVC-половина автоконфигурации обусловлена сервлетным веб-приложением. Пакетное задание или
консьюмер Kafka могут бросать и отрисовывать те же ошибки — в ответное сообщение, в лог, в
dead-letter-запись — без Spring MVC в classpath.

## Замечание о сборке

Поведение стартера зависит от одного флага компилятора — `-parameters`, выставленного в корневом pom.
Spring читает имена параметров метода, чтобы связать `@RequestParam` без повторения имени в
аннотации, а нарушение ограничения на уровне параметра может назвать отклонённый параметр только при
наличии этих имён в байткоде: без флага 400 сообщает об `arg0`.
