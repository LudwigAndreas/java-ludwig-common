# file-action-spring-boot-starter

[English](README.md) | [Русский]

Человек перетаскивает таблицу в браузер - и происходит бизнес-действие: четыреста строк листа Excel
становятся четырьмястами заказами или одним заказом из четырёхсот строк.

Сервис пишет `RowBinding`, обработчик и блок YAML. Всё остальное - этот модуль.

| | |
|---|---|
| **автор пишет** | какие столбцы ложатся в какие поля и что строка *значит* |
| **модуль владеет** | приёмом, бюджетом размера, определением формата по содержимому, сохранением до разбора, заявкой на идемпотентность, швом антивируса, читателем с ограниченной памятью, жизненным циклом, политикой фиксации, отчётом об отклонённых строках, конвертом операции, HTTP-поверхностью, шаблоном, удержанием, метриками и аудитом |

## Why this is not `file-ingest-spring-boot-starter`

Оба модуля читают файлы и при этом не совпадают; объединение сломало бы каждый из них.

[`file-ingest`](../file-ingest-spring-boot-starter) - **регламентный и управляемый партнёром**: он находит
объект, который кто-то положил в бакет, разбирает его относительно чекпойнта по байтовому смещению - так что
сбой продолжается ranged GET'ом, - пишет строки в промежуточную таблицу и сливает их в целевую вручную
написанным SQL. Его контракт построен вокруг четырёх миллионов строк в половине седьмого утра, когда никто
не смотрит.

Этот модуль - **интерактивный и управляемый человеком**. Ничто не продолжается с середины файла: запрос,
которого ждёт человек, не продолжают - его отправляют заново. Нет промежуточной таблицы, потому что строки
становятся вызовом домена, а не массовой вставкой. И результат отказа - не карантинная строка с байтовым
смещением, а фраза, называющая лист, номер строки и заголовок столбца, на языке читателя, в файле, который
он может исправить и загрузить снова.

Последнее отличие и есть причина, по которой контракты читателей разные. `RecordParser` сообщает абсолютные
байтовые смещения и объявляет `CheckpointKind`; здесь ни то, ни другое не имеет смысла, а то, что несёт
читатель этого модуля - лист, отображаемый номер строки, ячейки по имени заголовка, - `RecordParser` выразить
не умеет.

**Общего `file-format-core` сознательно нет.** `file-ingest` не поставляет ни одного конкретного читателя
(каждая реализация живёт в потребляющем сервисе), так что объединять было нечего, а модуль, выделенный ради
одного потребителя, - это преждевременное обобщение. Условие, при котором это изменится, записано, а не
оставлено на волю случая: *второму модулю понадобится читать CSV или XLSX*.

### Where the boundary actually is

Модуль объявляет предел - по умолчанию 25 МиБ и 100 000 строк - и отклоняет файл больше сообщением, которое
называет `file-ingest`. Выше предела - регламентный массовый импорт; ниже - то, чего ждёт человек. Предел
настраивается, а [`LargeWorkbookHeapMeasurementIT`](#the-memory-guarantee) - это то, что делает его повышение
обоснованным решением, а не надеждой.

## What a service writes

```java
@FileAction("order-import")
public class OrderImportHandler implements RowHandler<OrderLine> {

    private static final RowBinding<OrderLine> ORDER_LINES = RowBinding.of(OrderLine.class)
            .sheet("Orders")
            .column("sku", "SKU").aliases("Article")
            .column("quantity", "Qty")
            .column("price", "Price")
            .column("dueDate", "Due")
            .column("comment", "Comment").optional()
            .build();

    @Override
    public RowBinding<OrderLine> binding() {
        return ORDER_LINES;
    }

    @Override
    public RowOutcome apply(OrderLine row, FileActionContext context) {
        if (!catalogue.exists(row.sku())) {
            return RowOutcome.rejected("orders.import.unknown-sku", row.sku());
        }
        orders.create(row, context.submissionId());
        return RowOutcome.applied();
    }
}
```

```java
public record OrderLine(@NotBlank String sku, @Positive Integer quantity,
                        @PositiveOrZero BigDecimal price, LocalDate dueDate, String comment) {
}
```

```yaml
ludwig:
  file-action:
    storage:
      uploads: s3://orders/file-action/uploads
      artifacts: s3://orders/file-action/artifacts
    scanning:
      mode: required
    actions:
      order-import:
        commit-policy: PER_ROW
        mode: CONFIRM
        execution: INLINE
        required-authority: ORDER_IMPORT
```

Это всё. Эндпойнты ниже существуют с того момента, как действие настроено.

### Why the binding is code and not a row in a table

То же решение, что [`export`](../export-spring-boot-starter) принимает для своих определений отчётов, и по той
же причине. Очевидный способ сделать движок импорта переиспользуемым - дать администратору описывать
сопоставление данными через UI; и именно так модуль импорта становится вторым, непротестированным слоем
привязки без проверки типов, без поддержки рефакторинга и без ответа на вопрос «какие импорты пишут это поле».

Объявленная константой, привязка проверяет имена полей против компонентов записи при инициализации класса -
так что переименованный компонент становится отказом на старте в каждом окружении, а не пустым столбцом в
продакшене. Целевые типы берутся из записи. Ограничения - это Bean Validation на записи. Данными остаётся то,
что действительно меняется от стенда к стенду: бюджет размера, политика фиксации, окно подтверждения.

## The core path

```
POST /api/v1/file-actions/order-import   (multipart)
      |
      1. приём      предел размера проверяется ПО ХОДУ чтения тела, а не по объявленной длине
      2. спул       один проход: тело во временный файл через SHA-256
      3. формат     по магическим байтам; объявленный content type - только подсказка
      4. хранение   ObjectStore.put под хешом                 <-- ВСЕГДА, до любого разбора
      5. заявка     IdempotencyStore по хешу + действию + вызывающему
      6. запись     строка загрузки                           <-- до начала чтения
      7. антивирус  шов FileScanner, если он настроен
      |
      8. запуск ----+-- INLINE   читаем, привязываем, проверяем, применяем; 200 и терминальный конверт
                    +-- DEFERRED 202 + Operation-Location; воркер забирает по лизу
```

Ничто не разбирает файл, пока не выполнены первые шесть пунктов, и это не деталь реализации.

### Why the bytes are always stored first

Здесь планировался уровень - маленькие файлы прогонять потоком, сохранять только большие, - и это неверно по
пяти пунктам, первый из которых решает дело.

**«Потоковый» путь никогда не был потоковым.** Spring уже сбросил multipart в `java.io.tmpdir` до того, как
выполнится метод контроллера, так что отказ от хранилища не экономит запись - он только выбирает для неё
худшее возможное место. Кроме этого: запрос, не сохранивший вход, нельзя повторить, нельзя построить по нему
отчёт об ошибках со ссылкой на исходник, нельзя ответить на спор через три дня и нельзя пережить вытеснение
пода посреди разбора, пока браузер пользователя держит открытое соединение.

`FilesystemObjectStore` существует, поэтому «всегда хранилище объектов» не навязывает S3 маленькому стенду.

### Why `INLINE` and `DEFERRED` are a property and not two endpoints

Оба отвечают одним и тем же `OperationResponse`. Inline - просто случай, когда конверт уже терминален в момент
возврата, что платформенный контракт долгих операций разрешает прямо: *«202 может нести терминальный конверт,
а 200 обязан»*.

Что это даёт: стенд, обнаруживший, что его inline-действие слишком медленное, меняет одно свойство - и ни один
клиент не меняется. Будь это два эндпойнта, то же открытие стало бы несовместимым изменением API - а такие
изменения не делают, с ними живут.

Вместе с этим приходит ограничитель. Действие `INLINE`, настроенное выше
`ludwig.file-action.inline.max-rows`, **не запускается**: inline-действие на сто тысяч строк - это таймаут
запроса и удержанное соединение, обнаруженные в продакшене.

## The lifecycle

```
                        UPLOADED
                           |
          +----------------+----------------+
          |                |                |
      REJECTED         VALIDATED         APPLYING          (при mode: DIRECT VALIDATED пропускается)
                           |                |
                    (подтверждение)         |
                           +----------------+
                           |                |
                        EXPIRED           APPLIED
                     (истёк TTL)
```

`FileActionState` - это доменный жизненный цикл в `OperationResponse.detail()`, а не второй словарь статусов.
`UPLOADED` и `VALIDATED` оба отображаются в `PENDING`, и разница между ними - это и есть вся функция
подтверждения: клиент, показывающий спиннер для одного и кнопку **Подтвердить** для другого, по одному
статусу их не различит. `RuleGroup.OPERATIONS` из `architecture-rules` ломает сборку, если кто-то добавит тут
`COMPLETED`.

### Why `CONFIRM` is the default

«Перетащил лист - появилось четыреста заказов» без шага подтверждения - это четыреста неверных заказов без
отмены. Цену неверного применения платит тот, кто будет это разбирать, а предпросмотр - единственная точка,
где остановиться дёшево. `DIRECT` существует для машинных вызовов и действительно обратимых действий;
`VALIDATE_ONLY` не применяет ничего и нужен интерфейсу для мгновенной проверки.

### A confirmation applies the rows the user was shown

Проверка записывает привязанные строки в артефакт, и подтверждение применяет **этот артефакт** - оно не
перечитывает книгу.

Очевидная реализация перечитывает и привязывает заново: так проще, артефакт не нужен, и это проходит любой
тест, в котором между двумя запросами ничего не менялось. А делает она вот что: применяет не то, что было в
предпросмотре, каждый раз, когда что-то *изменилось* - справочник, прайс-лист, снятый с продажи товар, -
молча, в случае, который труднее всего воспроизвести. `ConfirmAppliesPreviewedRowsIT` подменяет байты
сохранённого объекта между проверкой и подтверждением и проверяет, что применяются всё равно строки из
предпросмотра.

Артефакт - причина, по которой `DIRECT` и `CONFIRM` - один путь кода, а не два, и он же позволяет отдать
`DocumentHandler` действительно ленивый `Stream` поверх push-ового SAX-чтения.

## The two handler shapes

```
sealed interface FileActionHandler<R>
   |- RowHandler<R>        строка за строкой   400 строк -> 400 заказов     частичный успех осмыслен
   `- DocumentHandler<R>   все строки сразу    400 строк -> 1 заказ         частичный успех бессмыслен
```

`RecordApplier` из `file-ingest` сознательно только построчный, чтобы одна плохая запись была одной карантинной
строкой, а не провалом партии из пяти тысяч. Для промежуточного импорта это верно, а здесь неверно: лист Excel,
строки которого - *позиции одного заказа*, представляет один бизнес-факт, и «мы создали первые 38 позиций
вашего заказа» - не тот результат, которого кто-то хотел. Модуль, предлагающий только построчную форму,
заставил бы каждого автора агрегатного импорта складывать строки руками внутри построчного колбэка, храня
изменяемое состояние между вызовами, которые модуль вправе батчить, повторять и распараллеливать.

Следствие, которое делает разделение несущим: **политика фиксации применима только к `RowHandler`.**
`DocumentHandler` по построению «всё или ничего», и действие, настроившее для него что-то другое, не
запускается. `FileActionHandler` запечатан по той же причине, что `Fetcher` в `reconciliation`: третья форма
была бы либо переименованием одной из этих, либо признанием, что модуль не знает, что для него значит
частичный успех.

## The one declaration the module cannot make for you

У `commit-policy` **нет значения по умолчанию** - по образцу `CachePurpose` из `cache-spring-boot-starter`,
который `CLAUDE.md` называет «единственной ошибкой, которую модуль не может обнаружить за вас».

| политика | одна отклонённая строка | подходит для |
|---|---|---|
| `ALL_OR_NOTHING` | не применяется ничего | проводка, оборотная ведомость, инвентаризация - всё, где частичный результат есть неверный результат |
| `PER_BATCH` | откатывается её партия, предыдущие остаются | массовое обновление цен, где переотправить хвост дёшево |
| `PER_ROW` | отклоняется эта строка, остальные применяются | импорт заказов, список контактов, обновление каталога |

Любое значение по умолчанию для кого-то молча неверно. Поставьте `PER_ROW` - и бухгалтерский импорт применит
две трети проводки; поставьте `ALL_OR_NOTHING` - и список из четырёхсот контактов будет отклонён целиком из-за
одной опечатки в адресе, что пользователи воспринимают как «не работает». Ни один из этих отказов не виден в
тесте - в фикстуре либо нет плохих строк, либо все плохие, - и оба видны в продакшене, как применённые
бизнес-данные. Поэтому действие без политики не запускается, а сообщение называет три значения.

Три политики отличаются ровно одним: **границей транзакции.** `PER_BATCH` и `PER_ROW` делят границу и
отличаются только тем, что делает с ней отклонённая строка, - поэтому `CommitPolicyTest` проверяет
фиксацию-против-откката, а не число применённых строк: тест по числу строк проходит для обеих на чистом файле
и не заметил бы подмены одной другой.

Отдельно от этого `reject-threshold` (по умолчанию `0.1`) отклоняет загрузку целиком, если отклонена большая
доля строк. Это защита от «это вообще не тот файл»: применять шестьдесят процентов, которые случайно
разобрались, не хотел никто, а пользователю, загрузившему прошлогодний шаблон, лучше об этом сказать. Строка,
сознательно пропущенная обработчиком, в эту долю не входит - файл, последние двести строк которого являются
намеренными дубликатами, не является «не тем файлом».

## Reading an untrusted spreadsheet

Вот здесь зубы. XLSX - это ZIP с XML, выбранный пользователем.

| Что | Как |
|---|---|
| **Никакого DOM-читателя** | `XSSFReader` + `XSSFSheetXMLHandler`, SAX. `new XSSFWorkbook(in)` превращает подготовленную книгу на 4 МБ в сотни мегабайт в памяти, так что требуемая сервису куча становится функцией того, что загрузил пользователь, - а отказ выглядит как `OutOfMemoryError`, уносящий под, в продакшене и никогда в тесте. `PoiConfinementTest` ломает сборку на самой ссылке |
| **Zip-бомбы** | нижний порог степени сжатия, предел числа элементов и суммарного распаковываемого объёма - всё решается по **центральному каталогу** ZIP, так что для решения ничего не распаковывается |
| **Таблица общих строк** | POI материализует её независимо от читателя, так что она и есть настоящий потолок памяти при чтении XLSX и проверяется отдельно, тоже по каталогу |
| **Внешние ссылки** | часть `/xl/externalLinks` - отказ. Книга, берущая значения из другого файла, импортировала бы то, что POI закешировал последним: устаревшее или пустое, и в любом случае не то, что видит пользователь |
| **Старый `.xls`** | отклоняется, причём *распознаётся*, чтобы в сообщении было «сохраните как .xlsx». У `HSSFWorkbook` вообще нет потокового режима, так что поддержка BIFF означает кучу, пропорциональную файлу пользователя |
| **Переименованный файл** | формат берётся из магических байтов. Пользователи переименовывают `.csv` в `.xlsx` постоянно, а ZIP-парсер на текстовом файле выдаёт ошибку про испорченный архив, которая ничего им не говорит |
| **Инъекция формул на выходе** | значение, начинающееся с `=`, `+`, `-` или `@`, нейтрализуется в каждом сгенерированном файле. Отчёт открывает тот, кто администрирует импорт, а не тот, кто загрузил файл |
| **XML-сущности** | единственный XML-документ, который модуль разбирает сам - `xl/workbook.xml`, ради эпохи дат, - читается с выключенными DTD и внешними сущностями |

### Why POI's own guard is not enough on its own

`ZipSecureFile.setMinInflateRatio` - **глобальный static на JVM**, поэтому он не может быть пределом на
действие, а `export` живёт в той же JVM и читает шаблоны администратора с другими допущениями. Поэтому пределы
на действие проверяются по центральному каталогу, где они могут различаться для каждой загрузки, а глобальная
настройка POI остаётся консервативным страховочным уровнем на случай, если каталог врёт. Два механизма - один
дешёвый и точный, другой дорогой и честный, - и причина, по которой нужны оба, записана у `ArchiveInspector`,
чтобы ни один не удалили как лишний.

### The memory guarantee

`PoiConfinementTest` не даёт *ссылаться* на DOM-читатели. Он не может сказать, действительно ли SAX-путь
ограничивает память: это свойство времени выполнения на ста тысячах строк - а весь модуль стоит на утверждении,
что ограничивает.

- `LargeWorkbookHeapIT` выполняется в каждой сборке и проверяет детерминированную половину: каждая строка книги
  из ста тысяч отдана наверх, и последняя несёт значения, записанные фикстурой. Читатель, ограничивший память
  тем, что тихо остановился или потерял строки под нагрузкой, падает здесь.
- `LargeWorkbookHeapMeasurementIT` держит само измерение, под `@Tag("measurement")`. Он проверяет *отношение* -
  что удержанная память после ста тысяч строк не пропорциональна файлу, - а не абсолютный предел в байтах,
  который был бы настроен под ту машину, где его впервые запустили. Он же делает DOM-чтение того же файла и
  проверяет, что оно удерживает минимум в пять раз больше, - так бюджет **доказуемо способен упасть**, а не
  предполагается таковым.

```bash
mvn -pl :file-action-spring-boot-starter verify \
    -Dfile-action.test.excluded.groups= -Dit.test=LargeWorkbookHeapMeasurementIT \
    -DargLine="-Xmx256m"
```

Он исключён из обычной сборки не потому, что медленный - он идёт секунды, - а потому что отношение памяти,
измеренное в JVM, разделяемой с другими интеграционными тестами и инструментированной JaCoCo, ненадёжно: он
проходил в одиночку и падал в полном наборе. Нестабильная гарантия хуже честного тега, потому что тест,
краснеющий по причинам, не связанным с тем, что он охраняет, кто-нибудь в конце концов удалит. Нагрузочный тест
`export` устроен так же.

## Locale, and the dates nobody notices are wrong

Каждое приведение ячейки читает локаль и часовой пояс **того, кто загрузил файл**, записанные в строку загрузки
при приёме, - а не потока: отложенная загрузка читается на воркере, где нет запроса, а подтверждение может
прийти от другого человека.

- `1 234,56` и `1,234.56` - одно и то же число для русского и американского вызывающего, а `1,234` - **нет**:
  это число около единицы для первого и около тысячи для второго. Прочитанное через `Locale.getDefault()` одно
  из них молча неверно, и какое именно - зависит от локали контейнера, а не от чего-либо в запросе.
  `RuleGroup.PRESENTATION` запрещает этот вызов.
- Разделитель групп у Excel в локалях с десятичной запятой - **неразрывный пробел**, а не обычный.
- Ячейка книги с датой хранит *число*. Модуль преобразует число, поэтому `01.02.2026` не разбирается никогда и
  вопрос «февраль или январь» не возникает.
- Эпох дат **две**. Книга, сохранённая Excel для Mac, несёт `date1904="1"`, и читатель, предполагающий
  windows-эпоху, читает каждую дату в ней **на четыре года и один день раньше** - невидимо в тестах, потому что
  фикстуры пишет та же библиотека, что читает, и невидимо на ревью, потому что код выглядит правильным.
  `WorkbookProperties` читает этот флаг.
- У локализованного короткого шаблона даты `en-US` **двузначный год**, поэтому `2/1/2026` - именно то, что
  печатает американский вызывающий, - по нему не разбирается, а средний шаблон требует названия месяца. Каждый
  локализованный шаблон пробуется ещё и с расширенным годом. Найдено тестом, а не чтением.

## Row errors are an artifact, not a `ProblemDetail`

`ProblemDetail` отвечает на «этот файл не подходит»: слишком большой, не тот формат, не прошёл антивирус,
нечитаемый архив, нет обязательного столбца. Это на файл, их мало, и они идут через единственный конвейер RFC
9457 из `web-core`, в который этот модуль вносит мапперы и для которого не поставляет своего
`@RestControllerAdvice`.

Отклонённые строки - другое дело. Их могут быть тысячи, а 400 с тремя тысячами записей - это не API, которое
клиент может отрисовать, а человек прочитать.

- `file_action_row_reject` хранит **ограниченную выборку** (по умолчанию 100). Неограниченная таблица - это сто
  тысяч строк на одну плохую загрузку, в таблице, единственный запрос к которой - «дай первую страницу».
- `GET .../rejects` отдаёт их страницами. Сравнение `rowsRejected` с `rejectsStored` - это то, как интерфейс
  понимает, что надо написать «показаны первые сто из трёх тысяч».
- `error-report: ANNOTATED_WORKBOOK` даёт пользователю **его собственный лист со столбцом `Problems`** - ту
  форму, которую он может исправить и отправить заново как есть. Для загрузки CSV отчётом будет CSV, потому что
  аннотировать нечего.
- Адресация - это лист, **1-based отображаемая строка** (включая заголовок, чтобы совпадало с нумерацией на
  полях) и **имя заголовка** столбца. Никогда не индекс: индекс неверен с момента, когда кто-то вставил
  столбец, и бесполезен пользователю в любом случае.
- Отклонение хранится как **код и аргументы**, а не как готовая фраза, - чтобы отчёт, построенный на воркере
  или прочитанный спустя месяцы, отрисовался на языке читателя, а правка пакета сообщений дошла до уже
  сохранённых строк.

## Scanning fails closed

`ludwig.file-action.scanning.mode` принимает `required` (по умолчанию), `optional` или `disabled`. Модуль
поставляет SPI `FileScanner` и **ни одной реализации**: какой антивирус работает в контуре - ICAP-устройство,
сокет `clamd`, облачный API - решение стенда, со своими секретами и режимами отказа.

При `required` и отсутствии бина `FileScanner` **приложение не запускается**, а сообщение называет значение,
отключающее требование. Так остаются только два честных исхода: «антивирус настроен» и «кто-то вслух сказал,
что его нет». Файл, отклонённый антивирусом, удаляется, а не сохраняется: бакет известно плохих файлов с теми
же правами доступа, что у хороших, - не улучшение.

Чего здесь проверить нельзя - действительно ли реализация сканирует. Бин, безусловно возвращающий `safe`,
удовлетворяет всем правилам. Этот пробел - в
[`docs/harness-enforcement.md`](../../docs/harness-enforcement.md), а не оставлен подразумеваемым.

## Idempotency

Ключ заявки - `sha256(содержимое) + действие + вызывающий`, через `IdempotencyStore`. Пользователь,
дважды щёлкнувший по зоне загрузки, или браузер, повторивший POST, ответ на который потерялся, получает конверт
первой загрузки, а не четыреста заказов дважды. Это обычный случай, а не краевой.

`IdempotencyFilter` сознательно **не** используется. Его собственный javadoc у `CachedBodyRequest` говорит это
прямо: *«Буферизация тела запроса в памяти - именно та ошибка, которой существует избежать `file-ingest`...
Эндпойнт, принимающий тела существенного размера, - не тот, где этому фильтру следует их читать»*. Multipart на
25 МиБ - именно такое тело, а хеш, который модуль и так считает по ходу потока, служит той же цели без
дополнительного прохода.

## The HTTP surface

```
POST   /api/v1/file-actions/{action}                    multipart -> 200 | 202  SubmissionResponse
GET    /api/v1/file-actions/{action}/{id}               -> SubmissionResponse (+ Retry-After, пока идёт)
POST   /api/v1/file-actions/{action}/{id}/confirm       -> 200 | 202
POST   /api/v1/file-actions/{action}/{id}/cancel        -> 202
GET    /api/v1/file-actions/{action}/{id}/rejects       -> PageResponse<RowRejectResponse>
GET    /api/v1/file-actions/{action}/{id}/error-report   -> аннотированная книга или CSV отклонений
GET    /api/v1/file-actions/{action}/template            -> пустая книга, построенная по привязке
```

`SubmissionResponse` вкладывает платформенный `OperationResponse`, а не заменяет его: универсальный клиент
опрашивает `operation` и игнорирует остальное, а клиент *этого* модуля читает счётчики строк, число отклонений
и признак того, что кто-то должен нажать **Подтвердить**, - ничего из этого шесть констант статуса выразить не
могут.

**`cancel` отвечает 202, а не 204.** Отмена кооперативная: флаг проверяется между партиями, так что остановка
*запрошена*, а не достигнута. Отмена уже завершённой загрузки возвращает конверт, а не 409, потому что
намерение вызывающего уже выполнено и ошибка заставила бы его обрабатывать успех.

**Эндпойнт шаблона** - самая дешёвая польза для пользователя из доступных. Самая частая причина падения
импорта - несовпавший заголовок, а заголовки здесь генерируются из той же привязки, по которой читатель
проверяет файл, - так что расходиться им некуда, в отличие от шаблона, который поддерживают руками в вики.

**Базовый путь фиксирован, а не настраивается.** Он был свойством, но `rest-paths` читает буквальное значение
аннотации - а значение с подстановкой никогда не совпадёт с шаблоном пути, что делало правило невыполнимым, а
не невыполненным. Правило указывало и на реальное: платформенный стартер, эндпойнты которого переезжают от
стенда к стенду, - это стартер, под который нельзя написать клиента.

## This is the only module that may name `MultipartFile`

`RuleGroup.UPLOADS` в `architecture-rules` ломает сборку в любом другом месте. До этого модуля в репозитории не
было ни одного `MultipartFile`, и первый сервис, которому понадобилась загрузка, написал бы её - с предсказуемо
плохо сделанными частями: без предела до чтения тела, с `getBytes()`, с DOM-чтением книги и с 400, несущим три
тысячи ошибок по строкам. Каждое из этих решений разумно локально и принято тем, у кого не было причин знать
лучше. Модуль исправляет состояние кода; только правило не даёт следующему сервису это повторить.

Три сознательных слепых зоны правила - реактивная загрузка, сырое тело `byte[]` и поведение самого этого
модуля - перечислены в его javadoc, а не оставлены на обнаружение.

## Configuration

```yaml
ludwig:
  file-action:
    enabled: true
    scanning:
      mode: required                 # required | optional | disabled - отказ в закрытую
    storage:
      uploads: s3://orders/file-action/uploads        # без значения по умолчанию, см. ниже
      artifacts: s3://orders/file-action/artifacts
      retention: P7D
      retention-interval: PT1H
      retention-batch-size: 100
      retention-lease: PT5M
    inline:
      max-rows: 5000                 # предел, выше которого действие INLINE не настраивается
    deferred:
      lease: PT5M
      batch-size: 5
      max-attempts: 3
      interval: PT10S
      initial-delay: PT15S
      drain-timeout: PT30S
    defaults:
      max-size: 25MB
      max-rows: 5000                 # совпадает с inline.max-rows, потому что execution по умолчанию INLINE
      max-rows-limit: 100000         # объявленный предел модуля; выше - file-ingest
      formats: [xlsx, csv]
      batch-size: 500
      reject-sample: 100
      reject-threshold: 0.1
      confirm-ttl: PT30M
      error-report: ANNOTATED_WORKBOOK
      archive:
        max-entries: 1000
        min-inflate-ratio: 0.01
        max-uncompressed: 512MB
        max-shared-strings: 16MB
        max-cell-characters: 32000
        read-timeout: PT2M
    actions:
      order-import:
        commit-policy: PER_ROW       # без значения по умолчанию; без него действие не запускается
        mode: CONFIRM                # DIRECT | CONFIRM | VALIDATE_ONLY
        execution: INLINE            # INLINE | DEFERRED
        required-authority: ORDER_IMPORT
        # любой ключ из defaults можно переопределить здесь
```

У `storage.uploads` и `storage.artifacts` **нет значений по умолчанию**, потому что единственное возможное -
локальный каталог, который работает на ноутбуке и молча пишет загрузки продакшена на эфемерный диск пода.

`defaults.max-rows` равен 5000 и совпадает с `inline.max-rows`, и это не совпадение: `execution` по умолчанию
`INLINE`, так что любое другое значение заставило бы каждое действие падать на старте, пока стенд что-нибудь не
переопределит. Было 100 000 против inline-предела 5000, и контекст с одним обычным действием не запускался -
стартер, собственные значения по умолчанию которого противоречат друг другу, не настраиваемый, а сломанный.

### Everything the application refuses to start for

`FileActionConfigurationValidator`, и каждое сообщение называет действие, свойство и допустимые значения -
потому что отказ на старте, не говорящий, что менять, это авария с лишними шагами:

- настроенное действие без бина `@FileAction` или бин без настройки;
- действие без `commit-policy`;
- построчная политика фиксации у `DocumentHandler`;
- `scanning.mode: required` без бина `FileScanner`;
- действие `INLINE` выше inline-предела или любое действие выше `max-rows-limit`;
- `required-authority` при отсутствии `security-spring-boot-starter`, когда проверять было бы нечем;
- `reject-threshold` вне 0..1 или неположительный `batch-size`;
- код сообщения из `FileActionProblemCodes`, не разрешающийся в обеих поставляемых локалях;
- бин с `@FileAction`, не являющийся `FileActionHandler`.

Сообщаются все проблемы, а не только первая.

## Deferred execution and retention

Строка загрузки **и есть** очередь, забираемая по лизу, - схема, которую уже используют `outbox` и
`reconciliation` и ради которой существует `job-core`. Брокер сообщений был бы вторым местом, где может
находиться загрузка, и эти два места умеют расходиться: сообщение без строки - работа, которую никто не найдёт,
строка без сообщения - работа, которая никогда не случится.

Лиз - это то, что делает смерть пода посреди применения восстановимой: инстанс, перестающий его продлевать,
теряет загрузку в пользу следующего тика другого, и никто в этом не участвует. `max-attempts` - причина, по
которой загрузка, падающая одинаково в четвёртый раз, попадает в отчёт, а не повторяется вечно.

**Отложенный воркер сознательно не держит `RunLock`, а задание удержания - держит.** Параллельная обработка
разных загрузок разными инстансами - это и есть смысл воркера, а `claimForProcessing` не даёт двум взяться за
одну; общекластерная блокировка там свела бы пропускную способность всего стенда к одному поду. У удержания
нечего распараллеливать, а несколько инстансов, удаляющих одни и те же объекты, - чистая потеря, так что один
держатель за раз просто правильно.

Удержание удаляет **сначала объекты**, потом помечает строку `EXPIRED`. Обратный порядок оставил бы строку,
утверждающую, что её артефактов нет, пока они ещё в бакете, - утечка, которую никто бы не заметил; этот порядок
в худшем случае оставит осиротевший объект, который видно в листинге бакета и который логируется.

Удержание - дело модуля, а не правила жизненного цикла бакета, потому что правило удалило бы объект и оставило
бы загрузку утверждающей, что результат есть, когда его больше нет, - и опрос ответил бы `SUCCEEDED` со ссылкой
в никуда, ради предотвращения чего и существует `OperationStatus.EXPIRED`.

## Audit

Через единственный `AuditSink` из `audit-core`. `FileActionAuditEvent` - типизированная поверхность для
авторов, а `toAuditEvent()` - единственное место, где собирается конверт; своего SPI здесь нет, логгера с
именем `*.audit` нет и второй маски редактирования нет. `record` **не** обёрнут в `try`/`catch`: решает ли
отказ приёмника судьбу вызывающего - это `AuditFailurePolicy`, читаемый из конфигурации, и catch в библиотеке
переопределил бы решение стенда.

Что записывается: имя файла, хеш содержимого, размер, счётчики, ответ антивируса и исход. **Ни одной ячейки
файла.** Журнал аудита читают операторы и хранят дольше, чем сам файл, и строка чьих-то заказов в нём была бы
копией персональных данных с другим сроком хранения, чем у файла, из которого она взята. Хеш - это то, что
связывает запись со сохранённым объектом, не дублируя его содержимое, - та же логика, что у
`RequestFingerprint` в `idempotency`.

## Data access

Только QueryDSL по сгенерированным Q-типам. **Это изменение не вводит третьего исключения для SQL** - их два,
`ru.ludwigandreas.ingest.bulk` и `ru.ludwigandreas.idempotency.sql`, - и `NoSqlStringsTest` ломает сборку этого
модуля, если появится ещё одно. Заявка пишется через ORM именно для того, чтобы работал столбец `@Version`,
который и не даёт потерять параллельную отмену.

Две таблицы, и сознательно не три: общей таблицы операций нет, согласно возможности
`long-running-operations`, поэтому модуль держит свою строку загрузки и отображается на конверт на своей
границе.

## What is deliberately not here

- **Нет чекпойнта с продолжением.** Ничто не продолжается с середины файла; запрос, которого ждёт человек,
  отправляют заново.
- **Нет промежуточной таблицы и `MERGE`.** Строки становятся вызовом домена, а не массовой вставкой.
- **Нет `.xls`, `.ods`, SpreadsheetML, HTML-таблиц, PDF и архива файлов.** Список разрешённых закрыт, и у
  каждого отсутствия есть причина в `SourceFormat`.
- **Нет реализации антивируса.** Есть шов и отказ на старте, если выбор не сделан.
- **Нет интерфейса.** Эндпойнты и генерируемый шаблон, а не виджет drag-and-drop.
- **Нет переиспользования `ReportWriter` из `export`.** Он связан с `ReportDefinition`, `WriterContext`,
  записями параметров и наборами столбцов по ролям, а отчёт об отклонениях - ничто из этого; зависимость от
  того модуля притащила бы его движок и одиннадцать необязательных зависимостей ради одной обёртки над
  `SXSSFWorkbook`. Дублирование сознательное и записано у писателя.

## What cannot be enforced, and is written down instead

Четыре вещи, перечисленные здесь и в
[`docs/harness-enforcement.md`](../../docs/harness-enforcement.md), а не тихо опущенные:

1. **`RowHandler` обязан быть идемпотентным по строке.** Отложенная загрузка забирается по лизу; если под умрёт
   после фиксации транзакции со строками 501-1000, но до записи прогресса, другой инстанс применит эти строки
   заново. Ничто в байт-коде не увидит, условна ли запись. Сказано на `RowHandler.apply`.
2. **`DocumentHandler` не должен вызывать партнёра внутри транзакции применения.** Одна транзакция покрывает
   все строки; вызов партнёра внутри держит соединение к базе на время его задержки, а если транзакция
   откатится - партнёр всё равно вызван. Сказано на `DocumentHandler.apply`.
3. **Верна ли объявленная `commit-policy` для домена.** Проверка на старте заставляет объявить; оценить может
   только человек.
4. **Сканирует ли `FileScanner` стенда на самом деле.** `scanning.mode` заставляет сделать выбор; проверить
   реализацию он не может.
