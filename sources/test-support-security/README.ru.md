# test-support-security

*[English](README.md) · **Русский***

Половина фикстур безопасности платформы, свободная от предметной области: билдер, который создаёт
`LudwigPrincipal` и оборачивает его в аутентификацию, переносимую запросом `MockMvc`, и `JwtDecoder`,
позволяющий контексту стартовать без OIDC discovery. Каждый сервис держит свои константы со своими ролями
и субъектами.

## Почему это отдельный модуль

Это выглядит оверинжинирингом, пока не попробуешь иначе.

Maven строит DAG реактора по **всем** объявленным зависимостям, независимо от области — включая `test`,
`provided` и `optional`. Этим фикстурам нужен `LudwigPrincipal`, значит они обязаны зависеть от
`security-spring-boot-starter`. Но [`test-support`](../../sources/test-support/README.ru.md) должен быть пригоден для
*каждого* модуля, включая самые верхние: интеграционные тесты есть и у `db-core`, и у `audit-core`. Будь
обе половины одним артефактом, этот артефакт зависел бы от `security-spring-boot-starter`, а от него
зависел бы `db-core` — и любая контейнерная зависимость с областью `test`, добавленная в стартер
безопасности, замкнула бы цикл, который валит весь реактор, а не только тот модуль, где её добавили.

Слитый модуль сегодня действительно собрался бы: у `security-spring-boot-starter` пока только юнит-тесты,
поэтому обратной зависимости он не объявляет. Это совпадение, а не проект: цикл возникнет в первый же
раз, когда стартеру безопасности добавят интеграционный тест, и лечиться он будет этим же разделением —
только под давлением и с красным реактором. Поэтому оно сделано сейчас, пока бесплатно.

Разделение к тому же честно описывает обе половины. Контейнерная — инфраструктура фреймворка, ничего не
знающая о предметной области платформы; эта знает, что такое principal.

## Что внутри

| Тип | Что это |
|---|---|
| `TestPrincipalBuilder` | `user(...)` / `partner(...)` / `service(...)`, далее роли, тенант, разрешения, атрибуты → `LudwigPrincipal`, `LudwigAuthentication` или `RequestPostProcessor` |
| `RejectingJwtDecoderConfiguration` | `@TestConfiguration`, чей `JwtDecoder` отвергает любой токен |
| `DefaultCallerConfiguration` | Опционально: `MockMvcBuilderCustomizer`, подставляющий одного вызывающего по умолчанию |

## Как включить

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>test-support-security</artifactId>
    <scope>test</scope>
</dependency>
```

Он тянет `test-support` за собой, так что сервис объявляет одну зависимость, а не две.

```java
@TestConfiguration(proxyBeanMethods = false)
@Import(RejectingJwtDecoderConfiguration.class)
public class TestSecurityConfiguration { }
```

и небольшой класс констант самого сервиса:

```java
final class TestPrincipals {

    static final String ADMIN_SUBJECT = "admin-subject";

    static RequestPostProcessor admin() {
        return TestPrincipalBuilder.user(ADMIN_SUBJECT).roles("ROLE_CATALOG_ADMIN").postProcessor();
    }
}
```

## Почему разделён только билдер

Классы `TestPrincipals` двух сервисов выглядели почти одинаковыми, но таковыми не были. У них общая
*форма* и полностью разный словарь: `crud-service-example` говорит про редакторов, наблюдателей, код
партнёра и `ROLE_CATALOG_ADMIN`; `notification-service` — про поддержку, тенантов и SPIFFE-идентификатор
сервиса-соседа. Вынести любой из них целиком означало бы выдать другому сервису фикстуру, набитую
именами из чужой предметной области: непонятную никому и неверную в проверках.

Поэтому сюда переехал механизм, а имена остались у сервисов. `TestPrincipalBuilder` не содержит
предметного словаря и не должен его приобрести.

## Почему декодер отвергает любой токен

Здесь легко ошибиться в обратную сторону. Декодер, который Spring Boot строит из `issuer-uri`, выполняет
OIDC discovery при создании бина, поэтому без замены тесту пришлось бы достучаться до провайдера
идентичности только чтобы поднять контекст. Замена именно **отвергает**, а не принимает: тесты
аутентифицируются подстановкой principal, так что принятый токен не нужен никому, а декодер, молча
принимающий что угодно, скрыл бы настоящую ошибку конфигурации — тест прошёл бы на цепочке безопасности,
которая в продакшене пропускала бы неподписанные токены.

Полезно знать и вне тестов: в продакшене предпочитайте `jwk-set-uri`, который загружается лениво, если
сервис должен уметь стартовать при недоступном провайдере.

## Почему вызывающий по умолчанию — опциональный

Отвергающий декодер нужен обоим сервисам. Подставлять админа по умолчанию нужно только
`crud-service-example`; `notification-service` намеренно называет вызывающего в каждом запросе, потому
что несколько его тестов проверяют именно то, в чём отказано вызывающему **без** роли. Вложи мы эту
подстановку в конфигурацию декодера — те тесты тихо превратились бы из «анонимному отказано» в «админу
разрешено»: тест продолжает проходить, но больше ничего не проверяет.

Поэтому `DefaultCallerConfiguration` отдельный, и сервис, который его включает, сам называет вызывающего.
Запрос по умолчанию применяется первым, а собственный `.with(...)` запроса — после него, так что тест,
назвавший более узкого вызывающего, побеждает; именно этот порядок и делает подстановку безопасной.
