# messaging-spring-boot-starter

[English version](README.md)

Потребительская половина конверта, который производит `outbox-spring-boot-starter`.

`outbox-spring-boot-starter` корректно владеет отправкой. Потребление же было настроено в этом
репозитории трижды, и ни одна пара настроек не совпадала ни в чём существенном — а две из трёх теряли
записи. Этот модуль — один набор решений о потребителе, принятый один раз, который сервис запрашивает по
имени.

## Что было не так

| | notification `NotificationMessagingConfig` | user-settings `UserSettingsKafkaAutoConfiguration` | identity-projection `IdentityKafkaAutoConfiguration` |
|---|---|---|---|
| фабрика контейнеров | своя, типизированная | своя, `ConsumerFactory<?,?>` с wildcard **и приведением типа** | **нет** — использовалась фабрика Spring Boot по умолчанию |
| обработчик ошибок | `DefaultErrorHandler` + `DeadLetterPublishingRecoverer` | **нет** | **нет** (по умолчанию от Boot) |
| задержки повторов | `ExponentialBackOff(1с, ×3, максимум 30с)` | — | — |
| без повторов | `DeserializationException`, `MessageConversionException` → сразу в DLT | — | — |
| режим подтверждения | `RECORD` | `MANUAL` | по умолчанию (`BATCH`) |
| десериализатор | `ErrorHandlingDeserializer` вокруг `JsonDeserializer`, `setUseTypeHeaders(false)` | значения по умолчанию, полезная нагрузка как `String` и разбор вручную | то же |
| dead-letter топик | `<topic>.dlt`, партиция `-1` | — | — |

Три режима подтверждения для одной семантики — это отдельная ошибка: `RECORD`, `MANUAL` и `BATCH` дают
три разных ответа на вопрос «что происходит с остальными записями этого опроса, когда одна из них
завершается неудачей».

Два режима отказа были разными, и оба теряют данные:

- **user-settings**: `AckMode.MANUAL` без обработчика ошибок. Слушатель, выбросивший исключение до
  подтверждения, никогда не подтверждал запись, поэтому она доставлялась повторно — бесконечно, без
  задержек, на полной скорости. Проекция, которая не смогла применить изменение из-за сработавшего
  ограничения, не отставала; она останавливалась, нагружая брокер, и оставалась остановленной.
- **identity-projection**: обработчик Boot по умолчанию делает десять попыток без задержек, а затем
  **пишет в лог и идёт дальше**. Запись терялась, и единственным следом была строка в журнале сервиса,
  который никто не читает.

Ещё два дефекта были обнаружены при разработке этого модуля — оба были невидимы, пока тест с настоящим
брокером не начал их искать. Ни один не является теоретическим; оба существовали в работающем коде.

- **Отравленную запись вообще нельзя было отправить в dead-letter топик.**
  `DeadLetterPublishingRecoverer` переотправляет исходный `byte[]`, если отказ произошёл при
  десериализации, — и это правильно, потому что байты, которые не удалось разобрать, — единственное
  достоверное представление такой записи. `KafkaTemplate` приложения настроен на `StringSerializer` или
  `JsonSerializer` и отправить их не может: публикация падает с `SerializationException: Can't convert
  value of class [B`, смещение всё равно фиксируется, и запись исчезает. Ровно в том единственном случае,
  для которого dead-letter топик и существует. Исправлено в `DeadLetterTemplates`, который выдаёт
  восстановителю продюсер с `DelegatingByTypeSerializer`.
- **Бюджет попыток был на единицу больше, чем говорил комментарий.** `ExponentialBackOff.maxAttempts` в
  Spring считает выдаваемые *интервалы*, то есть число повторов; перед первой доставкой интервала нет.
  Поэтому `setMaxAttempts(4)` даёт пять доставок. В `NotificationMessagingConfig` стояло 4 под
  комментарием «попытки до отправки записи в dead-letter, включая первую». Здесь `max-attempts` означает
  то, что говорил тот комментарий, а интеграционный тест считает доставки.

## Что такое этот модуль

Один построитель `ConcurrentKafkaListenerContainerFactory` плюс контракт заголовков, общий для обеих
половин. Больше ничего. Модуль не объявляет ни слушателя, ни топика, ни типа полезной нагрузки — они
принадлежат сервису-потребителю и остаются единственным, что потребитель обязан назвать сам.

```
ru.ludwigandreas.messaging
├── api             MessageHeaders, InboundEnvelope, EnvelopeReader, DeadLetterTopics
├── settings        MessagingProperties и разрешение настроек по потребителям
├── config          автоконфигурации
├── consumer        ListenerContainerFactoryBuilder — единый набор решений
├── serialization   безопасный JSON-десериализатор и проверка версии
├── dlt             продюсер dead-letter и восстановитель с аудитом
├── audit           DeadLetterAudit
├── metrics         счётчики и сигнал тишины
└── error           два отказа, которые поднимает этот модуль
```

`outbox-spring-boot-starter` **зависит от этого модуля** — от имён заголовков из `api`. Это единственное
работающее направление: данному модулю нужен `KafkaTemplate` для отправки в dead-letter, а не outbox, и
взаимная зависимость была бы циклом в реакторе независимо от scope — граф реактора Maven scope
игнорирует. Поэтому любая необязательная зависимость здесь становится зависимостью каждого потребителя
outbox, и именно поэтому spring-kafka, web-core, API валидации и starter идемпотентности объявлены
`optional`. Запасной вариант, если это ребро когда-нибудь придётся развернуть, записан в POM: выделить из
`api` модуль `messaging-core` без зависимостей.

## Конверт

`OutboxEvent` с самого начала несёт `aggregateType`, `aggregateId`, `eventType`, `eventVersion`,
`idempotencyKey` и `traceId`, и `KafkaOutboxDispatcher` часть из них помещал в запись — но имена жили в
диспетчере строковыми литералами, поэтому прочитать их обратно потребитель мог только скопировав литерал.
Один потребитель так и сделал, с комментарием о том, что две стороны обязаны совпадать. Двое других
сдались и разбирали полезную нагрузку — поэтому `eventVersion` дошёл до production, и его никто не читал.

| Заголовок | Что несёт |
|---|---|
| `ludwig-event-type` | вид события; то, по чему потребитель делает диспетчеризацию |
| `ludwig-event-version` | версия схемы полезной нагрузки — см. [Версии схемы](#версии-схемы-полезной-нагрузки) |
| `ludwig-aggregate-type` | тип агрегата, о котором событие |
| `ludwig-aggregate-id` | экземпляр агрегата |
| `ludwig-idempotency-key` | ключ дедупликации от производителя — работает и при повторной публикации |
| `ludwig-trace-id` | W3C trace id, если трасса производителя попала в выборку |
| `ludwig-produced-at` | когда производитель отправил запись, ISO-8601 UTC — **не** метка брокера |
| `X-Correlation-Id` | идентификатор корреляции |

`X-Correlation-Id` намеренно выбивается из схемы префиксов. Это то имя, которое
`observability-spring-boot-starter` уже читает и пишет и в HTTP-запросах, и в записях Kafka, и оно там
настраиваемое. Идентификатор, который ходит под одним именем по HTTP и под другим через брокер, — это два
разных идентификатора с точки зрения любого запроса к логам, а это и есть проблема «двух домов», которую
модуль призван устранить, а не добавить. Он перечислен здесь, чтобы у потребителя было одно место для
поиска, а `EnvelopeReader` принимает настроенное переопределение.

### Устаревшие имена и когда их можно убрать

`KafkaOutboxDispatcher` писал `event-type`, `event-version`, `idempotency-key` и `trace-id` до появления
этого модуля, и на реальных топиках есть записи с этими именами — срок хранения топика переживает релиз.
Поэтому **диспетчер пишет оба варианта**, а `EnvelopeReader` читает сначала канонический и при его
отсутствии — устаревший.

- Устаревшую **запись** можно убрать, когда во всех топиках пройдёт окно хранения с развёрнутым новым
  производителем.
- Устаревшее **чтение** — когда ни одну группу потребителей нельзя будет попросить перечитать поток с
  момента раньше этой точки; это наступает позже.

Убрать любую половину раньше — значит получить потребителя, читающего `null` там, где значение есть. Для
`ludwig-event-type` это означает запись, молча проигнорированную как неизвестный тип: нигде не ошибка, а
реплика просто никогда не узнает об этом изменении.

## Подключение

Потребитель запрашивает у построителя фабрику того самого типа, какой у его полезной нагрузки, и
регистрирует её под своим именем бина:

```java
@Bean(CONTAINER_FACTORY)
ConcurrentKafkaListenerContainerFactory<String, OrderCreated> orderListenerContainerFactory(
        ListenerContainerFactoryBuilder builder, OrderProperties properties) {
    return builder.forJsonPayload("orders-ingress", OrderCreated.class, properties.getTopic());
}
```

`forTextPayload(name, topics...)` — то же самое для потребителя, который сам разбирает JSON. Это верная
форма для слушателя, который делает диспетчеризацию по `ludwig-event-type` среди нескольких типов
полезной нагрузки в одном топике — чего фабрика, привязанная к одному типу, выразить не может.

Первый аргумент — **имя потребителя**: это ключ, под которым лежат его переопределения в
`ludwig.messaging.consumers.*`, и метка его метрик. Оно намеренно не совпадает с именем бина:
переименование бина не должно быть молчаливым изменением конфигурации.

### Почему конструирование, а не инъекция

`UserSettingsKafkaAutoConfiguration` раньше принимал `ConsumerFactory<?, ?>` и приводил его к типу, с
комментарием о том, что запрос `ConsumerFactory<String, String>` «выглядит аккуратнее и не работает»,
потому что у сервиса, объявившего собственную фабрику с другими параметрами типа, нет бина с такой
сигнатурой. Диагноз был верным, а приведение типа — неверным лечением: оно убирало проверку компилятора
вместо того, чтобы её удовлетворить. Здесь ничего с общей сигнатурой не запрашивается: фабрика
*конструируется* под собственный тип потребителя, поэтому конфликтовать не с чем и приводить нечего.

### Слушатель не должен объявлять `Acknowledgment`

Режим подтверждения по умолчанию — `RECORD`, а Spring Kafka передаёт `Acknowledgment` только в ручных
режимах. У слушателя, который всё же его объявил, этот параметр разрешается как **полезная нагрузка**, и
каждая запись падает с `Payload value must not be empty` — а при наличии обработчика ошибок это означает,
что каждая запись топика уходит в dead-letter. Обеим перенесённым проекциям пришлось убрать параметр.

Поведение фиксации смещений при этом не меняется: запись, дошедшая до конца слушателя, фиксируется
контейнером, а запись, обработка которой выбросила исключение, оставляет смещение незафиксированным.

## Соглашение об обработке ошибок

`NotificationMessagingConfig` был единственным из трёх, где решения были продуманы, поэтому именно его
решения стали значениями по умолчанию платформы, а его обоснования переехали в код, который теперь их
принимает.

- **`ErrorHandlingDeserializer` вокруг ключа и значения.** Некорректная полезная нагрузка становится
  записью, которую обработчик ошибок может классифицировать и отправить в dead-letter. Без него
  исключение возникает до слушателя, контейнеру нечего восстанавливать, и он бесконечно повторяет одни и
  те же неразбираемые байты — классическая остановка на «отравленной пилюле».
- **Авто-фиксация выключена безусловно.** Смещения фиксирует контейнер после возврата из слушателя, а не
  брокер по таймеру. При авто-фиксации отказ базы данных сдвигает смещение за все записи, пришедшие за
  это время, и эти записи исчезают — отказ, который выглядит как «уведомления за вторник не пришли» и не
  оставляет следов.
- **`DefaultErrorHandler` с `ExponentialBackOff`**: по умолчанию 1с × 3 с ограничением 30с, четыре
  доставки включая первую, переопределяется для каждого потребителя.
- **`DeserializationException` и `MessageConversionException` помечены как неповторяемые.** *Полезная
  нагрузка, которую не удалось десериализовать, не десериализуется никогда, поэтому она идёт прямо в
  dead-letter топик, а не тратит четыре попытки на доказательство этого.*
- **`DeadLetterPublishingRecoverer` в `<topic>.dlt`, партиция `-1`.** `-1` позволяет брокеру выбрать
  партицию: сохранение исходной требовало бы, чтобы у dead-letter топика было не меньше партиций, чего
  никто не гарантирует, — а отправка в несуществующую партицию **падает молча**.
- Задержка находится в *контейнере*, поэтому отказавшая запись не занимает поток в ожидании, и вся
  партиция приостанавливается — именно это сохраняет порядок повторённой записи относительно следующих.

Каждая отправка в dead-letter считается (`ludwig.messaging.dead.lettered`) и записывается как событие
`audit-core`. *Неудавшаяся* отправка считается отдельно (`ludwig.messaging.dropped`) и имеет собственное
действие в аудите, потому что она существенно хуже: запись исчезла, а платформа считает, что у неё есть
страховка, которой нет.

## Подтверждение смещений

Стандартом выбран `RECORD`. При доставке «хотя бы один раз» и доступной дедупликации перед слушателем
подтверждение по записи даёт наименьшее окно повторной доставки и самые простые рассуждения: запись
зафиксирована, когда её слушатель вернул управление, и отказ одной записи не влияет на остальные записи
опроса.

`MANUAL` остаётся доступным для потребителя, который действительно работает пакетами, и его выбор требует
установки `ludwig.messaging.consumers.<name>.ack-mode` — чтобы никто не получил его по наследству
случайно, как это произошло с user-settings, оказавшимся с ручным подтверждением и без обработчика
ошибок.

## Дедупликация на стороне потребителя

**Inbox уже существует.** `idempotency-spring-boot-starter` поставляет
`IdempotentRecordFilterStrategy`, `IdempotencyScopes`, `IdempotencyStore` с
`ClaimMode.TRANSACTIONAL`, таблицу заявок, TTL и `IdempotencyPurgeJob`. Общий inbox с дедупликацией и
удержанием готов, и создание второго здесь одним коммитом воспроизвело бы ровно ту проблему «двух домов»,
которую эта серия консолидаций устраняет.

Не хватало никогда не хранилища. Не хватало того, что его подключение требовало строки в собственной
фабрике контейнеров каждого сервиса, — поэтому дедупликацию сервис получал, если помнил о ней, а не по
конфигурации. Этот модуль по умолчанию присоединяет любой `RecordFilterStrategy` из контекста к каждой
фабрике, которую строит, — поэтому развёртывание с `ludwig.idempotency.kafka.enabled=true` получает
дедупликацию на каждом потребителе.

Отказ для отдельного потребителя — `ludwig.messaging.consumers.<name>.dedup=false`, и проекции, которая
сходится к значению, следует им воспользоваться: она уже корректна при повторной доставке, а заявка перед
ней добавляет таблицу, запись и режим отказа ради гарантии, которая у неё уже была.

### Транзакция, которая нужна заявке

Заявка в режиме `ClaimMode.TRANSACTIONAL` на контейнере без менеджера транзакций фиксируется **вне**
транзакции слушателя, поэтому ключ остаётся занятым работой, которая была откатана, — а повторная
доставка этой записи, неизбежная, поскольку смещение тоже не было зафиксировано, отбрасывается как
дубликат. Сообщение не доставляется никогда, и никто об этом не сообщает.

Поэтому `MessagingDedupAutoConfiguration` читает `ludwig.idempotency.kafka.mode` и присоединяет менеджер
транзакций приложения, когда режим `TRANSACTIONAL`. Установка
`ludwig.messaging.dedup.container-transaction=false` при транзакционном режиме заявки **отвергается при
старте**: это не тот компромисс, который развёртывание вправе выбрать.

## Версии схемы полезной нагрузки

`ludwig-event-version` производился с самого начала и не читался никем. Это не отсутствие удобства. Схема,
которая эволюционирует под потребителем, игнорирующим версию, — это путь молчаливой порчи данных: Jackson
отображает байты на *текущий* тип потребителя, переименованное или разделённое поле приходит со значением
по умолчанию для Java, слушатель пишет строку в базу, и нигде не фиксируется, что событие версии 2 было
применено потребителем версии 1. Строка выглядит как обычная строка.

Потребитель объявляет границы и получает отказ:

```yaml
ludwig:
  messaging:
    consumers:
      orders-ingress:
        accepted-versions: { min: 1, max: 1 }
```

`VersionGatingDeserializer` читает заголовок внутри `Deserializer.deserialize(topic, headers, data)` —
единственного места конвейера, которое может прочитать версию и решить **не** разбирать запись.
`RecordInterceptor` выполняется после того, как контейнер десериализовал значение, то есть отображение уже
произошло. Отказ проявляется как `DeserializationException`, который неповторяем, поэтому запись попадает
в dead-letter топик с первой попытки. И это правильно: версия не меняется при повторной доставке.

По умолчанию границ нет, и намеренно: граница, придуманная этим модулем, отправила бы в dead-letter
живой трафик в тот самый деплой, который её вводит.

Этот класс отвергает, но не маршрутизирует. Отправка неизвестной версии в отдельный топик — это тот же
dead-letter топик под другим именем, и потребитель, которому он нужен, задаёт `dead-letter.suffix`. Чего
не должно происходить и что здесь становится невозможным — это десериализация всё равно.

## Настройки безопасности, которые нельзя ослаблять

`setUseTypeHeaders(false)` — на каждом JSON-десериализаторе, который строит этот модуль, и **без свойства,
которое возвращало бы его обратно**.

> Тип фиксирован этим потребителем, а не берётся из заголовка записи: десериализатор, управляемый
> заголовком, создаст экземпляр любого класса, который назовёт производитель, и это готовый гаджет
> десериализации.

Конкретно: при включённых заголовках типа класс, экземпляр которого создаёт Jackson, выбирает тот, кто
записал сообщение. Всё, что может писать в топик, выбирает класс из classpath потребителя и получает его
экземпляр с полями, выбранными атакующим. Classpath сервиса на Spring Boot велик, а цепочки гаджетов
против полиморфной типизации Jackson — документированное и повторяющееся семейство CVE. «Мы доверяем своим
топикам» — это и есть то предположение, которое не выполняется, потому что топик не является
аутентифицированным вызывающим.

user-settings и identity-projection обходили этот вопрос, принимая полезную нагрузку как `String` и
разбирая её вручную. Перевод их на общую типизированную фабрику не должен выдавать им гаджет как цену
единообразия — поэтому настройка применяется один раз там, где ни один из них не может о ней забыть.
Потребитель, которому действительно нужно несколько типов полезной нагрузки в одном топике, делает
диспетчеризацию по `ludwig-event-type` — значению, которое *он* сопоставляет уже известному ему типу, а
не имени класса, выбранному производителем.

## Наблюдаемость

`MicrometerConsumerListener` привязан к каждой фабрике потребителей, которую строит этот модуль, и
публикует собственные метрики клиента Kafka — в том числе
`kafka.consumer.fetch.manager.records.lag`. **Раньше в этой платформе их не привязывал никто**, поэтому у
платформы со starter'ом наблюдаемости вообще не было метрики отставания потребителя — числа, с которого
начинается любой runbook по Kafka.

| Метрика | Значение |
|---|---|
| `kafka.consumer.fetch.manager.records.lag` | отставание по топику, партиции и группе, от клиента |
| `ludwig.messaging.consumed{topic}` | записи, переданные слушателю |
| `ludwig.messaging.retries{topic}` | попытки повтора |
| `ludwig.messaging.dead.lettered{topic,dlt,exception}` | **алерт на любое значение** |
| `ludwig.messaging.dropped{topic}` | неудавшаяся отправка в dead-letter — должна быть нулём всегда |
| `ludwig.messaging.silent{topic}` | 1, если за настроенное окно ничего не пришло |

### Тишина

`ludwig.messaging.silent` — это сигнал, которого отставание дать не может. Топик без трафика, потребитель
с умершим контейнером и потребитель с опечаткой в group id, из-за которой ему не назначили партицию, — все
дают отставание, равное нулю. Различить их могут только часы, и только если кто-то скажет, какое
отсутствие допустимо:

```yaml
ludwig.messaging.consumers.orders-ingress.silence-threshold: 15m
```

По умолчанию не задано, потому что порог — это утверждение о трафике топика, которое может сделать только
владеющая им команда, а неверный порог хуже отсутствующего. Это тот же отказ, что и не пришедший файл в
file-ingest, и выглядит он так же: живой pod, пустой лог и проекция, тихо устаревающая.

Часы запускаются при **старте**, а не с первой записью: потребитель, который вообще ничего не получает, —
самый важный случай, и иначе он никогда бы не сообщил о тишине. Датчик — это поставщик значения,
вычисляемый при сборе метрик, а не значение, которое кто-то периодически пишет: планировщик, который
должен продолжать работать, чтобы датчик оставался правдивым, — это ещё одна вещь, способная
остановиться молча, то есть ровно тот отказ, о котором датчик и сообщает.

Интерцептор корреляции, который поставляет `observability-spring-boot-starter`, **композируется** в каждую
построенную здесь фабрику, а не заменяется. Boot применяет его только к той фабрике, которую
конфигурирует сам, поэтому собственная фабрика `NotificationMessagingConfig` теряла идентификатор
корреляции для каждой потреблённой записи — латентно, потому что код слушателя был верным, а связать их
было нечем.

## Неблокирующие топики повторов

Поставляются, включаются по каждому топику отдельно и отвергаются при старте для потребителя, который
зависит от порядка.

Блокирующий `DefaultErrorHandler` приостанавливает партицию, пока выполняет повторы. Это блокировка головы
очереди, и именно она сохраняет порядок. Неблокирующие топики повторов не останавливают партицию,
переотправляя отказавшую запись, поэтому запись применяется **после** записей, произведённых позже неё.
Производитель публикует `orderingKey` в каждом событии, и это обещание, что события с одинаковым ключом
применяются по порядку. Перевод топика на неблокирующие повторы молча нарушает это обещание, а симптом —
значение, которое исправили и которое возвращается через несколько часов: труднее всего связать с
причиной, потому что к моменту, когда кто-то посмотрит, топик повторов пуст, а логи провернулись.

Включение состоит из двух явных шагов и одного объявления:

```yaml
ludwig:
  messaging:
    retry-topics.enabled: true          # включает @EnableKafkaRetryTopic для приложения
    consumers:
      search-index-feed:
        ordered: false                  # без этого старт падает
        topics: [ search.index.feed ]   # без этого конфигурация не применится ни к одному топику
        retry.non-blocking: true
```

Переключатель уровня модуля существует в дополнение к флагу потребителя, потому что
`@EnableKafkaRetryTopic` меняет способ инициализации *каждого* аннотированного слушателя в приложении, а
это не то, что свойство одного потребителя вправе сделать с сервисом, который этого не ожидал. `topics`
обязателен, потому что `RetryTopicConfiguration` без включённых топиков не применяется ни к чему —
включение выглядит сработавшим, а повторы продолжает делать блокирующий обработчик.

`ludwig.messaging.defaults.retry.non-blocking` отвергается сразу: отказ от порядка — это решение о
семантике одного топика.

Топики повторов работают *по времени* — запись уходит в топик повторов, а её потребитель приостанавливается
до истечения задержки, — поэтому `@EnableKafkaRetryTopic` нужен планировщик. Без него контекст падает с
сообщением `Either a RetryTopicSchedulerWrapper or TaskScheduler bean is required`, которое не называет ни
этот модуль, ни свойство, вызвавшее отказ. Модуль поставляет однопоточный
`RetryTopicSchedulerWrapper`, если у приложения нет ни того, ни другого. Обёртка, а не просто бин
`TaskScheduler`, и это намеренно: обычный бин был бы вторым `TaskScheduler` в контексте, а инфраструктура
`@Scheduled` в Spring разрешает его по типу — то есть модуль, публикующий такой бин, молча перевёл бы все
запланированные методы приложения на пул потоков, размер которого выбрал этот модуль.

## Справочник конфигурации

Каждый ключ под `ludwig.messaging.consumers.<name>` существует и под `ludwig.messaging.defaults`, что
применяется ко всем потребителям. Блок потребителя переопределяет только то, что назвал, — и все поля
объявлены допускающими `null` именно для того, чтобы это было возможно.

| Ключ | По умолчанию | Примечания |
|---|---|---|
| `enabled` | `true` | дополнительно требует `KafkaListener` в classpath |
| `correlation-header` | `X-Correlation-Id` | должен совпадать с `ludwig.observability.correlation.kafka.header-name` |
| `metrics.enabled` | `true` | включает метрики клиента Kafka, в том числе отставание |
| `dedup.enabled` | `true` | присоединяет `RecordFilterStrategy` из контекста, если он есть |
| `dedup.container-transaction` | из режима заявки | `false` при `TRANSACTIONAL` отвергается |
| `retry-topics.enabled` | `false` | включает неблокирующую инфраструктуру для всего приложения |
| `…<name>.ack-mode` | `RECORD` | `MANUAL` для потребителя, действительно работающего пакетами |
| `…<name>.concurrency` | как у фабрики | |
| `…<name>.ordered` | `true` | `false` — предварительное условие неблокирующих повторов |
| `…<name>.dedup` | `true` | `false` для сходящейся проекции |
| `…<name>.silence-threshold` | нет | датчик не создаётся, пока не задан |
| `…<name>.retry.initial-backoff` | `1s` | |
| `…<name>.retry.multiplier` | `3.0` | |
| `…<name>.retry.max-backoff` | `30s` | |
| `…<name>.retry.max-attempts` | `4` | **доставки, включая первую** |
| `…<name>.retry.non-blocking` | `false` | см. выше |
| `…<name>.dead-letter.enabled` | `true` | `false` означает «записать в лог и потерять» |
| `…<name>.dead-letter.suffix` | `.dlt` | |
| `…<name>.accepted-versions.min` / `.max` | `1` / без границы | граница включает проверку версии |
| `…<name>.topics` | пусто | нужны только для включения неблокирующих повторов |

## Предварительное условие развёртывания: dead-letter топики

**Это предварительное условие развёртывания, а не сноска. Создайте dead-letter топики до того, как это
попадёт в production.**

У двух из трёх перенесённых потребителей dead-letter топика не было вовсе, а теперь он есть. Топики:

| Исходный топик | Dead-letter топик | Новый в этом изменении |
|---|---|---|
| топик приёма уведомлений (`ludwig.notification.ingress.topic`) | `<он же>.dlt` | нет — уже существовал |
| `ludwig.user-settings.projection.topic`, по умолчанию `user.settings` | `user.settings.dlt` | **да** |
| `ludwig.identity.kafka.topic`, по умолчанию `oidc.users` | `oidc.users.dlt` | **да** |

Dead-letter топик, который автоматически создаётся в dev и отсутствует в production, — это та же
молчаливая потеря в другой одежде. `auto.create.topics.enable` в Kafka обычно включён в кластере
разработки и обычно выключен в production, а это ровно та конфигурация, при которой всё проходит любые
тесты и падает на первой отравленной записи в production: публикация не удаётся, смещение фиксируется, а
`ludwig.messaging.dropped` становится ненулевым для записи, которую теперь никто не найдёт.

Число партиций и репликация совпадать с исходным топиком не обязаны — восстановитель отправляет в
партицию `-1` и позволяет брокеру выбрать именно для того, чтобы это было не нужно. Срок хранения стоит
сделать *дольше*, чем у исходного топика: смысл этого топика в том, что его читает человек, а человек
читает его после выходных.

Настройте алерт на ненулевое значение `ludwig.messaging.dead.lettered` и на любое ненулевое значение
`ludwig.messaging.dropped` — второе означает, что отказывает сам восстановитель, и самая вероятная
причина — топик, который так и не создали.

## Правила, которые не дадут этому повториться

Оба дефекта, которые устраняет этот модуль, были дефектами **упущения** — а такие обзор кода не ловит,
потому что на экране нет ничего, против чего можно возразить. Исправление кода исправляет состояние
репозитория; повторение того же разумного локального решения в следующем квартале останавливает только
правило.

Группа `kafka` в `architecture-rules` получает два правила:

- **`kafka.container-factories-set-an-error-handler`** — каждый метод, возвращающий
  `ConcurrentKafkaListenerContainerFactory`, либо вызывает `setCommonErrorHandler`, либо получает фабрику
  из `ListenerContainerFactoryBuilder`. Это та проверка, которая делает дефекты user-settings и
  identity-projection невозможными повторно. Её границы указаны на самом правиле: она не видит фабрику,
  собранную во вспомогательном методе, и не видит фабрику, которую конфигурирует Boot.
- **`kafka.no-private-dead-letter-recoverer`** — никто вне `ru.ludwigandreas.messaging..` не создаёт
  `DeadLetterPublishingRecoverer`.

`checkstyle-rules` получает **`SecondDeadLetterSuffix`**, которое роняет сборку на втором объявлении
константы с суффиксом dead-letter. Разделение намеренное и совпадает с тем, которое репозиторий уже
провёл для маски редактирования: ArchUnit читает байт-код, где *значение* `static final String` — это
запись в constant pool, которую `JavaField` не раскрывает, поэтому «нет поля со значением `.dlt`» там
невыразимо.

Этот модуль прогоняет весь набор правил против себя, и набор нашёл две настоящие проблемы, которые были
исправлены, а не подавлены: цикл пакетов между `config` и `consumer` (настройки переехали в собственный
пакет — то же решение, к которому пришёл notification-service) и отсутствие `@Validated` на
`MessagingProperties`.

## Чего этот модуль намеренно не делает

- **Не поставляет хранилище дедупликации.** См. [Дедупликация](#дедупликация-на-стороне-потребителя).
- **Не унифицирует три употребления слова «идемпотентность» на платформе.**
  `OutboxProperties$Idempotency` — это дедупликация по собственной строке outbox в момент публикации;
  `IdempotencyKey` в reconciliation — тип-значение для ключа, обращённого к партнёру;
  `idempotency-spring-boot-starter` — хранилище дедупликации работы. Это три законно разных механизма, а
  не разбросанные копии одного.
- **Не берёт зависимость на web-core, которой можно избежать.** Здесь ничто не доходит до HTTP-ответа:
  неподдерживаемая версия события поднимается внутри десериализатора в потоке слушателя, и её пункт
  назначения — топик. Бандл i18n и поставляемый `ExceptionProblemMapper` существуют для сервиса, который
  решит переподнять одно из этих исключений на своей поверхности — например, для эндпоинта повторной
  обработки записи из dead-letter, — а web-core объявлен `optional`, чтобы
  `outbox-spring-boot-starter` его не наследовал.
- **Не переводит `OidcUserEventListener` на типизированный конверт.** Это изменение стоит сделать, и оно
  намеренно отдельное: оно меняет поведение слушателя при некорректной полезной нагрузке, а смешивание
  изменения поведения с исправлением молчаливой потери записей сделало бы исправление непроверяемым.
