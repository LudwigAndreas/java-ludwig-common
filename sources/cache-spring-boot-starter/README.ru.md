# cache-spring-boot-starter

**Единственный в платформе примитив кэширования**: именованные типизированные кэши, объявляемые владеющим
модулем и настраиваемые деплойментом, с локальным слоем на Caffeine, опциональным общим слоем на Redis,
склейкой промахов по ключу, вероятностным досрочным обновлением, негативным кэшированием, которое различает
*«нет значения»* и *«не удалось узнать»*, инвалидацией после коммита, версионированными пространствами ключей
общего слоя и метриками Micrometer на каждый кэш.

Главное, что стоит вынести из этого README:

> **Каждый именованный кэш объявляет, что *означает* его TTL.** `purpose: security` означает, что TTL — это
> срок, в течение которого отозванная роль продолжает работать. `purpose: performance` — что это срок, в
> течение которого пользователь видит старый часовой пояс. Управляются они по-разному: для первого — потолок
> и запрет чтения устаревших значений, для второго — минуты и stale-while-revalidate. И это единственная
> ошибка, которую модуль не может обнаружить за вас.

## Доказательство: один и тот же класс, написанный дважды

Два модуля независимо породили идентичную триаду, отличавшуюся только типами ключа и значения:

| | `user-settings` | `security` |
|---|---|---|
| SPI | `SettingsCache` | `AuthorityCache` |
| локальная реализация | `CaffeineSettingsCache` | `CaffeineAuthorityCache` |
| выключатель | `NoopSettingsCache` | `NoopAuthorityCache` |
| конструктор | `(Duration ttl, long maximumSize)` | `(Duration ttl, long maximumSize)` |
| операции | `get`, `get(k, loader)`, `put`, `evict`, `evictAll` (+ грубый `evict(PrincipalRef)`) | `get`, `get(k, loader)`, `put`, `evict`, `evictAll` |
| истечение | `expireAfterWrite`, с абзацем Javadoc о том, почему не `expireAfterAccess` | `expireAfterWrite`, с абзацем Javadoc о том, почему не `expireAfterAccess` |
| лавина промахов | `default get(k, loader)` — наивная форма без склейки, переопределяемая подклассом | то же самое, почти теми же словами |

Оба Javadoc даже приводили аргумент про «стадо» одинаково: *«каждое истечение срока для горячего субъекта
одновременно отпускает по одному запросу на каждый запрос в полёте — самому себе устроенное стадо против
хранилища ролей, приходящее ровно тогда, когда трафик максимален»*. Третьей частью был `AfterCommitEviction`
из `user-settings`, а `identity-projection` регистрировал собственный `TransactionSynchronization` для той же
цели в `IdentityProjectionService` — то есть инвалидация после коммита тоже была написана дважды.

Оба решения были разумны локально. Модулю нужен кэш, Caffeine — очевидный ответ, и никто не мог видеть второй.

**Дублирование стоило не строк:**

- ни одна из реализаций не вызывала `recordStats()`, поэтому **доля попаданий была ненаблюдаемой во всей
  платформе** — для обоих кэшей, через которые проходил каждый запрос;
- ни у одной не было негативного кэширования, защиты от лавины между репликами и пространства ключей;
- единственное действительно важное различие между ними — один TTL был окном отзыва прав, другой ручкой
  производительности — существовало только в прозе, в двух файлах, которые никто не читал вместе.

Никто этим не владел, поэтому следующий модуль написал бы это в третий раз.

## Один TTL, два смысла

Javadoc `SettingsCache` уже проводил различие, и это самое важное в модуле:

> TTL у `AuthorityCache` — это окно безопасности: столько отозванная роль продолжает работать, поэтому он
> измеряется в секундах и поэтому его Javadoc говорит, что выбор значения — решение по безопасности. **TTL
> этого кэша — решение по производительности, а не окно безопасности.** Устаревшая настройка означает, что
> пользователь недолго видит старый часовой пояс, — шероховатость корректности без привязки к правам.

Общий модуль с одним TTL по умолчанию делает одно из двух неверным при любом значении: секунды расточительны
для кэша настроек, минуты молча удлиняют окно отзыва прав. Поэтому смысл объявляется, значение по умолчанию
следует из него, а проверки, осмысленные лишь для одного из двух, применяются только к нему.

| | `purpose: security` | `purpose: performance` |
|---|---|---|
| TTL по умолчанию | 30s | 5m |
| потолок TTL | `ludwig.cache.security-ttl-ceiling` (2m), выше — **падение на старте** | нет |
| чтение устаревших значений | **запрещено** — ненулевой `stale-grace` роняет старт | доступно |
| кластерная аренда на загрузку | **запрещена** — она работает через выдачу устаревшего значения | доступна |
| досрочное обновление с джиттером | **доступно** — оно перезагружает *внутри* TTL | доступно |

Последняя строка заслуживает отдельного предложения, потому что два ответа на лавину промахов здесь не
равнозначны. Досрочное обновление перечитывает хранилище и заменяет запись **внутри** её TTL, поэтому самое
старое значение, которое может увидеть вызывающая сторона, по-прежнему ограничено TTL. Аренда же работает так,
что проигравшая реплика выдаёт значение **за пределами** его срока, — а это именно то, что окно отзыва прав
запрещает.

### TTL — не механизм согласованности

Механизм — инвалидация. `SettingsCache` говорил это прямо: *«TTL — страховка на случай, когда инвалидация не
сработала: потерянное событие, лежавший консьюмер, — чтобы неверное значение исцелилось само, а не жило до
следующего перезапуска»*.

Поэтому «инвалидация по коммиту вместо угадывания TTL» верна по акценту и неверна буквально: это инвалидация
по коммиту **с TTL как страховкой**. Кэш с инвалидацией и без TTL никогда не исцеляется от потерянного
события — поэтому TTL обязателен, а не опционален, при любом `purpose`.

### Истечение — `expireAfterWrite`, и это не настраивается

Оба удалённых кэша пришли к этому независимо и оба записали причину, разными словами:

- для `security` истечение по доступу позволяет активному вызывающему **держать выданное право открытым
  бесконечно**, просто вызывая часто. Окно, сбрасывающееся при использовании, — не окно;
- для `performance` запись активно используемого ключа не истекала бы никогда — и TTL перестал бы быть
  страховкой ровно для тех ключей, которые с наибольшей вероятностью заметят потерянное событие.

## API

Модуль объявляет кэш один раз, бином, и получает его из реестра.

```java
public static CacheDefinition<PrincipalRef, Authorities> definition() {
    return CacheDefinition.<PrincipalRef, Authorities>named("authorities", CachePurpose.SECURITY)
            .owner("security-spring-boot-starter")
            .defaultTtl(Duration.ofSeconds(60))
            .defaultMaximumSize(10_000)
            .valueType(Authorities.class)
            .keyRenderer(ref -> ref.type().name() + ':' + ref.subject())
            .build();
}
```

```java
@Bean
CacheDefinition<PrincipalRef, Authorities> ludwigAuthorityCacheDefinition() {
    return AuthorityCaches.definition();
}

@Bean
LudwigCache<PrincipalRef, Authorities> ludwigAuthorityCache(
        LudwigCacheRegistry registry, CacheDefinition<PrincipalRef, Authorities> definition) {
    return registry.cache(definition);
}
```

Чтение — один вызов, и форма с загрузчиком — та, которую следует использовать:

```java
Optional<Authorities> authorities = cache.get(ref, key ->
        CacheLoad.present(resolver.resolve(key)));
```

### Почему объявление, а не просто имя

Модель конфигурации — это сознательно модель `rest-client-spring-boot-starter`: карта именованных сущностей
под одним префиксом, где имя является ключом поиска, тегом метрики и строкой в каждой записи лога. Свойство,
благодаря которому эта модель работает, — **опечатка роняет старт, а не даёт молча ненастроенный экземпляр**,
и оно должно сохраниться. Проверяются оба направления:

- объявление без блока `ludwig.cache.caches.<name>` работает на значениях модуля — сервис не должен писать
  YAML, чтобы получить работающий кэш прав;
- блок `ludwig.cache.caches.<name>`, которому **не** соответствует ни одно объявление, **роняет старт**. Это
  случай опечатки, и без проверки он совершенно бесшумен: `authoritys:` привязывается, никто его не читает,
  кэш работает на значениях по умолчанию, а оператор делает вывод, что выставленный им TTL ни на что не
  влияет.

### Почему тип значения и рендерер ключа обязательны даже для локального кэша

Caffeine хранит ссылки на объекты и не нуждается ни в том, ни в другом; их использует только общий слой. Они
всё равно обязательны, чтобы **перевод кэша на `tiers: [local, shared]` был правкой одного YAML-файла, а не
правкой модуля, которому кэш принадлежит.** Объявление, которое нельзя повысить без изменения кода, сделало бы
общий слой архитектурным решением вместо эксплуатационного.

Рендерер ключа должен быть **всюду определён и инъективен**. Два разных ключа, дающих одну строку, выдали бы
значение одного вызывающего другому, и общий слой никак не может это заметить. Рендерера по умолчанию сознательно
нет: `Object#toString` не обязан быть стабильным между релизами, а тот, который работал до добавления поля в
record, хуже, чем никакой.

## Негативное кэширование и почему оно формирует API

Его не было ни в одном из удалённых кэшей, и в дизайне нужно одно различие, чтобы оно было полезным, а не
опасным.

- Ответ **«не найдено»** — это факт о данных, и его можно кэшировать, на собственном более коротком TTL, чтобы
  бомбардировка запросами по несуществующему ключу перестала доходить до хранилища.
- **Ошибку** — таймаут, отказ соединения, 5xx — кэшировать **нельзя никогда**. Кэширование сбоя превращает
  двухсекундный провал в устойчивую аварию ровно для тех ключей, которым не повезло, и оно самоподдерживающееся:
  негативная запись подавляет пробу восстановления, которая заметила бы, что хранилище вернулось.

Загрузчик, возвращающий `Optional.empty()` для обоих случаев, делает это различие невыразимым, а значит делает
безопасную реализацию невозможной. Поэтому загрузчик говорит, что именно произошло, в своём типе возврата:

```java
public sealed interface CacheLoad<V> {
    record Present<V>(V value) implements CacheLoad<V> { }
    record Absent<V>()        implements CacheLoad<V> { }   // кэшируется, недолго
    record Failed<V>(Throwable cause) implements CacheLoad<V> { }   // не кэшируется никогда
}
```

Загрузчик, бросающий исключение, обрабатывается ровно как `Failed`. `CacheLoad.ofOptional(…)` существует для
частого случая, когда репозиторий возвращает `Optional`, а любая проблема приходит исключением, и это *именованная*
фабрика — чтобы неоднозначность не вернулась через более короткую запись.

Негативное кэширование **выключено по умолчанию**: негативная запись — это обещание, что ключа не существует, а
замечает её неверность обычно тот, кто только что создал строку.

## Инвалидация и три составные части двухслойной инвалидации

Инвалидация, следующая за записью в БД, относится **к моменту после коммита**, и у `LudwigCache` это метод,
чтобы никому не приходилось помнить:

```java
cache.evictAfterCommit(subject);    // один ключ
cache.evictAllAfterCommit();        // запись на уровне роли, тенанта или платформы
```

Инвалидация внутри транзакции — очевидная реализация, и она неверна в обе стороны:

- она открывает окно, в котором другой поток промахивается, перечитывает строку в состоянии **до**
  незакоммиченного изменения и снова заполняет кэш устаревшим значением, которое затем живёт до истечения TTL —
  много позже той записи, в силу которой все уверены. Ранняя инвалидация не просто не помогает — она активно
  создаёт устаревшую запись, которой иначе не было бы;
- если транзакция откатывается, инвалидация всё равно произошла, и корректное закэшированное значение было
  выброшено напрасно.

Тесты фиксируют именно случай откатa, потому что инвалидация-на-коммите-с-гонкой корректна-но-расточительна, а
инвалидация-на-откате не кэширует ничего и скрывает баг.

### Три части

С общим слоем инвалидация состоит из трёх вещей, и все три заданы, а не предполагаются:

1. **инвалидировать локально, на этой реплике** — безусловно, не в зависимости от успеха (2). То, что эта
   реплика права, стоит иметь, даже если остальным нельзя сообщить;
2. **удалить общую запись**, с повторами и **метрикой на отказ** (`ludwig.cache.shared.eviction.failures`).
   *Настройте алерт.* Не состоявшаяся общая инвалидация оставляет устаревшее значение **на каждой** реплике —
   строго хуже однослойного случая, где неправа была только записавшая реплика, а TTL всех остальных уже был
   независимым и уже шёл;
3. **сказать остальным репликам сбросить локальные копии**, по каналу Redis pub/sub. Удаление общей записи
   ничего не делает с локальными копиями, которые держит каждая другая реплика.

Часть 3 **включена по умолчанию**, и её можно выключить — и это не бесшумно. Без канала локальный TTL перестаёт
быть страховкой на потерянное событие и становится *единственной* границей устаревшей копии на каждой другой
реплике после совершенно успешной инвалидации. Поэтому кэш с `shared.invalidation: false` обязан держать TTL не
выше `ludwig.cache.tiers.shared.local-ttl-cap-without-invalidation`, иначе старт падает. Именно это оставляет
выбор выбором, а не пятиминутным устаревшим чтением на весь парк, которое никто не выбирал.

Повторы идут **без задержек**, сознательно: удаление выполняется в `afterCommit` в потоке запроса, и задержка
держала бы ответ открытым в ожидании Redis, который внутри неё скорее всего не вернётся. Повторы покрывают
соединение, закрытое между коммитом и удалением, — частый случай, лечащийся немедленной повторной попыткой.

## Два слоя и почему по умолчанию только локальный

```
ludwig.cache.caches.<name>.tiers: [local]            # по умолчанию
ludwig.cache.caches.<name>.tiers: [local, shared]    # opt-in, и нужен второй выключатель
```

`local` присутствует всегда, перечислен он или нет. Кэш только из общего слоя — сетевой round trip за значением,
которое этот процесс вычислил миллисекунду назад — это не кэш, а вторая база данных, и позволить конфигурации
выразить такое значило бы позволить ей выразить ошибку.

**Общий слой включается для каждого кэша отдельно и выключен по умолчанию**, и причина не в осторожности:

- большинство кэшей платформы стоят перед базой, которая и так общая, поэтому общий слой экономит запрос,
  который база всё равно ответила бы из собственного буферного кэша;
- он добавляет режим отказа, которого у однослойной схемы нет, — см. пункт 2 выше.

Он оправдывает себя для действительно дорогой загрузки: агрегата отчёта, обращения к внешнему партнёру, прогрева
после старта, который иначе платится один раз на реплику на каждый деплой. И не оправдывает — для чтения одной
строки по первичному ключу.

Чтобы дойти до Redis, нужны **два** выключателя — `ludwig.cache.tiers.shared.enabled` и `shared` в `tiers` —
по той же причине, по которой в `rest-client` парные выключатели TLS: одна строка в одном YAML-файле, а
YAML-файлы копируют с ноутбука в Helm-чарт. Отдельный, иначе названный верхний выключатель означает, что копия не
начнёт молча использовать Redis.

### Недоступность — не ошибка

Каждое чтение и запись в общий слой — best effort. Недостижимый Redis делает сервис медленнее, а не сломанным,
поэтому недоступный слой считается, логируется раз в период охлаждения и обходится в пользу локального. Единственная
операция, сообщающая о своём отказе наверх, — инвалидация, по причине выше.

## Пространства ключей и версионирование

Ключи такие:

```
ludwig:{app}:{namespace}:v{version}:{key}
```

плюс два зарезервированных соседа: `:__shape` — записанный структурный отпечаток типа значения, и
`:__lease:{key}` — кластерная аренда на загрузку. Сегмент `{app}` — это `spring.application.name`, и общий слой
без него **роняет старт**: именно он не даёт двум сервисам, делящим Redis, разделить одно пространство ключей с
двумя типами значений в нём.

Версия обезвреживает реальную опасность плавающего деплоя. Поды v1 и v2 делят один Redis; v2 меняет
сериализованную форму значения; без версии под v1 читает запись v2 и либо падает, либо — хуже — десериализует во
что-то тонко неверное, в поле, которое молча отсутствует.

Два факта о ней стоит знать, прежде чем счесть её церемонией:

- **она важна только для общего слоя.** Локальный Caffeine держит ссылки на объекты в одном процессе и
  неуязвим. Тот, чей локальный кэш никогда не ломался, сделает вывод, что версионирование опционально;
- **вручную поддерживаемое целое, которое кто-то забыл увеличить, хуже, чем отсутствие версионирования вообще**,
  потому что оно превращает громкий отказ в бесшумный: читатель теперь уверен, что смотрит на совместимую запись.

Поэтому забывчивость сделана **громкой**, а не оставлена на надежду. При первом использовании общий кэш пишет
`ValueShape.of(valueType)` — отпечаток по имени типа и отсортированным компонентам record или полям, с рекурсией
в собственные типы платформы и остановкой на типах JDK и сторонних библиотек — в `:__shape` через `SET NX`. При
каждой последующей загрузке записанный отпечаток сравнивается с отпечатком этого процесса, и версия, переиспользованная
через изменение формы, **роняет контекст**, называя кэш, оба отпечатка и свойство, которое нужно изменить.
Оператор увеличивает версию — то самое исправление, которое он всё равно применил бы, но на три недели раньше.

Выводить версию *из* отпечатка — без целого числа вообще — было вторым кандидатом и было отвергнуто: тогда любой
попутный рефакторинг типа значения молча выбрасывает полный кэш, и косметическое переименование поля становится
холодным старом на весь парк, которого никто не выбирал.

Недостижимый Redis на старте — **не** отказ старта. Слой остаётся *непроверенным*, а значит не выдаёт и не
сохраняет ничего — выдача из непроверенного пространства и есть та самая опасность, от которой существует версия —
кэш работает локально, а проверка повторяется при использовании.

## Защита от лавины промахов

**Склейка промахов по ключу не опциональна**: так кэш загружает всегда. Одновременные промахи по одному ключу
выполняют загрузчик один раз, остальные получают его результат; блокировка по ключу, поэтому разные ключи не
мешают друг другу. Это поднято из обеих удалённых реализаций, включая устройство, при котором `default`-метод
интерфейса — наивная форма без склейки, а реальная реализация его переопределяет: хороший приём, потому что он
делает путь без склейки явным, а не случайным.

Чего склейка не решает: Caffeine вычисляет не более одного раза **на процесс**, поэтому N реплик всё равно
выполняют N загрузок по холодному ключу — одновременно, потому что все они закэшировали его в один и тот же
деплой или один и тот же холодный старт.

Два ответа, в порядке предпочтения:

1. **Досрочное обновление с джиттером** (`stampede.early-refresh`, **включено по умолчанию**). После настраиваемой
   доли TTL запись становится кандидатом на обновление, с вероятностью, растущей от нуля на пороге до единицы к
   истечению. Каждая реплика бросает кости независимо, поэтому перезагрузки распределяются по хвосту TTL, а не
   приходятся все на его край. Не нужна координация, не добавляется режим отказа и ничего нового, что может быть
   недоступно, — и это лечит настоящую причину, которой является **синхронное истечение**, а не конкурентность.
   Обновление выполняется в маленьком ограниченном **отбрасывающем** пуле: обновление, которого никто не ждёт, не
   должно ни копиться бесконечно, ни выполняться на вызывающем потоке.
2. **Короткая кластерная аренда на загрузку** (`stampede.lease`, opt-in, нужен общий слой). `SET NX PX`;
   проигравший **выдаёт устаревшее значение, а не блокируется**, и всё равно загружает, если устаревшего нет,
   потому что блокировка на аренде, чей владелец мог упасть, превращает медленную загрузку в зависший запрос.
   Запрещена для `purpose: security` и запрещена без `stale-grace` — проигравший, который всё равно загружает, это
   один round trip к Redis на промах, который ничего не меняет.

Обратите внимание, чем аренда сознательно **не** является: это не `RunLock` из `job-core`. Тот — арендуемая
блокировка для планируемых работ с обращением к БД на каждый захват; одно такое на промах кэша стоило бы дороже
загрузки, которую защищает. Это очевидный неверный шаг, и кто-нибудь его предложит.

Неудавшееся обновление ничего не меняет: существующая запись остаётся, а обычный путь истечения загрузит снова.
Отказ там не должен инвалидировать — это превратило бы временную проблему хранилища в гарантированный синхронный
промах для следующего вызывающего, что противоположно замыслу.

## Инвалидация по предикату и почему она запрещена вместе с общим слоем

`user-settings` она нужна: путь поддержки, у которого есть принципал и нет тенанта, должен инвалидировать этого
принципала во всех тенантах, под которыми он закэширован. Прежний API предлагал её как `evict(PrincipalRef)` —
безобидно выглядящую перегрузку рядом с `evict(SettingsSubject)` сложности O(1), со стоимостью, погребённой в
Javadoc реализации: *«сканирует набор ключей, потому что у Caffeine одна карта и нет вторичного индекса»*.

**Обобщённый метод, который втайне O(n), — это дефект производительности, ждущий своего второго вызывающего.**
Поэтому:

- операция называется `evictByScan(Predicate<K>)`. Стоимость — в имени;
- кэш обязан её объявить: либо владеющий модуль говорит `requiresScanEviction(true)`, потому что это свойство
  кода, а не деплоймента, либо деплоймент ставит `scan-eviction: true`;
- **она запрещена вместе с общим слоем, на старте.** Инвалидация по предикату против Redis требует либо прохода
  `KEYS` — который блокирует однопоточный сервер на всё своё время и уже ронял продуктивные инстансы, — либо
  настоящего вторичного индекса, то есть второй структуры данных, которую надо держать согласованной с первой ради
  одного административного места вызова. Отказ от комбинации — честный третий вариант, а отказ *на старте* —
  то, что не даёт ей работать в локальном окружении, где её написали, и падать на том запросе, которому она
  впервые понадобится в продакшене.

`user-settings` оставляет типизированную обёртку `SettingsCaches.evictAcrossTenants(cache, ref)`, чтобы замысел
читался, а причина допустимости O(n) жила в одном месте.

## Метрики

`recordStats()` у Caffeine включён безусловно, а `CaffeineCacheMetrics` привязывается к каждому именованному
кэшу — именно это наконец делает наблюдаемыми долю попаданий, время загрузки, число вытеснений и размер. Ничего
из этого до модуля не существовало.

Поверх того, что видит Caffeine:

| метрика | зачем |
|---|---|
| `ludwig.cache.hits{tier}` | попадание в общий слой и в локальный стоят по-разному |
| `ludwig.cache.misses` | вместе с попаданиями — доля |
| `ludwig.cache.loads{outcome}` | сколько на самом деле стоит промах и как часто он `absent` или `failed` |
| `ludwig.cache.negative.hits` | сколько экономит негативный TTL и куда смотреть первым делом, когда вызывающий говорит, что новая строка не видна |
| `ludwig.cache.early.refreshes` | работает ли джиттер |
| `ludwig.cache.lease.lost{served}` | как часто реплика выдавала устаревшее вместо загрузки |
| `ludwig.cache.shared.eviction.failures` | **настройте алерт.** Каждая реплика теперь выдаёт устаревшее значение |
| `ludwig.cache.shared.errors{operation}` | слой деградировал до локального |
| `ludwig.cache.shared.shape.mismatches` | ненулевое значение при плавающем деплое означает, что версию ключей не увеличили |
| `ludwig.cache.shared.available` | 0, пока слой недостижим или непроверен |
| `ludwig.cache.maximum.size` | потолок, для сравнения с размером от Caffeine: кэш, постоянно стоящий у потолка, недоразмерен, и давление вытеснения говорит об этом раньше и яснее, чем доля попаданий |

Каждая метрика несёт теги `cache` и `purpose`. `purpose` — тег, а не только значение конфигурации, чтобы дашборд
мог разделить два вида кэша без прошитого списка имён: доля попаданий кэша безопасности и кэша производительности —
разные величины и не должны делить ось.

## Конфигурация

```yaml
ludwig:
  cache:
    enabled: true                       # главный выключатель; выключенный не регистрирует ничего
    security-ttl-ceiling: 2m            # самый длинный TTL, который может объявить purpose=security
    refresh:
      pool-size: 2
      queue-capacity: 1000              # ограничен и отбрасывает; обновление — best effort
    tiers:
      shared:
        enabled: false                  # Redis; первый из двух выключателей
        local-ttl-cap-without-invalidation: 60s
    caches:
      authorities:
        enabled: true
        purpose: security               # значение по умолчанию в секундах, потолок, запрет устаревших чтений
        ttl: 30s
        maximum-size: 10000
        tiers: [local, shared]
        key-namespace: { name: authorities, version: 3 }
        negative: { enabled: true, ttl: 5s }
        shared: { invalidation: true, eviction-retries: 2 }
      settings:
        purpose: performance            # значение по умолчанию в минутах
        ttl: 5m
        maximum-size: 50000
        tiers: [local]
        scan-eviction: true
        key-namespace: { name: settings, version: 7 }
        stampede:
          early-refresh: { enabled: true, threshold: 0.75 }
          stale-grace: 30s
          lease: { enabled: false, ttl: 5s }
```

Любое незаданное поле падает на объявление владеющего модуля, а затем на значение по умолчанию для `purpose`.
Собственный блок кэша необязателен; блок для кэша, который никто не объявил, роняет старт.

### Что запрещает валидатор на старте

Всё это — связи между двумя настройками, поэтому Bean Validation не может выразить ни одну из них и поэтому они
проверяются вместе, с выводом сразу всех проблем:

| запрещено | потому что |
|---|---|
| `purpose: security` с TTL выше потолка | в рантайме об этом не сообщит ничто; симптом — отозванная роль, которая продолжает работать |
| `purpose: security` с ненулевым `stale-grace` | чтение за пределами TTL — именно то, что запрещает окно отзыва прав |
| `scan-eviction` с общим слоем | проход `KEYS` или вторичный индекс; неприемлемо ни то, ни другое |
| `shared` в `tiers` без `tiers.shared.enabled` | второй выключатель существует, чтобы скопированный блок YAML не дошёл до Redis молча |
| общий слой без `spring.application.name` | два сервиса делили бы одно пространство ключей |
| `shared.invalidation: false` с TTL выше предела | этот TTL теперь единственная граница устаревшей копии на каждой реплике |
| аренда без общего слоя | её негде взять |
| аренда с `purpose: security` | проигравший выдаёт устаревшее |
| аренда без `stale-grace` | проигравший всё равно загружает; round trip ничего не даёт |
| TTL аренды не меньше TTL кэша | она пережила бы запись, которую защищает |
| негативный TTL больше TTL значения | отсутствие — ответ, который с наибольшей вероятностью только что перестал быть верным |
| порог досрочного обновления вне `(0, 1)` | при 0 кандидатом является каждое чтение, при 1 окно пусто |
| блок `ludwig.cache.caches`, который никто не объявил | он привязывается и затем игнорируется, поэтому настройки молча ничего не делают |

Понижение объявленного модулем `purpose: security` до `performance` **разрешено** — объявление модуля является
значением по умолчанию, и деплоймент может знать то, чего не знает модуль — и логируется на уровне WARN тем подом,
который это делает, потому что оно снимает потолок и разрешает устаревшие чтения для кэша, автор которого сказал,
что его TTL — окно отзыва прав.

## Что модуль сознательно не поглощает

Три вещи в этом репозитории выглядят кэшами и ими не являются — или являются, но не должны становиться общими.
Сказано здесь, чтобы следующий читатель «не доделал работу».

| | что это | почему остаётся |
|---|---|---|
| `export/enrich/EnrichmentCache` | значения, которые один прогон отчёта уже получил | **Ограничен одним прогоном и ограничен им же.** Дать ему время жизни приложения — изменение *корректности*: отчёт есть утверждение на момент времени, два прогона с разницей в час должны каждый видеть данные партнёра такими, какими они были на старте этого прогона, а общий кэш сделал бы второй молча смесью. У него вообще нет TTL по замыслу — временем жизни является прогон — поэтому этому модулю нечем управлять. Он уже вызывает `recordStats()`. Это единственный тип, названный в списке исключений правила ArchUnit |
| `rest-client/auth/CachedToken` | хранилище одного OAuth-токена | Не кэш по ключу. Нужная ему семантика — обновлять *до* истечения, никогда не выдавать истёкший — не является кэш-семантикой, а выражение её через TTL перевернуло бы знак сравнения |
| `idempotency/web/CachedBodyRequest` | обёртка сервлетного запроса | Вообще не кэш, несмотря на имя. Буферизует одно тело запроса, чтобы его можно было прочитать дважды |

## Структура модуля и правило нулевых зависимостей

**Один модуль, ноль зависимостей внутри репозитория**, и это несущее свойство, а не аккуратность.
`security-spring-boot-starter` находится почти у основания реактора — от него зависят identity-projection,
user-settings, web-core и каждый сервис — и он один из двух модулей, чей рукописный кэш этот заменяет. Если бы у
этого модуля появилась зависимость на `audit-core`, `web-core` или сам `security`, `security` не смог бы зависеть
от него, и консолидацию пришлось бы откатить.

Режим отказа тихий и легко достижимый: кто-то захочет аудировать инвалидацию или отрендерить ошибку кэша как
`ProblemDetail`, и оба варианта в одном импорте и оба выглядят разумно. `ModuleIndependenceTest` роняет сборку на
этом и объясняет почему — чтобы верное исправление было очевидным, а не «перенести модуль кэша».

```
ru.ludwigandreas.cache
├── api/         LudwigCache, LudwigCacheRegistry, CacheDefinition, CacheLoad, CacheLoader,
│                CachePurpose, CacheTier, CacheSettings
├── core/        DefaultLudwigCache, CacheEntry, NoopLudwigCache, CacheRefreshExecutor
├── shared/      SharedCacheTier, SharedCacheView, SharedEntry, ValueShape,
│                RedisSharedCacheTier, RedisSharedCacheView
├── config/      CacheProperties, CacheSettingsResolver, CacheConfigurationValidator,
│                DefaultLudwigCacheRegistry, LudwigCacheAutoConfiguration,
│                LudwigCacheRedisAutoConfiguration
├── metrics/     CacheMetrics, MicrometerCacheMetrics, NoopCacheMetrics
├── tx/          AfterCommitEviction
├── error/       CacheConfigurationException, CacheLoadException, UnknownCacheException
└── test/        LudwigCacheTestSupport — строит настоящий кэш без контекста Spring
```

`test/` поставляется в основном jar — так же, как срез `@LudwigRestClientTest` в `rest-client` — чтобы
потребляющий модуль получал его вместе со стартером. До его появления у модуля, чей коллаборатор принимает кэш,
было два варианта в юнит-тесте: замокать кэш, что не проверяет ничего про кэширование и скрывает разницу между
попаданием и промахом, или поднять контекст, что в сотню раз медленнее тестируемого. Случалось и то, и другое — в
двух модулях, которые заменяет этот стартер.

Caffeine, `spring-tx` и `micrometer-core` — compile-зависимости; `spring-data-redis` опциональна. Сознательно
больше **нет `Noop` на модуль**: две удалённые «всегда промах» реализации существовали, чтобы выжить без Caffeine
на classpath, чего у стартера с именем «cache» разумно быть не может. Выключатель — `enabled: false`, решение
конфигурации, обслуживаемое одним `NoopLudwigCache`.

Версия Caffeine приходит из `spring-boot-dependencies`, поэтому в `ludwig-bom` она не фиксируется.

## Правило ArchUnit, которое не даёт появиться третьей копии

`RuleGroup.CACHING`, включена по умолчанию, в `architecture-rules`:

| правило | что проверяет |
|---|---|
| `caching:no-private-caffeine-cache` | ничто вне `ru.ludwigandreas.cache..` не зависит от билдера Caffeine (одно исключение, названное в правиле: `EnrichmentCache`) |
| `caching:no-second-cache-spi` | ни один интерфейс вне него не назван как кэш **и** не объявляет одновременно чтение по ключу и инвалидацию |

Выражено как *зависимость* от `Caffeine`, а не как вызов `Caffeine.newBuilder()`, потому что зависимость нельзя
спрятать: класс, дошедший до билдера через статический импорт, хелпер или ссылку на метод, всё равно несёт
`Caffeine` в своём пуле констант.

Чего правило сознательно не проверяет: разумно ли значение TTL и верен ли объявленный `purpose`. Ни то, ни другое
не выразимо структурно — TTL это конфигурация, а `purpose` это утверждение о том, что *означает* закэшированное
значение. Они покрыты там, где это возможно: TTL — валидатором старта этого модуля, `purpose` — тем, что автор
модуля его записал. Это то же разделение труда, которое репозиторий уже проводит: `architecture-rules` владеет
структурой, `checkstyle-rules` — текстом исходников, SonarQube — дефектами.

## Перевод модуля на именованный кэш

Оба перевода выполнены; вот из чего они состояли.

| шаг | `security` | `user-settings` |
|---|---|---|
| SPI | `AuthorityCache` **удалён** — вне модуля его никто не реализовывал | `SettingsCache` **удалён** |
| реализации | `CaffeineAuthorityCache`, `NoopAuthorityCache` **удалены** | `CaffeineSettingsCache`, `NoopSettingsCache` **удалены** |
| что осталось | `AuthorityCaches` — имя, `purpose`, TTL по умолчанию, рендерер ключа | `SettingsCaches` плюс `evictAcrossTenants` |
| `purpose` | `security` | `performance` |
| конфигурация | `ludwig.security.authorities.cache.*` → `ludwig.cache.caches.authorities.*` | `ludwig.user-settings.cache.*` → `ludwig.cache.caches.settings.*` |
| инвалидация после коммита | рукописный `TransactionSynchronization` в `IdentityProjectionService` → `cache.evictAfterCommit(ref)` | `AfterCommitEviction` переехал сюда; четыре места вызова → `cache.evictAfterCommit(subject)` / `evictAllAfterCommit()` |

Удалённые блоки свойств заменены комментарием в каждом классе свойств, называющим новый ключ, чтобы тот, кто
поищет старый, нашёл ответ, а не пустоту.

## Тесты

```
src/test/java/ru/ludwigandreas/cache/
├── unit/          CacheLoadingTest, CacheEvictionTest, StampedeTest,
│                  CacheConfigurationValidatorTest, CacheSettingsResolverTest,
│                  CacheAutoConfigurationTest, ValueShapeTest
├── integration/   SharedTierIntegrationTest — единственный класс, которому нужен Docker
└── architecture/  ModuleIndependenceTest
```

Поведения, которые стоит назвать:

- **потолок безопасности** — кэш с `purpose: security` и TTL в десять минут роняет старт сообщением, называющим
  кэш, а тот же TTL на кэше `performance` допустим;
- **склейка** — шестнадцать одновременных промахов по одному ключу вызывают загрузчик один раз;
- **инвалидация после коммита** — инвалидация внутри транзакции, которая **откатывается**, не происходит, а
  внутри той, что коммитится, происходит. Случай откатa и есть важный;
- **негативное кэширование** — отсутствие кэшируется недолго; **брошенное** загрузчиком исключение не кэшируется
  даже на кэше с включённым негативным кэшированием, и следующий вызов повторяет;
- **двухслойная инвалидация** — неудавшаяся общая инвалидация увеличивает метрику отказов, не бросает исключение,
  а локальная инвалидация всё равно произошла. Дальше тест показывает, чего стоит этот отказ: как только слой снова
  достижим, следующее чтение возвращает выжившую устаревшую запись обратно — на той самой реплике, которая её
  инвалидировала;
- **версионирование ключей** — записи под `v1` невидимы для кэша, настроенного на `v2`, против настоящего Redis; а
  переиспользование `v1` со значением иной формы роняет старт;
- **независимость модуля** — ничто здесь не зависит от другого модуля платформы, а публичный API не дотягивается до
  опциональных типов Redis.

Контейнер нужен только `SharedTierIntegrationTest`, и это Redis из `test-support`, зафиксированный по digest. Все
тесты локального слоя работают без Docker, сознательно: модуль кэширования, чьему набору тестов целиком нужен
Docker, — это модуль кэширования, для которого тесты перестают запускать.

```bash
mvn -pl cache-spring-boot-starter -am verify
# консолидация целиком и доказательство отсутствия цикла в реакторе
mvn -pl security-spring-boot-starter,user-settings-spring-boot-starter,identity-projection-spring-boot-starter -am verify
```
