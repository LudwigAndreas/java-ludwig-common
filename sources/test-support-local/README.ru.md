# test-support-local

*[English](README.md) · **Русский***

Запускает настоящую точку входа сервиса на вашей машине: с теми инфраструктурными сервисами, которые он
назвал, с HTTP-заглушкой для каждого партнёра и с начальными данными. Отладка любого сценария сводится к
«запустил, поставил точку останова». Те же заглушки и фикстуры используются в интеграционных тестах
сервиса. Подключается одной зависимостью в области `test`.

**API предварительный.** Пока его использует один сервис. Полный рабочий пример, который можно
скопировать, - раздел
[«Локальный запуск» в `notification-service`](../../services/notification-service/README.ru.md#локальный-запуск):
локальное приложение, три заглушки, фикстуры, тест правил и тест, который его запускает.

## Заглушка - это предположение о партнёре

Прочитайте это прежде всего остального. Заглушка отвечает так, как, *по вашему мнению*, отвечает партнёр.
Ничто в этом модуле не упадёт, когда партнёр изменит контракт, а заглушка нет, и сервис, проходящий все
локальные запуски на заглушках, может оказаться неправ на настоящей системе.

Отсюда два вывода. Держите заглушки маленькими и очевидно «консервированными», чтобы никто не принял их
за спецификацию. А когда вопрос звучит как «что партнёр делает на самом деле», направьте этот один
клиент на настоящее окружение: объявите его сквозным (ниже), и он сохранит адрес из своей конфигурации.

## Зачем

Запуск на ноутбуке раньше означал сервис с ампутированными частями. Профиль `local` в
`crud-service-example` выключает Kafka, останавливает опрос outbox и не имеет партнёра, которого можно
вызвать, так что код под точкой останова - не тот, что работает в эксплуатации. Примитивы для полного
сервиса уже были в [`test-support`](../test-support/README.ru.md) - закреплённые контейнеры, HTTP-сервер
заглушек, очистка базы, - но ничто не собирало их во что-то запускаемое, а каждая заглушка партнёра была
закрытым классом в одном пакете интеграционных тестов и годилась только для теста.

## Что внутри

| Тип | Что это |
|---|---|
| `LocalRun` | Запускает собственный `main` сервиса с названными сервисами, заглушками и фикстурами |
| `BackingService` | PostgreSQL, Kafka, LocalStack, Redis - закреплённые по digest синглтоны `test-support`, запускаются только когда названы |
| `PartnerStub`, `StubCatalog`, `StubAddress` | Одна HTTP-заглушка на партнёра, место публикации её адреса и единственный их список в сервисе |
| `LocalMailbox` | Почтовый сервер в процессе и то, что он получил |
| `StubServers`, `RunningStub` | Запущенные заглушки: адрес, записанные запросы, переключатель сбоя |
| `StubFault` | `unavailable`, `slow`, `reset`, `empty`, `refused` |
| `@WithPartnerStubs` | Те же заглушки для интеграционного теста, со сбросом после каждого тестового метода |
| `SeedFixture`, `SeedFixtures`, `FixtureMode` | Упорядоченные начальные данные и режимы `reset` / `keep` / `none` |
| `KafkaDeliveries` | Публикует начальные записи и доставляет одну запись несколько раз |
| `LocalRunRulesTest` | Правило времени сборки: у каждого rest-клиента есть заглушка или сквозной режим |

## Как включить

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>test-support-local</artifactId>
    <scope>test</scope>
</dependency>
```

Версия приходит из `ludwig-bom`. `<scope>test</scope>` обязателен: `ludwig-service-parent` валит сборку
сервиса, у которого любой артефакт `test-support` оказался в области compile или runtime, потому что
заглушка никогда не должна иметь возможность ответить за партнёра в развёрнутом образе.

Рядом, в области `test`, объявите то, чем пользуетесь. Здесь всё это `optional` по той же причине, что и в
`test-support`: сервис, использующий одну часть, не должен получать деревья зависимостей остальных.

| Вы используете | Объявите |
|---|---|
| Заглушки партнёров | `org.wiremock:wiremock-standalone` |
| `LocalRunRulesTest` | `com.tngtech.archunit:archunit` |
| `.kafka()`, `KafkaDeliveries` | `org.testcontainers:kafka` и `spring-kafka`, если его ещё нет в сервисе |
| `.localstack()` | `org.testcontainers:localstack` |
| `.mail()` | `com.icegreen:greenmail-junit5` |

## Локальное приложение

Класс с методом `main` в **тестовых** исходниках сервиса, в пакете с именем `local`:

```java
// src/test/java/ru/ludwigandreas/example/catalog/local/LocalCatalogApplication.java
public final class LocalCatalogApplication {

    public static void main(String[] args) {
        LocalRun.from(CatalogApplication::main)
                .postgres()
                .kafka()
                .mail()
                .stubs(new CatalogStubs())
                .fixtures(SupplierFixture.class, ProductFixture.class)
                .run(args);
    }
}
```

Запускайте из IDE или командой
`mvn -pl :<service> spring-boot:test-run -Dspring-boot.run.main-class=<локальное приложение>`.
Свойство нужно, потому что иначе плагин запустит собственный главный класс сервиса. После старта
приложение пишет в лог, что и где запущено:

```text
Local run is ready.
  Backing services
    postgres      jdbc:postgresql://localhost:54021/test
  Partner stubs
    suppliers     http://127.0.0.1:54033   admin http://127.0.0.1:54033/__admin   fault none
        set a fault:  curl -X PUT http://127.0.0.1:54033/__admin/scenarios/fault/state -H 'Content-Type: application/json' -d '{"state":"unavailable"}'   (unavailable | slow | reset | empty)
        clear it:     curl -X PUT http://127.0.0.1:54033/__admin/scenarios/fault/state
  Seed fixtures (mode reset)
    SupplierFixture, ProductFixture
```

Три решения, о которых стоит знать:

- **Запускается собственный `main` сервиса.** Класс приложения не подменяется и не объявляется заново,
  поэтому граф бинов под точкой останова - тот же, что собирается в эксплуатации, плюс локальные добавки.
- **Ничего не выводится автоматически.** Инфраструктурный сервис стартует только когда назван. Сервис, у
  которого `spring-kafka` есть в classpath, а потребители выключены конфигурацией, - обычное дело на этой
  платформе, так что classpath не говорит, что сервису нужно.
- **Профиль не навязывается.** Добавьте `.profiles("local")`, если он нужен. Сам запуск не активирует ни
  одного, потому что существующий профиль `local` может выключать ровно то, что запуск включает.

**`spring-boot:test-run` - это не тестовый classpath сборки.** Он работает с тем, что упаковал бы плагин
Spring Boot, плюс тестовые классы: зависимости `provided`, исключённой в `<excludes>` плагина, там нет.
Всё, что использует локальное приложение - фикстура, заглушка, - должно загружаться без неё. Запустите
приложение так хотя бы раз, прежде чем считать настройку готовой; тест failsafe, который его
запускает, об этом не скажет.

### Почта

`.mail()` запускает почтовый сервер в процессе на loopback и направляет на него `spring.mail.host` и
`spring.mail.port`. Ничто не покидает машину. Тест читает `LocalMailbox.received()`; разработчик
подключает почтовый клиент к адресу IMAP из сводки и входит под адресом получателя с любым паролем.

### Дополнение сводки

Бин, реализующий `SummaryContributor`, получает собственный раздел в сводке при старте - например,
готовую команду для вызова сервиса. Заглушка добавляет строки под своей записью, переопределив
`summaryLines`.

## Заглушки партнёров

Заглушка - обычный класс, не Spring-бин. Она называет свой rest-клиент и регистрирует «здоровые» ответы
партнёра средствами самого WireMock:

```java
public class SupplierDirectoryStub implements PartnerStub {

    @Override
    public String name() {
        return "suppliers";          // как в @LudwigRestClient("suppliers")
    }

    @Override
    public void register(WireMockServer server) {
        server.stubFor(get(urlPathEqualTo("/api/v1/suppliers"))
                .willReturn(okJson("[{\"id\":\"acme\",\"name\":\"ACME GmbH\"}]")));
    }
}
```

а сервис один раз перечисляет свои заглушки:

```java
public class CatalogStubs implements StubCatalog {

    @Override
    public List<PartnerStub> stubs() {
        return List.of(new SupplierDirectoryStub(), new NotificationStub());
    }

    @Override
    public Set<String> passThrough() {
        return Set.of("billing");    // намеренно вызывает адрес из конфигурации
    }
}
```

Модуль запускает по одному серверу на заглушку **до** обновления контекста и выставляет
`ludwig.rest-client.clients.<name>.base-url` впереди всех остальных источников свойств. Настоящий клиент
вызывает заглушку, поэтому работают его пул, таймауты, повторы, circuit breaker и трансляция ошибок.
Собственный `application.yml` сервиса с боевым хостом не побеждает; это проверено тестом, потому что
альтернатива - ноутбук, который ходит в эксплуатацию.

### Партнёр, который не является rest-клиентом

Имя заглушки по умолчанию - это rest-клиент, который она подменяет. Партнёр, до которого сервис
добирается иначе, переопределяет `address()`:

| `StubAddress` | URL заглушки публикуется как | Для чего |
|---|---|---|
| `restClient()` (по умолчанию) | `ludwig.rest-client.clients.<name>.base-url` | `@LudwigRestClient` |
| `property("...")` | названное свойство | клиент, который сервис строит сам из собственного свойства |
| `none()` | ничего | партнёр, адрес которого - данные, например получатель вебхуков; фикстура или тест читает `StubServers.stub(name).baseUrl()` |

Запуск отказывает заглушке, свойство которой не задаёт ни один другой источник, - это то, что остаётся
после переименования клиента или свойства. Пустое значение считается незаданным, поэтому сервис с
пустым значением по умолчанию задаёт свойству заглушку-адрес в локальной конфигурации.

Каждая заглушка слушает только `127.0.0.1`. Не занимайте приоритет маппингов `1` - его используют
маппинги сбоев. Файлы тел и маппингов заглушки, если они нужны, кладутся в
`src/test/resources/ludwig-local-stubs/<имя клиента>/`.

Настройки заглушки, все под `ludwig.local.stubs.<имя заглушки>`:

| Свойство | Смысл |
|---|---|
| `.port` | Фиксированный порт. Если не задан, порт выделяет операционная система |
| `.fault` | Сбой, действующий с момента старта |
| `.slow-delay` | Сколько ждёт `slow`. По умолчанию `30s` |
| `.mode` | `stub` (по умолчанию) или `passthrough` - второе пропускает заглушку на этот один запуск |

### В интеграционном тесте

```java
@SpringBootTest
@WithPartnerStubs(CatalogStubs.class)
class SupplierOutageIT {

    @Autowired
    StubServers stubs;

    @Test
    void degradesWhenTheDirectoryIsDown() {
        stubs.stub("suppliers").fail(StubFault.UNAVAILABLE);
        // ... вызвать сервис, проверить деградацию
    }
}
```

После каждого тестового метода каждая заглушка возвращается к здоровым ответам, без сбоя и с пустым
журналом запросов.

### Клиент, который получает токен

Переопределение одного `base-url` оставляет адрес токена указывающим на настоящий провайдер
идентификации. Клиент с `auth.registration-id` берёт этот адрес из регистрации клиента Spring Security,
поэтому пусть заглушка отвечает и за конечную точку токена, а свойство вернёт из `properties(baseUrl)`:

```java
@Override
public Map<String, String> properties(String baseUrl) {
    return Map.of("spring.security.oauth2.client.provider.suppliers.token-uri", baseUrl + "/oauth/token");
}
```

## Сбои

| Сбой | Что видит клиент | Состояние для установки по HTTP |
|---|---|---|
| `unavailable` | HTTP 503 | `unavailable` |
| `slow` | HTTP 503 через `slow-delay` - чтобы превысить таймаут чтения | `slow` |
| `reset` | Соединение сброшено до какого-либо ответа | `reset` |
| `empty` | Соединение закрыто без ответа | `empty` |
| `refused` | На порту никто не слушает | *по HTTP недоступно* |

Сбой - один переключатель, доступный из трёх мест:

- **Код теста:** `stub.fail(StubFault.SLOW)`, `stub.fail(StubFault.RESET, "/api/v1/suppliers/.*")` для
  одного пути, `stub.heal()`.
- **При старте:** `--ludwig.local.stubs.suppliers.fault=unavailable`.
- **На паузе в точке останова:** строка `curl`, которую сводка при старте печатает для этой заглушки. Это
  собственный admin API WireMock - модуль не добавляет ни одной конечной точки, - а `PUT` без тела
  снимает сбой.

`refused` останавливает слушатель заглушки, а вместе с ним и admin API, поэтому его нельзя задать по HTTP
или для одного пути. Сбой для одного пути по HTTP - это написанный вручную маппинг WireMock с приоритетом
`1`, отправленный на `/__admin/mappings`.

Сбой одной заглушки никогда не задевает другую - это и есть частичный отказ: один партнёр лежит,
остальные отвечают.

## Начальные данные

Фикстура пишет через собственные репозитории или сервисы приложения, которые получает через конструктор:

```java
public class ProductFixture implements SeedFixture {

    private final ProductRepository products;

    public ProductFixture(ProductRepository products) {
        this.products = products;
    }

    @Override
    public void seed() {
        products.save(new ProductEntity("SKU-1", "acme"));
    }

    @Override
    public List<Class<? extends SeedFixture>> after() {
        return List.of(SupplierFixture.class);
    }
}
```

Фикстуры выполняются после миграций сервиса, в порядке, удовлетворяющем каждому `after()`, каждая в
собственной транзакции. Фикстура, бросившая исключение, откатывает свои записи, останавливает запуск и
называется в ошибке; цикл валит старт с перечислением его участников.

**Не ставьте на фикстуры `@Component`.** Стереотип под базовым пакетом сервиса подхватит каждый
`@SpringBootTest` этого сервиса. Называйте их в `LocalRun.fixtures(...)` или в тесте:

```java
@SpringBootTest
@Import({SeedFixtureConfiguration.class, SupplierFixture.class, ProductFixture.class})
class CatalogueIT {

    @Autowired
    SeedFixtures fixtures;

    @BeforeEach
    void seed() {
        fixtures.reset();
    }
}
```

`ludwig.local.fixtures.mode` определяет, что запуск делает с уже имеющимися данными - а при включённом
повторном использовании контейнеров Testcontainers это вчерашние данные:

| Режим | Поведение |
|---|---|
| `reset` (по умолчанию) | Очистить все таблицы, кроме таблиц Liquibase, затем заполнить. Каждый запуск начинается одинаково |
| `keep` | Заполнять только если в базе нет строк; иначе ничего не трогать |
| `none` | Не очищать и не заполнять |

**Фикстура - это код, а не SQL-скрипт.** Файл с данными продолжает вставлять колонку, переименованную
месяц назад; фикстура, написанная против сущности, перестаёт компилироваться. Проверки на это нет и быть
не может - ничто не отличает скрипт с данными от любого другого тестового ресурса, - поэтому правило
записано здесь и на `SeedFixture`.

**Фикстура, которой нужен аутентифицированный вызывающий** - например, сущность с колонками аудита, -
строит принципала с помощью [`test-support-security`](../test-support-security/README.ru.md). Этот
модуль от него не зависит.

### Сообщения

```java
KafkaDeliveries.publish(kafkaTemplate, List.of(record1, record2));   // начальные записи, с ожиданием
KafkaDeliveries.duplicate(kafkaTemplate, record);                    // та же запись, дважды
KafkaDeliveries.deliver(kafkaTemplate, record, 5);
```

Копии совпадают по ключу, заголовкам и содержимому и различаются только смещением - так для слушателя
выглядит повторная доставка после потерянного коммита. Фикстура, которая публикует, переопределяет
`needsKafka()`, и тогда локальное приложение отказывается стартовать, если не назвало Kafka.

## Два правила

**У каждого rest-клиента есть заглушка или сквозной режим.** Сервис с локальным приложением добавляет:

```java
class LocalRunArchitectureTest extends LocalRunRulesTest {

    @Override
    protected String basePackage() {
        return "ru.ludwigandreas.example.catalog";
    }

    @Override
    protected StubCatalog catalog() {
        return new CatalogStubs();
    }
}
```

После этого новый интерфейс `@LudwigRestClient` без подмены валит сборку с именем интерфейса. Тот же тест
валит всё, что использует `LocalRun` вне пакета с именем `local`. Запуск проверяет ещё раз при старте, по
реестру rest-клиентов - он видит и клиента, существующего только как имя в конфигурации, - и в обратную
сторону: заглушка для клиента, которого больше нет, тоже останавливает запуск.

Правило поставляется здесь, а не как `RuleGroup` в `architecture-rules`, потому что та обвязка исключает
тестовые классы и не имеет зависимостей внутри репозитория, то есть не видит ни заглушки, ни `LocalRun`.

**Ни одного артефакта `test-support` вне области test.** Правило Maven enforcer в `ludwig-service-parent`.

## Чего модуль намеренно не делает

- **Не регистрирует автоконфигурацию.** В тестовом classpath, без `LocalRun` и без `@WithPartnerStubs`, он
  ничего не запускает и ничего не переопределяет. Это удерживает `InertOnClasspathIT`.
- **Не добавляет конечных точек.** Управление заглушкой - это admin API WireMock.
- **Не объявляет образов.** Контейнеры берутся из `LudwigTestImages` в `test-support` и больше ниоткуда.
- **Не использует `PostgresContainerConfiguration` для запускаемого приложения.** Она делает общий
  контейнер бином, и закрытие контекста останавливает контейнер для всех остальных контекстов в JVM, если
  не включено повторное использование Testcontainers. `LocalRun` вместо этого публикует параметры
  подключения.
- **Не поставляет заглушек с состоянием.** Заглушка может хранить состояние, если это необходимо; здесь
  таких нет.
- **Не даёт ни часов, ни шва для идентификаторов.** Управляемые часы требуют, чтобы сервис везде
  внедрял `Clock`, а детерминированные идентификаторы - абстракции, которой у платформы нет. И то и
  другое - изменения боевого кода.
- **Не имитирует отказ брокера или базы.** Для этого нужен прокси-контейнер, то есть ещё один закреплённый
  образ.
- **Не содержит правила «используется таблица - определена фикстура».** Спроектированное по одному
  примеру, оно было бы неверным; оно ждёт двух настоящих сервисов.
