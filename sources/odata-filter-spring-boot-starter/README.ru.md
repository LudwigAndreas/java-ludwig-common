# odata-filter-spring-boot-starter

*[English](README.md) · **Русский***

Промышленная поддержка OData `$filter`/`$top`/`$skip`/`$orderby` для REST API на Spring Boot и
Spring Data JPA. Разбирает параметры OData-запроса в типобезопасные предикаты QueryDSL над вашими
JPA-сущностями — с теми ограничителями, которые нужны боевому API: пределом вложенности фильтра,
белым списком полей с запретом по умолчанию, распространяющимся и на ассоциации, ролевым доступом к
полям, максимальным размером страницы, серверной сортировкой-тайбрейкером, благодаря которой
постраничная выдача остаётся детерминированной, и точкой для программной валидации. Добавьте
зависимость, разметьте сущности и вызывайте её из репозитория.

## Зачем

[`odata-server-api`](https://olingo.apache.org)/`odata-server-core` и `olingo-jpa-processor-v4` —
хорошие строительные блоки, но требуют реальной работы, чтобы стать безопасными для мультитенантного
боевого API: неограниченный `$filter` — вектор отказа в обслуживании, а в модели OData нет понятия
«по этому полю фильтровать может только администратор». Этот стартер использует ABNF-токенизатор
самого Olingo (`UriTokenizer`) для разбора стандартной грамматики OData `$filter`, затем переводит её
в `Predicate` QueryDSL через `PathBuilder` — без шага генерации `QEntity` процессором аннотаций — и
применяет политику до того, как построен хоть один JPQL-запрос.

## Быстрый старт

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>odata-filter-spring-boot-starter</artifactId>
    <version>1.0.0</version>
</dependency>
```

Разметьте поля сущности, по которым разрешены фильтрация и сортировка. Всё остальное, включая
ассоциации, по умолчанию недостижимо:

```java
@Entity
@FilterPolicy(maxDepth = 4, maxPageSize = 100, defaultPageSize = 20,
        defaultOrderBy = "createdAt desc, id asc")
public class Product {

    @Filterable
    private String name;

    @Filterable(ops = {EQ, GT, GE, LT, LE})
    private BigDecimal price;

    @Filterable(name = "cost", roles = "ROLE_ADMIN")   // наружу — под собственным именем
    private BigDecimal supplierCost;                   // и только для администраторов

    private String internalNotes;                      // без аннотации -> никогда не фильтруется

    @Filterable                     // открывает собственные @Filterable-поля Category как
    @ManyToOne                      // "category/code", "category/name", ...; без аннотации
    private Category category;      // ассоциация — глухая стена
}
```

Два момента здесь стоит перечитать дважды.

**Обход ассоциаций включается явно, как и всё остальное.** `@Filterable`-поля `Category` выбирались
для эндпоинта *самой Category*; без аннотации на поле `category` они здесь не видны. Будь обход
автоматическим, открытие одного поля у часто используемой сущности расширяло бы поверхность
фильтрации каждого эндпоинта, который до неё дотягивается. `roles` на ассоциации закрывает всё
поддерево: вызывающему нужны и роли ассоциации, и роли самого вложенного поля.

**`defaultOrderBy` — то, что делает постраничную выдачу корректной.** Запрос без полного порядка
позволяет базе возвращать строки как ей угодно, поэтому `$skip=0` и `$skip=20` — два независимых
запроса, которые могут показать одну и ту же строку дважды или не показать вовсе; такая ошибка
проявляется только на боевых объёмах. Эта сортировка *дописывается* к `$orderby` вызывающего, а не
используется лишь как запасная, поэтому разрывает ничьи и при `$orderby=status`. Заканчивайте её
уникальной колонкой. Эти пути — конфигурация сервера, а не ввод клиента, поэтому `@Filterable` им не
нужен (суррогатный ключ, по которому клиенту фильтровать нельзя, — обычный выбор), но они
проверяются по полям сущности при первом разрешении политики, так что опечатка падает явно, а не
доходит до базы.

Выполняйте запрос **в том слое, которому принадлежит сущность**, — в репозитории. Один вызов делает
всё: предикат, сортировку, смещение, лимит и подсчёт — если вызывающий от него не отказался:

```java
@Repository
@RequiredArgsConstructor
class ProductQueryRepositoryImpl implements ProductQueryRepository {

    private static final QProduct PRODUCT = QProduct.product;

    private final ODataQueryExecutor odataExecutor;

    @Override
    public ODataPage<Product> search(ODataQueryOptions options) {
        return odataExecutor.search(Product.class, options, ODataSearch.of(PRODUCT));
    }
}
```

`ODataSearch` — место, где репозиторий говорит, что ещё нужно его запросу. Всё в нём необязательно:

```java
return odataExecutor.search(Product.class, options, ODataSearch.of(PRODUCT)
        // Добавляется и в запрос строк, И в запрос количества, поэтому страница и итог согласованы.
        // Сюда идёт область данных вызывающего.
        .and(dataAccessGuard.predicate("product", DataAction.READ))
        // Меняет только запрос строк: QueryDSL запрещает fetch join в count, а соединение,
        // размножающее строки, изменило бы итог.
        .content(query -> query.leftJoin(PRODUCT.category).fetchJoin()));
```

**Передавайте корнем сгенерированный экземпляр по умолчанию.** У `QProduct.product` алиас `product` —
тот самый, по которому строятся предикат и сортировка; у `new QProduct("p")` — другой, а два разных
алиаса в JPQL не падают: они соединяют таблицу с собой и возвращают молчаливо неверные строки.
Исполнитель проверяет это и отказывается, называя оба алиаса. Проверка намеренно выполняется во время
исполнения: алиас — это *значение* строки, с которой был создан `Q`-тип, и прочитать его не могут ни
Checkstyle, ни ArchUnit.

Если запрос всё-таки нужно вести самому — проекция, оконная функция, что-то, чего два хука не
выражают, — возьмите сортировку из этого модуля, а не пишите обход пути заново:

```java
OrderSpecifier<?>[] order = ODataPaths.orderSpecifiers(Product.class, query.pageable().getSort());
```

Репозиторий Spring Data с `QuerydslPredicateExecutor` тоже по-прежнему работает, потому что предикат
строится по соглашению об алиасах `SimpleEntityPathResolver`:

```java
Page<Product> page = repository.findAll(query.predicate().orElse(null), query.pageable());
```

Контроллер принимает пять параметров одним объектом и передаёт их вниз неразобранными — так ни
JPA-сущность, ни типы QueryDSL не поднимаются выше репозитория:

```java
@GetMapping
public PageResponse<ProductResponse> search(ODataQueryOptions options) {
    ODataPage<ProductResponse> page = productService.search(options).map(mapper::toResponse);
    return PageResponse.of(page.content(), page.offset(), page.size(), page.totalElements());
}
```

```
GET /products?$filter=price lt 100 and category/code eq 'TOOLS'&$top=20&$orderby=name desc&$count=false
```

[`crud-service-example`](../../services/crud-service-example/README.ru.md) — это та же схема целиком:
контроллер -> сервис -> репозиторий, где область данных вызывающего попадает в тот же `WHERE`, что
и `$filter`.

### Что ответ сообщает о текущей позиции

`PageResponse` отдаёт и `offset`, и `page`, и причина этому — `$skip`: смещение в OData абсолютное и
явно не обязано быть кратным `$top`, поэтому у невыровненного `$skip` нет целой страницы. При
`$top=20` и `$skip=20`, и `$skip=25` дают `page=1`, и клиент, листающий по смещению, не смог бы
вычислить следующий запрос из ответа. `offset` — это достоверная позиция, `page` — удобство для
выровненного случая.

`totalElements` и `totalPages` **отсутствуют** — не null и не нуль, их просто нет в JSON — когда
вызывающий прислал `$count=false`. Запрос количества в этом случае не выполняется, а на глубоко
листаемой отфильтрованной выборке по большой таблице он обычно самая медленная часть запроса. Нуль
в роли признака «не считали» не подходит: нуль — настоящий итог.

### Почему не связывать разобранный запрос с параметром контроллера

Раньше модуль поставлял `ODataQueryArgumentResolver`, который заполнял `ODataQuery<Product>`
напрямую. Он был помечен `@Deprecated`, выключен по умолчанию, а теперь **удалён**. Четыре причины, и
каждую стоит прочитать, потому что каждая — о том, что этот резолвер *отдавал*, а не о том, как он
читал запрос:

- `ODataQuery<Product>` называет JPA-сущность в сигнатуре контроллера, что отвергает правило
  `web.controllers-do-not-expose-entities` из
  [`architecture-rules`](../../build/architecture-rules/README.ru.md): оно проверяет и аргументы обобщённых
  типов, поэтому параметр ловится даже когда возвращается DTO.
- Отдаёт он `Predicate` QueryDSL, выполнить который может только репозиторий. Значит, контроллер
  либо держит репозиторий сам — это `layering.controllers-do-not-access-persistence` и запрос вне
  транзакции, — либо передаёт предикат вниз, и тогда сущность оказывается в API сервисного слоя.
- springdoc не умеет описать параметр, заполняемый резолвером, поэтому `$filter`, `$top`, `$skip` и
  `$orderby` пропадают из документа OpenAPI.
- Разрешение аргументов выполняется до `@PreAuthorize` обработчика, поэтому вызывающий, которому
  эндпоинт вообще не положен, всё равно узнаёт из 403, какие поля фильтруются.

Замена — `ODataQueryOptions`, и ни одна из четырёх причин к ней не относится: у неё нет параметра
типа и она не называет сущность, она несёт запрос, а не план запроса, её пять параметров добавляет в
документ OpenAPI `ODataQueryOptionsOpenApiCustomizer` (работает всегда, когда springdoc есть в
classpath), и она не вычисляет политику — её резолвер может упасть только на неверном скалярном
параметре, а это 400 о самом запросе, который ничего не сообщает о модели данных.

Та половина старого резолвера, что читала запрос, сохранена ровно как была, включая алиасы без
префикса `$` для шлюзов, которые калечат ведущий `$`
(`odata.filter.web.dollar-prefixed-parameters-only=true` их отключает).

Разбор остаётся в репозитории, а `ODataFilterService` сохраняет независимость и от Spring MVC, и от
JPA — именно это позволяет `export-spring-boot-starter` повторно применить сохранённый фильтр в
рабочем потоке без запроса и без `EntityManager`. `JPAQueryFactory` нужен только
`ODataQueryExecutor`, и он живёт в отдельной автоконфигурации, зависящей от наличия этого бина, —
поэтому модуль, который только разбирает фильтры, по-прежнему стартует.

## Что ограничивается и где настраивается

| Предмет | Глобальное умолчание (`odata.filter.*`) | Переопределение на сущности (`@FilterPolicy`) |
|---|---|---|
| Вложенность фильтра | `max-depth` (4) | `maxDepth` |
| Максимальный размер страницы (`$top`) | `max-page-size` (200) | `maxPageSize` |
| Размер страницы по умолчанию | `default-page-size` (20) | `defaultPageSize` |
| Глубина обхода ассоциаций | `max-nested-property-depth` (2) | `maxNestedPropertyDepth` |
| Длина исходной строки `$filter` | `max-expression-length` (2048) | — |
| Сортировка, дописываемая к `$orderby` | — | `defaultOrderBy` |
| `$top` больше максимума | `page-size-exceeded-strategy` (`REJECT`/`CLAMP`) | — |
| Считать ли итог | `$count` вызывающего (по умолчанию да) | — |

На уровне поля, через `@Filterable`: какие операторы разрешены (`ops`), какие роли могут им
пользоваться (`roles`) и можно ли по нему сортировать (`sortable`).

Для всего, что декларативная политика выразить не может («фильтры по дате в Order не могут охватывать
больше года»), зарегистрируйте бин `FilterValidator` — он выполняется после встроенных проверок и до
построения предиката:

```java
@Bean
FilterValidator orderDateRangeValidator() {
    return context -> {
        if (context.entityType() == Order.class && spansMoreThanAYear(context.root())) {
            throw new FilterValidationException("фильтры по диапазону дат в Order не могут охватывать более 366 дней");
        }
    };
}
```

### Журнал аудита

Каждый применённый фильтр записывается в единственный `AuditSink` из
[`audit-core`](../audit-core/README.ru.md) — категория `query`, действие `query.filtered`, ресурсом
названа сущность. **Записываются пути свойств и операторы, но не значения**: `properties=email, name` и
`operators=email eq, name contains` говорят, что вызывающий фильтровал по адресу электронной почты, не
говоря, по какому именно.

Это не формальность. Журнал аудита хранится годами и читается людьми, которым сами данные не положены,
поэтому значение в нём — утечка с долгим следом. Значения при этом не хешируются и не обрезаются: хеш
обратим для всего, что берётся из небольшого набора (статус, канал, код страны), а обрезка оставляет
именно опознаваемое начало. Единственное безопасное обращение со значением, которое никому не нужно, —
не собирать его, поэтому `FilterSummary` выводится из разобранного AST и ни разу не читает литерал.

**Падает ли запрос при недоступном приёмнике — решает развёртывание, а не этот модуль.** Приёмник
вызывается без `try`/`catch`: `AuditFailurePolicy`, разрешаемая из конфигурации, решает, откатить ли
чтение при неудачной записи аудита или залогировать и продолжить. `catch` здесь переопределил бы это
решение жёстко прописанным в библиотеке. Настройте политику для категории `query` соответственно: тот,
кто предпочтёт потерять чтение, но не потерять запись о нём, ставит `FAIL_OPERATION`, и таких немного.

Приложение, не подключившее `audit-spring-boot-starter`, не имеет бина приёмника, и журнал тогда уходит в
`NoopAuditSink` из `audit-core`, а не ломает запуск.

Событие Spring `FilterAppliedEvent` **по-прежнему публикуется** и по-прежнему годится как внутренний
хук — метрика, инвалидация кеша. Чем оно больше не является, так это способом попасть в журнал аудита:
раньше это был единственный способ, а значит журнал существовал лишь если каждый потребляющий сервис
писал один и тот же пересылающий слушатель, ничего не редактировалось, и `AuditFailurePolicy` не
управляла ничем.

## Разрешение ролей

Если Spring Security есть в classpath, роли автоматически читаются из `GrantedAuthority` в
`SecurityContextHolder`. Иначе (или чтобы брать роли откуда-то ещё, например из заголовка, добавленного
шлюзом) реализуйте `FilterPrincipalResolver` и объявите его бином.

## Поддерживаемая грамматика `$filter`

`and`, `or`, `not`, группировка скобками; сравнения `eq ne gt ge lt le`; `in (v1, v2, ...)`; строковые
функции `contains`/`startswith`/`endswith`; пути свойств с обходом размеченных to-one-ассоциаций через
`/` (например, `department/manager/name`). Литералы строк, целых, decimal, double, булевых значений,
дат, datetimeoffset, GUID и перечислений. Намеренно не поддерживаются — ради ограниченной, обозримой
поверхности: арифметика, `any`/`all`, `$select`/`$expand` и прочие функции OData.

`$count` **реализован** и соблюдается: `$count=false` пропускает запрос количества, и тогда ответ не
несёт итога. Раньше модуль утверждал, что этот флаг ничего вызывающему не даёт, — и это было верно,
пока запрос здесь никто не выполнял: флаг на `ODataQuery`, с которым никакой код не мог ничего
сделать, хуже отсутствия флага. `ODataQueryExecutor` — единственное место, которое может его
соблюсти, и соблюдает. Значение, не равное `true` или `false`, даёт 400 с `$count` в поле `property`;
`Boolean.parseBoolean` намеренно не используется, иначе `$count=yes` был бы прочитан как `false` и
молча отнял бы у вызывающего итог.

Ещё две ловушки, обе унаследованы от SQL, а не от этой библиотеки: фильтр по вложенному пути
(`department/name eq 'Sales'`) превращается в inner join, поэтому строки с пустой ассоциацией
выпадают из результата — в том числе под `ne` и `not`, — а трёхзначная логика означает, что
`not (status eq 'X')` никогда не совпадёт со строкой, у которой status равен null.

## Ответы об ошибках

Каждое исключение этого модуля наследует `ODataFilterException`, а то, как оно доходит до клиента,
зависит от одного: есть ли в classpath
[`web-core-spring-boot-starter`](../../sources/web-core-spring-boot-starter/README.md).

**Если есть** — а это предполагаемая схема — модуль отдаёт в общий конвейер проблем того стартера
`ODataFilterProblemMapper` и bundle `i18n/ludwig-odata-filter-messages`. Ошибки запроса тогда
возвращаются **на языке вызывающего**, под кодами `ludwig.odata.error.*`, ровно в той же форме
RFC 9457, что и любая другая ошибка сервиса, а поле-нарушитель лежит в члене `property`, который
клиент читает, не разбирая предложение:

```json
{
  "type": "urn:ludwig:problem:ludwig.odata.error.field-forbidden",
  "title": "Доступ запрещён",
  "detail": "У вас нет прав на фильтрацию или сортировку по одному из полей этого выражения. См. поле \"property\".",
  "status": 403,
  "code": "ludwig.odata.error.field-forbidden",
  "property": "supplierCost"
}
```

Переформулировать что угодно можно, объявив тот же ключ в собственном bundle: конвейер сначала
смотрит в bundle приложения.

**Если нет**, вместо этого регистрируется старая advice `ODataFilterExceptionHandler`, так что сервис,
не использующий тот стартер, всё равно получает ответы RFC 7807 — на английском, из собственных
сообщений исключений, написанных для разработчика. Выключается через
`odata.filter.web.problem-detail-advice-enabled=false`, если вы хотите обрабатывать эти исключения
сами.

Вместе они не сосуществуют никогда. Та advice была первым ответом модуля, и у неё был структурный
изъян: библиотека может отдавать только тот текст, с которым была скомпилирована, поэтому её
английские сообщения оставались единственной непереводимой частью в остальном локализованного API — а
единственным выходом было выключить её и вручную переобработать все семь типов исключений, что каждый
потребитель затем и делал, одинаково. Маппер вместе с bundle убирает обе половины: смысл объявлен
здесь один раз, текст поставляется отсюда на всех поддерживаемых модулем языках, а приложение
по-прежнему может переопределить что угодно.

## Как узнать, что фильтруется

Клиент не должен выяснять фильтруемую поверхность, отправляя фильтры и читая отказы, — а это
единственная альтернатива, и именно это поведение описано ниже как сигнал для алерта по счётчику
`odata.filter.rejected`. Включите обнаружение, и вызывающий сможет спросить:

```
GET /api/v1/filter-metadata/product
```

```json
{
  "entity": "product",
  "maxDepth": 4,
  "maxPageSize": 100,
  "defaultPageSize": 20,
  "maxNestedPropertyDepth": 2,
  "defaultOrderBy": "createdAt desc, id asc",
  "properties": [
    { "path": "category/code", "type": "string",  "operators": ["contains", "endswith", "eq", "ge", "gt", "in", "le", "lt", "ne", "startswith"], "sortable": true },
    { "path": "name",          "type": "string",  "operators": ["contains", "endswith", "eq", "startswith"], "sortable": true },
    { "path": "price",         "type": "decimal", "operators": ["eq", "ge", "gt", "le", "lt", "ne"], "sortable": true }
  ]
}
```

Включить нужно два места, и так задумано:

```yaml
odata:
  filter:
    metadata:
      base-path: /api/v1/filter-metadata   # не задано — эндпоинта не существует вовсе
```

```java
@Entity
@FilterPolicy(maxPageSize = 100, defaultOrderBy = "createdAt desc, id asc",
        metadataName = "product")          // не задано — сущность не публикуется и отдаёт 404
public class ProductEntity { }
```

**Не задано — значит отсутствует, а не отказывает.** Документ метаданных — это карта запрашиваемой
поверхности, полезная и клиенту, и тому, кто её перебирает, поэтому поверхности не должно быть, пока
развёртывание не решило иначе. Эндпоинт, который существовал бы и отвечал 403, всё равно подтверждал бы
наличие функции и всё равно был бы в одной ошибке конфигурации от ответа. По той же причине включение
действует и на уровне сущности: сущность, которую никто не назвал, отдаёт 404 — и имя, которым никто не
пользовался, тоже; различать их значило бы превратить это в способ перебрать модель данных.

**У каждого вызывающего свой документ.** Роли берутся из того же `FilterPrincipalResolver`, что и в пути
запроса, а путь, по которому вызывающему фильтровать нельзя, **отсутствует** — а не присутствует с пометкой
«запрещено». Вызывающий, узнавший, что `supplierCost` существует и требует `ROLE_ADMIN`, узнал имя колонки и
имя привилегии от эндпоинта, задача которого — сообщить ему меньше. По той же причине в документе нет ни
одного имени роли, а закрытая ассоциация скрывает все пути под собой.

**Это проекция политики, а не второй список.** Каждое поле берётся из разрешённой `EntityFilterPolicy`,
которая берётся из аннотаций самой сущности, поэтому документ рекламирует ровно то, что принимает путь
запроса. Список полей, поддерживаемый рядом с аннотациями, расходился бы — и расходился бы незаметно именно в
тех двух случаях, которые важны: поле открыто в коде и всё ещё отсутствует в документе, и поле закрыто в
коде, но всё ещё рекламируется. Согласие проверяется тестом напрямую, потому что «эти два вычисления
согласованы» — свойство их результата, которого не видят ни ArchUnit, ни Checkstyle.

**Появляются только пути с `@Filterable`.** Неаннотированное поле недостижимо фильтром и остаётся
недостижимым для обнаружения: документ проецирует белый список, а не схему.

### Почему это не называется `$metadata`

`$metadata` в OData — это CSDL-документ, описывающий сервис: наборы сущностей, навигационные свойства,
действия, контейнер сущностей. Этот модуль реализует `$filter`, `$orderby`, `$top`, `$skip` и `$count` и
ничего из остального, поэтому документ, называющий себя `$metadata`, но описывающий лишь фильтруемое
подмножество, вводил бы в заблуждение любой универсальный OData-клиент, который его нашёл бы. Это хуже, чем
не иметь его вовсе.

### Почему нет кеша

Разрешённая политика уже запоминается в `FilterPolicyRegistry`, поэтому запрос стоит обхода нескольких
десятков записей map. Кеш пришлось бы ключевать по **разрешённому набору ролей** вызывающего, а не по
сущности — иначе список полей администратора попадёт непривилегированному вызывающему, — а это означает
объявление `CachePurpose.SECURITY`, чей TTL есть время, в течение которого отозванная роль продолжает видеть
поле. Платить такую цену за корректность, чтобы сэкономить обход map, — неверный обмен. Если кеш когда-нибудь
понадобится, он пойдёт через `LudwigCacheRegistry` с этой целью и этим ключом, а не через собственный
builder `Caffeine`.

## Метрики

Опционально (только при наличии Micrometer в classpath, включено по умолчанию через
`odata.filter.metrics.enabled`): `odata.filter.applied` считает успешно разобранные и переведённые
фильтры, `odata.filter.rejected` — каждое отклонение с тегами `entityType` и `reason` (простое имя
отклонившего исключения: `FilterSyntaxException`, `FilterAccessDeniedException`,
`PageSizeExceededException`, …), а `odata.filter.parse.duration` измеряет весь вызов `parse`
независимо от исхода. Устойчивый всплеск `rejected` — это либо баг клиента, либо чей-то перебор в
поисках того, что фильтруется; и то и другое стоит алерта.

`odata.filter.metadata.served` считает документы, отданные эндпоинтом обнаружения, с тегом сущности. Он
существует, чтобы читаться рядом с `rejected`: рост отказов — это либо ошибка клиента, либо чьё-то
прощупывание фильтруемой поверхности, и именно этот счётчик отличает клиентов, спросивших по-человечески, от
прощупывающих, чего счётчик отказов сам по себе не может.
