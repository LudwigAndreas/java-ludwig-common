# jira-client

*[English](README.md) · **Русский***

Типобезопасный Java-клиент для **Jira Server / Data Center REST API v2**, ориентированный на
**Jira Server 9.12.27 (buildNumber 9120027)**, а также для **ALM Works Structure 2.0 REST API**.

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>jira-client</artifactId>
</dependency>
```

```java
try (JiraClient jira = JiraClient.builder()
        .baseUrl("https://jira.example.com")
        .personalAccessToken(System.getenv("JIRA_TOKEN"))
        .verifyOnBuild(true)
        .build()) {

    jira.search()
            .searchAll(JqlQuery.builder()
                    .where(Jql.project().in("OPS", "PLAT"))
                    .where(Jql.status().notIn("Done", "Closed"))
                    .where(Jql.created().after("-30d"))
                    .orderByStableWalk()
                    .build())
            .forEach(issue -> log.info("{} {}", issue.key(), issue.fieldsOrEmpty().summary()));
}
```

---

## Чем этот модуль является и чем сознательно не является

Это **обычная библиотека**. Никакой зависимости от Spring, никакой автоконфигурации, никакого
стартера. Во время выполнения нужны ровно две зависимости — Jackson и SLF4J API; транспорт — это
`java.net.http.HttpClient` из JDK. Это решение, а не упущение: клиент к Jira вызывают из
Spring-сервисов, из batch-заданий, из CLI и из тестов, и тащить во всё это второй HTTP-стек вместе с
автоконфигурацией не даёт ничего. Сервису, которому нужен бин, достаточно одного метода `@Bean` — см.
[Использование из Spring](#использование-из-spring).

Модуль нацелен на **Server 9.12**, а не на Cloud. Эти два API разошлись, и различия не косметические:

| | Jira Server 9.12 (этот клиент) | Jira Cloud |
|---|---|---|
| Базовый путь | `/rest/api/2` | `/rest/api/3` |
| Идентификация пользователя | `name` (логин) и `key` | `accountId` |
| Форматированный текст | wiki-разметка, обычная `String` | Atlassian Document Format |
| Пагинация поиска | `startAt` / `maxResults` | курсор `nextPageToken` |
| Токены | personal access token (8.14+) | API-токены, OAuth 2.0 |

Каждый из этих пунктов здесь смоделирован по-серверному. Против Cloud клиент в основном работает, а
его работа с пользователями — нет; `verifyConnection()` предупреждает, если за базовым URL обнаружился
Cloud.

## Устройство

### Слои

```
JiraClient                    фасад: issues(), search(), projects(), structures(), ...
  └── JiraRestClient          сборка URI, аутентификация, интерсепторы, ретраи, ошибки, JSON
        └── JiraTransport     один метод: отправить запрос, вернуть ответ
              └── JdkJiraTransport   java.net.http.HttpClient
```

Каждая граница существует потому, что на ней что-то должно быть заменяемым. `JiraTransport` — чтобы
команда, уже стандартизовавшаяся на Apache HttpClient, или нуждающаяся в обёртке с mutual-TLS, или
записывающая фикстуры в тесте, могла заменить низ, не трогая ничего выше. `JiraRestClient` — потому
что **ни одна клиентская библиотека не покрывает все endpoint'ы**: каждое приложение из Marketplace
добавляет собственное пространство имён под `/rest`. Библиотека без выхода за пределы собственной
модели вынуждает поднимать рядом второй HTTP-клиент со вторым экземпляром аутентификации, ретраев и
обработки ошибок:

```java
JsonNode boards = jira.rest()
        .get("/rest/agile/1.0/board")
        .query("projectKeyOrId", "OPS")
        .operation("agile.board.list")
        .asTree();
```

Этот вызов получает те же учётные данные, ту же политику ретраев, те же метрики и то же отображение
ошибок, что и смоделированный.

### Ошибки

Любой сбой — это unchecked `JiraException`. Подклассы выделены там, где реакция вызывающей стороны
различается:

| Исключение | Когда | Что делать |
|---|---|---|
| `JiraAuthenticationException` | 401 | Никогда не ретраится — повтор 401 приводит к CAPTCHA-блокировке служебной учётной записи |
| `JiraAuthorizationException` | 403 | Проверить `mypermissions`; может быть и вызовом CAPTCHA |
| `JiraNotFoundException` | 404 | Означает «не видно этой учётной записи» не реже, чем «не существует»: Jira скрывает существование от тех, кому нельзя смотреть |
| `JiraConflictException` | 409, устаревшая версия леса Structure | Перечитать и применить заново; не отправлять повторно |
| `JiraRateLimitException` | 429 | Несёт `Retry-After`; снизить параллелизм |
| `JiraApiException` | любой другой не-2xx | Несёт `errorMessages` и пофайловые `errors` от Jira |
| `JiraTransportException` | ответа не было вовсе | Чтение повторять безопасно; запись могла уже примениться |
| `JiraSerializationException` | тело не совпало с моделью | Обычно HTML-страница прокси или смена версии Jira |

`JiraApiException` разбирает error collection от Jira, поэтому `getFieldErrors().get("summary")`
отвечает «Summary is required.» без повторного разбора тела.

### Ретраи

Три попытки, база 500 мс, экспонента, **полный джиттер**, потолок 20 с — и только для:

- **идемпотентных методов.** `POST`, завершившийся таймаутом, мог уже создать задачу, а механизма
  ключа идемпотентности, который сделал бы повтор безопасным, в Jira нет. `/search` и `/value` из
  Structure включают ретраи явно, потому что это чтения, которым просто выпало быть `POST`.
- **429, 502, 503, 504** и транспортных сбоев. **500 исключён сознательно**: Jira возвращает его на
  серверную ошибку, которая повторится точно так же, а ретраи лишь утроят нагрузку на и без того
  тяжело работающий экземпляр.

Джиттер здесь не украшение. Когда узел Jira перезапускается, все клиенты, бывшие в процессе запроса,
ретраятся одновременно; backoff без джиттера снова сводит их в одну точку — и ещё раз после этого.

`Retry-After` от сервера всегда побеждает — с потолком, чтобы прокси, попросивший час, не занял поток
на час.

## JQL

Построитель, в котором **типы решают, какие операторы существуют**. У текстового поля есть `~`, у
поля даты — `>=`, и ни у одного нет операторов другого: Jira отвергает `summary >= "x"` во время
выполнения запроса, а эта библиотека предпочитает, чтобы это была ошибка компиляции.

```java
String jql = JqlQuery.builder()
        .where(Jql.project().is("OPS"))
        .where(Jql.assignee().inGroup("platform-team"))
        .where(Jql.status().changedTo("Done").after("-7d"))
        .where(Jql.summary().contains(userSuppliedText))
        .whereIf(onlyUnresolved, Jql.resolution().isEmpty())
        .where(Jql.numberCustomFieldById(10004).atLeast(3))
        .orderByStableWalk()
        .render();
```

**Экранируется каждое значение.** `userSuppliedText` выше не может выйти за пределы своего литерала,
какие бы кавычки и обратные слэши он ни нёс, — а это и есть JQL-инъекция, достижимая из любой строки
поиска, проброшенной прямо в запрос. Имена полей заключаются в кавычки тогда, когда этого требует JQL,
включая совпадающие с зарезервированными словами.

`orderByStableWalk()` добавляет `ORDER BY created ASC, issuekey ASC`. Зачем это нужно: Jira
пагинирует по смещению, поэтому обход, упорядоченный по `updated`, читает набор результатов, который
переупорядочивается под ним, и строки возвращаются дважды либо теряются. Сортировка по неизменяемым
ключам — то, что делает постраничную выгрузку полной.

Запасные выходы — `JqlValue.raw(...)` для конструкции, которую построитель не моделирует, и
`JqlFunction.of(name, args...)` для функции из Marketplace; вторая всё равно экранирует аргументы,
поэтому она предпочтительнее.

## Пользовательские поля

Идентификаторы пользовательских полей **зависят от экземпляра**. `Story Points` — это
`customfield_10004` в одной Jira и `customfield_11702` в другой, и отказ при жёстко прописанном
идентификаторе беззвучен: чтение несуществующего поля возвращает отсутствие значения, а не ошибку.

Разрешайте имена один раз, при старте:

```java
CustomFieldRegistry fields = jira.customFields();
CustomField<Double> storyPoints = fields.field("Story Points", Double.class);

Optional<Double> points = jira.fieldAccess().read(issue, storyPoints);
String jqlName = fields.jqlClauseName("Story Points");   // cf[10004] - переживёт переименование
```

Реестр **отказывается угадывать**, когда два пользовательских поля носят одно отображаемое имя (Jira
это допускает, и это разные поля), и вместо угадывания перечисляет кандидатов — так проблема всплывает
при старте, а не в виде интеграции, полгода читавшей не то поле.

Чтение и запись несимметричны, и именно здесь ошибаются самописные клиенты. Поле-список *читается*
как `{"self":..., "value":"Blue", "id":"10100"}`, а *записывается* как `{"id":"10100"}`.
`FieldAccess` декодирует формы чтения, `FieldValues` строит формы записи:

```java
jira.issues().update("OPS-1", IssueInput.builder()
        .field(storyPoints.id(), 5)
        .field(team.id(), FieldValues.option("10500"))
        .field(reviewers.id(), FieldValues.users("jsmith", "adoe"))
        .build());
```

### Привязка задач к собственным типам

```java
record Ticket(
        @JiraFieldBinding(id = "key")            String key,
        @JiraFieldBinding(id = "summary")        String summary,
        @JiraFieldBinding(name = "Story Points") Double storyPoints,
        @JiraFieldBinding(name = "Team")         CustomFieldOption team) { }

List<Ticket> tickets = jira.search().searchAll(query)
        .map(issue -> jira.binder().bind(issue, Ticket.class))
        .toList();
```

`name = ...` разрешается через реестр в момент привязки, поэтому один и тот же исходник корректен во
всех средах. Работают и record'ы, и неизменяемые классы, и собственные аннотации Jackson: привязчик
переписывает задачу в JSON-объект с ключами по именам ваших свойств и отдаёт его Jackson, а не
присваивает поля рефлексией.

## Запись задач: `fields` против `update`

В теле записи у Jira две секции, и различие между ними важнее, чем различие между созданием и
обновлением:

```java
IssueInput.builder()
        .labels("a", "b")      // fields: ЗАМЕНЯЕТ набор меток
        .addLabel("c")         // update: добавляет одну, остальные не трогает
        .removeLabel("d")
        .clear("customfield_10001")   // явный JSON null - «очистить поле»
        .addComment("done by automation")   // атомарно с правкой
        .build();
```

`.labels(...)` отбрасывает всё, что там было, включая метку, которую другой процесс добавил между
вашим чтением и вашей записью. `.addLabel(...)` — нет. Ради этого у каждого многозначного поля здесь
есть пара add/remove.

Неупомянутое поле остаётся как было; `clear(...)` выставляет его в null. На проводе это разные вещи,
поэтому неустановленный optional никогда не сериализуется как `null`: маппер клиента опускает null, а
`clear()` пишет `NullNode`, чтобы различие сохранилось.

### Переходы

```java
jira.issues().transitionByName("OPS-1", "Resolve Issue",
        IssueInput.builder().resolution("Fixed").addComment("fixed in 1.4.2").build());
```

Никогда не прописывайте идентификатор перехода жёстко: идентификаторы принадлежат workflow, поэтому
работающий в одном проекте идентификатор в другом означает другой переход — или ничего.
`transitionByName` стоит одного дополнительного запроса и падает громко, перечисляя, что *было*
доступно.

Выставление полей через переход — это также не то же самое, что правка с последующим переходом. Только
форма перехода может удовлетворить обязательные поля экрана перехода, и только она атомарна.

## Пагинация

```java
// Лениво: findFirst по запросу на 200 000 задач делает один HTTP-запрос.
Optional<Issue> first = jira.search().searchAll(query).findFirst();

// По странице за раз, для пакетной обработки.
jira.search().searchAllPages(request).forEach(page -> repository.saveAll(page.values()));
```

Jira непоследовательна в том, как сообщает об окончании обхода: одни endpoint'ы присылают `isLast`,
другие `total`, третьи ничего, а поиск присылает `total: -1`, если его попросили не считать.
`Page.hasMore()` сводит все три случая к одному ответу. Кроме того, обход продвигается по
**фактически возвращённым** строкам, а не по запрошенному размеру страницы, потому что Jira молча
ограничивает `maxResults`, и продвижение по запрошенному размеру пропустило бы удержанные строки.

## Structure (ALM Works)

Есть только там, где установлено приложение; без него каждый вызов в этом пространстве имён возвращает
404. Проверяйте один раз при старте, а не на каждом запросе.

```java
Forest forest = jira.forests().readStructure(113);
List<ForestNode> tree = forest.tree();

// Свёрнутые колонки - значения, которых нет в собственном API Jira, потому что у Jira нет
// иерархии, по которой что-либо сворачивать.
ValueResponse values = jira.structureValues().compute(
        ForestSpec.structure(113),
        forest.rows().stream().map(ForestRow::rowId).toList(),
        List.of(AttributeSpec.field("customfield_10004")));

jira.forests().move(ForestSpec.structure(113), rowId, underRowId, afterRowId);
```

Три вещи про Structure, которые этот клиент берёт на себя и в которых легко ошибиться вручную:

- **Строка — это не задача.** Это *позиция*, и одна задача может занимать несколько строк в одной
  структуре. Любая запись адресуется по `rowId`.
- **Лес приходит одной строкой `formula`**, а не вложенным JSON: структура на пятьдесят тысяч строк в
  виде объектов весила бы десятки мегабайт. `ForestFormula` декодирует
  `10394:0:4/356,10332:0:14707,...` в строки и восстанавливает иерархию.
- **Каждое изменение указывает версию, относительно которой оно вычислено.** Structure отвергает
  обновление по устаревшей версии, а не сливает его, — это единственное, что стоит между двумя
  одновременными перестановками и молчаливой потерей данных. Отказ приходит как
  `JiraConflictException`; лечится перечитыванием и пересчётом, а не повторной отправкой.

Покрытие здесь — ресурсы Structure, Forest, Value и Item, сверенные с опубликованной документацией
Structure 2.0 REST. Всё сверх этого достижимо через `jira.rest()`.

## Наблюдаемость

```java
JiraClient.builder()
        .metrics(new MicrometerJiraClientMetrics(meterRegistry))
        .addInterceptor((request, chain) -> chain.proceed(
                request.toBuilder().header("X-Correlation-Id", MDC.get("correlationId")).build()))
        .build();
```

| Метрика | Тип | Теги |
|---|---|---|
| `jira.client.requests` | timer | `operation`, `method`, `status` (группы `2xx`/`4xx`/`5xx`/`none`), `outcome` |
| `jira.client.retries` | counter | `operation`, `reason` |
| `jira.client.rate.limited` | counter | `operation` |

Теги несут **операцию** (`issue.get`, `search`), а не URI. Один временной ряд на ключ задачи — это
авария системы метрик; по той же причине статус сгруппирован.

Micrometer — `optional`-зависимость, и `MicrometerJiraClientMetrics` — единственный класс, который на
неё ссылается, поэтому потребителю, который её не вызывает, она не нужна на classpath.

## Использование из Spring

```java
@Configuration
class JiraConfiguration {

    @Bean(destroyMethod = "close")
    JiraClient jiraClient(JiraProperties properties, MeterRegistry meterRegistry) {
        return JiraClient.builder()
                .baseUrl(properties.baseUrl())
                .personalAccessToken(properties.token())
                .metrics(new MicrometerJiraClientMetrics(meterRegistry))
                .verifyOnBuild(true)
                .loadCustomFields(true)
                .build();
    }
}
```

Один экземпляр на одну Jira на приложение, живущий всё время работы процесса. Клиент потокобезопасен;
создание экземпляра на запрос выбрасывает пул соединений, а вместе с `loadCustomFields` ещё и
перечитывает каталог полей каждый раз.

`verifyOnBuild(true)` и `loadCustomFields(true)` стоит включать в любом долгоживущем сервисе. Они
переносят «токен истёк», «в базовом URL опечатка» и «имя пользовательского поля написано неверно» с
первого запроса в три часа ночи на момент старта контекста.

## Раннее падение

Что построитель проверяет до возврата, без обращения по сети:

- базовый URL разбирается, абсолютен и использует `http`/`https`;
- базовый URL оканчивается слэшем — без него `URI.resolve` отбрасывает последний сегмент пути, и
  экземпляр, отдаваемый по context path (`https://example.com/jira`), молча отправляет каждый запрос
  на `https://example.com/rest/...`, где каждый из них получает 404;
- учётные данные выбраны. Неявного анонимного режима по умолчанию нет: анонимный клиент против Jira с
  правами получает 404, а не 401, что читается как «не те ключи задач», а не как «не аутентифицирован».
  `anonymous()` говорит об этом явно, когда это и требуется.

`verifyOnBuild(true)` добавляет то, что может ответить только сервер: `/serverInfo` (большинство
экземпляров отвечают на него анонимно, поэтому он отделяет «не тот URL» от «не те учётные данные») и
`/myself`.

## Аутентификация

`personalAccessToken(...)` — верный выбор на 9.12. PAT можно ограничить и просрочить, не трогая пароль
учётной записи; он не принимается не-REST endpoint'ами Jira, поэтому утёкший токен не даст войти в
веб-интерфейс; и он не запускает защиту «CAPTCHA после неудачных входов», которая при Basic-аутентификации
блокирует служебную учётную запись на *всех* последующих вызовах.

`basicAuth(...)` поддержан для старых экземпляров. У обоих есть варианты с ротацией
(`PersonalAccessTokenCredentials.rotating(supplier)`), опрашиваемые **на каждой попытке**, так что
секрет, провернувшийся посреди ретраев, подхватывается, а не даёт три 401 подряд. `JiraCredentials` —
открытый SPI для всего остального.

Переключателя `trustAllCertificates` нет и не будет: передавайте `SSLContext`, построенный над
truststore с вашим CA. Клиент, которому можно велеть не проверять сертификат, рано или поздно получит
такую команду в продакшене.

## Покрытие API

**Jira Platform v2** — задачи (CRUD, массовое создание, назначение, переходы, метаданные правки и
создания, уведомления, архивирование), поиск JQL, комментарии, списания времени с корректировкой
оценки, вложения, связи задач и типы связей, внешние ссылки, наблюдатели, голоса, entity properties,
проекты, версии, компоненты, роли проекта, пользователи, группы, определения полей и опции
пользовательских полей, типы задач, статусы, категории статусов, приоритеты, резолюции, фильтры и
права доступа к ним, разрешения, сведения о сервере и конфигурация, роли приложений.

**Structure 2.0** — структуры, правила доступа, леса (чтение, обновление, перемещение, удаление,
добавление задач), вычисляемые значения атрибутов, элементы.

**Всё остальное** — через `jira.rest()`, включая пространства имён Jira Software Agile и Service Desk,
которые вне заявленной области этого модуля, но в одном вызове от неё.

## Тестирование

113 модульных тестов, Jira не требуется. `RecordingTransport` отвечает из очереди заготовленных ответов
и записывает, о чём его спросили, — только так интересные пути вообще покрываются: 429 с `Retry-After`,
обрыв соединения посреди записи и HTML-страница ошибки от обратного прокси не воспроизводимы против
настоящего сервера.

Набор проверяет **то, что уходит на провод**: URL, строки запроса, заголовки и формы тел. Это та часть
REST-клиента, которую не покрывает никакое тестирование моделей и о которой настоящая Jira сообщила бы
лишь кодом 400.

## Каким соглашениям модуль следует, и одному — нет

Он следует конфигурации сборки реактора, общим правилам Checkstyle и платформенной привычке объяснять
*почему* в коде, а не только в README.

Он не следует правилу платформы «три слоя моделей с генерируемыми мапперами», и причина в том, что
правило здесь неприменимо. Оно про то, чтобы сервис не протекал своей моделью хранения в свой API; у
этого модуля нет ни хранения, ни собственного API — его модели *и есть* граница, а отображение JSON
Jira в промежуточную модель, а затем во вторую, добавило бы слой, существующий только затем, чтобы его
пересекать. `IssueBinder` — это шов для потребителя, которому нужен собственный доменный тип, и тип
этот принадлежит потребителю, а не модулю.
