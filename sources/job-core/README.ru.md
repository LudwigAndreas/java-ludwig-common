# job-core

*[English](README.md) · **Русский***

Строительные блоки каждого планируемого воркера платформы, работающего с БД: экспоненциальный backoff с
jitter, самопланирующийся жизненный цикл с дренажом при остановке, запрос захвата
`FOR UPDATE SKIP LOCKED`, идентичность экземпляра для колонок владельца блокировки и единственная
распределённая блокировка платформы. Собственных задач у модуля нет. Одна реализация каждого элемента
означает, что каждый воркер - outbox, reconciliation, export, ingest, очистки - ведёт себя одинаково во
время сбоя партнёра или rolling deploy.

| | |
|---|---|
| Роль | library (с автоконфигурацией) |
| Зависит от (в репозитории) | ничего (test: `test-support`) |
| Используется | стартерами `audit`, `export`, `file-action`, `file-ingest`, `idempotency`, `messaging-db`, `outbox`, `reconciliation`; `notification-service` |
| Поверхности | нет |

| Элемент | Что это |
|---|---|
| `BackoffPolicy` / `BackoffCalculator` | Экспоненциальный backoff с множителем, потолком и jitter, вычисляемый для сохраняемого `next_attempt_at` |
| `ScheduleSpec` / `SelfSchedulingLifecycle` / `ScheduledJob` | База `SmartLifecycle`, которая сама планируется на внедрённом `TaskScheduler`, никогда не запускается дважды одновременно, гасит исключения и дренируется при остановке |
| `SkipLockedClaim` | Запрос `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *` |
| `ClaimOwner` / `JobInstanceIdentity` | Строка, которую процесс пишет в колонки `locked_by` / `owner` |
| `RunLock` / `JdbcRunLock` | Арендуемая, защищённая `run_id` блокировка на кластер для именованной единицы планируемой работы |
| `RunLockListener` / `MicrometerRunLockListener` | Опциональная инструментация блокировки |

## Использование

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>job-core</artifactId>
</dependency>
```

Зависимости времени выполнения: Spring Context, Spring Boot autoconfigure, Jakarta Persistence API (для
JPA-варианта хелпера захвата; сущности не маппятся), resilience4j-core, SLF4J. Liquibase и Micrometer
опциональны.

### Backoff

```java
BackoffCalculator backoff = new BackoffCalculator(
        new BackoffPolicy(Duration.ofSeconds(2), 2.0, Duration.ofMinutes(10), 0.3));

message.setNextAttemptAt(Instant.now().plus(backoff.nextDelay(message.getAttempts())));
```

`attempt` - номер попытки с единицы **после** только что случившейся ошибки: первая ошибка передаёт `1` и
получает `initialInterval`.

Задержка записывается в строку и подхватывается следующим тиком; ничто не спит внутри вызова.
resilience4j-core используется только как функция интервала, никогда как `@Retry`, который держал бы поток
и соединение с БД весь backoff и терял бы его при переносе пода.

**Jitter** разносит повторы записей, упавших вместе, чтобы только что восстановившийся партнёр не получил
весь бэклог разом. В продакшене используйте `0.2`-`0.3`; `0` делает кривую детерминированной для тестов.

### Планирование

```java
public class BillingStatusPoller extends SelfSchedulingLifecycle {

    public BillingStatusPoller(TaskScheduler scheduler) {
        super("billing-status", scheduler,
                ScheduleSpec.fixedDelay(Duration.ofSeconds(30), Duration.ofSeconds(10)),
                Duration.ofSeconds(20));
    }

    @Override
    protected void runOnce() {
        // один цикл; исключения пробрасывайте - базовый класс залогирует, какая задача упала
    }
}
```

Или, если тело живёт в сервисном бине: `new ScheduledJob(name, scheduler, spec, drainTimeout,
service::pollOnce)`.

| Свойство | Почему |
|---|---|
| **Не `@Scheduled`** | Стартер должен работать без `@EnableScheduling` в сервисе; забытая аннотация иначе означала бы тихий бэклог |
| **Fixed delay, никогда fixed rate** | Медленный запуск откладывает следующий, а не накапливает пересекающиеся запуски, когда система и так под нагрузкой |
| **Нереентерабельность** | Второй вход (пересечение cron, административный запуск посреди запуска) - залогированный no-op, а не второй параллельный захватчик |
| **Дренаж при остановке** | `stop()` отменяет без прерывания и ждёт до `drainTimeout`, поэтому захваченные строки не остаются брошенными до реклеймера. Держите `drainTimeout` ниже termination grace period пода |

`runNow()` использует ту же защиту от повторного входа и возвращает, был ли запуск. Административный запуск,
`POST /admin/v1/jobs/{name}/run`, не вызывает его в потоке запроса: он использует `runSoon()`, который переносит
следующий плановый запуск на сейчас в собственном планировщике задачи и отвечает `409`, пока аренду запуска задачи держит любая реплика.

### Захват

```java
List<OutboxMessage> claimed = SkipLockedClaim.claim(entityManager, OutboxMessage.class,
        "outbox_message",
        "status = 'PROCESSING', locked_at = now(), locked_by = :lockOwner",
        "t.status IN ('PENDING', 'FAILED') AND t.next_attempt_at <= :now",
        "t.created_at, t.id",
        batchSize,
        Map.of("lockOwner", lockOwner, "now", Instant.now()));
```

формирует

```sql
UPDATE outbox_message
   SET status = 'PROCESSING', locked_at = now(), locked_by = :lockOwner
 WHERE id IN (SELECT t.id FROM outbox_message t
               WHERE t.status IN ('PENDING', 'FAILED') AND t.next_attempt_at <= :now
               ORDER BY t.created_at, t.id
               LIMIT :jobClaimLimit
               FOR UPDATE SKIP LOCKED)
RETURNING *
```

- **Блокирующая конструкция - в подзапросе.** PostgreSQL не позволяет повесить её на `UPDATE`, а
  блокировки строк при update блокирующие. С `SKIP LOCKED` в подзапросе N экземпляров делят работу, а не
  ждут друг друга.
- **`RETURNING *`.** Один round trip и нет окна, в котором строка захвачена, но не загружена.
- **Полный `ORDER BY`.** Иначе бэклог может бесконечно откладывать свои самые старые строки.

Фрагменты и имя таблицы берутся из кода модуля, никогда из конфигурации или запроса; каждое значение -
связанный параметр. Есть JPA-перегрузка (параметры `:name`) и JDBC-перегрузка (параметры `?`).

### Блокировка запуска

Единственная распределённая блокировка платформы. Всё, что должно выполняться ровно на одной реплике,
берёт её отсюда.

```java
boolean ran = runLock.runIfAvailable("billing-status", handle -> {
    for (Batch batch : batches) {
        if (!handle.renew(runLock.defaultLeaseTtl())) {
            return;               // вытеснены: другая реплика уже переделывает этот запуск
        }
        process(batch);
    }
});
```

- `false` - нормальный исход: на трёх репликах две пропускают каждый запуск.
- Аренда освобождается в `finally`, в том числе когда работа бросает исключение, поэтому следующий запуск
  не блокируется на целую аренду. Исключение пробрасывается без изменений.
- Перегрузки: с явной `Duration` и примитив:

```java
Optional<RunLockHandle> held = runLock.tryAcquire("billing-status", Duration.ofMinutes(5));
if (held.isEmpty()) {
    return;                       // запуск у другого экземпляра
}
try (RunLockHandle lease = held.get()) {
    // периодически: if (!lease.renew(Duration.ofMinutes(5))) { немедленно остановиться; }
}
```

**Правила для вызывающего кода:**

1. **Аренда - не доказательство, что вы её ещё держите.** `renew` возвращает, ваша ли она ещё. При
   `false` остановитесь немедленно - другой экземпляр уже перехватил работу.
2. **`tryAcquire` никогда не блокирует.** Задача, не получившая аренду, возвращается и пробует на
   следующем тике.
3. **Не блокируйте работу, которую уже делит `SKIP LOCKED`.** Построчному поллеру блокировка не нужна; она
   свела бы N реплик к одной. Блокировки - для работы над *множеством* строк: дайджесты, очистки по сроку
   хранения, компакции.

Поведение специфицировано как capability `run-lock` в
[`openspec/specs/run-lock/spec.md`](../../openspec/specs/run-lock/spec.md); изменение поведения сначала
обновляет спецификацию.

## Конфигурация

| Свойство | По умолчанию | Смысл |
|---|---|---|
| `ludwig.job-core.enabled` | `true` | Главный выключатель |
| `ludwig.job-core.owner` | hostname + случайный суффикс | Идентичность, записываемая в колонки владельца блокировки |
| `ludwig.job-core.lock.default-lease` | `5m` | Аренда для `runIfAvailable(name, work)`. Это же время failover: под, умерший с блокировкой, блокирует задачу на этот срок |
| `ludwig.job-core.liquibase.enabled` | `true` | Применять changelog модуля собственным бином `SpringLiquibase` |

Расписания, размеры пачек и бюджеты повторов настраивает модуль, владеющий задачей, под своим префиксом.
Поэтому `BackoffPolicy` и `ScheduleSpec` - value-типы, а не классы свойств. Задача, чьи запуски сильно
отличаются от 5 минут, передаёт свою аренду в явную перегрузку.

Идентичность экземпляра **не** стабильна между перезапусками: перезапущенный под - новый владелец, и
подхват работы предшественника - явный шаг reclaim.

## Развёртывание

**Схема (только PostgreSQL).** `db/changelog/job-core/job-core-changelog.xml` создаёт `job_run_lock`
(`lock_name` уникален, `owner`, `run_id`, `acquired_at`, `heartbeat_at`, `expires_at`). Применяется
`JobCoreLiquibaseAutoConfiguration` отдельным бином `SpringLiquibase`; выставьте
`ludwig.job-core.liquibase.enabled=false`, чтобы подключить его из собственного master changelog.
`job-core-0002` создаёт `job_admin_approval`, где административная поверхность хранит согласования «четырёх глаз»;
запись в неё идёт только когда `ludwig.admin.approval.required` перечисляет операцию.

`expires_at` - единственный источник истины для «удерживается». Освобождение очищает `owner` и ставит
`expires_at = now()`; строки не удаляются, поэтому в таблице одна строка на имя блокировки.

Операции с арендой используют собственные короткие auto-commit JDBC-соединения, а не транзакцию
вызывающего: аренда должна сразу быть видна другим экземплярам и не откатываться вместе с упавшим
запуском. Менеджер транзакций, сущности и их сканирование не нужны.

## Наблюдаемость

**Метрики** (регистрируются, если есть Micrometer и бин `MeterRegistry`):

| Метрика | Тип | Теги | Смысл |
|---|---|---|---|
| `ludwig.job.lock.acquisition` | counter | `lock`, `acquired` | Попытки захвата. Если все реплики пытаются и никто не захватывает дольше аренды - аренда застряла |
| `ludwig.job.lock.lost` | counter | `lock` | Продление обнаружило, что аренды нет: запуск вытеснен посреди работы. **Алерт на любое значение** |

Владелец не является тегом (случайный суффикс → неограниченная кардинальность); он есть в строках лога.

**Логи:**

| Уровень | Сообщение | Смысл |
|---|---|---|
| `ERROR` | `Job '<name>' run failed` | Цикл бросил исключение; следующий цикл идёт по расписанию |
| `WARN` | `Job '<name>' did not finish within the <t> drain timeout` | Остановка бросила незавершённую работу; её подберут реклеймеры |
| `WARN` | `Run lock '<name>' was lost by <owner> (run <id>)` | Аренда истекла и была перехвачена |
| `WARN` | `Could not acquire / renew / release run lock '<name>'` | Ошибка БД при операции с арендой; трактуется как «занята другим» / «потеряна» / «истечёт сама» |

**Рекомендуемые алерты:**

| Условие | Почему |
|---|---|
| `increase(ludwig_job_lock_lost_total[15m]) > 0` | Работа сделана дважды или брошена наполовину; аренда короче запуска |
| `sum by (lock) (increase(ludwig_job_lock_acquisition_total{acquired="true"}[1h])) == 0` при запланированной задаче | Задача нигде не выполняется |
| Частота строк `Job '...' run failed` | Воркер падает каждый цикл |

**Известные пробелы:** `SelfSchedulingLifecycle` / `ScheduledJob` не публикуют собственных метрик - нет
числа запусков, ошибок, длительности и времени последнего успешного запуска по задаче. Воркер, падающий
каждый цикл, виден только в логе, а переставший планироваться не виден вовсе. Этот пробел наследует
каждый воркер платформы; таймер на задачу и gauge «последний успех» здесь закрыли бы его для всех.

## Аудит

Не применяется: модуль не меняет бизнес-состояние. Модули, построенные на нём, аудируют свои операции сами.

## Администрирование

Эндпоинты оператора находятся на административной поверхности платформы, `/admin/v1/{area}`, и существуют только там, где есть поверхность `security-spring-boot-starter`. Каждый защищён одной операцией; какие роли сервиса ею владеют, решает собственный `ludwig.admin.grants` сервиса (роли из резолвера полномочий, никогда не из claims токена), а операция, не выданная ни одной роли, запрещена всем. Вызов уровня `privileged` требует заголовка `Admin-Reason`, и каждый вызов записывается в аудит с категорией `admin` и идентификатором операции в качестве действия. `GET /admin/v1/me/operations` показывает, какие операции есть у вызывающего.

| Операция | Эндпоинты | Что разрешает |
|---|---|---|
| `jobs.read` | `GET /admin/v1/jobs`<br>`GET /admin/v1/jobs/locks` | Просмотр плановых заданий и владельцев их блокировок запуска. |
| `jobs.operate` | `POST /admin/v1/jobs/{name}/run` | Запустить плановое задание сейчас. |
| `jobs.privileged` | `POST /admin/v1/jobs/locks/{name}/release` | Принудительно освободить блокировку запуска, владелец которой исчез. |

Блок выдачи (имена ролей - собственные роли сервиса):

```yaml
ludwig:
  admin:
    grants:
      "[jobs.read]": [ORDERS_ADMIN, ORDERS_SUPPORT]
      "[jobs.operate]": [ORDERS_ADMIN]
      "[jobs.privileged]": [ORDERS_ADMIN]
```

**Хранилище согласований «четырёх глаз».** Рядом с административной поверхностью job-core предоставляет её
`AdminApprovalStore` (`JdbcAdminApprovalStore`, таблица `job_admin_approval`): каждое изменение состояния - условное
обновление, поэтому из двух одновременно одобряющих выполнит запрос один, а тело запроса удаляется, как только по
согласованию принято решение. Если `ludwig.admin.approval.required` перечисляет операцию, задание
`ludwig-admin-approval-expiry` (под одноимённой блокировкой запуска, раз в минуту) переводит нерешённые согласования
в истёкшие и помечает прерванными те, что остановившаяся реплика оставила выполняться. Сами эндпоинты согласований -
часть стартера безопасности.

## Runbook

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Задача-синглтон не запускалась с момента смерти пода | Аренду держит мёртвый под до `expires_at` | Подождать `default-lease` (5 мин по умолчанию). Освободить сразу: `UPDATE job_run_lock SET owner = NULL, expires_at = now() WHERE lock_name = '<name>';` - безопасно, только если ни один живой экземпляр не выполняет эту задачу |
| Растёт `ludwig_job_lock_lost_total` | Запуск длиннее аренды и продлевается недостаточно часто, или БД задерживала продления | Продлевать на каждую пачку; передать задаче более длинную аренду через `runIfAvailable(name, ttl, work)` |
| `Job '<name>' did not finish within the drain timeout` на каждом деплое | `drainTimeout` меньше цикла, или цикл слишком велик | Уменьшить пачку или поднять drain timeout (оставаясь ниже termination grace period) |
| Кто держит блокировку? | - | `SELECT lock_name, owner, run_id, heartbeat_at, expires_at FROM job_run_lock ORDER BY lock_name;` |
| Старт падает на changeset `job_run_lock` | Changelog подключён дважды (в собственном master changelog и бином стартера) | Выставить `ludwig.job-core.liquibase.enabled=false` при собственном подключении |

## Тестирование

- `mvn test`: кривая backoff и окно jitter, валидация `ScheduleSpec`, нереентерабельность жизненного цикла,
  гашение исключений, дренаж при остановке.
- `mvn verify`: `JdbcRunLockIT` на реальном PostgreSQL (Docker): живая аренда пускает один экземпляр;
  истёкшую аренду можно захватить без освобождения; продление после истечения и повторного захвата тем же
  владельцем не проходит (защита `run_id`); освобождение мгновенно; `runIfAvailable` освобождает при
  исключении в работе; N конкурирующих потоков дают ровно одного победителя. Схема берётся из поставляемого
  changelog.

## Проектные решения

- **Аренда, а не блокировка.** Блокировка мёртвого процесса удерживается вечно, и никто об этом не
  сигнализирует; аренда истекает.
- **Продление проверяет `run_id`, а не только `owner`.** Аренда, которая истекла, была перехвачена и
  вернулась к той же строке владельца, потеряна, а не удерживается.
- **Освобождение сохраняет строку.** Один путь захвата (запрос `SKIP LOCKED`) вместо отдельных веток
  insert и update; таблица ограничена числом имён блокировок.
- **Micrometer опционален** и подключается через SPI `RunLockListener`, поэтому у блокировки нет
  зависимости от наблюдаемости.
