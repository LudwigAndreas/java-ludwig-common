# messaging-db-spring-boot-starter

*[English](README.md) · **Русский***

Съёмная замена Kafka-кластера, который у этой стороны будет, но пока отсутствует. Модуль хранит лог в
форме Kafka в общей для сервисов базе PostgreSQL. Сервисы продолжают публиковать через
[`outbox-spring-boot-starter`](../outbox-spring-boot-starter) и потреблять через `@KafkaListener` и
[`messaging-spring-boot-starter`](../messaging-spring-boot-starter); сейчас только добавляется
зависимость, позже она удаляется. Больше ничего в сервисе не меняется ни в одну сторону.

| | |
|---|---|
| Роль | starter (временный транспорт) |
| Зависит от (в репозитории) | [`job-core`](../job-core), [`messaging-spring-boot-starter`](../messaging-spring-boot-starter) |
| Используется | в этом репозитории никем (подключают сервисы без собственного Kafka-кластера) |
| Поверхности | Kafka-совместимый лог в PostgreSQL |

```
 сервис A (outbox, transport: kafka:internal) ──► message_log (общий PostgreSQL) ──► потребители internal
                                                   ▲ своя позиция у каждой группы: каждая группа получает каждую запись
 кластер партнёра ─────────────────────────────────┼──────────────────────────────► его потребители, без изменений
                                                   │
 все dead letter, адресованные internal ───────────┘
```

## Использование

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>messaging-db-spring-boot-starter</artifactId>
</dependency>
```

Объявите кластер, который будет вашим, так же, как любой другой кластер, и укажите его как заменённый:

```yaml
ludwig:
  kafka:
    clusters:
      internal:
        client-id: catalog-service   # объявлен; адрес не нужен до режима draining
  messaging:
    db:
      clusters: [internal]           # по умолчанию
    consumers:
      catalog:
        cluster: internal
  outbox:
    routes:
      products:
        transport: kafka:internal
```

Это всё подключение. Listener-ы, их бины `containerFactory`, построенные `ListenerContainerFactoryBuilder`,
и маршруты outbox написаны для кластера, поэтому в день появления кластера единственное изменение -
задать ему адрес.

**Зависимость нужна и продюсеру, и потребителю.** Продюсер без неё пишет в настоящий кластер, а
потребитель, читающий этот кластер из лога, такую запись никогда не увидит.

- **Запись.** Каждая запись, которую платформа отправляет в заменённый кластер (события outbox через
  `kafka:<cluster>`, все dead letter, адресованные ему), добавляется в лог с тем же топиком, ключом,
  заголовками и payload. Подключение к кластеру не выполняется. Другие кластеры не затронуты.
- **Чтение.** Потребитель с заменённым `ludwig.messaging.consumers.<name>.cluster` читает все свои топики
  из лога. Потребитель кластера партнёра может отправлять свои dead letter в лог через
  `dead-letter.cluster: internal`.

### Что сохраняет потребитель

| Поведение | На логе |
|---|---|
| Форма записи | Настоящий `ConsumerRecord`: ключ, заголовки и значение как записаны, плюс топик, партиция и offset лога. `EnvelopeReader` работает без изменений |
| Партиционирование | Стандартный партиционер Kafka (`murmur2(key) % partitions`). Запись без ключа идёт в партицию 0 |
| Порядок | В пределах группы - один потребитель на партицию в момент времени. Запись доставляется только после обработки или dead-letter всех более ранних записей её партиции |
| Fan-out | У каждого `groupId` своя позиция на партицию. Новая группа стартует по `auto-offset-reset`: `earliest` читает с начала, `latest` - только новые записи |
| Доставка | At least once. Позиция сдвигается только после возврата listener-а или отправки в dead-letter. Упавший экземпляр повторно доставит не больше той записи, что обрабатывал |
| Повтор | Разрешённые настройки `retry.*` потребителя: то же число попыток и тот же экспоненциальный backoff. Партиция удерживается на время ожидания; ни один поток не спит |
| Без повтора | `DeserializationException` («ядовитый» payload, неподдерживаемая версия) и `MessageConversionException` сразу уходят в dead letter |
| Dead letter | `<topic><suffix>` в логе, с исходным ключом, **байтами** payload и заголовками, плюс `kafka_dlt-original-topic/-partition/-offset` и `kafka_dlt-exception-fqcn`. Сообщение исключения не пишется (может цитировать payload). Считается и аудируется recoverer-ом messaging |
| Неудачный dead letter | Позиция не сдвигается; записываются `ludwig.messaging.dropped` и событие аудита dropped; запись повторяется после самого длинного backoff |
| Дедупликация, корреляция | Применяются `RecordFilterStrategy` и все `RecordInterceptor` контекста; менеджер транзакций контейнера используется, когда его требует дедупликация |

### Что запрещено при старте

- `ludwig.messaging.db.clusters` называет кластер, не объявленный в `ludwig.kafka.clusters`.
- Потребитель заменённого кластера задаёт `retry.non-blocking=true` (retry-топикам нужен брокер).
- Listener заменённого кластера подписан через `topicPattern` (укажите топики явно).
- Listener читает `default` через фабрику, построенную не `ListenerContainerFactoryBuilder`, при
  заменённом `default` (без билдера нет настроек потребителя).
- У listener-а заменённого кластера нет group id.

## Конфигурация

| Свойство | По умолчанию | Смысл |
|---|---|---|
| `ludwig.messaging.db.mode` | `active` | `active`: запись заменённых кластеров идёт в лог. `draining`: запись идёт на адрес кластера, потребители читают оба источника. См. [Переход на настоящий кластер](#переход-на-настоящий-кластер) |
| `ludwig.messaging.db.clusters` | `[internal]` | Кластеры, которые заменяет лог, по именам из `ludwig.kafka.clusters` (`default` = `spring.kafka.*`). Каждый должен быть объявлен |
| `ludwig.messaging.db.partitions` | `8` | Партиций на топик. **Фиксируется после появления записей**: изменение переносит ключи между партициями и ломает порядок по ключу на стыке |
| `ludwig.messaging.db.poll-interval` | `1s` | Сколько простаивающий воркер ждёт перед новым опросом |
| `ludwig.messaging.db.retention` | `7d` | Записи старше этого удаляются, **прочитанные или нет** |
| `ludwig.messaging.db.purge-interval` | `1h` | Как часто запускается очистка |
| `ludwig.messaging.db.schema` | `ludwig_messaging` | Схема таблиц. Одинакова во всех сервисах. **Фиксируется после развёртывания** (контрольные суммы changeset-ов включают её) |

Число воркеров на listener следует `concurrency` listener-а, как потоки Kafka-потребителя.

## Развёртывание

- **Схема.** Liquibase changelog `db/changelog/messaging-db/messaging-db-changelog.xml`, применяется
  стартером при запуске. Каждый сервис выполняет его со своей таблицей changelog; каждый changeset -
  `IF NOT EXISTS` и сначала берёт advisory lock, поэтому сервисы могут стартовать в любом порядке и
  одновременно.
- **Таблицы.** `message_log` (записи), `partition_head` (следующий offset партиции; блокировка строки
  сериализует писателей, и offset-ы никогда не становятся видимыми не по порядку), `consumer_offset`
  (позиция группы; блокировка строки - это назначение партиции), `consumer_pause` (группа, приостановленная
  оператором на топике; её читает выборка каждой реплики).
- **Пул соединений.** Воркер держит одно соединение пула, пока обрабатывает запись, и ещё одно использует
  транзакция listener-а: добавьте `concurrency × 2` на каждый listener лога к уже нужному сервису размеру
  пула.
- **Нагрузка на БД.** Один индексный запрос на простаивающий воркер за интервал опроса. Пропускная
  способность - как у одного общего PostgreSQL: сотни записей в секунду.

### Переход на настоящий кластер

1. **Задайте каждому заменённому кластеру адрес** (`ludwig.kafka.clusters.<name>.bootstrap-servers` и
   настройки безопасности) **и выставьте `ludwig.messaging.db.mode=draining` во всех сервисах**, в любом
   порядке. Запись теперь идёт в кластер; потребители читают **и** лог, **и** кластер, поэтому ничего из
   лога не теряется.
2. **Дождитесь, пока `ludwig.messaging.db.lag` станет 0 для всех групп.**
3. **Удалите зависимость и свойства `ludwig.messaging.db.*`.** Listener-ы, бины фабрик и маршруты outbox
   остаются как есть.
4. **Удалите схему** (Liquibase этого не сделает: changeset-ы уходят вместе с jar):

   ```sql
   DROP SCHEMA ludwig_messaging CASCADE;
   DELETE FROM databasechangelog WHERE author = 'ludwig-messaging-db';   -- в таблице changelog каждого сервиса
   ```

Пока топик дренируется, у одного ключа могут быть записи и в бэклоге лога, и в Kafka, и два контейнера
их перемежают: порядок по ключу соблюдается до и после переключения, но не во время. Если порядок важен,
переключайте, когда топик спокоен. `mode` переключает все заменённые кластеры сразу, поэтому задайте
адрес каждому до переключения.

## Наблюдаемость

**Метрики:**

| Метрика | Тип | Теги | Смысл |
|---|---|---|---|
| `ludwig.messaging.db.lag` | multi-gauge | `group`, `topic` | Записи, не прочитанные группой; обновляется каждые 30s, чтобы scrape не ходил в БД |

Прочитанные, повторённые и отправленные в dead-letter записи считает
[messaging](../messaging-spring-boot-starter/README.ru.md) (`ludwig.messaging.*`), как и для настоящего кластера.

**Логи.**

| Уровень | Сообщение | Смысл |
|---|---|---|
| `INFO` | `Reading <topics> from the log as group '<g>' with <n> worker(s)` | Listener подключён к логу |
| `INFO` | `Purged <n> log record(s) produced before <t>` | Отработала очистка |
| `WARN` | `Purging <n> record(s) of topic '<t>' that group '<g>' never consumed` | **Потребитель остановился или слишком медленный**: данные удаляются непрочитанными |
| `ERROR` | `Polling the log as group '<g>' failed; retrying` | Проблема с БД у этого воркера |
| `ERROR` | `Skipping the record at ... dead-lettering is off` | Запись отброшена по конфигурации |

**Health.** Health-индикатора нет.

**Рекомендуемые алерты:**

| Условие | Почему |
|---|---|
| `ludwig_messaging_db_lag` растёт дольше 15 мин | Потребитель застрял или медленный; через `retention` записи удалятся непрочитанными |
| Строка лога `never consumed` | Удалены непрочитанные записи |
| `ludwig_messaging_dropped_total` > 0 | См. runbook messaging |

**Известные пробелы:** нет метрики скорости записи в лог и размера таблицы, нет health-индикатора
воркеров опроса. Размер `message_log` отслеживайте мониторингом БД.

## Аудит

Самостоятельно не применяется: dead-letter аудирует recoverer messaging (`messaging.dead-lettered`,
`messaging.dropped`). Добавление в лог и очистка - транспортные операции, а не изменение бизнес-данных.

## Администрирование

Эндпоинты оператора находятся на административной поверхности платформы, `/admin/v1/{area}`, и существуют только там, где есть поверхность `security-spring-boot-starter`. Каждый защищён одной операцией; какие роли сервиса ею владеют, решает собственный `ludwig.admin.grants` сервиса (роли из резолвера полномочий, никогда не из claims токена), а операция, не выданная ни одной роли, запрещена всем. Вызов уровня `privileged` требует заголовка `Admin-Reason`, и каждый вызов записывается в аудит с категорией `admin` и идентификатором операции в качестве действия. `GET /admin/v1/me/operations` показывает, какие операции есть у вызывающего.

| Операция | Эндпоинты | Что разрешает |
|---|---|---|
| `messaging.read` | `GET /admin/v1/messaging/consumers` | Просмотр отставания каждой группы потребителей по каждой партиции журнала в базе данных, а также приостановлена ли она, кем и с какого времени. |
| `messaging.operate` | `POST /admin/v1/messaging/consumers/{group}/topics/{topic}/pause`, `.../resume` | Остановка и возобновление доставки одного топика одной группе, сразу на всех репликах. |
| `messaging.privileged` | `POST /admin/v1/messaging/consumers/{group}/topics/{topic}/offsets` | Сдвиг позиции приостановленной группы на одной партиции или на всех, с пропуском или повторной доставкой записей. |

Приостановить или сдвинуть можно только группы, под которыми читают собственные listener-ы сервиса; любая другая
группа или группа без позиции на топике - `404`. Приостановка и возобновление идемпотентны и возвращают состояние
пары; приостановка - это строка, которую читает выборка каждой реплики, поэтому она действует везде без рассылки, а
запись, которая уже обрабатывается, сначала дообрабатывается.

Сдвиг отклоняется с `409`, если группа не приостановлена на топике, - так ни одна реплика не обрабатывает записи, мимо
которых сдвигается позиция. Тело - `{"to": "earliest" | "latest" | "offset" | "timestamp", "value": ..., "partition":
n}`: `offset` - следующий доставляемый offset, `timestamp` - момент ISO-8601 (доставка начнётся с первой записи,
опубликованной в этот момент или позже), отсутствие `partition` означает все партиции. Результат ограничивается
записями, которые ещё хранятся. Ответ и событие аудита содержат старую и новую позицию каждой партиции и число
пропущенных или повторно доставляемых записей; неизвестная цель или неразбираемое значение - `400`.

Блок выдачи (имена ролей - собственные роли сервиса):

```yaml
ludwig:
  admin:
    grants:
      "[messaging.read]": [ORDERS_ADMIN, ORDERS_SUPPORT]
      "[messaging.operate]": [ORDERS_ADMIN]
      "[messaging.privileged]": [ORDERS_ADMIN]
```

## Runbook

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Потребитель ничего не получает | У продюсера нет зависимости (пишет в настоящий кластер) или `cluster` потребителя не заменён | Проверить зависимости обоих сервисов и `ludwig.messaging.db.clusters`; `SELECT topic, count(*) FROM ludwig_messaging.message_log GROUP BY 1;` |
| Растёт `ludwig_messaging_db_lag` | Listener медленный или падает | Смотреть `ludwig_messaging_retries_total` и лог сервиса; поднять `concurrency` (≤ `partitions`) и, соответственно, размер пула |
| Предупреждение `never consumed` | Группа не читала дольше `retention` | Удалённые записи потеряны; при необходимости попросить продюсера переопубликовать. Починить потребителя |
| Исчерпание пула / таймауты соединений | Пул не рассчитан на `concurrency × 2` на listener лога | Увеличить `spring.datasource.hikari.maximum-pool-size` |
| Старт падает с упоминанием `topicPattern`, group id, неблокирующего повтора или неизвестного кластера | Одна из [запрещённых конфигураций](#что-запрещено-при-старте) | Исправить, как сказано в сообщении |
| Одна запись падает при каждой попытке и держит партицию | Ядовитая запись: payload не может обработать ни одна версия listener-а | Приостановить группу на топике (`.../pause`), взять `committedOffset` из `GET /admin/v1/messaging/consumers`, сдвинуть на следующий offset (`{"to":"offset","value":"<committed + 2>","partition":n}`), возобновить. Запись пропускается, а не уходит в dead letter: если она нужна, сначала забрать её из `message_log` |
| Записи обработаны неверно из-за ошибки, которая уже исправлена | Повтор после исправления | Приостановить, сдвинуть на момент выхода ошибки (`{"to":"timestamp","value":"2026-10-01T09:00:00Z"}`), возобновить. Все записи с этого момента будут доставлены снова, включая обработанные верно: listener должен быть идемпотентным, иначе их побочные эффекты повторятся. При дедупликации на стороне потребителя (по ключу `ludwig-idempotency-key`, который при повторной доставке тот же) повторные записи будут отброшены как дубликаты, если сначала не удалить их записи дедупликации |
| Нужно перейти на Kafka | - | [Переход на настоящий кластер](#переход-на-настоящий-кластер) |

## Тестирование

`mvn verify` (Docker): `LogStoreIT`, `LogOnlyTransportIT`, `MixedTransportIT` (лог и настоящая Kafka в
одном сервисе), `DrainingIT`, `SchemaInstallIT` (параллельные установки), `ConsumerPauseIT` и `ConsumerOffsetMoveIT`
(приостановка и сдвиг на нескольких репликах и через HTTP), `MessagingAdminIT`, плюс `StartupValidationTest`
для запретов и `ArchitectureTest`.

## Проектные решения

- **Подключается, не редактируя другие модули.** Запись идёт через декорированный шов `KafkaClusterProducers`
  модуля messaging; listener-ы - через `BeanPostProcessor`, который оборачивает каждую фабрику контейнеров
  в маршрутизирующую и строит исходный Kafka-контейнер, чтобы переиспользовать его listener,
  десериализаторы и менеджер транзакций.
- **Съёмность проверяется.** Архитектурное правило `kafka.nothing-depends-on-the-db-log-transport` валит
  любой модуль, который ссылается на класс этого.
- **Непрочитанные записи удаляются.** БД общая; остановившаяся группа не должна раздувать её без
  ограничений. Сигнал - предупреждение в логе.
- **Не брокер.** Нет компакции, транзакций через лог и listener, seek-а, `LISTEN/NOTIFY`, retry-топиков;
  кластер заменяется целиком (без настройки по топикам).
