# messaging-db-spring-boot-starter

[English version](README.md)

Временная, удаляемая замена собственных кластеров Kafka, которых пока нет.

Сервисы уже публикуют через `outbox-spring-boot-starter` и потребляют через `@KafkaListener` и
`messaging-spring-boot-starter`. Пока у этой стороны нет своего кластера, модуль даёт этим записям место:
журнал в общей для всех сервисов базе PostgreSQL, устроенный как Kafka. Это зависимость, которую
добавляют сейчас и убирают потом. Больше в сервисе ничего не меняется ни в одну, ни в другую сторону.

## Что он делает

```
 сервис A (outbox, transport: kafka:internal) ──► message_log (общий PostgreSQL) ──► потребители internal
                                                   ▲ своя позиция у каждой группы: каждая группа получает каждую запись
 кластер партнёра ─────────────────────────────────┼──────────────────────────────► его потребители, без изменений
                                                   │
 каждый dead letter, адресованный internal ────────┘
```

- **Запись.** Каждая запись, которую платформа отправляет в заменённый кластер — названный в
  `ludwig.messaging.db.clusters`, по умолчанию `internal`, — вместо этого дописывается в журнал с тем же
  топиком, ключом, заголовками и содержимым. Это события outbox через `kafka:<cluster>` и каждый dead
  letter, адресованный этому кластеру. Подключиться к нему не пытается ничто. Остальные кластеры получают
  свои записи как раньше.
- **Чтение.** Потребитель, чей кластер (`ludwig.messaging.consumers.<name>.cluster`) заменён, читает все
  свои топики из журнала. Остальные потребители читают свой кластер. Потребитель кластера партнёра
  отправляет свои dead letter в журнал через `dead-letter.cluster: internal`, потому что своего кластера,
  куда их записать, у этой стороны нет.

## Подключение

Добавьте зависимость и объявите кластер, который у вас будет, так же, как `add-kafka-clusters` объявляет
любой кластер:

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>messaging-db-spring-boot-starter</artifactId>
</dependency>
```

```yaml
ludwig:
  kafka:
    clusters:
      internal:
        client-id: catalog-service   # объявлен; адрес не нужен до draining
  messaging:
    db:
      clusters: [internal]           # значение по умолчанию
    consumers:
      catalog:
        cluster: internal
  outbox:
    routes:
      products:
        transport: kafka:internal
```

Это всё. Слушатели, их бины `containerFactory`, собранные через `ListenerContainerFactoryBuilder`, и
маршруты outbox написаны для кластера, а не для журнала, поэтому в день, когда он появится, единственное
изменение — дать ему адрес. Таблицы создаются при первом старте.

Зависимость должна быть и у публикующего, и у потребляющего сервиса. Сервис без неё пишет в кластер, а
потребитель, читающий этот кластер из журнала, такую запись не увидит.

## Что сохраняется у потребителя

Контейнер журнала запускает слушателя, которого spring-kafka уже адаптировал для endpoint, за теми же
объектами, что билдер messaging дал контейнеру Kafka:

| Поведение | В журнале |
|---|---|
| Форма записи | Настоящий `ConsumerRecord`: ключ, заголовки и значение как записаны, плюс топик, партиция и смещение журнала. `EnvelopeReader` работает без изменений |
| Партиционирование | Стандартный партиционер Kafka (`murmur2(key) % partitions`). Запись без ключа уходит в партицию 0 |
| Порядок | Внутри группы с одной партицией одновременно работает один потребитель. Запись не доставляется, пока каждая более ранняя запись её партиции не обработана или не отправлена в dead letter |
| Fan-out | Каждый `groupId` хранит свою позицию на каждой партиции. Новая группа начинает по `auto-offset-reset`: `earliest` читает журнал с начала, `latest` — только новые записи |
| Доставка | Хотя бы один раз. Позиция сдвигается только после того, как слушатель вернул управление или запись ушла в dead letter. Упавший экземпляр передоставит не больше одной записи — той, которую обрабатывал |
| Повторы | Настройки потребителя `ludwig.messaging.consumers.<name>.retry.*`: то же число попыток, та же экспоненциальная задержка. Пока идёт ожидание, партиция удерживается, поток не спит |
| Без повторов | `DeserializationException` (испорченное содержимое, неподдерживаемая версия события) и `MessageConversionException` сразу уходят в dead letter |
| Dead letter | `<topic><suffix>` в журнале, с исходными ключом, **байтами** содержимого и заголовками, плюс `kafka_dlt-original-topic/-partition/-offset` и `kafka_dlt-exception-fqcn`. Текст исключения не пишется, потому что в нём цитируется содержимое. Считается и аудируется собственным recoverer из messaging |
| Неудачный dead letter | Позиция не сдвигается, записываются `ludwig.messaging.dropped` и событие аудита dropped, а запись пробуется снова после самой длинной задержки |
| Дедупликация, корреляция | Применяются `RecordFilterStrategy` и каждый `RecordInterceptor` из контекста. Если дедупликация требует менеджер транзакций контейнера, он используется |

## Что запрещено

Сервис не стартует, называя, что исправить, если:

- `ludwig.messaging.db.clusters` называет кластер, не объявленный в `ludwig.kafka.clusters`.
- потребитель заменённого кластера задаёт `retry.non-blocking=true`. Retry-топикам нужен брокер.
- слушатель заменённого кластера подписан по `topicPattern`. Шаблон нельзя разрешить против журнала,
  поэтому назовите топики явно.
- слушатель читает `default` через фабрику контейнеров, собранную не `ListenerContainerFactoryBuilder`,
  а `default` заменён. Без билдера нет настроек потребителя, которые можно применить.
- у слушателя заменённого кластера нет group id.

## Справочник настроек

| Свойство | По умолчанию | |
|---|---|---|
| `ludwig.messaging.db.mode` | `active` | `active`: записи заменённых кластеров идут в журнал. `draining`: они идут на собственный адрес каждого кластера, а его потребители читают оба места. См. [Переход на настоящий кластер](#переход-на-настоящий-кластер) |
| `ludwig.messaging.db.clusters` | `[internal]` | Кластеры, которые заменяет журнал, по именам из `ludwig.kafka.clusters` (`default` — это `spring.kafka.*`). Каждый должен быть объявлен |
| `ludwig.messaging.db.partitions` | `8` | Число партиций на топик. **Не меняется, когда записи уже есть**: изменение переносит ключи в другие партиции, и порядок по ключу на границе изменения теряется |
| `ludwig.messaging.db.poll-interval` | `1s` | Сколько простаивающий обработчик ждёт перед следующим опросом |
| `ludwig.messaging.db.retention` | `7d` | Записи старше этого удаляются, **прочитаны они или нет** |
| `ludwig.messaging.db.purge-interval` | `1h` | Как часто запускается очистка |
| `ludwig.messaging.db.schema` | `ludwig_messaging` | Схема, в которой лежат таблицы. У всех сервисов значение должно совпадать. **Не меняется после развёртывания**: контрольные суммы changeset считаются с подставленным именем |

Число обработчиков на слушателя следует его `concurrency`, как и потоки потребителя Kafka.

## Эксплуатация

- **Таблицы.** В `message_log` лежат записи, в `partition_head` — следующее смещение каждой партиции
  (её блокировка строки упорядочивает писателей, поэтому смещения никогда не становятся видны не по
  порядку), в `consumer_offset` — позиция каждой группы (её блокировка строки и есть назначение
  партиции).
- **Соединения.** Обработчик держит одно соединение из пула, пока обрабатывает запись, а транзакция
  самого слушателя использует ещё одно. Закладывайте `concurrency × 2` на каждого слушателя журнала
  сверх того, что сервису уже нужно.
- **Нагрузка.** Простаивающий обработчик выполняет один индексированный запрос за интервал опроса.
- **Очистка.** Непрочитанные записи удаляются намеренно: база общая, и группа, которая перестала
  читать, не должна раздувать её без предела. Перед удалением очистка пишет предупреждение по каждой
  группе и топику: сколько записей эта группа так и не прочитала. Это предупреждение и есть сигнал, что
  потребитель остановился.
- **Отставание.** `ludwig.messaging.db.lag{group,topic}` — число записей, которые группа ещё не
  прочитала. Обновляется раз в 30 секунд, поэтому сбор метрик никогда не ждёт базу.
- **Установка схемы.** Каждый сервис выполняет changeset со своей таблицей журнала изменений. Каждый
  changeset написан через `IF NOT EXISTS` и сначала берёт одну advisory-блокировку, поэтому сервисы
  могут стартовать в любом порядке или одновременно.

## Переход на настоящий кластер

Порядок важен, и он короткий:

1. **Дайте каждому заменённому кластеру адрес** — `ludwig.kafka.clusters.<name>.bootstrap-servers` и
   нужные ему настройки безопасности — и **выставьте `ludwig.messaging.db.mode=draining` во всех
   сервисах**, в любом порядке. С этого момента записи кластера идут на этот адрес, а его потребители
   читают **и** журнал, **и** кластер, так что ничего из уже записанного в журнал не теряется.
2. **Дождитесь, пока `ludwig.messaging.db.lag` станет 0 у каждой группы.**
3. **Уберите зависимость и свойства `ludwig.messaging.db.*`.** Больше ничего не меняется: слушатели,
   бины фабрик и маршруты outbox с самого начала были рассчитаны на кластер.
4. **Удалите схему.** Liquibase этого сделать не может, потому что changeset уходят вместе с jar:

   ```sql
   DROP SCHEMA ludwig_messaging CASCADE;
   DELETE FROM databasechangelog WHERE author = 'ludwig-messaging-db';   -- в таблице журнала изменений каждого сервиса
   ```

**Порядок во время переключения.** Пока топик дочитывается, у одного ключа могут быть записи и в
остатке журнала, и в Kafka, и два контейнера перемешивают их. Порядок по ключу соблюдается до и после
переключения, но не во время. Если порядок важен потребителю, переключайтесь, когда в топике тихо.
Дедупликация защищает от дублей, но не от перестановок.

**Все заменённые кластеры переходят разом.** `mode` — один переключатель для всего `clusters`. Если
заменённых кластеров несколько, дайте адрес каждому до переключения: один кластер не может дочитываться,
пока другой остаётся на журнале.

## Как он подключается

Модуль ничего не правит в модулях, поведение которых меняет:

- **Запись.** `KafkaClusterProducers` из messaging — единственное место, откуда берётся каждый producer
  платформы: шаблоны outbox и каждый шаблон dead letter. Этот модуль регистрирует его раньше, с
  декоратором: заменённый кластер получает фабрику producer, которые сериализуют как просили и дописывают
  байты в журнал. Сборка заголовков и выбор сериализаторов остаются в своих модулях, а правило
  `kafka.producers-come-from-the-cluster-seam` следит, чтобы это место оставалось единственным.
- **Слушатели.** spring-kafka находит `@KafkaListener(containerFactory = "...")` по имени, как
  `KafkaListenerContainerFactory`. `BeanPostProcessor` заменяет каждый бин фабрики маршрутизирующей
  фабрикой, которая стоит вместо него. Для потребителя заменённого кластера маршрутизирующая фабрика
  просит оригинал собрать контейнер Kafka для endpoint и берёт у этого контейнера слушателя,
  десериализаторы и менеджер транзакций. Остальные потребители получают контейнер оригинала без изменений. Тот же
  post-processor проксирует `ListenerContainerFactoryBuilder`, чтобы запомнить, для какого имени
  потребителя собрана каждая фабрика: по этому имени определяются настройки повторов и dead letter.
- **Удаляемость проверяется.** Правило архитектуры `kafka.nothing-depends-on-the-db-log-transport`
  роняет любой модуль, который называет класс этого модуля.

## Чего этот модуль сознательно не делает

- **Не брокер.** Нет compaction, нет транзакций, охватывающих журнал и слушателя, нет seek, нет
  push-уведомлений `LISTEN/NOTIFY` и нет retry-топиков. Пропускная способность — то, что даёт один общий
  PostgreSQL: сотни записей в секунду, а не показатели Kafka.
- **Не заменяет часть кластера.** Кластер заменяется целиком: настройки по топикам нет, и слушатель читает
  один кластер.
- **Не остаётся навсегда.** Это замена на один год. Путь удаления, описанный выше, — часть замысла, а
  не запоздалая мысль.
