# `pat-spring-boot-starter`

Выдающая половина персональных токенов доступа платформы - готовая к подключению. Добавьте зависимость,
подключите changelog, передайте ключ подписи, и у поставщика идентичности появляется полная подсистема
PAT: таблица, API управления, обмен по RFC 8693, аудит, метрики, i18n и problem details.

*Проверяющая* половина находится не здесь. Она уже есть в каждом сервисе - в `security-spring-boot-starter`.

## Топология одной схемой

```
  CI / curl / ноутбук
        │  Authorization: Bearer lpat_<keyId>_<secret>_<crc>     ← ОДИН статический заголовок, навсегда
        ▼
  ┌──────────────────────────────────────────────────────────┐
  │ ПЕРИМЕТР (Envoy / шлюз)   ← НЕ в этом репозитории          │
  │   префикс "lpat_" ?  ──▶ попадание в cache[(дайджест,     │
  │                           аудитория)] ?                    │
  │                            да   ──▶ переиспользовать       │
  │                            нет  ──▶ обменять и закешировать│
  │                                     на expires_in - люфт   │
  └───────────────────────────┬──────────────────────────────┘
                              │ POST /oauth2/token
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │ identity-provider-service   (этот стартер)                │
  │   разбор → контрольная сумма → лимит → точечное чтение    │
  │   → сравнение дайджестов за постоянное время              │
  │   → не отозван / не истёк → источник разрешён             │
  │   → аудитория разрешена                                    │
  │   → выпуск JWT: sub=<владелец>, ludwig_pat={id, scopes}   │
  └───────────────────────────┬──────────────────────────────┘
                              │ короткоживущее заявление для одной аудитории
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │ ЛЮБОЙ сервис - цепочка фильтров без изменений             │
  │   права владельца = AuthorityLookup.lookup(sub) ← ЖИВЫЕ   │
  │   действующие     = владелец ∩ ludwig_pat.scopes          │
  └──────────────────────────────────────────────────────────┘
```

Свойство, на которое стоит обратить внимание: **клиент отправляет один статический заголовок и никогда не
выполняет обмен сам**. Ни вызова точки выдачи токенов, ни `jq` для извлечения поля из JSON, ни отслеживания
истечения, ни обновления. Это и есть главная причина выбора этой топологии вместо обмена на стороне клиента,
который затащил бы логику OAuth в каждый `curl` в каждом runbook.

## Быстрый старт

```xml
<dependency>
    <groupId>ru.ludwigandreas</groupId>
    <artifactId>pat-spring-boot-starter</artifactId>
</dependency>
```

```yaml
ludwig:
  pat:
    exchange:
      issuer: https://idp.internal            # ОБЯЗАТЕЛЬНО - без него запуск падает
      audiences: [deploy-service, billing-service]
  security:
    public-paths:
      - /actuator/health
      - /oauth2/token                          # ОБЯЗАТЕЛЬНО - см. «Обмен должен быть публичным»
```

Плюс бин `RSAKey` для минтера по умолчанию - или свой `PatAssertionMinter`, если ключом подписи уже владеет
поставщик идентичности. Второй вариант лучше, и именно для него существует SPI.

## Что должен периметр, и почему никакая сборка здесь это не проверит

Три обязательства находятся вне этого репозитория. Они выписаны дословно, потому что ничто в сборке не
может их наблюдать, и этот пробел записан в таблице обеспечения изменения, а не оставлен на обнаружение.

**1. Обмен для аудитории назначения и кеширование по паре `(дайджест секрета, аудитория)`.**

```
POST /oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<значение lpat_ из заголовка Authorization>
&subject_token_type=urn:ludwig:params:oauth:token-type:pat
&resource=<сервис, куда идёт этот запрос>
```

Кешируйте ответ на `expires_in` секунд минус люфт часов. **Ключ только по дайджесту неверен**: он отдал бы
заявление одного сервиса другому, и каждый такой запрос затем провалил бы проверку аудитории в точке
назначения.

**Без кеширования весь дизайн разрушается.** Каждый запрос к сервису становится запросом к издателю через
посредника - то есть той самой топологией «удалённая проверка на каждый запрос», которая была отвергнута по
соображениям доступности. Наблюдаемое доказательство работы кеша: `ludwig.pat.exchange` остаётся
пропорциональным *числу различных токенов за время жизни заявления*, а не растёт с объёмом запросов.
Поставьте на это алерт.

**2. Отображайте неудачный обмен как клиентский `401`.** Клиент вызывал *сервис*; он никогда не вызывал
обмен и не знает о его существовании. Единообразный отказ издателя предназначен периметру.

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token"
Content-Type: application/problem+json

{ "type": "https://problems.ludwigandreas.ru/credential/rejected",
  "status": 401,
  "detail": "Эти учётные данные не приняты. ...",
  "manageCredentialsAt": "/api/v1/personal-access-tokens" }
```

Константы публикуются как `PatProblemTypes` в `pat-core`, чтобы периметр настраивался по определению, а не
изобретал своё. **Не раскрывайте причину.** Ни одну из одиннадцати, ни «отозван», ни «истёк».

**3. Удаляйте учётные данные `lpat_` перед проксированием.** Сервис получает заявление, а не токен.

## Обмен должен быть публичным

`/oauth2/token` обязан быть достижим без аутентификации. Он *потребляет* токен как свой субъект, а не
принимает его как учётные данные вызывающего - то же правило, которое не пускает токен на поверхность
управления.

`PatExchangeConfigurationValidator` предупреждает, если путь отсутствует в `ludwig.security.public-paths`.
Предупреждение, а не падение при старте, потому что режим отказа громкий и безопасный: периметр получает
401, заявление не выпускается, PAT наглядно не работают, и ничто не раскрыто. Отказ от запуска был бы также
неверен для приложения, опубликовавшего путь через собственный `SecurityFilterChain`, которого этот модуль
не видит.

## Окно отзыва, вычисленное за вас

Три TTL складываются в то единственное число, которое имеет значение, и никто не перемножает их в
продакшене. При старте вычисляются **оба** пути, логируются и приводят к отказу запуска, если любой
превышает предел:

```
запрос/ответ:          время жизни заявления + время жизни кеша периметра + TTL кеша прав
долгоживущее:          интервал переполучения + TTL кеша прав
```

Со значениями по умолчанию: `5m + 5m + 60s = 11m` и `1m + 60s = 2m` против предела `15m`.

Чтобы сократить окно, сокращайте `ludwig.pat.exchange.assertion-lifetime` **и** кеш периметра вместе: это
одно число, разделённое между двумя системами, и уменьшение только первого делает вычисленную цифру
фикцией.

Оба пути вычисляются намеренно. Вычисление только первого логировало бы правильно выглядящее число, ложное
как раз для тех вызывающих, чьё окно самое большое.

## Что обеспечивается за вас

| Правило | Чем |
|---|---|
| Действующие права - владелец ∩ области действия, никогда не объединение | единственное место создания, `credentials.one-attenuation-path` |
| Нет второго хранилища, SPI или формата учётных данных | `credentials.no-second-credential-store`, `...-spi` |
| Сырой секрет не покидает модули учётных данных | `credentials.secret-carrier-stays-inside` + огороженный доступ + маскирующий `toString()` |
| Токен не может создать, провернуть или отозвать токен | `PatCredentialGuard`, проверено на **каждой** точке |
| Обязательный срок, максимальное время жизни, непустые области действия и аудитории | отказ при выдаче, у каждого своё локализованное сообщение |
| TTL проверки - это ограниченное окно отзыва | `CachePurpose.SECURITY` - предел при старте, без устаревших чтений |
| Нигде нет SQL или JDBC | `SqlConfinementTest`, обратная форма двух исключений |
| Нет слабого алгоритма дайджеста | Checkstyle `WeakDigestAlgorithm` |

## Чеклист развёртывания

1. **Зарегистрируйте формат `lpat_` в сканерах секретов *до* выдачи первого токена.** Сканер, добавленный
   позже, по умолчанию не просматривает историю, поэтому токены, закоммиченные в этом промежутке, остаются
   невидимыми ровно столько, сколько остаются действительными. Шаблон и готовое правило `gitleaks` - в
   `pat-secret-detection.properties` модуля `pat-core`.
2. Подключите `db/changelog/pat/pat-changelog.xml` или дайте `PatLiquibaseAutoConfiguration` его применить.
3. Передайте ключ подписи либо `PatAssertionMinter`, делегирующий вашему поставщику.
4. Добавьте `/oauth2/token` в `ludwig.security.public-paths`.
5. Выдайте `pat:manage` всем, кому можно иметь токен, и `pat:manage:any` только тем, кому можно создать
   токен для другого субъекта: именно так учётные данные переживают создавшего их человека.
6. Поставьте алерт на `ludwig.pat.exchange.failure{reason="revoked"}`. Предъявление отозванных учётных
   данных означает, что ими кто-то всё ещё владеет.
7. Поставьте алерт на рост `ludwig.pat.exchange` вместе с объёмом запросов. Это некеширующий периметр.

## Что модуль намеренно не трогает

- **Проверку.** `security-spring-boot-starter`, в каждом сервисе. Этот модуль никогда не видит запрос,
  аутентифицированный токеном.
- **Формат токена.** `pat-core`, у которого нет внутренних зависимостей, чтобы обе стороны границы
  разделяли одно определение утверждения `ludwig_pat`.
- **Подпись в продакшене.** SPI `PatAssertionMinter`. Развёртыванию с поставщиком OIDC следует указать на
  него: один ключ для ротации, один JWKS для публикации.
- **Потоковые транспорты.** `ludwig.pat.revalidation-interval` и долгоживущая композиция выше поставляются
  сейчас, чтобы ручка существовала до появления первого транспорта. Правила ArchUnit намеренно **нет**:
  ничто в этом репозитории не держит соединение открытым, поэтому правило проходило бы вхолостую и читалось
  бы как покрытие. Тот, кто добавит первый потоковый транспорт, должен этому модулю обеспечивающий тест.
- **Общую таблицу учётных данных.** У ключа развёртывания или подписанного секрета вебхука другое время
  жизни, другие полномочия на выдачу и другая история отзыва. Таблица, построенная для всех трёх, не
  держала бы хорошо ни одну.
